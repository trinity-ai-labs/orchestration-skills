# Changelog

Versions are the `version` field in `.claude-plugin/plugin.json`. Because that field is set, an installed plugin only picks up changes when it **changes** — pushing to `main` alone ships nothing. CI enforces the bump.

## 3.2.0

- **The blind `git stash pop` kept happening, so the argument-less form is now banned outright rather than left to follow from the reasoning.** The rule was complete — a repo-global stack, a marker per agent, a re-match by marker before every touch — and it was still being broken occasionally, which is a placement problem rather than a content one: `git stash pop` is one of the most automatic commands there is, it *is* correct in a single-checkout repo, so the instinct arrives already justified and never reaches the paragraph that would have stopped it. `execute`'s stash rule now leads with the mechanical form — every `pop`, `apply` and `drop` carries an explicit ref re-matched one command earlier — and names the case that gets rationalized: a `git stash list` showing exactly one entry, which is the weakest evidence on the list, because that list is repo-wide and the gap between your two commands is precisely when a sibling worktree pushes onto the stack. The costs are stated beside it, because they are not comparable: re-matching is one `git stash list | grep`, and a wrong pop takes a human's WIP out of the tree they left it in and drops it from the stack, recoverable only through `git fsck --unreachable` and only until the next gc.

- **The ban is now stated at the two places an agent actually reaches for a stash**, since a rule at the bottom of *Hard rules* is not where anyone is standing when the urge arrives. Holding a whole slice uncommitted for the review pass is one — the temptation is a clean tree for a check, and the answer is a WIP commit on your own branch, which is worktree-local where the stash stack is shared. Resolving a merge conflict is the other, and it is the worse one: stash-resolve-pop is reached for at the one moment several worktrees are guaranteed to be live and touching the stack.

## 3.1.0

Eight rules, every one of them found by running this pipeline rather than by reading it — three days on a large TypeScript monorepo, 134 merges, 464 commits, four multi-slice epics. Where a bullet says *Observed*, that is what it means.

- **A slice's scope had two dimensions and needed a third, so `decompose` grew a `Derives` field.** `Owns` and `Do NOT touch` are both file lists, and between them they cover exactly the collisions git can show you. Neither has any concept of a file whose correct contents are a function of the **whole tree** rather than of any one slice's files — a ratchet ledger, a backlog JSON a checker regenerates, a generated type, an unimported-exports manifest. Two slices edit disjoint sources, each is individually correct, and the shared artifact is right on neither branch; it merges clean, because there was never a textual conflict to stop on. Observed: a slice converting an exported `interface` into an inferred type removed an anchor a duplicate-detector scans for, while a sibling slice was simultaneously changing that detector's rules and owned its backlog ledger — both green in isolation, neither merge conflicting, the ledger correct on neither branch. A slice now declares what it derives, may not treat a derived artifact as final, and reports what its change did to it; the **dispatcher re-derives it on the merged tip before gating** (`execute` → *Gate the integrated whole*), which is the one thing per-slice gates structurally could not have covered. `orchestrate` §5's shared *runtime string* is cross-referenced rather than restated — that one is a shared **value** and a question of wave placement, this one is a derived **file** and a question of slice scope.

- **`orchestrate`'s reconcile checklist interrogated the plan five times and the tree not once.** Every item asked whether the plan still held against the merged tree — coordinates, senses, forced work, assumptions, deferrals. A sixth item now asks whether the *tree's own derived state* still holds, re-derived with the project's regenerator rather than read and reasoned about. The failure the other five structurally miss: nothing moved, nothing was renamed, nothing was falsified, nothing was deferred — and the ledger on the merged tip is wrong anyway, in the one file the next increment reads as ground truth, so the error is inherited by every slice grounded after it instead of surfacing.

- **`Owns` accepted a predicate as though it were a scope.** The field admits both a named list (`src/a.ts`, `src/b.ts`) and a predicate (*every caller of `<helper>`*), and a predicate's file set does not exist at decomposition time — it is discovered by the implementer, in its worktree, after dispatch. So there is nothing to check a sibling's named list against, and `Do NOT touch` cannot help, because it would have to name an intersection nobody computed. Observed: one slice got a named list, a sibling got "every caller of `<helper>` — 40 references, find them, they are yours", and both edited the same file; neither diverged, both were exactly in-brief, and the decomposition was wrong. The brief even carried the count, so the query had been run and only its cardinality kept. The rule is that a predicate is not a scope until it has been evaluated: run it while grounding, write the files down, check them against every sibling — or declare the slice exclusive over the predicate's whole domain and give no sibling a file that could fall inside it. It is silent in every channel a dispatcher watches, which is why it is a rule and not a judgement: the divergence tick sees two agents each inside its own brief, and the first sign is two diffs on one file at merge.

- **"The docs a slice falsifies" was the right question asked of one artifact class.** `decompose`'s doc bullet already derived falsified docs from what a reader would newly believe false rather than from a keyword grep — and stopped at docs. A slice also falsifies a guard-proof row, a `package.json` script entry, a pre-commit chain entry, a fixture, a CI job, a ledger entry, and an enforcement artifact left behind is worse than a stale paragraph because it keeps *asserting* something the tree no longer supports. Observed: deleting one temporary check meant removing its script entry, its pre-commit chain entry, its fixture, its guard-proof table row and a paragraph of testing docs — and the chain was declared in four places, so removing the one the first search found would have left three referencing a deleted file. The bullet now carries both halves: the same derive-from-behavior discipline applied to enforcement artifacts, and *find every declaration, not the first*.

- **Inside an epic, docs were written per slice against states nobody would ever see.** Docs describe an end state; an epic's intermediate states are by construction not shipped. So a doc rewritten by slice 1 is rewritten again by slice 3, and the intermediate version was true of nothing anyone saw — while doc files behave as hotspots in a way source files usually do not: one chapter describing a mechanism four slices are each changing a quarter of turns four patched sentences into four conflicts whose resolution is *semantic*, handed to the person least equipped to do it. Simply deferring the docs breaks the forcing function instead, since the implementer is the only party that knows what its change actually falsified. So the two halves split: `decompose` still names the docs each slice falsifies, the slice's **deliverable becomes an entry in the epic's falsification ledger** rather than the edit, one **closing docs slice** consumes the ledger against the final tree, and **an epic cannot close with a non-empty ledger** — the same ratchet shape this flow already uses elsewhere, and what keeps this from decaying into deferred docs. The ledger is the epic's record, not a file in the tree: a file every slice appends to is the exact hotspot the arrangement exists to avoid. Two carve-outs: a docs-only slice writes inline, and single-slice work has no end of an epic, so its docs ship with the change exactly as before.

- **Scaffolding had no name in the skills, so its teardown had no slice.** Build a temporary enforcer — a ratchet file plus the check that reads it — drain it to zero across several slices, then delete the enforcer, its fixture, its ledger and its documentation together. The pattern ran twice in three days and worked both times, but nothing said the teardown was a *planned* slice, so its precondition lived only in the dispatcher's head and had to be fenced off by hand in four separate briefs. `decompose` now plans the two ends together, with the teardown's precondition written down when the build is planned. The failure runs both ways: a teardown that lands early removes the enforcement while the thing it enforced is still incomplete — an empty ledger reads as an invitation — and a teardown never planned at all leaves dead scaffolding that reads as live machinery to everyone who arrives later.

- **The `Verify` bar asked for pass-after and never for fail-before.** It was "what 'done' looks like: the behavior, the tests to add/touch, the acceptance check". Every check that actually caught something across three days was strictly stronger: restore the old matcher and confirm the new fixture goes red, point a test's mock back at the old symbol and confirm it fails loudly, reverse a rename across 87 files and confirm the formatter reproduces the original byte for byte. Any slice that adds a check or fixes a bug now has to prove the new test fails against the pre-change code, with the specific reversal named in the bar rather than a bare "confirm it fails first". A test that passes both before and after proves nothing and is indistinguishable, in a green run, from one that proves everything — so the slice reports success having verified nothing.

- **Model tier was predicted by how hard the work looked.** `opus` was reserved for subtle algorithms, ambiguity, tricky concurrency, security, large cross-cutting changes — a list of things that *look* hard. Observed: the most dangerous slice of the whole run matched none of them and read as the most mechanical work on the board — point four imports at a shared schema. The shared schema and the inline one disagreed, the shared one was the weaker, and the obvious execution would have silently removed strictness from three live HTTP routes. The list stays, with a better predictor beside it: **does the slice touch something declared, or enforced, in more than one place?** If so the work is not the edit, it is adjudicating a disagreement between two sources of truth. Diff size does not predict difficulty; the number of places the truth is stated does.

- **The gate-cost economics were correct and had a blind spot: an epic that gates once on the merged tip.** The sizing guidance reasons carefully about N slices meaning N serialized drained gate runs. When an epic converges on an epic branch and gates as a whole, that cost is largely gone — and the constraint that replaces it is the dispatcher's own capacity to actually read N diffs, which is well below the number of slices the gate would have tolerated. Removing the serialized gate removes the only bound anyone was measuring, and the wave then grows until the reviews are skimmed — in a flow where no gate can tell whether the agent solved the right problem, the diff review is the only thing standing between a green slice and a wrong one.

## 3.0.1

- **`orchestrate` §2 delegated the divergence tick to a pointer, and a pointer is skippable.** The paragraph named the tick, then sent you to `/pipeline:execute` for the interval, the purpose and every mechanic — so a reader who did not follow it still had enough text to feel informed. What that reader reaches for instead is `ScheduleWakeup`'s own tool description, which warns against scheduling wakeups to poll for background work the harness tracks; that warning is about polling **for completion**, but nothing in §2 said so, and the conclusion "this does not apply to my sub-agents" looks sound. Observed: a dispatcher did exactly this, ran an entire session with no tick armed, and wrote a confident critique of the skill listing three defects the unopened section already answered. §2 now states the load-bearing minimum itself — poll every ~10 minutes (≈600s), completion notifications are free and are NOT the mechanism, the tick is for early divergence detection — keeps the pointer for the detail, and names that rationalization so the next reader cannot reuse it. The mechanism did not change; the delegation is what failed.

- **§2's cadence contradicted the mechanic it pointed at.** It read "you owe a tick for every minute in between" — per-minute against `execute`'s ~10 minutes. Two numbers for one timer means a reader either picks one at random or reads the whole instruction as approximate. §2 now carries `execute`'s number.

## 3.0.0

**Breaking: `/pipeline:execute` and `/pipeline:orchestrate` have exchanged meanings.** The arc loop — the leg you type after `/pipeline:write-issue` — is now `/pipeline:orchestrate`. The per-increment worktree playbook it drives each cycle is now `/pipeline:execute`. Anything that invokes `/pipeline:execute` to run an issue end to end must move to `/pipeline:orchestrate`. *The failure this rename creates for anyone who does not follow it, and the reason it is called out first: the old name still resolves. A saved prompt or a downstream repo's `AGENTS.md` that says `/pipeline:execute #123` now reaches the skill that ships ONE increment and stops — no reconcile, no second cycle, no close-out — and it reports success, because shipping one increment is exactly what it was asked to do.*

- **The two coordination skills had each other's names, and both claimed the same trigger word.** `execute` ran the whole arc while `orchestrate` ran one increment, so `execute`'s description had to offer "coordinate/**orchestrate** a body of work end to end" and `orchestrate`'s had to answer "running a whole arc or epic to completion is `/pipeline:execute`'s loop, not this skill's". Two skills competing for one word is a routing hazard, and it was being paid for in every description that had to fence the other one off. The names now state the level instead of the action: you **orchestrate** an arc, and the loop **executes** an increment of it.

- **The public surface is two commands and says so; the rest are passes the loop drives.** `/pipeline:write-issue` → `/pipeline:orchestrate` is what a person types. `decompose`, `execute` and `review` now describe themselves as reached from the loop rather than as places an arc starts — still directly invocable when you want one increment grounded, one increment shipped, or one diff reviewed. *The failure this prevents: a skill that reads as an entry point gets used as one, and an arc entered at the increment pass ships its first wave and stops, with nothing left holding the loop.*

- **The dispatcher role is named `DISPATCHER`, not `orchestrator`.** Every one of the 94 occurrences of the old role word meant the increment coordinator — the role that cuts a worktree per slice, reviews each PR's diff, drains the gate and merges — including the four inside the arc-loop skill, which read "invoke `/pipeline:orchestrate` and act as the **orchestrator**". The vocabulary now stacks with the skills: `orchestrate` hands you the **ORCHESTRATOR** role and the arc; `execute` hands you **DISPATCHER** for an increment or **IMPLEMENTER** for a slice. *The failure this prevents: leaving the word in place would have put "you are the ORCHESTRATOR" inside `/pipeline:execute` while `/pipeline:orchestrate` sat beside it as a live sibling skill — an agent reading its role as the name of another skill has a path straight back into the loop it was dispatched from.*

## 2.3.0

- **`execute`'s step 2 now owns the wait, not just the dispatch.** The five-step loop reads as a sequence, so the interval between dispatching implementers and merging them — where the agents actually live — was invisible in it, and the only instruction that arms a divergence tick lives in `orchestrate`, reached by a pointer, at the moment the orchestrator is busiest. A run could satisfy every step in order with no tick ever scheduled. Arming the tick is now part of dispatching: step 2 is not finished until the timer is set, and a dispatch report that does not name it is a step still open.

- **An alarm gets confirmed against the fork point before anyone reaches for `TaskStop`, whatever channel it arrived on.** `orchestrate`'s fork-point discipline was written for the diff the orchestrator runs on its own tick, but the alarm that reaches it is usually a fragment from elsewhere — a pasted screenshot, a line in a hand-back. A fragment carries no base, and the direction of a change cannot be read off a hunk: a rename back to the old name is byte-identical whether it is divergence or the **revert** of an out-of-scope rename. Only the fork-point state of that symbol separates them, and confirming costs one `git show` against a mis-cut that throws away the run.

- **The gate drain is sized to the fan-out.** Draining on every tick is right for several slices enqueueing at unpredictable times and near-dead weight for one, whose hand-back is a free notification. It stays on the tick to cover an agent dying between `enqueue` and hand-back, with the rule that its presence there never stands in for the divergence check — the half of the tick that costs a whole run to skip.

- **`execute`'s reconcile checklist grew a fifth item: deferred decisions.** A question an increment deliberately left open is neither a stale coordinate nor a falsified assumption, so items 1-4 cannot catch it — nothing stops resolving, nothing gets falsified, and the brief still reads fine. So the deferral renews itself every cycle in silence, and the half-state ships: a field named `accountId` typed `UserId`, worse than either endpoint because a half-done rename reads as a deliberate distinction to everyone who arrives later. Each deferral is re-asked at the new horizon against one test — does the merged tree still hold together with it open?

- **`AGENTS.md`'s hand-back rule named a draft PR as the endpoint and had no way to express an authorized merge.** The draft is still the default hand-back and the interlock against merging an unread diff, but a maintainer saying "ship it" *is* the review — so the flow now carries through to ready, merge, and a synced integration branch rather than stopping at a draft. The failure runs both ways: merging on your own initiative spends the only review artifact a prose repo has, and handing back a draft after being told to ship leaves a bumped version and a green gate that shipped nothing.

## 2.2.1

- **The epic branch's name carries no mechanical meaning; `transient-red/<epic-slug>`'s name is the contract.** Nothing reads an epic branch's name — not a helper in `bin/`, not a step in the playbook — because the branch is identified by what forks from it and PRs into it, so any prefix a team likes is fine. The marker is the opposite: the detector finds the window by looking for that exact ref, so its spelling is exact and not a matter of taste. `orchestrate`'s epic-branch mechanics state the two together, where the branch is cut, because the branch's name is free precisely *because* the marker took the job of being found — and a reader who carries the freedom across to the marker writes one no detector will find.

- **A detector never keys on a branch-name prefix.** `orchestrate`'s transient-red guidance still names the two prefixes that look right, `epic/*` and `integration/*`, and now carries the rule they are instances of: tooling that has to ask "is this an epic branch" answers with a dedicated ref of its own, the way the marker does.

- **`decompose`'s breakdown header takes the real epic branch name, not a `feat/<epic-leaf>` template.** A `feat/…` epic branch is indistinguishable in a PR list from the `feat/<leaf>` slices merging into it, which is the one distinction that header carries; the slot is a neutral placeholder with a one-line note that the only thing worth choosing the name for is that it does not read like a slice.

## 2.2.0

- **The transient-red window was described but never opened, and a relaxation that never fires is indistinguishable from one that was never built.** `orchestrate` told you to put the window on an epic branch and how to read a drained gate's red against it; `decompose` flagged which slices lived in it. Both are judgments made by something that can read prose. A project's **commit-time** tooling cannot — and where a repo relaxes its pre-commit compile check for exactly this window (forgiving diagnostics that all point at files the branch never touched, holding the branch's own files to the full bar), the only thing it can consult from inside a slice worktree is the ref graph. Nothing in the flow ever put the fact there. The gap is silent in both directions: a detector looking for one ref and a flow that pushed another never meet, nothing errors, and every slice pays full strict-path friction for a relaxation the repo believes it has.

- **Opening the window is now a step, and it is one marker ref.** An epic branch cut under Rule 1's primary trigger gets `transient-red/<epic-slug>` cut and pushed beside it, in the same breath as the branch itself; nothing forks from it and nothing merges into it, and it is deleted with the epic branch at close-out, which is what closes the window with nothing to unwind. `decompose`'s existing transient-red flag is now what tells the orchestrator to open it, not merely to expect red. The ref is deliberately the whole contract: it exists ⇔ the window is open.

- **Two near-miss keys are named explicitly, because both look right.** A detector must not key on the **epic branch itself** — Rule 2 cuts one for parallel dispatch alone, on epics where every intermediate state is green, so keying on `epic/*` would silently forgive real sibling breakage on every one of them — and not on `integration/*`, which this playbook reserves for the shared branch and says never means anything else. The separate marker is what keeps "this epic is isolated" and "this epic is knowingly red" from collapsing into one signal.

- **And one check, once per epic: confirm it actually fires before dispatching the first slice.** Both failure directions are silent, so the only evidence is evidence you go and ask for — from inside the first slice's worktree, where the tooling runs, not from the main checkout. The close-out deletion carries the same weight for the same reason: a marker left behind outlives the epic that justified it and quietly relaxes the next unrelated slice's compile check against a window that closed weeks ago.

## 2.1.0

- **`write-issue` grounded `file:line` for the whole arc while the loop that consumes it grounds only the horizon, and one word wearing two meanings is what hid the contradiction.** **Grounding** is how you know a plan is *true* — this function exists, this really is the only call site, this consumer would ripple. **Coordinates** are how an implementer *finds* the work: a `file:line` to-do list. The skill did both under one unqualified rule ("Ground every target before you write it"), and its `Targets` section was defined as "the concrete `file:line` list the work touches, as the to-do list" — so a five-phase issue carried line anchors for all five phases, and phases 2-5 of that list were the exact stale-coordinate class 2.0.0 rebuilt the pipeline to eliminate. Worse, they sat in the one artifact nothing in the loop re-checks: `execute`'s reconcile pass is scoped to the *remaining plan*, not to the issue body, so a coordinate written here survived every cycle that would have caught it anywhere else. Nothing errored. The issue read well, `decompose` grounded the horizon correctly on top of it, and the later phases' coordinates simply went quietly wrong.

- **The grounding stays, and its purpose is now stated: it is how you establish the plan is TRUE, never how you produce a to-do list.** The cheap fix — ground less — reintroduces the failure the skill exists to prevent, so it was refused outright. `write-issue` still spawns read-only research per subsystem, still greps the WHOLE repo and cites the definition line before a load-bearing claim counts, and still cross-checks anything that surprises it. What changed is what it does with the result: **ground with `file:line`; write down the module and the file.** An ungrounded issue does not come out vague, it comes out *confidently wrong* — asserting a consumer that isn't one, a sole call site that is one of six, a function deleted last month — and nothing downstream can tell those claims from correct ones. A stale coordinate can at least be re-checked against the tree, which is precisely what reconcile does; a false claim has nothing to check it against.

- **`Targets` is now `Surface`, and the rename is the substance rather than the decoration.** The old name read as a to-do list because it was defined as one, and a section that reads as a to-do list gets executed as one — item by item, with a phase-4 coordinate opened as an instruction rather than as context. `Surface` states **where the work lands and what it touches**: real modules and files, grouped by area, plus the consumers each change ripples into — a map, not a checklist, with no line numbers, nothing phrased as a sequence to work down, and explicitly *not* the per-slice owned-file list with do-not-touch boundaries, which belongs to `/pipeline:decompose` and gets drawn at the horizon. A path survives the phases in front of it; a line number does not, and `decompose` re-derives the exact anchors every cycle against the tree an implementer will actually open — so writing them into the issue buys nothing and costs accuracy. The KEEP/STRIP list, the frontmatter description, the follow-up section, the hard-boundaries list and the closing argument all moved with it. The issue comes out **shorter and more durable, not vaguer**: `Goal`, `Approach`, `Phases`, `Seams`, `Verify` and `Constraints` are untouched, because they were always the vision-and-shape half and they are what makes an issue reviewable before anyone builds.

- **`execute`'s reconcile item 1 claimed "everything past the horizon is at shape depth and names no coordinates" — false before this change, and *nearly* true after it, which is the more dangerous of the two.** It now says the list is short because everything past the horizon is at shape depth **and** because a `write-issue` body names modules and files rather than a line-level to-do list — then adds the half that keeps the check alive: **short is not empty.** A module path is still a path, item 1 checks "every path, symbol, table, route, or key", and the increment that just merged is the likeliest thing in the world to have moved one. *The failure this prevents: reading the discipline as a guarantee turns the item into a formality, and a formality reports the same clean result whether or not anything moved* — the same shape as the write-it-down-even-when-empty rule two paragraphs below it.

- **`README.md`'s `write-issue` row now says what an issue actually contains.** It had said only "grounds an idea in the real code and files it as a forward-facing issue" — true under the old model and true under the new one, and therefore silent about the only thing that changed. It now names the sections a body carries and puts "write a line-level to-do list" in the never-does column. *The failure this prevents: a doc that reads correct under both the old behavior and the new one is the kind nothing ever flags — it carries none of the new vocabulary, so a grep for the new terms misses it, and it carried none of the old vocabulary either, so a grep for the stale wording misses it too. It just goes on quietly under-describing the artifact a user is about to receive.*

## 2.0.0

- **The pipeline is two commands now — `/pipeline:write-issue` → `/pipeline:execute` — and that is what makes this a major rather than a 1.19.** The user-facing command surface changed and trigger vocabulary moved between skills: *execute a plan*, *work or complete a GitHub issue*, *handle a batch of tasks*, *ship an arc or an epic*, *coordinate a body of work* now reach `/pipeline:execute`, a skill that did not exist on 1.x. `orchestrate` keeps entry at the level it actually works at — one increment, or a dispatch brief — and `decompose` keeps direct invocation for anyone who wants a single grounded breakdown. Nothing was deleted and every skill still runs when it is named, but a session reaching for the old arc-level phrasing now lands on a different skill than it did yesterday, and the version string is the only thing that can tell an install so.

- **What the new leg replaces: a plan grounded once, up front, is at its most accurate the moment before any of it runs, and decays from there.** A front-loaded decomposition grounds every wave against the tree as it stands when the pass runs, then writes `file:line` coordinates into briefs that later waves execute. A wave-4 brief naming a route is correct when written and wrong when run, because wave 1 renamed that route — and **nothing errors**. The brief still reads well; the implementer opens a tree where the target is not there, finds the nearest plausible thing, and builds against that, because an implementer handed a coordinate does not treat its absence as a stop. The same pass also asserts a completeness it cannot have: work the arc structurally forces but no slice owns stays invisible until an implementer walks into it mid-wave, out of scope, with no owner and no boundary. Grounding the whole arc is indistinguishable from grounding it *better* right up to the moment a wave lands and moves the paths, which is why this is now a rule rather than a judgement call.

- **Two grounding depths, separated by a horizon, and reaching the horizon is the only thing that promotes an item between them.** The **horizon** is the next dispatchable set — every remaining item whose dependencies have already landed, which is usually a wave and sometimes only the genuinely dispatchable part of one. Inside it, **slice depth**: owned files as real paths, do-not-touch boundaries, depends-on, framework skill, model tier, brief, verify bar, grounded against the tree as it stands right now and dispatched in the same cycle. Outside it, **shape depth**: goal, area, what it waits on, one line on why it comes after the thing before it — and no coordinates of any kind. An item at shape depth is *finished*, not half-written. Both failures are silent and they run in opposite directions: grounding early produces the stale coordinate above, and dispatching at shape depth hands an implementer no owned-file list and no boundary, so it invents its own scope and the first anyone hears of it is a PR in a sibling slice's core files — by which point the sibling has already forked. Nothing else promotes an item: not being well understood, not being small, not a user having asked about it.

- **Reconcile is the step a front-loaded decomposition does not have, and it is a fixed four-item checklist because a step re-derived from scratch each cycle gets a little shorter each cycle.** It runs after the increment has **merged**, against the **merged tree** — not the PR diffs and not a summary of them, since the merged tree is the one the next increment forks from and therefore the only tree whose state can falsify anything. In order: coordinate drift (a target that does not resolve is stale by definition, not a maybe); **vocabulary drift checked per sense, not per string**, because one word routinely carries two meanings a rename splits and a find-and-replace rewrites the surviving sense too — producing a change that compiles, passes, and is wrong; revealed forced work, asked against the tree rather than against the plan, since the plan is the thing that failed to mention it; and falsified assumptions, which are plan defects fixed in the plan rather than discovered later by whoever inherits the brief. **The outcome gets written down even when it is empty**, because a cycle that reconciled and found nothing and a cycle where nobody ran the checklist produce identical plans, and the record is the only thing that tells them apart.

- **Fold vs. file, decided by one test asked in the direction of the arc: can it land without this?** Forced work — the arc cannot compile, pass, or ship without it — gets **folded in** as a named slice with its own wave. Adjacent work — real, worth doing, but the arc is correct without it — gets **filed and linked**, never folded. That guard is what keeps a re-decomposing loop finite: re-grounding every cycle makes absorbing new work trivially easy, since the increment is already open and the tree already read, so an arc that absorbs everything it touches never terminates — and no single cycle is where that becomes obviously wrong, because each fold is individually defensible and the close-out simply never arrives. The mirror failure is just as real and looks even more like diligence: filing something that was actually forced ships an arc that does not build, and leaves a tidy linked issue behind as evidence of thoroughness. Asked in the direction of the *item*, every item looks worth doing; asked in the direction of the *arc*, the answer is checkable.

- **Where a folded item goes is decided by merge surface first, with slice cohesion only as a tiebreaker between placements that have the same merge surface.** Ordered, not balanced: when cohesion says *this belongs with the slice that owns that module, which is running right now* and merge surface says *it rewrites a shape forty files reference*, cohesion loses outright. Churn discovered mid-arc goes in a **serial wave** — one slice, nothing else in flight — because parallel slices fork from different bases, so a large-footprint change dispatched alongside them merges textually clean and semantically wrong: git merges by line and has no idea two edits must compose. When the shared shape is a **runtime string** — a query key, a table name, a route, a config key — the bad merge does not even fail to compile; it splits one cache entry into two or collides two into one, and every gate in the wave stays green. And nothing folded ever joins a wave that has already been dispatched, whatever its size, because those slices forked before the folded item existed and their do-not-touch boundaries cannot name it.

- **The decide-don't-ask bar, plus the one property of it that is specific to a loop: it gets applied once per cycle, so setting it slightly too low multiplies.** Wave assignment, fold-vs-file, sizing and re-slicing are the loop's calls to make and report, not questions to put to the user; the single escalating class is a product or design fork the code and conventions cannot settle, asked in plain chat, one question at a time, with a recommendation and why. The split itself is stated once — in `decompose`'s *Validate the plan and fill the gaps* — and pointed at rather than copied, because two statements of one rule drift and nothing then marks which is stale. What the loop adds is the arithmetic: one avoidable question per cycle across eight cycles is eight user turns spent on things the repo already answers, and each one teaches the user that the loop cannot be left to run, which is the entire value it was supposed to deliver.

- **The loop's state is the umbrella body, its history is that issue's comments, and termination needs two halves rather than one.** The body always describes what is *left*, at the depth the horizon assigns, and is rewritten every cycle rather than appended to; one comment per completed increment records what landed and what it invalidated. Neither artifact works alone — with only comments, the current plan has to be reconstructed by reading the whole thread in order and applying each correction in sequence, and two readers reconstruct it differently; with only a rewritten body, an item that disappears leaves no trace of why, so nobody can tell a completed item from a dropped one. Done means **the remaining plan is empty AND the close-out is green**: an empty plan over a red close-out is not done, and a green gate with items still outstanding is not done either. And a cycle that finishes with the remaining plan identical to the one it started with **stops and reports** — a loop whose structure is *re-ground, dispatch, reconcile, repeat* has no natural stopping condition when an increment keeps failing, so it will re-ground the same frontier indefinitely while every individual cycle looks locally like progress.

- **A verify rider that generalises past this arc: any slice renaming an identifier that crosses a string boundary carries a bare-string sweep in its verify bar.** A table, a route, a cache key, a config key, an env var, a feature flag — anything that leaves the type system's reach and re-enters the program as text. The sweep greps the *old literal* across the whole tree, fixtures, snapshots, generated files, docs and config included, and proves either zero hits or that every survivor is deliberate. The failure it prevents is structural rather than careless: a typecheck cannot see a renamed table asserted as a literal in a fixture, and the single targeted test file an implementer is allowed to run will not be the file that asserts it — so **both** checks an implementer actually runs are blind to the thing, the slice reports green, and the break lands. It attaches to a *shape* of slice rather than to one change, which is why it lives in the skill and not in whichever brief trips it this week, and it goes into the verify bar at **grounding** time: added at review it arrives after the implementer has already reported green, costing a round trip to reopen a worktree that was about to be torn down.

- **`orchestrate` and `decompose` were re-scoped rather than rewritten, and the sharper of the two edits is a role-entry rule.** `orchestrate` now says which role you are in is decided by **how you got here, not by how the work looks** — orchestrator from the loop or from a direct ask to coordinate one increment, implementer from a dispatch brief or a direct build instruction. Both misreadings are silent and both produce work that looks like progress: read as an implementer, an orchestrator writes the code it should have been dispatching, one agent in one worktree with no boundaries and nobody but the author reading the diff; read as an orchestrator, an implementer dispatches the slice it was handed, and its sub-agents inherit a brief whose imperatives end in *commit, push, open a PR* — so the PR is open before the agent that owns the worktree has decided what goes in it. `decompose` is now explicitly the loop's per-increment grounding pass: it grounds the horizon and emits the remainder at shape depth on **all three** of its input paths, since reading the horizon as a property of having been called by `/pipeline:execute` would make a directly-invoked decomposition the one that grounds the whole arc — the same stale coordinates, reached by deciding the discipline did not apply here. Its wave map still covers the whole arc, because a dependency ordering names no files and the horizon is *defined* as the next set whose dependencies have landed; without it the next cycle has nothing to move the horizon along by.

- **The rest of the surface had to be made to agree, and that half of the change is the one nothing would have caught.** `README.md`'s *Why this shape* opened with **"Front-loaded planning → `write-issue` and `decompose` do the expensive grounding before any worktree exists"** — the README advertising, as the flow's headline virtue, the exact defect this arc replaces. It is now the just-in-time argument. `write-issue` hands to `/pipeline:execute` and `setup` onboards a repo onto a two-command pipeline; both had named the three-leg one in their **frontmatter descriptions**, which is the text every session reads when deciding whether to invoke a skill at all. That README bullet and `write-issue`'s "`decompose` turns it into orchestration-ready slices" were both found only because Wave 1 slices reported docs they were forbidden to edit, and both sat a few lines outside every line anchor the tracking issue listed — an anchor list reads as exhaustive, so a falsified sentence just outside one survives while every listed line is correctly fixed, and the slice goes green with the file contradicting itself. And `README.md`'s install-verification line claimed the plugin ships **four** skills; it had shipped five since `review` landed, and would now have been wrong by two. A count-shaped sweep catches that class where a sweep for the exact stale wording never can, because the next drift will be spelled a way no targeted grep is looking for.

## 1.18.0

- **Nothing in this plugin had ever said the word `stash`, and the stack it left unmentioned is shared by every worktree in the repo.** `refs/stash` is a **common ref**: the main checkout and every linked worktree push onto and pop off the same stack, and `git stash list` in one tree lists every other tree's entries indistinguishably from its own. A bare `git stash pop` therefore takes whatever is on top regardless of whose it is — it applies those changes into *your* tree and **drops** them from the stack. And this flow's default dispatch shape is several worktrees live at once, so that is not an edge case — it is the ordinary state of a run.

- **What that cost, observed.** In a repo with the main checkout and two slice worktrees all live and all having stashed, a bare `git stash pop` in one slice worktree applied the main checkout's stash into the slice and dropped it. The human's WIP was gone from where they left it and sitting silently in an agent's worktree, and nothing errored — no warning, no conflict, exit 0. Recovery from a dropped stash is `git fsck --unreachable` and only until the next gc, so the window in which the loss is even repairable closes on its own.

- **The fix is a marker plus a re-resolve, and neither half works alone.** Git's auto-generated `WIP on <branch>: <sha> <msg>` subject identifies nobody — two agents on one branch write the same line, and so does one agent resumed after a stall — so agents now stash with `git stash push -m "pipeline-stash/<branch-leaf>/<epoch>: <purpose>"`. The prefix makes every agent stash greppable as a class, the leaf says whose it is, and the epoch separates the two identical-subject cases. But a name is not a handle: `stash@{n}` is renumbered by every push and every drop **anywhere in the repo**, including in trees you cannot see, so an index resolved at the start of a turn can point at a different entry by the end of it. Hence the second half — re-match the marker immediately before every pop, apply or drop, and treat **zero matches or two-plus matches as a STOP-and-report**, never as a reason to fall back to `stash@{0}`. Your entry not being where you left it means something else moved the stack, which is the moment to hand back rather than to guess.

- **Two bans and a preference ride along, because the destructive operations here are the ones with no undo.** `git stash clear` destroys every other worktree's entries and the human's in one command with no confirmation; dropping an entry you did not create is the same act retail rather than wholesale. And a **WIP commit on your own branch** avoids the whole class: it is worktree-local, unstealable, and unwinds with `git reset --mixed HEAD~1` when a plain uncommitted diff is what the review pass needs. Ending a turn with a stash still on the stack is out for a reason worth stating: once that worktree is torn down, the entry is unattributable, and an unattributable stash is one nobody can ever safely pop. The orchestrator gets the matching sweep — `git stash list --format='%gd %gs' | grep -F 'pipeline-stash/'` on the tick it already runs — with the reading that a hit while the fleet is quiet is a defect to chase, not noise.

- **The second rule: an agent owns its follow-ups, and no skill said so.** The work a change creates or reveals — residual cleanup, a doc it made stale, the second call site, the missing test, the rename left half-done — was landing in hand-back prose as "flagged for follow-up: X, Y, Z". That reads as thoroughness and is indistinguishable from it, which is exactly the problem: the items are untracked the moment the turn ends, and nothing in the gate, the PR, or the orchestrator's review can tell they were ever raised. Untracked, a follow-up is not a follow-up; it is a defect with a polite name. Each one now becomes a real issue via `/pipeline:write-issue`, linked to the originating issue or umbrella, decomposed if it is more than one slice, and folded into the orchestration. The economics are one-sided: the agent holding the item has the worktree open, the install paid for, and the change that caused it on screen, and a later session has to rebuild all three before it can start reading.

- **The rule binds the orchestrator too, and forwarding is the same defect one level up.** An orchestrator reading a report that names unfinished work owns the next move — a fix agent into that worktree, a resume to the same implementer, or a filed and linked issue folded into the wave plan. It is worse from there than from a slice, because the orchestrator is the only party in the run holding the decomposition, the sibling slices, and the plan the item has to be placed against; a triage it declines is a triage nobody in the run can do.

- **A follow-up inherits the arc's branch level, which is the case the existing branch rule most often loses.** "Branch from the branch the work converges on" already covers this, but a follow-up *feels* like new work rather than like part of the arc that produced it, so it gets routed at the integration branch by reflex. While an epic branch is live, a follow-up the epic surfaced forks from and PRs into the **epic branch** like any other slice of it. Routing it to the shared branch instead bypasses precisely the isolation the epic branch was cut for, and delivers the epic's leftovers piecemeal while the epic itself is still converging.

- **Two existing paragraphs were bounded rather than rewritten, because read loosely each of them launders the defect.** `orchestrate`'s stuck-hand-back sanctions handing back when you are *blocked*, and its missing-input paragraph sanctions it for an identifier that names a real thing you cannot obtain. Neither sanctions handing back work you simply did not do — but a hand-back reporting a blocker and one reporting an unfinished intention are the same artifact from the orchestrator's side, both prose naming work that did not land. The test is now stated where those paragraphs live and it is mechanical: **if you can still act on it, it is not a blocker** — fix it in its own commit, or file and link it. `review`'s *Flagged, out of scope* bucket got the same treatment from the other end: an item is admissible only when fixing it falls outside the slice boundary the brief drew or is unverifiable from that worktree, and what stays flagged is the **caller's** to file, since that pass reports and neither dispatches, commits, nor pushes.

- **The general form, and it is why both rules landed in `orchestrate`'s hard rules rather than in one role's section: work that changes hands without a name on it is lost silently, and fan-out is what makes that routine.** The two look unrelated — one is a git command, the other a reporting habit — and they fail identically. A stash with no marker is an entry nobody can claim, so the next agent that needs the top of the stack takes it. An item named only in a hand-back is work nobody has been given, so the run ends with it un-owned. Neither produces an error, and both are indistinguishable, in every artifact this flow inspects, from the correct behavior. The fix is the same shape in both: **make the thing carry the name of whoever owns it — a marker on the stash, an issue number on the follow-up — and require that name to be re-established before anyone acts on it.**

## 1.17.0

- **`write-issue` authors the artifact `decompose` consumes, and it did not know either of the two path decisions that artifact has to answer.** `decompose` makes two calls off an issue: the **output path** — post the breakdown as a comment, or convert the issue into an umbrella with one sub-issue per slice — and the **epic-branch path** — whether the slices fork from the integration branch or from an epic branch cut off it, so the shared branch never carries the work half-finished. The second turns on facts that are properties of the plan its author has just designed rather than of the code as it stands: whether the branch is shippable at each phase boundary, and which producer → consumer seams the plan creates. Nothing in `write-issue`'s body structure asked for either, so neither was written down, and the pass that has to decide had nothing to decide from.
- **What that costs is an unasked question read as a no.** An issue that states no shippability fact is indistinguishable from an issue whose every intermediate state is fine, and the shape that then goes wrong is exactly the one an epic branch exists for: a foundational phase every later phase must follow lands on the shared branch and sits there half-migrated — green at every step, and forked from by every other session. Contract seams fail the same way and more quietly, since a seam whose halves land in different phases shares no file with itself and is invisible to a file-based conflict map by construction; the cross-tree ones — code ↔ docs, code ↔ prompt, code ↔ config — have nothing mechanical linking the halves at all, and the author who designed the change is the last person who can still see them without rediscovering them. `write-issue` now asks for both facts by name, and its hard-boundaries list gains the matching prohibition: state the facts, and never write "use an epic branch" into an issue body — a verdict in the body reads as settled downstream though it was reached without the grounding pass that is supposed to reach it.
- **A terminology collision fixed alongside it: an umbrella is not an epic branch.** The two are orthogonal — an umbrella is a tracking shape, how work is written down, assigned and closed; an epic branch is a branch lifecycle, where slices fork from and PR into — and "epic" is the same word for both, including as the label name `write-issue` tells authors to apply. Read as one thing, filing an umbrella looks like it settled the branch question, and the facts that would actually settle it never get written. Step 3 and the Labels bullet now say so, and the umbrella warrant is worded the way `decompose` states its own test rather than paraphrasing it.
- **`decompose` re-ran its own warrant test against a decision the user had already made, and overruled it.** Told to do the work "as an epic", the pass treated that as a hypothesis to check rather than a decision to execute, ran the epic-branch trigger, and wrote "Epic branch: not needed" into a breakdown — and the instruction had to be given twice before it moved. The cost has two halves and the second is the worse one: the user spends turns repeating themselves, and the overruling does not stay in the conversation, because this question is answered in one line inside a document that is then handed to `/pipeline:orchestrate` and executed as written. Every slice would have targeted the shared integration branch while the user had asked for exactly the isolation an epic branch provides, and an unwarranted "not needed" produces a perfectly well-formed plan, so nothing downstream could tell it apart from a correct one. **The general form, now stated in both skills because it is not specific to this decision: a skill's decision procedure exists for when nobody has decided, and never overrides a stated instruction — once the call is made, the skill is read for mechanics, not for a second opinion.**
- **In that same breakdown four documented contract seams sat beside the answer "not needed", and nothing reconciled the two.** A contract seam whose halves land in different waves is one of the two named shapes that fire the trigger, so the document's own evidence contradicted the document's own answer. The map and the answer come out of different steps and get read as independent, which is how a trigger fires on facts the same document already contains and the answer still comes back "no" — a wrong call reached with everything needed to get it right already written down. `decompose` now requires the epic-branch answer to be reconciled against the seam map it just emitted: a seam whose halves land in different waves, or a wave-0 foundational change every consumer must follow, has to be named and dismissed by name before "not needed" is available.
- **The epic-branch trigger gains a second rule, and this reverses a sentence both skills stated emphatically.** They said slice count is not the trigger — a five-slice run whose every slice is independently shippable wants no epic branch at all. That argument is correct and is kept intact, because it answers a **correctness** question: would a partial state on the shared branch be *broken*? Counting slices cannot answer that and never could. What it was never asked is the **operational** question, which is now the second rule: what does running several slices concurrently cost the shared branch, whether or not every intermediate state would ship? Four costs land regardless — every live slice's base moving under every other one, a shared branch routinely carrying merged trees no single slice's gate ever ran, N merges to unpick instead of one to revert, and a contract seam far easier to compare while both halves are still converging somewhere you control — and all four were already documented in `orchestrate` as things to work around. So **multi-slice work dispatched in parallel now defaults to an epic branch**, keyed on your own fan-out across one change rather than on a threshold: unrelated one-slice fixes running side by side are not an epic, "the integration branch is busy" stays rejected as the opposite concern, and single-slice work still never cuts one. The cost section is untouched and the merge-back cadence stays mandatory — more load-bearing now, since this default fires on the shape the flow reaches for most often.
- **The general form behind the first change, worth stating because it is not specific to these two skills: a downstream pass can only decide from facts the upstream artifact was asked to carry.** `decompose` grounds a plan in real code, so anything readable from the tree it will find on its own. What it cannot find is a property of the plan that existed only in its author's head at the moment of writing, and the only place that ever gets recorded is the artifact the author is already filling in. `write-issue` states the test once and points at `/pipeline:decompose` for the rest rather than restating its reasoning — two copies of one rule drift, and nobody can tell which one is stale.

- **`orchestrate` told every implementer to run a quality pass this plugin does not own, and that pass changed underneath running epics.** The instruction was a bare `/simplify` — a skill bundled with the CLI, versioned on its own schedule, with no relationship to the plugin's version field. It began fanning its reviewers out as **forks**, and a fork inherits the spawning agent's entire conversation. In this flow that conversation is an implementer's brief, and an implementer's brief is a list of imperatives ending in *commit, push, open a draft PR, enqueue the gate*. A reviewer handed that does not read it as background; it reads it as its instructions.

Every artifact looked right, because the reviewers were faithfully executing a correct brief; they simply were not the agent whose judgment those artifacts were supposed to represent. Three worktrees were being written to concurrently by agents that each believed they were the implementer, and in one of them a deliberate fixture corruption (a drift-guard proving its own failure mode) raced a root-level formatter run in the same tree.
- **The second-order failure is the expensive one, and it is the argument for fixing this at the plugin boundary rather than with a better prompt.** Once unauthorized writes are in play, agents lose the ability to distinguish authorized work from rogue work — a careful agent and a runaway agent produce identical artifacts: a branch, a PR, a queued ticket. Every step of that was good defensive practice, and it was wrong on the one fact it structurally could not see — that the orchestrator had cut that branch itself, on the user's request. Legitimate work sat un-gateable until a human looked.
- **The fix is `/pipeline:review`, shipped here, and the load-bearing property is that it dispatches nothing.** It is one agent reading its own uncommitted diff — reuse, simplification, efficiency, altitude *and* correctness in one ordered pass, since a correctness fix can introduce something to simplify and a simplification can expose a correctness problem. It never spawns, never commits, never pushes, and never runs a full-suite or whole-package test (the drained gate owns that, one PR at a time). Verification is the project's own `scopedCheck` plus at most a single targeted test file, read from `.agents/worktree.json` rather than assumed.
- **Inline rather than findings-only-with-read-only-tools, which was the obvious fix and the wrong one.** The objection is not that a quality pass writes; it is that a *sub-agent* decided what goes in. When the pass runs in the implementer's own context, the agent applying the change is the agent that owns the slice, and the principle is satisfied with no new machinery. A read-only reviewer would also have been weaker than it looks: the natural "read-only" agent types still hold `Bash`, so a findings-only contract is a convention rather than a guarantee, and even a non-fork sub-agent that inherits no conversation can act on a misread prompt. Spawning nothing is the only version of this with no exception to reason your way into.
- **One rule inverted rather than moved, and leaving it un-inverted would have been the silent half.** `orchestrate` had *accommodated* the fan-out: a standing rule telling orchestrators not to mistake a `/simplify` pass for a stall, because it spawns its own reviewers and legitimately takes minutes, so an implementer reporting that it is waiting on review agents is self-suspended and must be left alone. Against an inline pass that signal means the opposite — an implementer waiting on reuse/simplification/efficiency/altitude reviewers did not run this plugin's skill, and something is writing to its worktree on its behalf. The general form of the rule survives for genuine nested waits; the review-specific case is now an alarm that sends the orchestrator to look at the worktree.
- **Naming: review contains simplify, so the skill is `review`.** The broad tier of review already exists in this flow and is deliberately not what this ships — the orchestrator reads each PR's diff and the drained gate runs the full build and suite over the committed result. `/pipeline:review` is the narrow, early tier that runs where neither of those can: inside the implementer's turn, on uncommitted work, before the commit blocks exist. It is not a leg of the write-issue → decompose → orchestrate pipeline; it is the pass an implementer calls on itself mid-slice.
- **The general form, worth stating because it is not specific to this skill: a flow that depends on a tool outside its own version boundary inherits that tool's changes without review.** The plugin pins its own behavior with the `version` field and a CHANGELOG entry per change; a slash-command it merely names does neither. Anything this flow's correctness rests on belongs in the plugin.

## 1.14.0

- **The integration gate was stated unconditionally, and it is only load-bearing in the case its own reasoning describes.** "N green PRs ≠ a green epic — each branch was gated against its own fork point, blind to the other slices" is true for **parallel** slices forked from a shared base and merged independently. It is not true for a run whose worktrees are each cut from the current tip and merged sequentially: there every branch is `tip + its own changes`, its gate already saw all prior merged work, and a conflict-free merge produces a tree **byte-identical** to the branch tip that was just gated. So the close-out gate re-executes the same tree for the same answer — on a monorepo whose full gate is ~10 minutes, a real cost paid for zero information, every epic. Observed across a thirteen-merge arc: twelve of thirteen merges introduced nothing beyond the already-gated branch tip.
- **It is now the cheap check that distinguishes the two cases, not a habit:** after each merge, `git diff --name-only <merge>^2 <merge>`. Non-empty means the merge produced content no gate has seen, from exactly two causes — a conflict resolution, whose resolved tree is new content by definition, or a sibling branch that merged in between, which this branch was cut before and gated without — and the merged result gets one gate run. Empty means the pre-merge gate already ran precisely this tree. The rule is kept in both directions because the failure runs both ways: an unconditional gate burns the suite on an already-gated tree, and "the last slice was green, so the epic is green" is wrong the moment two slices ran in parallel, which is this flow's default dispatch shape. The general form, worth stating once: a blanket rule that is right in the dangerous case and wasteful otherwise is better expressed as the check that tells them apart.
- **Two things the empty answer does not buy, both of which would be silent if left unsaid.** It proves the tree was *run*, not that the run was *green* — in the transient-red window slices merge on a green-modulo-baseline judgment rather than a green exit, so an epic tip can be byte-identical to a tree nothing ever observed fully green, and skipping requires both halves (nothing added **and** an actual green behind it). And it governs re-running the **suite** only: the merged *code* still gets read by hand wherever 2+ slices touched one structure, because the semantic drift that section describes is invisible to a green gate and equally invisible to an empty diff.
- **The epic branch made this sharper rather than obsolete — and the closing merge is the one that is usually non-empty.** 1.12.0 moved this gate onto the epic branch; what it did not say is that a gate on the epic tip is not a gate on what lands, because the integration branch moved while the epic ran, so `epic → integration` combines two histories nothing has tested together. The fix is ordering, not another gate: merge the integration branch INTO the epic one final time *before* the close-out gate — the same merge the drain tick already runs — and the gate then covers the exact tree the closing merge produces, whose `^2` diff comes back empty. That gives the mandatory per-tick merge a second reason to exist beyond bounded conflicts, and it means the epic close-out is at most one gate, sometimes none, rather than one by ritual.

## 1.13.0

- **`merge-pr` synced the PR's base branch by *switching the main checkout to it*, which is safe for exactly one session and corrupts a branch the moment there are two.** The main checkout is the one piece of global mutable state in a flow that is otherwise isolated per worktree, and multi-session work in one repo is now ordinary. Observed: three sessions in one repo; one ran `merge-pr.sh` for a slice PR based on an epic branch, so the helper switched the checkout off `release/0.4.0` onto `epic/…` and merged on the remote; in the window before the sync finished, another session's work put the checkout back on `release/0.4.0`; the sync then fast-forwarded *whatever was checked out*, retried six times, and exited with its loud "SYNC FAILED; do NOT cut new worktrees" error — correct, and the only reason the damage was caught. By then the local `release/0.4.0` ref pointed at the **epic branch's merge commit**: six commits of unrelated epic work on the release branch locally, while `origin/release/0.4.0` had independently advanced. Nothing was pushed, so no remote damage; the next worktree cut from `release/0.4.0` would have forked off a poisoned base.
- **The base is now synced by ref whenever it is not the checked-out branch — no switch, so no window.** A branch nothing is standing on needs no working tree to move: `git -C <main> fetch origin` then `git -C <main> branch -f <base> origin/<base>`. There is nothing for another session to land in the middle of and nothing to switch back afterwards. The old `pull --ff-only` path survives unchanged for the case where the base **is** the current branch, which needs no switch either because you are already on it. Both paths keep the existing verification that the local branch actually reached the merged tip — the path changed, the guarantee did not — and the ref path is only ever a *forward* move: a local base carrying commits the remote does not is refused outright with the reconcile command, rather than force-moved past them, since that is precisely the state the observed failure leaves behind. A base checked out in a **linked** worktree cannot be moved by ref at all (git refuses to move a branch any worktree is standing on) and is reported by path, because someone is working there — a condition to hand back, not to suppress.
- **And a branch you did not intend to move having moved is now an alarm.** The old error only ever checked that the *intended* branch reached the merged tip; it had no opinion about a branch that moved **instead**, which is the half that actually corrupts and the half that is silent — every other signal after the merge reads as a clean close-out. The helper now records the main checkout's branch and HEAD before it touches anything and verifies both at the end: if the checkout is on a different branch, or a different commit, it says so and exits non-zero, naming the branch, where it was, where it is now, and that another process moved it mid-run. It also re-checks the branch before **every** advance inside the retry loop, not only at the end, because the on-base decision is made once and then used across seconds of teardown, merge and polling — and on that path `git merge --ff-only` names no branch, so it moves whatever is checked out at the moment it runs. Checking once at the start would have left the original bug intact for that path. The result is a stop rather than a silent corruption, and a re-run finishes the sync as it always did.
- **Both shells, verified against a real git topology rather than by eye.** `bin/merge-pr.ps1` gets the same two paths, the same messages and the same exit codes, and `scripts/check.sh` holds the pair to matching usage lines and env-var sets as always. Behavioral equivalence was exercised in **both** implementations across the same five scenarios in a sandbox repo with a stubbed `gh`: base not checked out (checkout untouched, base ref advanced to the merged tip), base checked out (still fast-forwards), base held by a linked worktree (named and refused), a local base that had diverged from the remote (refused, ref untouched), and another process switching the checkout mid-run (alarm, non-zero). The frozen helper contract does not move: no argument, environment variable, `READY:`/`HEAD:` line or exit code changes.
- **The skill's claim that the helper parks the checkout on the base is corrected, and the concurrency hazard is stated where the wrong-repo hazard already lives.** 1.12.0's epic-branch section told you to switch the main checkout back after every slice close-out, and called that "the third path that parks the main checkout on the epic branch" — true then, and superseded now: there is nothing to switch back, so that instruction is gone rather than left as a harmless-looking ritual whose reason has evaporated. The hand-run close-out's sync step carries both forms for the same reason the helper does. The new hazard paragraph sits beside the wrong-repo one, because they are the same shape — a helper resolving shared state from ambient context — and both are stated with the failure that produced them.

## 1.12.0

- **`orchestrate` documented a cost it had no way to avoid, and now has the branch that avoids it.** Its transient-red section already said the quiet part: for a schema-first / all-or-nothing epic a full-green gate is unattainable mid-epic *by design*, and the instruction was to merge slices onto the shared integration branch anyway, on a green-modulo-baseline judgment. So the shared branch was knowingly red for the duration, and every worktree anyone cut from it during that window started from a red base — a cost stated plainly with no alternative offered. The **epic branch** is the alternative: a convergence branch cut from the integration branch that a multi-slice epic's slices fork from and PR into, gated as a whole, then merged back in one ordinary PR. The transient red now lives there, the integration branch never sees a state the epic has not finished converging on, and the "gate the integrated whole before you close" rule moves onto the epic branch too — where a cross-slice break surfaces before the shared branch has seen any of it, instead of after every slice has already merged into it.
- **The new concept is named `epic branch`, and `integration branch` keeps its existing meaning, deliberately.** The tempting alternative was to rename the base to "release branch" and call the new one the integration branch — and it is wrong twice. `integration branch` is this skill's project-*agnostic* term, where `release/x.x.x` is merely Trinity's instance of it, so the rename would bake one project's convention into the generic vocabulary; and it would silently repoint a live term, so that the same phrase names a different branch than it did in every older cached copy and CHANGELOG entry. In a document agents execute literally, that is the most expensive kind of ambiguity in the exact instruction where being wrong costs most ("branch from the integration branch"). The two-level vocabulary is instead stated once, where the skill first introduces the integration branch, so a reader meets both terms together rather than discovering the second one mid-procedure.
- **The trigger is one question, and slice count is explicitly not it.** *Does any intermediate state leave the integration branch in a condition you would not ship?* Primary: the epic is only correct as a whole — a NOT-NULL schema swap, a required interface field, a renamed module, where every state before the last consumer migrates is unshippable. Secondary: a contract seam, whose two halves landing separately means the branch is wrong in between — the primary condition by another route. Two conditions are marked contributing-but-never-sufficient, because each alone would degrade the trigger into a default: **slice count**, which measures how long a partial state sits on the branch rather than whether that state is broken (a real five-slice run — cache invalidation, a UI gate, a query poll, a SQL predicate, a store guard — was independently shippable at every step and left the branch green after every merge; a count trigger would have fired and bought nothing), and **an integration branch busy with other sessions**, which is the opposite concern and near-permanently true in a multi-session shop, so on its own it means "always".
- **The cost is stated, not buried: conflicts are deferred and concentrated, and the mitigation is mandatory.** Nothing about an epic branch makes a collision go away. It moves it — from a slice author resolving a small one against code they just wrote, to whoever lands the epic resolving a bigger one later with less context. The mitigation rides the wakeup tick that already runs the drain and the local fast-forward: merge `integration → epic` on that same cadence, so drift stays bounded and each collision surfaces while its slice author is still live. Merge, never rebase. A skill that sells a technique without its cost produces agents that apply it everywhere, which is the failure this framing prevents.
- **`decompose` finds it; `orchestrate` acts on it — the split already established for contract seams.** `decompose` grounds slices in real code and emits the producer → consumer map, so it is the only pass positioned to see whether two halves must land together, and it now answers the epic-branch question explicitly in every breakdown — recommended and why, or not-needed and why. An unanswered question reads as "no" without anyone having asked it, so the parallelization-plan template carries the line with its "not needed" default filled in. `orchestrate` holds the lifecycle: cut it in the main checkout (`git switch -c <epic> <integration>` — worktrees are only ever for slice work), point each slice's `setup-worktree.sh <slice> <epic>` at it, gate it once the fleet is quiet, then one ordinary PR into the integration branch, and delete it after that merge under the same never-past-git's-"not merged"-warning guard as any slice branch. Cutting it is three commands, not one, and the two easy to drop are the load-bearing ones: **push it**, or `origin/<epic>` does not exist and neither the HEAD-verification invariant nor `gh pr create --base` has anything to resolve; and **switch the main checkout back off it**, or the every-tick reconcile — which takes no branch argument and follows whatever is checked out — silently stops fast-forwarding the integration branch for the epic's whole duration, and the next unrelated worktree forks off a stale HEAD. The per-tick mitigation carries the same two steps for the same two reasons, and `merge-pr.sh` is a third path to the same parked state — it syncs the PR's base by checking it out, so a slice close-out during an epic leaves the main checkout on the epic branch and it has to be switched back. The helper is right to do that and is not changed; the skill just says what to do after it.
- **No helper changes were needed, which was checked rather than assumed.** `merge-pr.sh` reads the base off the PR itself (`baseRefName`) and drives the mergeability preflight, the merge, and the local fast-forward from that value — so a slice PR based on an epic branch closes out identically, fast-forwarding the local epic branch in the main checkout, with no argument or flag to add. The frozen helper contract does not move.
- **Both shapes stay readable, which was the constraint on how this was written rather than an afterthought.** Single-slice work is the common case and must remain followable start to finish without ever meeting an epic branch — if cutting one worktree for one bug fix required understanding epic branches, the change would have made the skill worse. So the concept lives in one self-contained section that opens by telling a single-slice reader to skip it, and the rest is surgical: the branch-from hard rule refined **in place** (epic branch when there is one, integration branch otherwise) rather than left as two rules that appear to contradict, and one bullet on the drain tick. The instructions naming a branch literally were re-pointed at *the PR's own base* rather than at the integration branch by reflex — the two conflict-resolution commands especially, since merging the integration branch straight into an epic's slice drags in commits the epic has not converged on and defeats the isolation the branch exists for. The one place a conditional would have reached an implementer is resolved by the orchestrator instead: the pasted handoff block now carries a `<base-branch>` the orchestrator substitutes, because it already knows which branch that is and an implementer left to work it out is one that can open its PR against the wrong one.

## 1.11.0

- **`merge-pr` ordered two irreversible steps before the only step that can fail, and now preflights the merge before touching anything.** The close-out has to tear the worktree down before merging — git refuses to delete a branch that is checked out in one, so `--delete-branch` needs the tree gone — and GitHub refuses to merge a draft, so the review flag has to be set before the merge too. Both constraints are real and both stay. What they cost was ordering: the worktree teardown and the `ready` flip ran first, and `gh pr merge` ran last, so a PR whose base had moved under it failed at the merge with `GraphQL: Pull Request has merge conflicts` — leaving no worktree to resolve the conflict in and a PR marked ready with no review behind it, which this workflow's own rules call a bug. It now asks GitHub whether the PR is mergeable before anything is touched: `CONFLICTING` stops with a non-zero exit, the worktree intact and the PR still a draft, and a message naming the fix — merge the base IN, in the branch's worktree, never rebase. `mergeable` is computed asynchronously, so `UNKNOWN` is treated as "not yet known" rather than as either verdict: it polls a few times and then falls through to the merge, because a preflight that hard-failed on `UNKNOWN` would be flaky on exactly the PRs that were just pushed.
- **And it restores the draft flag when the merge fails anyway.** `ready` has to precede `merge`, but it must not *survive* a merge that did not happen, or the PR sits wearing the one signal this flow reads as "an orchestrator read this diff and is merging it". The failure path now puts it back — and only when this run is what set it, so a PR that arrived already ready keeps the state it came with rather than being pushed into a draft nobody asked for. This matters most in the `UNKNOWN` fall-through, where the preflight could not rule the conflict out. The failure message names the recovery for the case the teardown already happened.
- **`setup-worktree --existing <branch>` attaches a worktree to a branch that already exists.** Until now no helper could: `setup-worktree` only ever ran `git worktree add -b`, which creates a branch and fails when one is already there — so recovering from the failure above took a raw `git worktree add` outside the helpers, and a tree cut that way gets none of the env symlinks, none of the config's `env`, and no install. `--existing` is the recovery form for a branch that outlived its tree, and everything downstream is unchanged, so a re-attached tree is as self-contained as any other and can face the gate. It takes **no base** — an existing branch's base is whatever it already forked from, so the argument shape is the flag and the branch, nothing else. If only `origin/<branch>` is left (the local branch is deleted on every successful merge) it recreates a local branch tracking the remote; if the branch does not exist at all it stops rather than creating one, because the fallback would fork off whatever HEAD it found. It is a flag and **never** an inference: attaching merely because a branch happens to exist would silently reuse a branch a caller meant to fork fresh off `<base>`, which is the stale-base seeding the worktree rules warn about hardest, and it arrives with a real tree and a real install where only the HEAD is wrong.
- **Both modes now print the worktree's resulting commit on its own line — `HEAD: <sha>`, beside `READY: <path>`.** The worktree flow's second invariant requires verifying that a new tree's HEAD equals the base tip before an agent is dispatched, and states that the helper does not do it for you. The old output invited *inferring* it from the `READY: … off <base>` text instead — which says what was asked for, in exactly the situation the invariant exists for. Printing the sha the tree actually landed on makes the honest check and the lazy read the same act. `READY:` itself is byte-identical, because callers parse it.
- **The frozen helper contract moves, on the record, in exactly two additive ways: a new `--existing` argument on `setup-worktree`, and a new stdout line beside `READY:`.** Nothing else does — no environment variable added, renamed or repurposed, no exit code reused, the `READY:` line untouched, and `merge-pr`'s and `remove-worktree`'s argument shapes unchanged. `AGENTS.md` now spells the contract out as it stands rather than pointing at "whatever is on `main`", since a frozen contract that is only described by reference is one nobody can check a change against. Both changes landed in both shells together, per the parity rule — and the parity check compares surface shape only, so behavioral equivalence was held to by hand and exercised in both: fresh fork, attach to a local branch, attach when only `origin/<branch>` survives, a branch that does not exist, a base passed to `--existing`, and a re-run over a tree that is already there.

## 1.10.0

- **`decompose` mapped conflicts by file, and file-disjointness turns out to predict almost nothing.** Both existing maps key on files — the conflict map for pairs brushing one file, shared hotspots for 3+ slices editing one structure — and a run whose slices were perfectly file-disjoint (zero merge conflicts across every worktree) still produced several genuine cross-slice breaks, every one of them a contract. The gap is the case where two slices touch **no file in common at all** and still break each other, because one produces a shape the other consumes: a return type, a schema field, a tool grant, a prompt variable, a config key. Neither existing map can see it, and the shared-hotspot remedy cannot help — there is no shared structure to hoist. So `decompose` now emits a second, separate map: producer → consumer → the shape between them. Two seams are called out as the ones a file map structurally cannot see, because nothing mechanical connects their halves: a producer and consumer in different languages or different trees (code defining a value that documentation or a prompt describes), and a seam with no compiler between the halves (a config, a prompt template, a generated brief). The producer's gate is green, the consumer's gate is green, and the break appears only when both are on the branch.
- **`orchestrate` gained the half that acts on it, because a map nobody checks is decoration.** A hand-back report is evidence about its own half and hearsay about the other — an implementer can say what it built, never what its counterpart now expects, having never seen the counterpart. So for any pair the decomposition flagged as a contract seam, reading each diff alone is two half-reviews rather than one review; the rule is to diff both halves against each other before merging either, checking the specific thing (the shape the producer now emits against the shape the consumer now reads). Both PRs will be green, because each gate only ever exercised one side. Split across the two skills deliberately: `decompose` is the pass that grounds in real code and is therefore the only one positioned to *find* a seam, while `orchestrate` is the only one holding both diffs at merge time and therefore the only one that can *check* it. In one skill alone it is either a map nobody acts on or a check with nothing to check against.
- **`orchestrate`'s stuck-handback rule covered blockers you can see, and missed the failure that does not feel like being stuck.** The existing paragraph handles a blocker, an unresolvable ambiguity, a check that will not go green — all states an implementer recognizes it is in. The new paragraph covers the inverse: the brief needs an identifier for something real (an id, a key, an owner, a path, a version), the thing does not exist yet or is unreachable from where the slice runs, and nothing is erroring — a value of the right *shape* can be produced and everything downstream accepts it. Types satisfied, scoped check green, tests passing, PR reading clean. That is the failure, not the escape from it: a fabricated identifier records the wrong fact permanently and quietly, with every guardrail confirming it. The rule names the tell (the input identifies a real thing, and you cannot obtain the real one) and the required move (stop, report what was needed and why it was unavailable *where you stand*, and what the orchestrator must decide). Written from the case where an implementer declined to synthesize an owning identifier and reported the gap instead — the alternative would have passed every check while silently attributing work to the wrong thing. Shape-correct and fact-wrong is the hardest defect class to find later, precisely because nothing about it looks broken.
- **`decompose` now treats documentation of a changing model as a sequencing constraint rather than a file question.** A slice that documents a subsystem must land after every slice that changes it, or it documents a shape that no longer exists by the time it merges — and unlike stale code, nothing fails. The exemption is stated with it, because the unqualified rule is also wrong: documentation of a part of the system the epic does not touch should say so in the wave note, otherwise "docs last" strands a correction that is already misleading its readers. Written from a dispatch where file-disjointness was checked, found clean, and two agents ran in parallel anyway — one documenting a model, the other rewriting it.

## 1.9.5

- **`orchestrate`'s no-suppressions rule was an unqualified absolute that this repo's own shipped code correctly violates, and it now distinguishes gaming from a documented exception.** Since `1.9.2`, `bin/setup-worktree.ps1` has carried a one-function `SuppressMessageAttribute` for `PSAvoidUsingInvokeExpression`: a project's `install` config value is a command *line* (`pnpm install --frozen-lockfile`, possibly with a pipe), so it has to be interpreted rather than spawned as an argv — which is what the `.sh` sibling's `eval "$INSTALL_CMD"` does, at the same stated trust level. "Fix the cause instead of suppressing" has no meaning against it: the flagged construct *is* the intended behavior, deleting the suppression turns CI red, and spawning an argv instead breaks every project whose install command carries a flag. The fix is precision, not exemption.
- **The default stays absolute; a suppression you ADD is permitted only when all four conditions hold.** Narrowest scope the tool allows — never file-wide, and never a settings-file exclusion that silences the rule repo-wide, which is indistinguishable from deleting the check. That justification saying why the flagged construct is correct *there*, not that the check is noisy. And a call-out in the hand-back report, so it is reviewed at merge rather than reconstructed later. The second condition is the load-bearing one: a justification-bearing suppression states a claim a reviewer can see and reject in the diff, while a bare disable asserts nothing and is invisible to review — which is what gaming looks like. Every prohibition the rule already named is unchanged and explicitly still gaming: bare disables, widening to `any`, deleting the flagged assertion, shaving comments to duck a max-lines cap, nudging one line under a threshold. None of them can satisfy the four conditions, because for none of them is there a correct-construct claim to write down.

An existing suppression is the previous author's claim, already reviewed on the PR that added it: if you think it fails a condition, report it and leave it. The reviewer's copy carries the same scoping, so a pre-existing suppression a diff merely left alone is not that PR's to re-litigate.

A four-condition exception written out twice drifts, and the next editor then has no way to tell which copy is authoritative, so only the Implementer paragraph defines it and says so; the Hard rules bullet keeps a compressed checklist for the reviewer holding a diff, names where the definition lives, and adds the half only a reviewer needs — bounce a suppression that meets the first three conditions but never appeared in the hand-back report, since one nobody flagged is one nobody reviewed.
- **`AGENTS.md` now states this repo's own position, because two places already asserted it did.** Both `CHANGELOG.md`'s `1.9.2` entry and a comment in `scripts/check.sh` refer to "the guardrail-gaming `AGENTS.md` forbids" — a rule `AGENTS.md` did not actually carry. It carries it now, together with the shipped suppression it makes an exception of, so a contributor working in `bin/` gets the answer locally instead of inferring it from a skill that describes other projects' workflow. The bullet **points at** `skills/orchestrate/SKILL.md` for the four conditions rather than paraphrasing them, per the rule `AGENTS.md`'s own preamble already states — a first draft did paraphrase, and had already drifted to three conditions by merging the two that a reader most needs kept apart. What it states locally is what only this repo can: which suppression exists, that it is load-bearing and not to be deleted for compliance, that it is not precedent, and that a repo-wide PSScriptAnalyzer settings-file exclusion is never the answer. The failure runs both ways: read the suppression as permission and you add an unjustified one beside it; read the rule as unqualified and you delete the load-bearing one and turn CI red.

- **`scripts/check.sh` now enforces the parity mechanically, because prose does not stop two hand-maintained copies of the same logic from drifting — it only makes the drift someone's fault afterwards.** `AGENTS.md` states the rule; this makes it a check that fails closed. Every `bin/<name>.sh` must have a `bin/<name>.ps1` sibling and vice versa, the two must agree on their runtime usage line and on the **contract** environment variables they consume, and every `.ps1` must be printable ASCII terminated by LF. The env-var comparison is scoped to the frozen contract surface (`WORKTREE_HOME`, `REPO`, `WORKSPACE`, `WORKTREE_DEST`, `MERGE_PR_FORCE`) rather than to every variable each side happens to touch: the bash helpers need MSYS path-translation plumbing that has no PowerShell counterpart at all, so demanding identical sets would go red on a correct implementation and the only way to green it would be to invent a variable nobody reads — exactly the guardrail-gaming `AGENTS.md` forbids. The usage line is read from **code, not comments**, so a header that paraphrases the invocation cannot shadow the runtime line the comparison exists to check. The `.ps1` scan set carries its own non-empty assertion, and so does the env-var extraction — two empty sets compare equal, so a pattern that quietly stopped matching would otherwise report perfect agreement.
- **The ASCII rule is enforced at the byte level, not by decoding the file.** Windows PowerShell 5.1 reads a file with no byte-order mark using the system ANSI codepage, so one non-ASCII byte — an em-dash in a comment being the likely one, since these helpers' comments are full of them — is decoded as mojibake and surfaces as a parse error nowhere near the character that caused it. Shipping a BOM to dodge that is worse than staying ASCII, so the check reports the offending byte and its line directly.
- **PSScriptAnalyzer reports `SKIP`, never `ok`, when `pwsh` is not installed.** It is the one step here that needs an optional tool, and `pwsh` is deliberately absent from the gate's required-tool list: this repo is zero-dependency by design, and a gate that needs an install is a gate nobody can run before pushing. The parity checks need no `pwsh` and always run; the analyzer is left to CI. A check that could not run must not print green, because that is a claim CI will later contradict — and the contradiction arrives after the merge.
- **CI gained a `windows-latest` job, because a Windows claim no runner exercises is a claim nobody checks.** Both existing jobs run on `ubuntu-latest`, so until now nothing on Windows was ever executed. The new job runs the real scenario end to end — init a throwaway repo, cut a worktree, assert its HEAD is the base tip and that the `READY:` line printed, tear it down, assert it is gone — in **both** shells a Windows user can land in: Git Bash and Windows PowerShell 5.1 (not `pwsh`, because 5.1 is what ships in-box and is therefore the compatibility target). It does not run `scripts/check.sh`: this branch's first CI dispatch found `windows-latest` has no `shellcheck`, and the script's own required-tool check correctly refused to print green there rather than silently skip it — a check that cannot run must not report ok, and this is that rule catching the exact gap it exists for. The job was restructured on the spot to give each runner only the job it can do: the "PSScriptAnalyzer must not SKIP" assertion moved to the `check` job on `ubuntu-latest`, which ships both `pwsh` and PSScriptAnalyzer preinstalled, so it lints `bin/*.ps1` there with no install step to be defeated by a transient PSGallery failure. `windows-latest`'s remaining and entire purpose is the one thing no other runner can do: actually execute the helpers on Windows, in both shells.
- **The docs that stopped being true came along.** The README's prerequisite line said "macOS or Linux… on Windows, run under WSL" and is now the real support matrix; "four executables" is eight; the repo tree grew the four `.ps1` files plus `AGENTS.md` and `.gitattributes`, which landed last release without being listed. `orchestrate` and `setup` both told an agent to invoke the helpers bare as `.sh`, which is exactly the instruction that fails on a PowerShell-tool session — both now carry the shell-selection rule and name the failure it prevents.
## 1.9.1

- **The four bash helpers now agree with themselves about what a path is.** Under Git Bash on Windows, `git` prints Windows-form paths (`C:/Users/…`) while anything derived from `$HOME` is MSYS-form (`/c/Users/…`). The filesystem accepts both, so a mismatch is never an error — only a string comparison can see one, which is why every failure in this release was silent rather than loud. Each helper now carries a `norm_path()` (`cygpath -u` where it exists, the identity function everywhere else) and routes every value that is later compared, grepped, or prefix-matched through it at the point of production. It is duplicated per script on purpose: `bin/` ships on a user's PATH under a parity rule that pairs every `bin/<name>.sh` with a `bin/<name>.ps1`, so a shared file would become a fifth helper owing a PowerShell sibling with nothing to do — PowerShell has no MSYS form to convert.
- **`setup-worktree.sh`'s idempotency guard failed OPEN on Windows.** It asked `git worktree list | grep -qF "$WT"`, comparing git's Windows-form output against an MSYS-form path, so the match never fired: a re-run fell straight through to `git worktree add`, which then died with "already exists" — the exact error the guard was written to prevent. It now reads `git worktree list --porcelain` and compares normalized paths for **exact equality**, which also closes a second, quieter bug the substring match had on every platform: a leaf that is a prefix of another registered worktree (`pfx` against `pfx-retry`) matched it, so setting up `pfx` reported the wrong worktree as already existing and created nothing.
- **`setup-workspace.sh` hung forever when started from a Windows-form path.** Its walk up to `.agents/workspace.json` looped `while [ "$DIR" != "/" ]`, and `dirname` starting from `C:/Users/…` bottoms out at `C:/`, which is never `/` — an outright hang with no output at all, the worst failure shape in the set. It now loops until `dirname` reaches a fixed point, which terminates from any root spelling.
- **`remove-worktree.sh` resolved the wrong target for an absolute Windows path.** A `C:/…` path does not begin with a slash, so the `== /*` test filed it as a *branch leaf* and the script looked for `$WORKTREE_HOME/<project>/C:/…` — a path that never exists, so the run reported "already removed" and exited 0 having removed nothing. All three sites now accept `[A-Za-z]:[\\/]` as absolute too, and the kill-scope prefix is normalized alongside them.
- **`remove-worktree.sh` now finds and kills processes on Windows.** `lsof` and `pgrep` do not exist in Git Bash and both call sites were `command -v`-guarded, so the scan found exactly zero processes, printed "no running processes found", and the removal then failed on files Windows still had locked. There is now a third scan using `Get-CimInstance Win32_Process` for the command-line match and `taskkill /PID <n> /T /F` to terminate. **Windows PIDs and MSYS PIDs are unrelated numbers from unrelated counters**, so the two are kept in separate arrays and each only ever reaches its own killer; the scan also excludes this shell and every one of its ancestors, because `/T` kills a process *tree* and the script's own argv contains the worktree path whenever the caller passed one. What has no cheap Windows equivalent — `lsof +D`'s open-handle enumeration, which needs Sysinternals `handle.exe` — is now printed as an explicit SKIPPED notice, so an undetected lock holder reads as "we did not look" rather than as "nothing was there".
- **`setup-workspace.sh` no longer fails outright on a node-only machine.** It read its manifest with `python3` and nothing else, while `setup-worktree.sh` — reading the same kind of file for the same flow — had had a node fallback all along. It has one now.
- **Both JSON readers now pick an interpreter by RUNNING it, not by `command -v`.** On Windows `command -v python3` succeeds against the Microsoft Store's `python3.exe` App Execution Alias: a stub that opens the Store, prints nothing, and exits. A `command -v`-only probe therefore selects an "interpreter" that emits an empty config, which the caller `eval`s into silence — a bare worktree, or a workspace reported as having no members, with no error anywhere. Each candidate (`node`, `python3`, `python`, `py -3`) is now validated by executing it and checking what came back, and `setup-worktree.sh` additionally captures its reader's output *before* `eval`ing it, so a reader that failed is a hard stop instead of an empty assignment.
- **`setup-worktree.sh` says when an env file was copied instead of symlinked.** Git Bash's `ln -sf` copies unless Windows Developer Mode is on — an unprivileged process cannot create a symlink otherwise — and `ln` exits 0 either way. A copy is a point-in-time snapshot, so later edits to the main checkout's env file stop reaching the worktree, and that surfaces much later as a test reading a stale value with nothing pointing back at setup. It now checks the result and names the files, with the fix.
- **`WORKTREE_HOME` defaults to `%LOCALAPPDATA%/wt` on Windows.** `~/.worktrees/<workspace>/<leaf>/<repo>/node_modules/.pnpm/<pkg>@<version>/…` routinely runs past Windows' 260-character `MAX_PATH`, and the install then fails naming some deeply nested file rather than the length that actually broke it. The default is identical in all four helpers, which matters because `merge-pr.sh`'s wrong-repo guard decides "is there anything to close out here?" from whether a worktree exists under it — a helper that disagreed would look at an empty directory and refuse to close out a perfectly normal merged PR. An explicitly set `WORKTREE_HOME` still wins everywhere, unchanged. `setup-worktree.sh` also warns when `git config core.longpaths` is unset, since that is the same ceiling from git's side.
- **The docs stop stating `~/.worktrees` and `~/.zshenv` as unconditional facts.** Both are now qualified per platform. `~/.zshenv` in particular has **no Windows equivalent** — PowerShell's `$PROFILE` is interactive-only and is therefore the exact same trap `~/.zshrc` is — so the docs name the real answer: a persisted user environment variable, which every later process inherits regardless of shell.

## 1.9.0

- **`.gitattributes` pins `bin/*.sh` and `bin/*.ps1` to LF.** Git for Windows defaults to `core.autocrlf=true`, so without this file a Windows clone checks the shell helpers out with CRLF line endings, and every one of them dies at `#!/usr/bin/env bash\r` with "bad interpreter" — before any other Windows problem is even reachable. Pinning the line ending at the repo makes the checkout correct regardless of the cloning machine's `autocrlf` setting, rather than depending on every contributor's local git config agreeing.
- **`bin/merge-pr.sh`'s close-out step 1 was calling a path that does not exist, on every platform, not just Windows.** It invoked `"$WORKTREE_HOME/remove-worktree.sh"`, which resolves to `~/.worktrees/remove-worktree.sh` — but the helper ships in `bin/`, next to `merge-pr.sh` itself, never under `$WORKTREE_HOME`. It now resolves the sibling the way `setup-workspace.sh` already does, via `HERE="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"` computed at the top of the script, so the call no longer depends on `$WORKTREE_HOME` pointing anywhere in particular.
- **The same script's wrong-repo guard only recognized one worktree layout.** It checked for a worktree at `$WORKTREE_HOME/$PROJECT/$LEAF`, which is where a worktree lands outside a workspace — but a workspace member lands at `$WORKTREE_HOME/<workspace>/<slug>/<project>` instead (`setup-worktree.sh`'s own layout rule). The guard now checks both layouts, so closing out a merged PR for a workspace member no longer misreads a perfectly normal worktree as evidence of the wrong repo.
- **`AGENTS.md` now exists, and carries this repo's conventions instead of `.agents/worktree.json`'s `briefConventions` field.** That field had grown into a full rulebook packed into one JSON string — hard to read, hard to diff, and exactly the kind of convention the `setup` skill itself says belongs in `AGENTS.md` with a pointer left behind, not copied inline. Nothing was dropped in the move; every sentence carried over verbatim. `AGENTS.md` also gains two new sections this release starts needing: **the frozen helper contract** — the CLI arguments, env vars, the `READY: <path>` stdout line, and exit codes that this repo's bash helpers expose are pinned as of this version, because a PowerShell port of the same helpers is about to be built against exactly this contract, and an unannounced change on the bash side would silently break parity with a language nobody would think to re-check; and **the `bin/` parity rule** — every `bin/<name>.sh` will need a `bin/<name>.ps1` sibling with a matching usage line and env-var set, kept ASCII-only because PowerShell 5.1 misreads UTF-8 without a BOM and these helpers' comments are full of em-dashes, since a helper shipped in only one shell is simply unavailable to users on the other.

## 1.8.2

- **`setup`'s bootstrap exception claimed something false, and this repo was the counter-example.** It read *"the repo can't cut a worktree until this file exists — the flow can't bootstrap itself"*, which licensed a direct push to the integration branch for any repo lacking a config. But `setup-worktree.sh` cuts a worktree with or without one — it warns on stderr and makes a **bare** one — and bare is only fatal where the project **has an install step**, because then the worktree has no `node_modules` and every check inside it fails for reasons that read as code bugs rather than as a missing config. For a zero-dependency repo a bare worktree is fully functional and the config lands through a normal PR. The exception now says exactly that, and names the failure it prevents; the old wording made a legitimate PR look like a rule violation, which is the direction that costs a review record.
- **The repo that ships `setup` finally has the file `setup` tells everyone to write.** `orchestration-skills` had no `.agents/worktree.json`, so an orchestrator working here had to improvise the gate and the conventions — a guessed gate is one that passes while testing nothing. It declares what is actually true rather than the full key set: zero dependencies means no `install` and no `envFiles`, and a check that runs in under a second means `gate` and `scopedCheck` are the same command with no queue. Both readings are ones `orchestrate` already handles explicitly, so the repo lands in a mode the skill understands instead of one it has to infer.
- **There is now one gate, `scripts/check.sh`, and CI runs that rather than a second copy.** Every check lived inline in the workflow, so a contributor had nothing to run before pushing and CI was the first thing that ever evaluated a change. Two copies of a check drift, and the one that stops firing prints the same green as the one that passed — which is also why every check here asserts its file set is non-empty before scanning, and why the script reports *every* failure before exiting rather than stopping at the first. The version-bump guard deliberately stayed inline: it diffs against a PR base and reads the manifest as it was at that commit, so a local copy would either not work or lie about what a merge would ship.
- **`.agents/` and `scripts/` are exempt from the version-bump guard.** Both are contributor tooling — Claude Code never loads either and neither reaches a user's install — so a PR touching only them ships nothing, and demanding a bump for it invites a bump that ships an unchanged plugin. `market-skills` already exempted both; the two repos disagreeing was the inconsistency to remove. The exempt list stays deliberately inverted — it names what does NOT ship, so a new directory requires a bump by default — and now says why each entry earns its place.
- **Two statements about this repo went stale and are corrected.** `setup`'s tier table listed it under "no flow at all", and `orchestrate` used it as the example of a repo that edits `main` directly — both written before 1.8.1 made all three skills repos PR-only, and both now contradicted by the config that just landed. An agent reading the tier prose would have concluded it could push straight to `main` here, on the authority of the same skill that forbids it a hundred lines later.

## 1.8.1

- **The `orchestration-skills`-repo exemption from worktree/PR ceremony is withdrawn — this repo, `market-skills`, and `framework-skills` are all PR-only now, docs and CHANGELOG included.** The exemption let an editor push straight to `main` on the reasoning that this is "tooling"; but a plugin install is pinned to `.claude-plugin/plugin.json`'s `version` exactly like the other two repos, so a change here reaches users exactly the way theirs do — there was never a real difference to justify the special case. And a repo whose product is prose has no gate that can tell whether a rule is *correct*; the diff is the only review artifact there is, so a direct push spent that record to save a worktree. The rule now lives as its own hard-rules bullet instead of a clause in the `setup-worktree.sh` parenthetical, where an agent skimming for worktree mechanics was never going to look for a repo-wide policy.

## 1.8.0

- **Docs are now a slice's responsibility, stated in three places because the miss is silent.** Nothing in a gate fails when a doc stops being true: the slice goes green, the PR merges, and the miss surfaces later as a user acting on something that changed underneath them. That silence is the whole problem — an implementer that never considered the docs and one that considered them and found nothing produce identical output, so there was no way to tell them apart at review. `decompose` now names the docs each slice falsifies in its `Owns` list, `orchestrate` carries the docs rule as a fifth paste-verbatim brief item, and the implementer's hand-back reports a per-doc verdict rather than a bare "docs reviewed".
- **The rule that makes it work: search by the behavior, never by the vocabulary the change introduces.** This is the failure that motivated the release, and it defeats the obvious version of the check. Prose written for a user describes a feature in plain language and contains none of the identifiers a change adds, by construction — so grepping the docs for your own new terms returns nothing and reads as "no docs affected", with the search itself supplying the false confidence. The observed shape: a README paragraph enumerating the levers a user controls, which a change added a member to, described entirely in words the change never used. Both skills now say to ask what a reader currently believes and which of those beliefs the slice makes false, then to READ the candidate docs rather than grep them.
- **Scoping a doc out is a decision that has to be recorded, because an implementer will not revisit it.** A decomposer works from the plan, not from the diff, so "this doc is unaffected" is a claim made before the code exists — and once it reaches a brief as a do-not-touch, it is settled for everyone downstream. Both skills now require the negative case to be written down as an explicit not-affected-because, which is what lets an implementer overturn it when the diff disagrees. `orchestrate`'s review loop names the orchestrator's own version of this as the failure mode to watch for: a stale doc most often ships not because the implementer skipped it, but because the brief told it not to look.

## 1.7.1

- **`decompose` prescribed the `gh api` flag that publishes the path instead of the body.** Its three write examples used `-f body=@<file>`, and `-f` is `--raw-field` — it sends the value verbatim, so following the skill posted the literal string `@/tmp/…/decomp-36.md` to GitHub. Only `-F` expands a leading `@`. The failure is silent in the worst direction: `gh` exits 0 and prints a comment URL, so the agent reports success and only a human opening the issue ever sees it. One run put four unusable comments across three issues before anyone noticed. `write-issue` documented the trap correctly from its first commit; `decompose` — the skill that posts the largest bodies — never got the same treatment.
- **The warning travels with the flag, not just the correction.** A corrected flag with no rationale reads as arbitrary style and gets reverted by the next editor, so the fix carries the reason and the **verify-after** step: refetch the body and confirm it's markdown. The refetch is the only thing that catches this at the time it happens, since nothing in the exit code will.
- **CI now fails a skill that prescribes `-f` with an `@file` value.** This is a docs bug in a repo whose product is docs — nothing mechanical stopped it reappearing in the next skill written, and the author cannot see it at author time. The grep is anchored on `gh api` so that prose *quoting* the wrong flag to warn against it stays legal: a guard that can't tell a prescription from a warning would flag `write-issue`'s own warning line and force the next author to delete the warning to get green.

- **The gate queue lives under the user's home, not the OS temp dir.** 1.5.0 made a verdict survive a failed post by writing it to the ticket before reporting it, then left that ticket in a directory the system is licensed to reap — so the one artifact added to keep a verdict recoverable was handed to a sweeper with no idea anyone was still waiting to read it. The root is now `~/.gate-queue/<project>/`, alongside the `~/.worktrees/<project>/` convention, and its placement is stated as generic rather than something a project chooses.
- **The slot stays in the OS temp dir, and the reference says why.** Otherwise the first reader to move the queue moves the lock too, for symmetry, and believes they have been consistent. The slot is a mutex, not data: it carries no verdict, its holder-PID is liveness-checked so an abandoned one is stolen rather than trusted, and it is held only for the minutes a gate runs — well inside any reaper's threshold. Losing it to a sweep costs the next runner one `mkdir`.
- **A retention invariant bounds `done/`, keyed on delivery rather than age.** Nothing previously said what limited the ledger, so a project built from the reference grew one forever. The predicate is the whole rule: a ticket flagged for a human — retries exhausted, or the head moved off the gated SHA — still holds a verdict nobody has seen, and `reported: false` is what an abandoned ticket keeps, so a prune trusting age plus "not reported" deletes exactly the escalated records and spares the delivered ones already posted to the PR. The prune rides the reconcile walk, which already reads every ticket, and the clock is injectable so the rule is testable without waiting.
- **The failing tail is scoped to a red verdict.** A green comment is one line that quotes nothing, so a tail captured on green is the ledger's largest field in its most common case and no reader ever opens it. Called out with the trap it hides: when the routine computing the tail also cleans up the task-runner's run-summary scratch files, that cleanup has to be lifted out to survive being skipped on green.
- **The queue layout diagram shows `done/` as `<name>.json.<runnerPid>`.** Settling is a rename out of `processing/` and the claim suffix rides along; the diagram claimed a bare `<name>.json`, which had a reader coding a normalization step with no job.

## 1.6.0

- **`draft → ready` now means "an orchestrator read this diff and is merging it".** It used to encode a gate verdict, which is a claim a machine cannot make: a green suite says the tests passed, never that the agent solved the right problem, stayed in scope, or didn't reach green by weakening an assertion. Nothing mechanically stopped a PR nobody had read from being merge-eligible, and the playbook patched that with prose. The flag that authorizes a merge is now set by the reader.
- **The gate reports green as a PR comment, and leaves the PR draft.** It already commented on red; it now comments in both directions and never touches the draft flag. That collapses the reading to one sentence that holds in every mode — **a PR is gated iff it carries a gate comment** — with three states: `draft + ✓ comment`, `draft + ✗ comment`, and `draft + no comment` (the gate never reported: reconcile and look again).
- **`bin/merge-pr.sh` performs the flip, one line above `gh pr merge`.** Approval and merge are one invocation, so `ready` can never be a durable badge that goes stale when a fix agent pushes after the review. It sits inside the not-yet-merged branch, so a re-run of a half-done close-out stays idempotent.
- **Override gate mode keeps one axis and loses the other.** It still decides *who runs the gate and when* — the implementer runs the full `gate` itself, in the foreground, instead of enqueuing — and both reasons to grant it stand, as does the permanent override for repos with no queue. It no longer decides *who says the diff was read*: an override-mode implementer opens a draft PR and posts its own gate result as a comment, exactly like the queued path. The `--draft`-less PR disappears from every path, and an implementer that opens one is a bug with a mechanical consequence rather than a cosmetic slip.
- **This revises the 1.5.0 delivery rule** — *"a green counts as delivered only when the ready-flip **and** the comment both succeed"* — to: a verdict is delivered exactly when its comment lands. That is not a reversal. 1.5.0 made a verdict survive a failed post, by recording it on the ticket before reporting it; 1.6.0 makes a verdict stop meaning "approved". Both hold, and the reconcile-before-claim pass and the stale-SHA refusal that 1.5.0 introduced are untouched — a stale green comment on a moved head is still a false report.

## 1.5.0

- **A gate verdict is recorded before it is reported.** The queue's invariants covered process death and filesystem races but not the one step that depends on a machine you do not control — the report. A failed post destroyed the verdict outright, since the ticket moved to `done/` unchanged and the result existed nowhere but GitHub. The ticket now carries the outcome, exit code, failing tail, the SHA that was gated, and whether delivery succeeded, so `done/` is a ledger rather than a record that something happened.
- **Drain reconciles before it claims.** Each pass re-posts verdicts that were decided but never delivered, without re-gating. A re-post is refused when the PR's head has moved off the gated SHA — that verdict describes code the PR no longer carries, which is the same false-report as gating a mutated worktree — and retries stop at a cap so a deleted PR cannot make every future pass re-attempt a doomed post.
- A green counts as delivered only when the ready-flip **and** the comment both succeed; a PR left in draft reads as ungated whatever the comment says.
- `orchestrate` gains the missing reading for **a draft PR with no gate comment** — a third state that is neither green nor red, produced by a report that never landed as much as by a gate that never ran. It was previously indistinguishable from red, which invites dispatching a fix agent at a slice with nothing wrong with it.

## 1.0.0

First release as a Claude Code plugin.

- **Four skills** — `setup`, `write-issue`, `decompose`, `orchestrate`, namespaced `/pipeline:*`.
- **`bin/` on PATH** — `setup-worktree.sh`, `merge-pr.sh`, `remove-worktree.sh` are bare commands while the plugin is enabled, replacing the old `install.sh` symlink dance.
- **Per-project config moved into each repo** at `.agents/worktree.json`, declarative rather than sourced bash. The previous location keyed config to a checkout's *directory name*, which had already forced a duplicate config file for one repo cloned under two names.
- **`setup` skill** — onboards a repo by grounding its real lockfile, scripts, and CI, then scaffolds a durable gate queue into that repo if it wants one. The plugin carries the knowledge; the project owns the code.
- **Tiering** — a repo may want no flow at all, worktrees plus a single check, or the full gate-and-queue. `gate` == `scopedCheck` is a valid answer, and absent `enqueue`/`drain` means the implementer gates in-line.
