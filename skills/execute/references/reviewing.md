# Reading a gate result, and the transient-red window

Reference for `skills/execute/SKILL.md` → *Dispatcher*. **Read it the moment a verdict lands on a PR** — a green flag and a green gate are not the same claim, and one epic shape makes red the expected answer.

## Reading a gate result — verify the WHOLE failure set, and read the comment, not the flags
Two misreads have shipped a red integration branch and closed an epic on top of it. Both are structural and cheap to avoid — internalize them before you ever conclude "green" or merge. A third runs the opposite way and costs the opposite thing: reading an **environmental** red as N code defects, which spends whole runs debugging innocent diffs. The bullet on a PR that arrives without `--draft` is the adjacent bug they make easy to wave through. **All of it is about reading a verdict somebody else POSTED.** A gate you ran yourself has none to read at the moment you need one — you are the party who produces it, if anyone does — so its **exit status** is the reading instead (*Gate the integrated whole* below). Naming that boundary is load-bearing rather than tidy: this section is thorough enough to look complete, so a dispatcher standing in front of a gate log it produced itself finds nothing here that fits its situation and falls back on whatever the shell said — which is how a piped gate's exit 0 got read as green.

**Two counts moved when the flow started enqueueing its own gates, and they moved by DIFFERENT amounts — say which one you mean.** In a project with a queue, the epic's close-out gate and the mid-arc integration gate are both enqueued now (*Gate the integrated whole*). So: **paths that produce no durable record at all go 3 → 1.** A hand-run gate is the only one that writes no streamed log, no ticket and no ledger entry, and it is left in **two** places rather than one: a project that declares no queue, where an override-mode slice is the whole of it, and a queued project whose runner refuses the PR-less ticket, where the mid-arc integration gate alone falls back to it (*Gate the integrated whole*). **Paths that produce no PR comment go 3 → 2.** The close-out gains one, on the very PR the verdict is about; a PR-less integration ticket does not and never will, because there is no PR; and an override-mode slice's comment is one the agent *writes* rather than one it reads. So the mid-arc gate does not leave this section's scope — what changes is what you read: **the verdict on its ticket in `done/`, not a shell's exit status.**

- **A gate spans every workspace — read every package's result, never one package's summary.** `gate` runs the task-runner across ALL packages (Trinity: trinity, trinityailabs.com, cf, api-types). A `Failed: <pkg>#test` line plus a non-zero exit is **RED**, even when the *first* package's summary you happen to see looks like only the known baseline. Concluding "green-modulo-baseline" (see the transient-red window below) from one package's `Test Files N failed` line — without confirming the failing SET across *every* package is exactly the baseline — is precisely how a real regression in a *second* package rides through to merge and surfaces only at the epic's integration gate. When you assert green-modulo-baseline, enumerate the failing files across all packages and match them to the baseline set by name; a `cache miss, executing …` line for a package whose *result* you never saw is a signal to go read that result, not to assume it passed.

- **Several worktrees red at the same moment, with infrastructure-shaped errors, is ONE shared resource before it is N code defects — and it is the same instrument as the bullet above, pointed one level out.** That one says the failure set spans every package, so don't stop at the first summary; this one says the failure set can span every *worktree*, so don't read a simultaneous multi-slice red as N independent verdicts. They compose: widen within a gate, then widen across gates. **The tell is the shape of the errors, not their count** — deadlocks, unique-constraint violations, lock timeouts, "address already in use", a fixture another run truncated, a cache another run evicted — and the confirmation is that the *same* named resource appears in failures on branches whose diffs have nothing to do with each other. Check `sharedResources` (*Per-project config*) before you dispatch a single fix agent: an entry with `"isolatedBy": null` means the flow already knows these runs collide, and a missing key means nobody ever asked, which is not the same as no. Re-gate the branch **alone** to separate the two — a red that survives in isolation is a code defect, one that evaporates was the race — and where it was the race, the move is to narrow the wave, not to touch a diff.

- **The gate comment is the only evidence a gate ran — a PR's flags are not.** Trust exactly two signals that a gate is actually green: a runner-drained **`gate ✓ passed`** comment, or an override-mode agent's own gate comment on its PR reporting a full green with zero failures — and on the close-out/integration slice, independently re-run the previously-red files yourself before you believe it. Nothing else attests to a gate, and an empty PR conversation means nothing has. Read the comment and its failure set; the draft flag is about review, not about the suite.

- **An implementer that opens its PR without `--draft` is a bug you act on, not a formatting slip.** The ready flag means "a dispatcher read this diff and is merging it", and `merge-pr.sh` is the only thing that should ever set it — so a PR that arrives non-draft is claiming a review that never happened and is sitting in the merge-eligible state without one. Put it back to draft (`gh pr ready --undo`), then gate and review it like any other.

## Transient-red window (schema-first / all-or-nothing epics)
When a foundational change lands first — a NOT-NULL schema swap, a required interface field, a renamed module — it makes `gate` impossible to get fully green branch-wide until every consumer migrates. A full-green gate is **unattainable mid-epic BY DESIGN**; holding slices to it just paralyzes progress.

**Put this window on an epic branch.** An epic in this shape is the primary trigger for one (*The epic branch* above), and this section is the reason: the window has to exist somewhere, and the only real choice is whether it sits on the branch every other session cuts its worktrees from. On an epic branch it does not — the integration branch stays shippable throughout and sees the epic only as the single merge at the end, so nobody else forks off a knowingly-red base. Read the rest of this section as describing the **epic branch** when the epic has one, and the integration branch when it does not.

**The window is a fact on disk, not a note in a plan — declare it or it does not exist.** `decompose` flags which slices live in the window and you read a drained ticket's red against that flag, but both of those are judgments made by something that can read prose. A project's **commit-time** tooling cannot. Where a repo relaxes its pre-commit compile check for exactly this window — forgiving diagnostics that all point at files the branch never touched, while holding the branch's own files to the full bar — the only thing it can consult from inside a slice worktree is the ref graph. So the marker ref from *The epic branch* above is the contract, and it is deliberately the whole contract: `transient-red/<epic-slug>` exists ⇔ the window is open, and deleting it at close-out closes the window with nothing to unwind.

**Two things a detector must not key on instead, both of which look right — and the one rule behind both.** Not the **epic branch itself** — Rule 2 cuts one on multi-slice width alone, so there is an epic branch on *every* multi-slice arc including all the ones where every intermediate state is green, and a relaxation keyed on `epic/*` would silently start forgiving sibling breakage that is real on every one of those. And not `integration/*` — this playbook's opening reserves "integration branch" for the shared branch and says it never means anything else, so a detector keyed on that word is reading a level of the hierarchy that was never the window's home. **Generally: no branch-name prefix is ever the key.** The epic branch's prefix is read by nothing (*The epic branch* → *Mechanics*), so a detector keyed on it is keyed on taste, and tooling that has to ask "is this an epic branch" answers it with a dedicated ref of its own — the way this marker does — never with a prefix match.

**Confirm it actually fires before you dispatch the first slice.** A window that failed to open and a project that never had one are byte-for-byte indistinguishable: nothing errors, nothing warns, and every slice just takes the strict path as though that were the design. So the evidence is only ever evidence you went and asked for. From inside the first slice's worktree — where the tooling actually runs, not from the main checkout — confirm the marker is visible (`git for-each-ref refs/heads/transient-red refs/remotes/origin/transient-red` naming the ref you pushed) and that the project's own detector agrees the window is open. One check, once per epic.

In that window a drained ticket's gate will exit non-zero on the pre-existing baseline failures until every consumer migrates, and the runner will comment that failure on the PR. That's expected, **not** a real block. Read the runner's output as: the compile half (typecheck + lint) is GREEN, the task's OWN new/affected tests are GREEN, and there are NO failures beyond the baseline SET that pre-dated this task on its fork point (file + test names, not a count — fixing one stale test and breaking a new one keeps the count identical but is still a regression; the absolute count drifts between tasks forked at different tips and as consumers migrate). If it clears that bar, merge it with `merge-pr.sh` on that bar rather than a green exit — the merge is where you record having read it, and a red comment you have *judged* is not a blocker, only a verdict you have to read carefully.

## The PR review loop
Each implementer opens **its own draft PR** back to the branch its worktree was cut from — the integration branch, or the epic branch when the epic has one; the runner comments the gate's verdict on it. That comment is the gate signal, and it is all the gate can tell you — the PR stays draft until *you* merge it, because marking it ready is your signature that you read the diff. So **review each PR and actually read the code involved**, not just the agent's summary or the green comment. Read the diff: verify correctness, that it does what the issue/plan intended, that the scope is right, and scrutinize anything the agent flagged or where it went wider than the planned files. A green gate and a confident agent report are necessary but **not sufficient** — the merge decision is yours and must be grounded in the actual changed code.

**A hand-back report is evidence about its own half and hearsay about the other.** An implementer can tell you what it built; it cannot tell you what its counterpart now expects, because it never saw the counterpart. So for any pair the decomposition flagged as a **contract seam** — one slice produces a shape another consumes — reading each diff on its own is not review, it is two half-reviews. **Diff both halves against each other before merging either**, and check the specific thing: the shape the producer now emits against the shape the consumer now reads. **And where that shape is a status, flag or state value, the two halves agreeing on it is not the whole check — read what the consuming side DOES with it.** A consumer that only filters is safe; one whose read drives an action is where the break is, because the action may be computed from a snapshot taken before the producer's value could exist. Both PRs will be green — each gate only ever exercised one side. When the producer has merged and the consumer has not, the consumer's next re-gate catches it; when they merge in the same drain, nothing does.

**Review BEFORE you drain, never after.** Reviewing is where you decide whether the code changes, so draining first is both wasted (a full serialized gate burned on code you're about to replace) and *unsafe*: the fix agent you dispatch next would edit a worktree with a gate still running in it, which produces a green that corresponds to no commit (see *Draining the gate queue*). The order per PR is: implementer hands back a **draft PR + an enqueued ticket** → **you read the diff first** → needs changes? dispatch the fix agent **now**, before any drain — it re-pushes and re-enqueues → re-review → only once the code is final do you drain, so the gate verdict corresponds to the exact commit you're going to merge. Then verify that correspondence explicitly before merging: compare the SHA the gate comment names against the PR's current head, since a verdict that predates the last push describes a tree the PR no longer carries.

**Judge the diff against the slice's GOAL, and read the review pass's verdict on it rather than deriving your own.** A `Goal` states in outcome terms what the slice was for, and it is the only artifact in the run the right-problem question can be put to: the gate runs commands, the brief describes a route, and a diff matching its brief exactly is still wrong when the brief was aimed wrong. The implementer's inline pass reports its verdict on that goal, so read it here beside the diff — one you disagree with is a fix-agent round trip, and one the report does not carry is the same two-faced blank as a missing `Rejected` list, so check what you asked for in the brief before you read the silence as agreement. **Where the slice you wrote carried no goal at all, that gap is yours and it is answered now**: say in one line what the slice was for and judge against that, rather than reading the brief back to itself.

**Review the implications, not just the brief.** A PR can match its slice's brief, pass its own gate, and stay perfectly in scope — and still be wrong once it lands among its siblings. Read for *second-order* effects, not only local correctness: (1) **cross-slice composition** — when two slices each own one half of a contract (slice A stamps a header, slice B reads that header for the credential; one slice renames/derives a field, another consumes it), confirm the halves still agree *on the merged branch*, even though the files are disjoint. (2) **shared global state** — a change that's correct in isolation can be silently defeated by a process-wide cache, singleton, or memo it didn't author (does that cache key on the value you just made per-tenant, or globally?). (3) **emergent interactions** — a fix that corrects one path can expose or shift a neighbor's behavior (tightening identity makes a queue correctly *wait* instead of mis-running; a now-required field surfaces a caller nobody listed). File-disjointness buys *textual* independence, never *semantic* independence — so the review asks "what does this imply for everything it touches indirectly?", not just "does it match the brief?". When a second-order effect is load-bearing, go read the shared dependency yourself (the cache, the consumer, the sibling's half) rather than assuming it composes.

**And the spot check you run to test a claim is an instrument, not a verdict — read the dependency at the level production reaches it.** Calling a module's function directly, below whatever preprocessing its real callers go through, is evidence about that function and not about the pipeline, so a correction you send on that basis is a claim of exactly the same kind as the one you are correcting. Check the call path before you send it, and read a push-back that answers with a call path as the work rather than as resistance to review.

**Check the docs before you flip it ready — every PR, not just the ones that look documentation-shaped.** The implementer's report carries a per-doc verdict; read it against the diff rather than accepting it, because the implementer can only report on docs it thought to look at. Ask the question yourself from the diff: what does this change make true, or stop being true, for someone who reads the docs instead of the code? Then check that the docs saying otherwise are in this PR. A missing docs commit is a fix-agent round trip, not a merge blocker to argue about — but it is caught *here*, because after the merge the only thing that surfaces it is a user acting on something that stopped being true. **The failure mode to watch for is your own:** if you scoped a doc out of the brief, you did it from the plan rather than from the diff, so re-derive it now from what actually changed. That is exactly how a stale README ships — not because the implementer skipped it, but because it was told not to look.

**The review pass's rejected findings are addressed to YOU and reach you by one route only — read them, and read a hand-back that carries none against your own brief before you read it as a clean pass.** `/pipeline:review` runs inline inside the implementer, so its `Rejected` list — each finding that implementer considered and deliberately did not act on — is written for the reviewer of this PR, and the hand-back is its only way here. That list is written for the reviewer of this PR — you, holding this diff. A rejection you disagree with is a fix-agent round trip; one you agree with is the cheapest evidence in the run that the diff was reasoned about rather than typed, and it is evidence no gate and no diff can produce. **When the list is absent, the blank is two different facts wearing one face, and you are the only party who can tell them apart** — a slice you told to skip the pass has no findings by construction and the blank is correct, while a slice that ran it and forwarded nothing is indistinguishable from one whose pass raised nothing, which is the exact indistinguishability that list exists to remove. So check the review decision you made in the brief, then read the silence: correct where you skipped it, a round trip where you did not.

**A report that names unfinished work hands YOU the next move, not the user.** A hand-back is allowed — required, even — to say what it did not land. The item stops with you: your moves are a fix agent into that same worktree, a resume message to the same implementer, or a filed and linked issue folded into the wave plan (*Hard rules* — the follow-up-ownership rule binds you exactly as it binds the implementer, and *The epic branch* says which branch the follow-up targets while one is live). **Forwarding the list to the user is the same defect one level up**, and it is worse from here: you are the only party in the run holding the decomposition, the sibling slices, and the wave plan the item has to be placed against, so a triage you decline is a triage nobody in the run can do.

**Two artifacts of every PR sit outside the diff — the commit messages and the PR body — and attribution is the one thing that lives in exactly those two. Read both before you flip it ready.** `git diff` shows the code and shows neither, so nothing you read *for* the diff can catch attribution and it has to be its own read — the gate judges a tree, the docs check works from the diff, the SHA comparison works from a comment, and not one of them opens either artifact. Read for the **class** and not for the strings any brief happened to name — a trailer, line, footer or URL naming Claude, the assistant, the model, the harness, or the session the work ran in — because the harness's set is extended from outside any repository's control, without notice, so the brief that briefed this implementer may have been written before the form it was handed mid-run existed. **A clean PR body and a PR body nobody opened are the same blank page, which is why this is a read you perform rather than an absence you notice** — nothing about compliance reports itself, and there is no artifact anywhere whose presence would tell you the question was asked. **The one PR where you are both author and reviewer is the one that most needs this**: the epic → integration close-out has no implementer behind it (*The epic branch* → *Mechanics*), so no brief ever carried the ban to the party that wrote its body, and that party is you. Timing is the whole value of catching it here: before the merge this is a fix-agent round trip on a branch nothing else has been built on, and after it a trailer is permanent history in a flow that never rebases, while a PR body in a public repository has already been published.

**Diff against the merge-base, not the integration tip.** The integration branch advances *while a worktree is open* (other agents' PRs merging in parallel), so `git diff <integration-branch>..HEAD` shows the OTHER work's additions as phantom **deletions** in this PR — a clean change then looks like it ripped out unrelated code, and you'll raise a false alarm. Always diff the fork point: `git -C <wt> diff $(git merge-base HEAD origin/<integration>)..HEAD` (re-`fetch` first — the tip moves). Confirm by test-merging the current base in: if the "deleted" files come back as *additions*, the PR never touched them — which is the review cycle a "destructive deletion" that was only the base moving otherwise costs.

If it needs changes, **dispatch a FRESH fix agent into that same worktree** (never a fork — it would inherit your dispatcher conversation) — but only once that worktree's ticket has SETTLED, or was never enqueued. **Not "once no gate is running in it":** a ticket sitting **queued and unclaimed** freezes the tree exactly as a claimed one does, and queued is the state a slice is in the moment its implementer hands back — which is this step, reached from a review you were told to run *before* draining. So the check that feels sufficient here, looking for a live gate, is the one that structurally cannot see the hazard: the claim is an atomic rename and lands between your look and the agent's first edit. **A gate that judged a mutated tree posts a verdict indistinguishable from any other — and on a SHA that may still match the PR's head**, so the SHA comparison that *Review BEFORE you drain, never after* has you run before merging passes on it too, and nothing left in the flow can catch it. *Draining the gate queue* carries the operative rule. Once the ticket has settled the fix agent re-pushes and re-enqueues, and the runner re-gates. Iterate until the PR is good and green. Only when satisfied do you **merge and clean up** — and the *order* matters because of worktrees (see next section): the implementer has already pushed everything, so you **remove the worktree first**, then merge with `gh pr merge --merge --delete-branch`.

**In in-line gate mode your satisfaction is not the only precondition on this step — the implementer's hand-back is.** A gate comment there was posted by the agent itself, before its hand-back and through a channel you are already watching, so it says a gate finished and nothing about whether that agent is still working — and this step is the one that tears down the tree it may still be standing in. *Dispatch* → **Gate mode for this slice** carries the rule and both directions of the misreading; wait for the hand-back before you remove the worktree or merge.

## Merging a shared hotspot — `mergeable` ≠ correct
When several slices edited the **same function or structure** (a control loop's `tick()`, a reducer, a registry, an exhaustive switch — anything the decomposition flagged as a *shared hotspot*), a clean auto-merge is **not** proof of correctness. Git merges by line: two slices that added code in *different* spots produce `mergeable: MERGEABLE` with no conflict markers — but git has no idea the two additions must **compose**. The recurring failure shape: a structure has sibling branches that must stay **twins** (e.g. two "parked → freeze every kill-clock" branches), each slice added its new clock's freeze-line only to the branches that existed *when it forked*, and the merge silently leaves the newer branch missing it — textually clean, behaviorally a reaper that kills a healthy job. **The integration gate won't catch it** unless a test exercises that exact cross-slice interaction, which is precisely the case nobody wrote.

So whenever a merge — auto-clean OR conflicted — touches a structure 2+ slices edited: **open the merged region and read it; do not trust `mergeable`.** Diff the parallel-edited siblings against *each other* — whatever should be parallel (twin branches, every case of a switch, all handlers of an event, the reducer vs the renderer) must have received the **same** treatment from each slice. Honor the **shared invariant** the decomposition handed you, if any. Fix drift forward as a small, clearly-messaged merge-reconcile commit, then re-verify the interaction — enqueue an integration gate, PR-less if the merged tree has no PR (*Gate the integrated whole*), and run one directly only where there is no queue to put it in **or a runner that refuses the PR-less ticket** — two conditions, because a project with a working queue can still be the second (*Gate the integrated whole*). Resolve actual conflicts by **merging the branch's own PR base into it, in its worktree** (`git fetch && git merge origin/<the PR's base>`, keep BOTH concerns) — never rebase. Merge the base the PR actually targets, not the integration branch by reflex: for a slice based on an epic branch those are different branches, and merging the integration branch straight into the slice drags in commits the epic has not converged on, defeating the isolation the epic branch is there for. Then push and `gh pr merge`. And if you park the tree to clear it for a resolve, **this is the moment the shared stack costs the most** — a conflicted merge is reached at exactly the point where several worktrees are guaranteed to be live and pushing onto it, so the entry on top when you come back is the least likely to be yours of any moment in the run. Park under your own named ref instead (*Hard rules*); if you are recovering something already on the stack, re-match it by marker first and never pop blind. Two more conflict-resolution hazards: (1) **lockfile conflicts between sibling PRs are never hand-merged** — take the base's side (`git checkout --theirs pnpm-lock.yaml`), regenerate with the package manager (`pnpm install --no-frozen-lockfile`) so it reconciles ALL merged packages, verify the scoped check, and commit that; (2) **git happily commits leftover conflict markers once the file is staged** — `git add` marks a path resolved whether or not it is, so after ANY conflict edit (especially a scripted one) run `git diff --check` or grep for `<<<<<<<` BEFORE committing; a botched scripted resolution ships markers into a pushed branch exactly this way. A textually-clean auto-merge drops a line just as quietly and with no marker to find: a freeze-line dropped out of a parked-state check reads as a clean merge and reaps a healthy queued job.

## On the gate — the runner gates; you read the diff
**The RUNNER runs `gate` once per PR — that IS the gate.** `gate` is the HEAVY full suite: build + the entire test run, serialized behind the slim machine-wide slot (`scripts/gate-slot.mjs` for Trinity) so concurrent gates can't saturate the box. Implementers don't run it (their commits are held only to the cheap scoped check by the pre-commit hook), and release-branch PRs typically get no CI — so the runner's drained gate is what stands in for CI.

**Per-PR, the dispatcher reads the diff — it does NOT hand-re-run the heavy gate.** The runner's green comment is the per-PR signal; don't duplicate it. Re-gate — **by enqueuing it**, which for a merged tree with no PR is a PR-less ticket (*Gate the integrated whole*), and by hand only where there is no queue or the runner refuses that ticket — only for a genuine reason: the runner never got to a ticket, or a **merge integrates branches that weren't tested together** (one integration gate on the merged result). That second one is not a judgment call — it is `git diff --name-only <merge>^2 <merge>` coming back non-empty, and an empty answer means the merged result is the tree the gate already ran (*Gate the integrated whole* below). Even then prefer the minimum — the affected/changed tests over the whole suite where possible. Your always-on job is reading the **diff**; heavy re-gating is conditional.

**A stale slot self-heals; you rarely touch it.** The slot's holder-PID is liveness-checked, so a crashed gate's slot is stolen by the next drain within a poll, and a runner that dies mid-gate has its ticket reclaimed and re-gated. There is no "strangling orphan" for you to clear by hand and no lock dir to `rm` — the queue and slot handle their own dead work. (If you ever do need to forcibly stop a runner's gate, clear its worktree via `remove-worktree.sh <leaf>`, which signals the processes; never `rm` the slot dir out from under a possibly-live holder.)
