# Execute — release-branch worktree workflow

Our main dev workflow: we work off an integration branch (for Trinity, `release/x.x.x` — discover the active one with `git branch --list 'release/*'` / the current branch; never hardcode a version). For each task we cut a git worktree, do the work there, commit, push, and open a PR back into the integration branch. The heavy build+test gate does NOT run in the worktree that produced the change — the implementer **enqueues** it and durable dispatchers **drain** it (see *The durable gate queue* below). After a PR merges we **sync the local integration branch first**, then clean up the merged branch and its worktree.

**Two branch levels, and only one of them is always there.** The **integration branch** is the shared one every task merges into and every worktree forks from — that is what `integration branch` means everywhere in this playbook, and it never means anything else. Above it sits one optional level: an **epic branch**, cut from the integration branch, that a multi-slice epic's slices fork from and PR into so the shared branch never carries the epic half-finished. Two rules reach for it — an epic whose intermediate states are unshippable, and, separately, any multi-slice epic at all — and *The epic branch* below states both. Single-slice work never cuts one, and everything in this playbook reads the same when there isn't one.

This is project-agnostic. The per-project specifics — which env files to symlink, the install command, the gate command, and the conventions to bake into briefs — live in a config the tooling reads (see *Per-project config* below), not in this playbook.

**Default to planning for parallelization.** Given a batch of work, the first move is to decompose it into independent tasks that can run concurrently in their own worktrees — don't default to doing everything sequentially yourself. Spin up as many worktrees/branches as the work needs. Because implementers don't run the heavy gate themselves (they enqueue it), a wide fan-out doesn't serialize on a gate lock — fan out as wide as the work is genuinely independent.

## First: which role are you?

Before acting, decide whether you are the **dispatcher** or an **implementer**. **Which one you are is decided by how you got here, not by how the work looks** — they behave very differently, and both mistakes are silent.

- **DISPATCHER** — entered from **`/pipeline:orchestrate`**, which invokes this skill once per cycle to dispatch the increment it has just grounded, or from a user asking you directly to *execute / dispatch* one increment. You are the coordinator. **Do NOT write the implementation yourself.** You decompose the increment into independent tasks, create + verify worktrees, dispatch an implementer sub-agent into each (in parallel when independent), then run the review loop, **drain the gate queue**, and merge. You hold the plan, the reviews, the gate runs, and the merges — not the file edits.

- **IMPLEMENTER** — entered from a **dispatch brief** (a dispatcher handed you one slice and the worktree to build it in), or from a user *directly telling you to implement / build / fix* a specific thing. You do the actual code in your assigned worktree, pass a cheap scoped check, push, open a **draft** PR, **enqueue the gate**, and hand back. **You do not run the full gate, you do not mark your own PR ready, and you do not merge your own PR** — a runner gates it and comments the verdict, and the dispatcher reads the diff, marks it ready, and merges. The ready flag is the reviewer's signature, so it has no override carve-out: in every gate mode your PR is a draft when you hand it back.

**One increment is the unit this playbook works in.** An arc, an epic, or a whole issue enters at **`/pipeline:orchestrate`** instead: it grounds only the **horizon** at **slice depth** (everything past it stays at **shape depth**), invokes this skill to dispatch that increment, then **reconciles** what is still outstanding against the tree the increment actually produced, and goes round again — `skills/orchestrate/SKILL.md` §1–2. That holds even for an arc that turns out to be a single increment, because working out where the horizon falls is the loop's first cycle rather than a precondition for entering it. From inside here you are always running one increment; the loop around it is the caller's.

*The failure this prevents: the wrong role raises no error, and both mistakes produce work that looks like progress. Read as an implementer, a dispatcher writes the code it should have been dispatching — one agent, one worktree, no do-not-touch boundaries, and nobody but the author ever reading the diff. Read as a dispatcher, an implementer dispatches the slice it was handed instead of building it, and its sub-agents inherit a brief whose imperatives end in commit, push, open a PR — so the PR is open before the agent that owns the worktree has decided what goes in it.*

**The harness's default "do not call the Agent tool unless the user requested it" is satisfied by the invocation of a pipeline skill itself.** A user who typed `/pipeline:orchestrate` or `/pipeline:execute` has asked for exactly the fan-out that guard exists to prevent an agent doing unasked — dispatching implementers into worktrees is what this skill IS, not a liberty it takes along the way. What the invocation buys is bounded, though: **exactly the sub-agents the pass you are in declares it uses, and no more.** Each pass is the sole authority on its own answer and states it in its own file, so read it there; a roster here would be a second copy of what every pass already declares, and once two copies disagree nothing marks which one is stale. **A pass that declares none is not an exception to this rule — it is this rule returning its answer.** `skills/review/SKILL.md` §1 is one such answer, argued there on its own terms, and nothing in this paragraph reaches into it, softens it, or licenses anything against it. Where a pass declares none, the invocation authorizes none.

*The failure this prevents runs both ways. Read as still in force, the guard forbids the dispatch the command was invoked to perform, so the dispatcher writes every slice itself — one agent, one worktree, no do-not-touch boundaries, nobody but the author reading the diff — which is the wrong-role failure above arriving through a rule that was never about this. Read as a blanket permission, a pass that bans sub-agents for cause gets one anyway, its own correctness argument overridden by a permission read out of another file. The tell for the first direction is mechanical:* ***a reading that makes the command the user just invoked inoperable is the wrong reading.***

## Per-project config

The worktree tooling is generic; each project declares its specifics in **its own repo** at `<repo>/.agents/worktree.json`. **Two** helpers read that file, not one: `setup-worktree` reads `envFiles`, `env`, and `install`, and `merge-pr` reads `epicMerge` — a config `merge-pr` did not open at all until it gained a merge mode to pick. You read the rest (`cat <repo>/.agents/worktree.json`) to learn the gate, the framework skills, and the brief conventions — and `install` as well, the one key both a helper and you read, because the epic worktree's tick re-runs it (*Draining the gate queue*).

Config lives in the repo — not in your home directory — so it travels with the clone, works under any checkout directory name, and is reviewed in the same PR as the change that alters it. **No config → STOP and say so.** The helper will happily cut a bare worktree (no env symlinks, no `node_modules`) and only warn on stderr; an implementer dispatched into that worktree then fails its checks for reasons that look like code bugs. Don't dispatch into a config-less repo — get the file written first. Keys:

- `envFiles` — gitignored env files to **symlink** from the main checkout into each worktree.

  ⚠️ **The symlink is why nothing reachable through `envFiles` can ever hold a per-worktree value — and that is a consequence this key has always had and never stated.** It is the same inode in every worktree, so a value written into one of these files is written into all of them at once. Which disqualifies both places a reader looking for somewhere to put such a value will reach for: the **tracked config** beside it is one file, identical on every branch, and the **env file** is one file, identical in every tree. What is left is derivation at runtime from the one thing that is already unique per worktree — the worktree's own absolute path — which is what `sharedResources` below is a declaration about. *The failure this prevents: the disqualification is invisible until someone tries it, and it fails by appearing to work. The value resolves in every worktree, so nothing errors and no check fires; the trees simply share whatever the last writer put there, and the first symptom is two gates fighting over one resource in a flow that says worktrees are isolated.*
- `install` — install command run inside a new worktree (worktrees don't share `node_modules`), and re-run on every tick in the epic worktree, the one tree whose dependencies can go stale under it (*Draining the gate queue*).
- `gate` — the heavy full gate (build + test). This is what the RUNNER runs against a queued PR's worktree; implementers do NOT run it (they enqueue it). It's also what a human runs for a manual full check.
- `scopedCheck` — the cheap, unlocked check an implementer's commits are held to (format-check + lint + typecheck; no build, no test). For Trinity this is `pnpm check`, and the agentic pre-commit hook already enforces it on every commit.
- `sharedResources` — what the checks touch that lives **outside** the worktree, and how each worktree gets its own. A list of `{resource, isolatedBy}` entries: `resource` names the thing — a database, a Redis instance, a cache directory, a fixed port, a queue, a bucket — and `isolatedBy` names the project's own mechanism *and the entry point it sits at*. **An entry whose `isolatedBy` is `null` declares a resource that is shared and stays shared**, which is a legitimate answer and the one that says this project's checks are not parallel-safe — write it as an explicit `null` rather than leaving the field out, for the same reason `[]` beats omitting the key. **Three states, and the absent one is not the safe one:** the key missing means nobody has asked; `[]` means somebody asked and the checks touch nothing outside their own tree (this plugin's own repo is that answer); entries mean the question was answered per resource. *The failure this prevents: a missing key and `[]` are the same file to a reader and opposite facts to a dispatcher — one is an open question, the other a tested answer — so a dispatcher that reads absence as "nothing shared" fans out against a database.*

  **The key DECLARES and `/pipeline:setup` VERIFIES it. Nothing here provisions anything, and this plugin never calls a project's isolation mechanism.** `/pipeline:setup` Step 1 has to *ask* — this is a value that cannot be ground out of a lockfile, a script or a CI config — and its Step 4 *falsifies* the answer empirically, by cutting two worktrees and gating both at once. **Where the mechanism sits is the project's, necessarily**, and that is a constraint rather than a preference: this flow's own verify bars routinely tell an implementer to run a targeted test file directly, so anything isolating only the runs the plugin launches isolates the wrong set. It has to sit at the entry point *every* invocation reaches — the test bootstrap, not the `gate` command.

  **And whatever the project derives, it derives from the worktree's own absolute path — which forces two things on the mechanism, one of which it needs before anything sweeps at all.** That path is the one thing already unique per worktree (the `envFiles` bullet above is why both obvious alternatives are disqualified), but it is a *path*, not a branch, so a resource belonging to a torn-down worktree is indistinguishable **by name** from a live one's, and `remove-worktree` removes the tree knowing nothing the tree created.

  - **Take the path from `git rev-parse --path-format=absolute --show-toplevel`, never from `$PWD`.** *The failure this prevents is live today wherever a mechanism reads `$PWD`, and has nothing to do with cleanup: a worktree entered through a symlink gives `$PWD` the link's spelling and `rev-parse` the real one — the same directory, the same tree, two strings, two hashes, two databases. This repo already carries `norm_path` and `real_dir` in `bin/` for the same failure class arriving from Git Bash and from `/tmp`, and every comment on them says the same thing: only string comparison can see it, which is what makes every resulting failure silent.*
  - **Mark the resource with that path as you create it, and re-assert the mark every time the mechanism runs.** Postgres has `COMMENT ON DATABASE`, Redis a key in its own keyspace, a cache directory a file inside it; a fixed port needs no mark, because a port is not durable and cannot leak. The mark is what turns a name nothing can attribute into a resource that names its owner — and where the marker can only live *on* the resource it names, creation cannot precede it, so idempotent re-assertion on each boot is what closes the window a crash between the two would otherwise open. *The failure this prevents: an unmarked resource is permanently out of scope for `reclaim` — never dropped, which is the safe direction, and never seen either, which is the leak this key exists to close.*

  A GC-root file *inside* the worktree looks like the obvious alternative and dies with the worktree. The durable root already exists and is git's own: `$GIT_DIR/worktrees/<id>/gitdir` is a file in a central place holding a path into an ephemeral thing. What was missing was never the root — it is the link from the root to the resource, and the mark is that link. `reclaim` below is what walks it.
- `reclaim` — the project's own sweep for resources whose worktree is gone: `{report, drop}`, both naming commands **in that project**. `report` lists and deletes nothing; `drop` deletes. One object rather than two flat keys, so a config cannot ship a `drop` with no `report` — a delete command with nothing to review first — and top-level rather than per-`sharedResources`-entry, because the *marker* varies per resource and belongs in that entry's `isolatedBy` beside the derivation it is part of, while the *sweep* is one operation a dispatcher runs. **Omit both where nothing durable is created**: a project whose `sharedResources` is `[]`, or whose only entries are non-durable (a fixed port), has nothing to reclaim, and there the absence is derived from a key already in the file rather than a question nobody asked — which is why this key has none of `sharedResources`' three-state reading. This plugin's own repo is that case.

  **The plugin gives the project the RULE, never the data.** It cannot enumerate a project's resources — it has no idea what a Postgres cluster is — and it must not hand one a live worktree set either: the project's command already stands inside the repo with git right there, and a set passed across a shell boundary has one input — the empty one — that is both the easiest to produce and the most destructive to act on. *The failure this prevents: an empty live set read as "nothing is alive" is a licence to drop every database on the box.* So the rules the command has to satisfy, each with what it costs to get wrong:

  - **Liveness is git's registry minus `prunable` — `git worktree list --porcelain`, never `test -d`, never a scan of `WORKTREE_HOME`.** A hand-deleted worktree stays listed with a `prunable <reason>` line until a prune runs, so "listed" alone over-counts liveness and reading the flag is strictly better. *The failure this prevents: a `locked` worktree whose directory is missing is listed with **no** `prunable` line and survives `git worktree prune` — git's lock exists for a tree on a removable or network volume — so a filesystem test calls it dead and drops a live tree's database. And a `WORKTREE_HOME` scan assumes one layout where there are several: worktrees live at `$WORKTREE_HOME/<project>/<leaf>` **and** at `$WORKTREE_HOME/<workspace>/<leaf>/<repo>`, and `WORKTREE_DEST` overrides both outright. That assumption is a bug this repo has already shipped in both ports at once — `remove-worktree` resolved a path that never exists for every workspace member, printed "already removed" and exited 0, and the two ports agreed with each other perfectly the whole time (`AGENTS.md` → *The `bin/` parity rule*).*
  - **Consider only resources whose mark names a worktree of THIS clone.** Anything else is out of scope, not orphaned. *The failure this prevents: another machine sharing one Postgres host is invisible to this clone's registry, so a bare set difference marks its live databases orphaned — a cleanup that becomes an outage. Report mode does not save you here either: it hands a human a tidy list of someone else's live databases and invites them to run the drop.*
  - **Enumerate the resources first, then the live set.** *The failure this prevents: in the other order, a worktree created between the two reads is absent from the live set and present in the resource list — a false positive on a live database.*
  - **No authority means refuse.** Outside a repo `git worktree list` fails, and an unobtainable or empty live set is a refusal, never an empty set.
  - **`report` prints counts — considered, in scope, live, dead — not just findings.** *The failure this prevents: "0 dead" and "0 considered" are different claims, and a sweep that scanned nothing otherwise reads as a clean bill of health. `scripts/check.sh` holds itself to exactly that standard when it fails a check that scanned nothing.*

  No creation-side grace period is needed, and that is a property of the helper rather than luck: `setup-worktree` runs `git worktree add` before the install and before any test can run, so a worktree is registered with git before anything inside it can create a resource. Nothing in `bin/` participates otherwise — the sweep is the project's command, run by a dispatcher at arc close-out (*Merge & cleanup*).
- `enqueue` / `drain` — how an implementer enqueues its PR for gating, and how the dispatcher drains the queue. For Trinity: `pnpm gate:enqueue` and `pnpm gate:drain`. **Both absent means the project has no queue** — see below.

⚠️ **Not every project is queue-shaped, and three config readings change the whole flow.** Check them before dispatching:

- **No `enqueue`/`drain`** → this project gates in-line. The implementer runs `gate` **itself**, in the foreground, and posts the result as a comment on its own **draft** PR — that is override gate mode, and here it is the *default* rather than something you grant. The PR is still a draft when it hands back, exactly as in queued mode; only who ran the gate changes. Do not tell an implementer to enqueue against a project with no queue: the command doesn't exist, and the run ends with committed work and no handoff.
- **`gate` == `scopedCheck`** → the project has one authoritative check and no separate heavy tier. There is nothing for a runner to add, so don't build a queue around it or split briefs into "cheap" and "full" bars that are the same command.
- **A `sharedResources` entry whose `isolatedBy` is `null`** → **"default to parallelization" does not hold in this project**, and that is the one reading that contradicts this playbook's opening rather than refining it. File-disjoint slices contend for that resource the moment two of them run checks at the same time. **Read the exposure against the slot, because the slot covers less than it looks:** the machine-wide slot serializes *drained gates*, so in a queued project what is left uncovered is everything the slot never sees — every implementer's `scopedCheck` and targeted test file, which are concurrent by construction. In a project with **no queue** there is no slot at all and every implementer runs the full gate itself, so the exposure is the whole fan-out. Either narrow the wave to one live slice against that resource, or sequence the slices that touch it across waves; `skills/decompose/SKILL.md`'s *Sizing* is where that is priced. *The failure this prevents: nothing in the fan-out reports the contention — it surfaces as a red in whichever slice lost the race, which is the misread *Reading a gate result* covers.*

A repo can also be small enough to want none of this — a scratch repo with nothing to isolate. Absence of a config is a signal to ask, not to improvise one.
- **Gate mode** (optional, per-project) — a project may offer a lighter gate for a prose-only slice (Trinity: `--mode docs` → the runner gates with `pnpm docs:gate` instead of the full `pnpm gate`). The mode is a property of the *ticket*, set at enqueue — **never inferred from the branch name**, since a rename must not silently change how a PR is gated. Treat it as a **speed choice, not a workaround**: every worktree gets a real install, so a light-mode slice that turns out to touch code just enqueues in the default mode and faces the full gate. Nothing to install by hand, nothing to except.

  ⚠️ **Never give a worktree a shared `node_modules`.** An earlier version of this tooling had a docs fast path that skipped the install and symlinked the main checkout's `node_modules` — saving ~8s and letting prettier resolve. It cost far more than it bought: the worktree couldn't face the full gate (so a whole light-gate *mode* existed to compensate), and its escape hatch — "if the slice touches TypeScript, run a real install by hand" — resolved **through the symlink** and recreated the *main checkout's* `node_modules` underneath every other live worktree and any gate running at that moment. The script that created the symlink even warned "never run `pnpm install` against this symlink" while the project config instructed exactly that. The result was a red on an unrelated branch that nobody could reproduce, because the cause was a directory being swapped mid-run rather than anything in a commit. **A worktree is only isolated if its dependencies are.** Pay the install.

  **And "its dependencies" is one noun short of the whole of it.** A worktree with its own checkout, its own branch and its own `node_modules` is isolated on the **filesystem** and nowhere else: it still reaches the same database, the same Redis instance, the same cache directory, the same fixed port, the same queue, the same bucket as every other worktree on the machine. Everything that made the shared `node_modules` a false economy applies unchanged to a shared service, and worse — the failure is not even a directory swapped mid-run but two runs writing the same rows, which produces a red on a branch whose diff is innocent and nobody can reproduce alone. `sharedResources` above is where a project says which of those its checks touch and what gives each worktree its own; nothing in this playbook makes that true, and a project that has never been asked has not answered no.

  **A base merge invalidates the mode, so re-derive it before you re-enqueue.** The mode is set at enqueue, against the tree as it stood *then*. The sanctioned recovery from a `merge-pr` that stopped at its mergeability preflight with `Base branch was modified` is to re-attach a tree and `git merge origin/<base>` (*Merge & cleanup*), and that merge can land **code** on a branch that was prose-only when its mode was chosen. So after any such merge, derive the mode again from what the branch now carries — `git diff --name-only $(git merge-base HEAD origin/<base>) HEAD` — and enqueue in the **default** mode if anything outside the light mode's prose set appears. Recompute that fork point *after* the merge and never carry a SHA forward from the dispatch: a branch that merged its base in has moved its fork point, and a stale one diffs against a commit the branch no longer forks from. **This does not soften the ban above** — it keys on the merged tree's **file set**, which is what the gate will actually run over, and never on the branch's name, which still cannot change how anything is gated; a rename is exactly as inert after this rule as before it. **And the speed-choice argument does not already cover it:** *a light-mode slice that turns out to touch code just enqueues in the default mode* is written for a slice that **discovers** it touches code while being built, with its enqueue still ahead of it — not for one that **acquires** code from its base after it has already handed back and been gated green.

  *The failure this prevents is the one that looks correct.* Only one of the two readings of that recovery is caught, and it is not the dangerous one. Re-running `merge-pr` on the existing green comment is caught, because that comment gated the **pre-merge** SHA, and *The PR review loop*'s drain-ordering bullet closes on the step that catches it — *compare the SHA the gate comment names against the PR's current head, since a verdict that predates the last push describes a tree the PR no longer carries*. **Re-enqueueing unchanged is caught by nothing**, because it satisfies both layers at once: the PR carries a gate comment, so it reads as gated, and that comment's SHA now *matches* the head, so the comparison passes too. Neither layer asks **which** gate ran — neither a comment's presence nor its SHA says which gate produced it — so a light gate over a tree carrying code is indistinguishable from a full one, and it is exactly the evidence this flow treats as proof a gate ran, over a tree the full gate never saw. *Observed on a docs-mode slice — one changelog entry and two skill files — whose base merge brought a component and its test onto the branch. Re-enqueued in the default mode by hand, the full gate ran a typecheck and a whole test suite the docs gate does not run at all. It came out green, so nothing broke; but the mode was corrected by someone noticing TypeScript in the merge's diffstat, and nothing in the flow asked. The blind spot was wider than the merge, too: that changelog entry is consumed by the site build, so a docs-mode gate structurally could not have said the site still built, merge or no merge.*
- `frameworkSkills` — `{skill, when}` pairs naming the framework skill each area opens with, so a brief can say "invoke the `frameworks:solid` skill as Step 0" without you guessing the stack.
- `briefConventions` — project conventions to bake into every dispatched implementer brief (compat policy, comment style, test-invocation rules, etc.).
- `format` — the auto-formatter in *write* mode, run right before committing (the scoped check only format-*checks*).
- `upstreamFindings` — a boolean, and what decides whether a finding may leave this project at all. `true` lets an arc's close-out file a pipeline finding as an issue **against the plugin's own repository** — resolved from the `repository` field in the plugin's own manifest, `.claude-plugin/plugin.json`, which ships beside these skills. **Absent, `false`, or any value that is not exactly `true` means no**, and that absence is a settled answer rather than an unasked question — the exact opposite of how `sharedResources` above reads its own absence, because there the unsafe direction is assuming and here it is acting. `skills/orchestrate/SKILL.md` §7 carries the rule: what the close-out answers when the key is off, the bar a finding clears before it is filed at all, the genericising guard that binds whether or not the key is on, and the same-repository carve-out. **Omit it** unless the project's owner has actually decided to publish findings upstream — which is a decision about a finding **leaving** the project, and therefore one the key has nothing to make where the resolved target and the project are the **same repository**: an arc running inside the plugin's own repository files without it, because nothing crosses anything. §7 carries that carve-out's mechanical test, and why it relaxes neither the genericising guard nor the key anywhere the two differ. *The failure this prevents: the plugin's tracker is public and most projects installing the plugin are not, so a default-on key files from inside a private tree into a public one on a choice nobody made — as a perfectly well-formed issue, which is why nothing downstream looks wrong.*
- `epicMerge` — `"merge"` (the default) or `"squash"`, and the only key a *helper other than* `setup-worktree` reads: `merge-pr.{sh,ps1}` reads it, on every close-out, and decides the merge mode from it. It governs exactly one merge — an epic branch collapsing back into the integration branch it was cut from — **and only when that integration branch is not the repository's default branch.** Absent, unreadable, unrecognised, or any value that is not exactly the lowercase string `squash` means `merge`, as does every question the helper cannot get an answer to. **Omit it** unless the project genuinely wants one commit per arc on a long-lived release branch; a project whose integration branch *is* its default branch should omit it because it does nothing there, which is a harder reason than a preference. *The epic branch* → *Mechanics* carries the rule, both conditions, and the trade — this entry is the key, not the argument.

  It is deliberately a config key rather than a `merge-pr --squash` flag, and that is not an implementation detail for someone to improve on later. The helper CLI contract is frozen (a project's `AGENTS.md` may say so outright, as this plugin's own does) — and the larger reason is the one *The epic branch* → *Mechanics* states as the rule: a flag would hand the decision to whoever runs the close-out, at the moment they run it, which is the one thing the key exists so that nobody does.

The config's `env` map is exported before the install runs — most usefully a **shared build cache** for a monorepo (turbo/nx/bazel): `"env": {"TURBO_CACHE_DIR": "${TURBO_CACHE_DIR:-$HOME/.cache/<project>-turbo}"}` lets a fresh worktree's gate **replay** tasks another checkout already built (near-instant on unchanged packages) instead of running cold every time. A remote cache (a shared HTTP/S3 backend the runner declares in its config — e.g. turbo's `remoteCache.apiUrl`) extends the same replay *across machines and CI*. ⚠️ **A cache var must live where NON-INTERACTIVE shells read it.** The gate runner, the `drain` pass, and dispatched implementer agents all run in non-interactive shells — a var set only where an interactive shell reads it reaches your terminal but *not* the fleet, so the shared cache silently never applies to gated PRs and every drain runs cold. The config's `env` map covers the install step; this covers the gate. In zsh that means `~/.zshenv`, NOT `~/.zshrc`. On **Windows there is no equivalent file**: persist a real user environment variable instead (`setx VAR value`, or System Properties → Environment Variables), which every later process inherits regardless of shell — PowerShell's `$PROFILE` is interactive-only and is therefore the exact same trap as `~/.zshrc`. (This is a real trap we hit: the 287x cache speedup showed up in the terminal but not in a single gated worktree until the export moved to `~/.zshenv`.)

**Go through the task-runner, never around it.** A shared cache only helps commands that actually invoke the runner (turbo/nx/bazel): the project's `scopedCheck` and `gate` do, by construction. Invoking the underlying binary **directly** — `vitest`, `tsc`, `eslint` — or running a per-package script that shells straight to it (e.g. `pnpm --filter <pkg> test` when that package's `test` script is a bare `vitest run`) **bypasses the cache entirely and always runs cold**, both locally and in the drained gate, and never *populates* the cache for anyone else either. So steer every whole-package / whole-suite run that is *supposed to happen* — the runner's drained gate, a dispatcher's integration gate, an override-mode slice — to the cached runner command (`turbo run <task> --filter=<pkg>`, or the project's own `scopedCheck`), and say the same in briefs and the project's `AGENTS.md`. (This is a routing rule, not a permission: for a default-mode implementer, whole-package/whole-suite *test* runs are banned outright — see the Implementer section — so "route it through turbo" never applies to them.) Reserve a direct-binary run for a **single targeted file** (`vitest run path/to/x.test.ts`), where wrapping one file in a whole-task cache entry is pointless overhead. If the project's `AGENTS.md` still documents the raw-binary form as the default for a whole package, that's a leak — fix the doc, don't propagate it into briefs.

To onboard a new project, add `<repo>/.agents/worktree.json` declaring the keys above and commit it — one PR, reviewed like any other change. Read the repo's `AGENTS.md`, its package scripts, and its CI to fill in the commands rather than guessing them.

## Polyrepo workspaces

Some projects are a **containing folder of sibling repos** rather than one repo — an API, its clients, an admin panel, a marketing site, all released together. The folder itself is not a git repo, so every helper that resolves the repo from CWD fails at its root.

A workspace declares itself with `.agents/workspace.json` at that root:

- `integrationBranch` — the branch every member shares (they release together; that's what makes it a workspace).
- `members` — the repos, as names or `{path, default}`. A member with `"default": false` is skipped unless named — for the one repo the others rarely change with.
- `crossRepoContracts` — the shared artifacts (generated types, notification payloads, translations) and which repo owns each. This is the polyrepo form of the shared-hotspot problem: the owning side must land first, and the consumer regenerates rather than hand-edits.
- `briefConventions` — conventions shared by every member, so five repos don't each restate the same branch policy.

**One task gets one worktree per repo, laid out like the workspace:**

```
setup-workspace.sh <branch> [repo ...]
setup-workspace.sh <branch> --exclude <repo,repo>
```

→ `$WORKTREE_HOME/<workspace>/<branch-leaf>/<repo>/`, using the **same branch name in every member** so the PRs are visibly one change. Mirroring the layout is the point: relative paths between repos still resolve and both stacks run side by side, which is what a change spanning an API and its client actually needs. Each member is provisioned through `setup-worktree.sh`, so it still gets its own `.agents/worktree.json` treatment.

**Name the repos a task touches.** Every repo you cut is an install you pay for, so the default set is a floor, not a target. `--exclude` is for when a task touches most of the workspace and you want to drop one.

**What changes for you as dispatcher:**

- **Verify HEAD in every member**, not just one — and **fetch in every member too**, because invariant 2's comparison reads a remote-tracking ref and those are per-repository. A polyrepo's integration branch is a convention, and one repo lagging is the normal failure. *The failure this prevents: this is the shape the stale-cache case actually arrives in. A fetch in one member updates that member's cache and leaves every other member's exactly as stale as it was, while the session that ran it now feels fetched — so the members that never got one return a clean PASS against their own stale pair, and the check reports agreement across a workspace it only ever asked one repository about.*
- **Order merges by contract.** A slice that changes a contract and its consumer is two PRs with a mandatory order — the owning repo lands first. Nothing enforces this; you do.
- **Each member gates itself.** There are as many queues as repos, so per-repo green says nothing about the pair. Treat the cross-repo pair the same way you treat a multi-slice epic: independently green is necessary, integrated-green is what ships.

A repo inside a workspace also gets its plain `setup-worktree.sh` worktrees namespaced under the workspace, because bare polyrepo names (`api`, `client`, `admin`) collide across unrelated projects in a flat worktree home.

## Worktree creation (both roles depend on this being done right)

**⛔ HARD BAN — the Agent tool's `isolation: "worktree"` parameter (and ANY harness / auto worktree provisioner) is FORBIDDEN. Never use it.** It (a) creates the worktree under `.claude/worktrees/agent-*` (violates invariant 1 below) and (b) repeatedly seeds it at a STALE base — far behind the integration tip (observed ~1000+ commits behind, a previous-minor-version commit) — which has burned us over and over (agents waste cycles re-basing, or stale code silently leaks in). There is exactly ONE way to make a worktree: the helper script below, then **verify HEAD yourself**, THEN dispatch a plain agent (no `isolation`) pointed at that worktree path.

**Helper script — `setup-worktree.sh`** (ships in this plugin's `bin/`, which Claude Code puts on your shell tool's `PATH` while the plugin is enabled — so it's a bare command, no path prefix, alongside its siblings `merge-pr.sh` / `remove-worktree.sh`). It auto-detects the project and reads that project's `.agents/worktree.json`, so it works the same for any repo.

⚠️ **Pick the extension from the shell tool you were actually handed, not from habit.** Every helper ships twice: `<name>.sh` for the **Bash tool**, `<name>.ps1` for the **PowerShell tool**. A session on native Windows with no Git for Windows installed gets the PowerShell tool and has **no bash at all** — so `setup-worktree.sh` there is not a script that fails, it is a command that does not exist, and the error reads as a broken or missing plugin rather than as a wrong extension, which sends the whole run off diagnosing the wrong thing. The rule: **if the only shell tool you have is PowerShell, call `setup-worktree.ps1` / `remove-worktree.ps1` / `merge-pr.ps1` / `setup-workspace.ps1`; otherwise call the `.sh`.** Arguments, environment variables, the `READY:` line, and exit codes are identical either way, so nothing else in this playbook changes — and `scripts/check.sh` in this repo enforces that they stay identical.

Usage: `setup-worktree.sh <branch> <base>` — both **required**. Run it from **anywhere inside the target repo** (the root, a subdirectory, a monorepo subpackage, or even a linked worktree — it walks up to the repo's common gitdir). If cwd isn't inside the repo, prefix `REPO=/path/to/repo`.
- `<branch>` = full name of the branch to create (any prefix: `feat/…`, `fix/…`, `refactor/…`, `docs/…`); the worktree dir is named after the segment past the last slash (`feat/toasts-top-right` → `toasts-top-right`).
- `<base>` = the branch to fork from, with **no default** (integration branches roll over often, so a hardcoded default just goes stale); it errors early with a `git fetch` hint if `<base>` isn't a local ref yet.

**Recovery form — `setup-worktree.sh --existing <branch>`** attaches a worktree to a branch that already exists, instead of creating one. Reach for it when a **branch outlived its tree**: a `merge-pr.sh` that failed at the merge after tearing the worktree down, a tree removed by hand or lost to a cleanup, a branch you need to pick back up after its close-out was interrupted. It takes **no base** — an existing branch's base is whatever it already forked from, so there is nothing for a second argument to mean. If only `origin/<branch>` survives (the local branch is deleted on every successful merge), it recreates a local branch tracking the remote and attaches to that; if the branch doesn't exist at all it **stops** rather than creating one, because the fallback would silently fork off whatever HEAD it found. Everything downstream is identical to a fresh worktree — env symlinks, the config's `env`, a real install — so a re-attached tree can face the gate like any other.

⚠️ **It is a flag, never an inference — do not reach for it just because the branch exists.** Attaching to a pre-existing branch when you meant to fork off `<base>` is the stale-base seeding this whole section warns about hardest, and it arrives silently: the tree is real, the install is real, and only its HEAD is wrong. Use the two-argument form for new work, always.

⚠️ **Every helper resolves its target repo from your CWD** (or an explicit `REPO=`). Running `merge-pr.sh <n>` while your shell sits in a *different* repo's checkout operates on THAT repo — observed failure: it switched an unrelated main checkout off its integration branch onto the default branch and attempted to merge *that repo's* PR `<n>` (same number, wrong project; only luck — the PR was long merged — kept it a no-op). When orchestrating across multiple repos, `cd` into the target repo immediately before EVERY helper invocation, and treat an unexpected "behind by thousands of commits" line in helper output as a wrong-repo alarm: stop and verify before anything else runs. (`merge-pr.sh` also self-guards now: it refuses when the PR's head branch is unknown to the resolved repo; when an already-merged PR has no worktree/local branch left to close out — `MERGE_PR_FORCE=1` overrides that one; and when the copy being run, or the directory it is being run from, is **inside the worktree the close-out has to tear down**, because that teardown kills every process rooted in the tree and the close-out would be one of them. So the directory to stand in is the **main checkout**, never the PR's own worktree — and `cd`-ing into a worktree to merge its PR is the shape that gets refused. `remove-worktree.sh` refuses the same two shapes for the same reason.)

⚠️ **The main checkout is the one piece of shared mutable state here — a branch you did not touch that has moved is an alarm, not a curiosity.** Every worktree is isolated by construction; the main checkout is not, and in a multi-session shop several sessions reach into the same one. So `merge-pr.sh` never switches it: a base branch that is not the checked-out one is synced without touching the checkout at all — fast-forwarded inside whatever linked worktree is standing on it, or moved by **ref** (`fetch` + `branch -f`) when none is — and the helper fails loudly if the checkout is on a different branch, or a different commit, than when it started. Observed failure: a close-out switched the checkout from the release branch onto a slice's epic-branch base, another session switched it back mid-sync, and the local release branch was left pointing at the epic branch's merge commit — six commits of unrelated work — while `origin/release/…` had independently advanced. Nothing was pushed, so no remote damage; the next worktree cut from that release branch would have forked off a poisoned base. Treat any report that the checkout moved, or any local branch pointing somewhere you never merged, as a **stop**: re-point it at `origin/<branch>` and verify before dispatching anything else.

It creates the worktree at `$WORKTREE_HOME/<project>/<branch-leaf>`, symlinks the config's `envFiles`, and runs `install` — automating invariants 1, 3, 4 below outright, and **part of** invariant 2. Every branch is treated the same, docs included: a worktree always gets its own install, so it is always self-contained and can face any check the project has. It finishes by printing two lines on stdout — `READY: <path>` and then `HEAD: <sha>`, the commit the tree actually landed on, which is what invariant 2 has you compare — and in the new-branch mode it will not print them at all unless the tree it is handing back **contains** `<base>`. Read invariant 2 for what that refusal does not reach: it is a weaker comparison than the one invariant 2 asks for, in both what it compares and what it compares against.

⚠️ **A `READY:` line also warrants that the install SUCCEEDED — so its absence after a failed one is the refusal, not an omission.** Both ports fail the same way and say the same thing: a message naming the worktree, stating that the tree was created and is being **left standing** so you can diagnose it, that its install did not complete, and that re-running the same command reuses the tree and retries the install — then exit 1, with no `READY:` line at all. Read a missing `READY:` as an instruction not to dispatch into that tree, and re-run rather than reaching in by hand. *The failure this prevents: an install that dies partway leaves a **partial** dependency tree, which is the worse of the two states — a bare tree is obviously bare, a half-populated one looks provisioned and fails selectively — so a dispatcher who reads the install tool's stderr as noise and dispatches anyway hands an implementer a tree whose checks fail for reasons shaped exactly like code defects, with nothing inside it recording that an install ever failed there. This is the same reading *The epic branch* → *Mechanics* already gives the helper's branch-back check: a `READY:` line is what every refusal in this helper is defined against, so what it does NOT print is as load-bearing as what it does.*

`WORKTREE_HOME` defaults to `~/.worktrees`, **except on Windows, where it defaults to `%LOCALAPPDATA%\wt`** — a worktree path there carries a whole dependency tree (`…/<repo>/node_modules/.pnpm/<pkg>@<version>/…`), and from `~/.worktrees` that routinely exceeds Windows' 260-character `MAX_PATH`, which surfaces as an install failing on some deeply nested filename rather than on the length. Setting `WORKTREE_HOME` yourself still overrides it everywhere. Two more Windows-only notes worth knowing before you read a worktree's stderr as a code bug: `setup-worktree.sh` warns when `git config core.longpaths` is unset (the same MAX_PATH ceiling, from git's side), and it warns when an env file was **copied** rather than symlinked — Git Bash's `ln -s` silently copies unless Windows Developer Mode is on, and a copy is a snapshot, so later edits in the main checkout stop reaching the worktree.

⚠️ **The config it reads is the MAIN checkout's working copy, as a file on disk — which is why a slice that CHANGES that config cannot exercise its own change.** The helper resolves the main checkout from the repo's common gitdir, so it finds the same one from any cwd — the root, a subdirectory, a linked worktree, or an explicit `REPO=` pointed at one — and then reads `<main checkout>/.agents/worktree.json` out of that tree. `<base>` never enters the lookup, and neither does any other ref (`merge-pr` reads `epicMerge` from the same copy). So a slice whose job is to add an `envFiles` entry, change `install`, or introduce a new key works in a tree provisioned from the **pre-change** config — as does every worktree cut anywhere while the change is unmerged. **Two routes look like they get round that and neither does, which is worth knowing before you spend a worktree finding out.** Reading the config from the branch being cut would change nothing: at cut time the new branch equals its base and the commit that adds the key does not exist yet, because provisioning necessarily happens before the work that changes provisioning. And cutting a **second** worktree off the branch once it is pushed changes nothing either, for an unrelated reason — the lookup consults no ref at all, so a fetch moves nothing it reads, and the main checkout is still standing on the integration branch with the old file in its working tree. The honest statement is the strong one, and it is a statement about the merge that reaches **the tree the helper reads**: a change to this config cannot be exercised through the helper until it lands in the main checkout's working tree, which holds the integration branch and nothing else, ever — *The epic branch* → *Mechanics* is where that rule is stated and where parking an epic branch there is rejected outright. **So there are two merges to tell apart, and on a multi-slice arc it is the second one.** Off an epic branch the slice's own merge into the integration branch closes the window, and there is nothing further to say. On one — which *The epic branch*'s Rule 2 makes the **default** for multi-slice work, so this is the ordinary shape rather than an aside — a slice→epic merge moves nothing the lookup reads, and the window closes only at the **epic → integration** close-out, which is the end of the arc: not one slice awaiting one merge, but every worktree the arc cuts after that slice lands, for the arc's whole remaining life. What to do instead is apply the effect by hand in your worktree — symlink the env file, run the new install command — and **say in your hand-back that the config path itself was never exercised**, so a reviewer knows which half was tested; the first real exercise is the next worktree cut after *that* merge, which is a consequence to state rather than a check the slice can pass. Editing the main checkout's working tree so the helper sees the change early is **rejected rather than unmentioned**: it is the one thing that would work, and it writes to the piece of shared mutable state the ⚠️ above names as exactly that — another session cutting a worktree inside that window is provisioned from an unmerged config, with nothing anywhere to tell it. And none of this is a defect in the helper: `skills/setup/SKILL.md`'s Step 4 proves a **new** config by cutting a real worktree before anything is committed, which works *because* the read comes from the main checkout's working tree rather than from a ref. *The failure this prevents: the slice reports green having tested everything except the thing it changed, and nothing in the diff, the gate or the hand-back distinguishes that from a config change that was actually verified — while every worktree cut before it merges is silently still provisioned the old way. Observed: a slice adding a test env file to `envFiles` could not test it, and three worktrees had to be hand-symlinked afterwards.*

⚠️ **The remedy above reaches one tree; the rest of the arc's trees are the DISPATCHER's, and applying the change by hand in them is a standing obligation beside invariant 2 below.** *Apply the effect by hand in your worktree* and *say so in your hand-back* are written to the implementer, and they are right for the tree that implementer is standing in — which is the only tree they can reach. Every later worktree of the arc is cut by **you**, after that slice merged, out of a main checkout that still does not carry the change. So while an arc has an unmerged change to this config: **apply that change's effect by hand in every worktree you cut for the rest of the arc, and say so in the brief you dispatch into it.** The saying-so is not a courtesy — the implementer receiving that tree cannot tell a hand-symlinked env file from a helper-symlinked one, and has no reason to look. *The failure this prevents, observed across three waves of one arc: an `envFiles` entry landed in wave 1, and every api worktree cut in waves 2 and 3 was provisioned from the pre-change config and had the symlink chained in by hand. It held only because the dispatcher happened to remember — nothing in the brief, the hand-back, the helper's output or the gate would have said otherwise. And the tree a forgotten one produces is not broken, which is why nothing catches it: it fails later, inside a slice that never touched the config, as a test-environment error with no visible relation to a merge two waves back.*

**The four invariants** (the helper covers 1, 3, 4 outright and part of 2 — the rest of step 2 is always on you):
1. The worktree lives under `$WORKTREE_HOME/<project>/`, **never** under `.claude/worktrees`.
2. **Verify its HEAD == the base tip BEFORE dispatching any agent** — compare the `HEAD: <sha>` line the helper just printed against `git rev-parse origin/<base>` (e.g. `origin/release/x.x.x`), or re-read it yourself with `git -C <worktree> rev-parse HEAD`. **The helper now makes a comparison of its own here, and it is a WEAKER one — so this check is still owed on every dispatch.** In the new-branch mode it refuses, with no `READY:` line, unless the resolved base tip is an **ancestor** of the tree's HEAD; and it resolves that tip in the **main checkout**. Two gaps follow from exactly those two words, and a tree in either state prints an entirely ordinary `READY:`/`HEAD:` pair. **Ancestor, not equal:** a tree carrying commits on top of the base passes, because a caller re-attaching to a tree that has legitimately advanced must not be refused — and a tree that has moved off the base tip is precisely what this invariant's equality comparison is here to catch. **The main checkout, not `origin`:** a local base branch that is itself behind the remote is an ancestor of everything cut from it, so a stale base passes there and is caught only here. A mismatch means STOP and fix the base; do not dispatch. Read the sha, never the `READY: … off <base>` text: that says what was *asked for*, and this invariant exists for the case where what you got is something else. (`--existing` takes no base, so that refusal does not run there at all — the branch read-back still does, but a re-attached tree's commit is covered by this comparison and nothing else.)

   ⚠️ **`origin/<base>` is a local cache, so FETCH FIRST — in the repository being verified — and the fetch is part of this check rather than preparation for it.** A remote-tracking ref is what the remote looked like at *that clone's* last fetch, and reading one contacts nothing; so in a checkout that has not fetched, the local base and `origin/<base>` hold the same commit for the same reason, the comparison above is true, and the invariant returns **PASS in exactly the case it exists to fail**. Run `git -C <repo> fetch origin` immediately before you compare, and run it in the repo you are verifying — a fetch in some *other* repository you touched earlier in the session moves nothing here. **Then name the freshness, not only the equality:** after the fetch, `git -C <repo> rev-list --count <base>..origin/<base>` answers *how far behind is the base I just forked from*, which is the question this invariant is actually asking, and anything but `0` is the same STOP. Equality cannot answer it, because it compares two refs that go stale together; the count is checkable where equality is not. *The failure this prevents, observed before the fetch was part of this invariant: a dispatcher cut a worktree in a project it had not fetched, ran the equality comparison on its own, and got a clean PASS on a tree 2,392 commits behind the real base tip — that checkout's `FETCH_HEAD` was seventeen days old, so the local base and the remote-tracking ref were byte-identical and the comparison was true and meaningless. It had fetched a **different** repository in the same session and carried the assumption across, which is why the fetch is now stated as a step rather than assumed: a rule reading* compare against `origin/<base>` *names a remote and reads as though it went to one. And the cost does not stop at the dispatch — the same unfetched checkout was then read for facts about the project and reported a merged config key as absent, because reading a stale working copy is indistinguishable from reading a current one.*
3. Env files are symlinked into the worktree (they aren't carried over automatically).
4. Deps are installed (worktrees don't share `node_modules`, and the gate can't run without them).

## The durable gate queue

The heavy gate (`gate` = build + full test suite) is expensive and CPU-saturating: running several concurrently across worktrees stacks builds and vitest/workerd forks until the box thrashes. So implementers never run it — they enqueue a durable ticket and hand back, and dispatchers drain the queue and gate one at a time. This keeps the wait off the implementer entirely and makes a mid-flight death impossible to lose work to:

- **Implementers never run the full gate.** They get their code to a cheap **scoped check** (format-check + lint + typecheck; the pre-commit hook enforces this on every commit), commit, push, open a **draft PR**, then **enqueue** a durable gate request (`enqueue`) and hand back. The work is pushed and the PR is open before the ticket exists, so an implementer death after enqueue strands nothing — worst case the work sits as a visible draft PR.
- **Dispatchers drain the queue.** On each tick a runner (`drain`) claims a queued ticket, runs the gate its declared mode selects (`gate`, or a project's lighter gate for a prose-only ticket — see *Gate mode* above) **one at a time** in that ticket's worktree behind a slim machine-wide slot, then comments the verdict on the PR — a pass on green, the failing tail on red — and leaves the PR draft either way. Multiple dispatchers can drain the same queue safely: every state transition is an atomic rename that exactly one runner wins, and a runner that dies mid-gate has its in-flight ticket reclaimed and re-gated (the gate is idempotent).

- **A dispatcher's OWN gates go in the same queue — in a project whose runner will take them, no gate is run by hand.** The two the flow runs outside a slice PR are enqueued like everything else: the epic's **close-out gate**, against its own draft PR (*The epic branch* → *Mechanics*), and the **mid-arc integration gate** on a merged tree, as a **PR-less ticket** whose verdict settles onto the ticket because there is no PR to comment on (*Gate the integrated whole*). **The qualifier in that first sentence is load-bearing and is the whole of the exception**: a runner scaffolded before the PR-less ticket refuses that second one outright, and there the hand-run gate is sanctioned rather than forbidden — *Gate the integrated whole*'s *A runner scaffolded before the PR-less ticket REJECTS it* is the only route this rule reopens, and it reopens it for the mid-arc gate alone. *The failure this prevents: a hand-run gate is the only path in this flow that records nothing — no streamed log, no ticket, no ledger entry — so the two gates covering trees no per-slice gate ever saw were also the two least-observed gates there are, their verdicts surviving only as an exit status in one terminal. That is why a whole hard rule about capturing `EXIT=$?` and never piping had to exist: it is this flow hand-rolling, on its least-observed gate, bookkeeping the runner does for free.*

The consequences ripple through everything below: there's no gate lock for implementers to wait on, no thundering herd of concurrent gates, and no way for a dying agent to strand committed work. Fan out freely; drain steadily; the queue + draft PRs make lost work structurally impossible.

## The epic branch

**Skip this section unless you are running a multi-slice epic.** Single-slice work — one fix, one feature, one PR — never cuts an epic branch, and nothing else in this playbook changes when there isn't one.

An **epic branch** is a branch cut from the integration branch that an epic's slices fork from and PR into, gated as a whole once they have all landed, then merged back to the integration branch in one ordinary PR. It is the same shape as the integration branch, one level down: the epic converges there instead of on the shared branch, so the shared branch only ever sees the epic finished.

### Two rules reach for one — and neither of them is a slice count

They answer different questions, and either one fires on its own. When neither does, there is no epic branch: the slices merge into the integration branch as they land, exactly as they do today.

**Unless the user already decided — then there is nothing to ask.** These rules are for when nobody has made the call. When the user names the approach, that is a decision rather than a hypothesis to check: **"do it as an epic" means the branch is decided.** Read the rest of this section for the **mechanics** — how the branch is cut, who owns its lifecycle, what it costs, and the merge-back cadence it requires — then cut it and point the slices at it. Do not re-run either rule to see whether the user was right. **The general form, and it is not specific to this decision: a skill's decision procedure never overrides a stated instruction — once the call is made, the skill is read for how, not for a second opinion.** *The failure this prevents: the user spends turns repeating an instruction they already gave, and the overruling does not stay in the conversation — this question is answered in one line inside a plan that gets handed onward and executed as written, so every slice targets the shared integration branch while the user had asked for exactly the isolation this branch provides. An unwarranted "not needed" produces a perfectly well-formed plan, so nothing downstream can tell it apart from a correct one.*

**Rule 1 — the shippability trigger. It answers: _would a partial state on the shared branch be broken?_**

> **Does any intermediate state leave the integration branch in a condition you would not ship?**

If yes, cut one — at any width from two slices up. A two-slice epic whose foundation lands before its consumer migrates needs the isolation exactly as much as a ten-slice one does.

- **Primary — the epic is only correct as a whole.** A foundational change whose consumers must all follow it: a NOT-NULL schema swap, a required interface field, a renamed module. Every state between the foundation landing and the last consumer migrating is unshippable. This is exactly the shape *Transient-red window* below describes, and the case this branch exists for — the window has to sit somewhere, and an epic branch is what keeps it off the branch everyone else forks from. It is still a recommendation you weigh, not an automatic cut: a small foundational change whose consumers all land in the same afternoon may not be worth the branch.
- **Secondary — a contract seam.** `decompose` emits a producer → consumer map naming the shape one slice emits and another reads. Two halves of one contract landing separately means the branch is wrong in between — the primary condition arriving by a different route.

**Rule 2 below cuts the branch on width alone, so Rule 1 has stopped deciding *whether* and now decides *which kind of branch you are holding* — answer it on every multi-slice arc anyway.** A "yes" says the epic is **knowingly red** until its last consumer migrates, and that is what opens the `transient-red/<epic-slug>` window (*Mechanics* below, and *Transient-red window* for what reads it). A "no" leaves a branch that is isolation and nothing else, strictly gated at every step, with no window and no marker ref. Two things downstream key on exactly that distinction, which is why Rule 1 survives Rule 2 widening past it. *The failure this prevents: once every multi-slice arc cuts a branch, Rule 1 reads as dead weight and the next editor tidies it away as redundant — taking the only thing that says whether the window opens with it. Nothing reports that, because a window that never opened and a project that has none are byte-for-byte indistinguishable: every slice of a knowingly-red epic just pays full strict-path friction for a relaxation the repo believes it has, and the loss surfaces as nothing at all.*

**Rule 2 — the multi-slice default. It answers a different question: _what does landing one change on the shared branch as N separate merges cost, whether or not every intermediate state would ship?_**

**Multi-slice work defaults to an epic branch.** The condition is one change decomposed into slices — not a number you count to, and not how you dispatch them. Five costs land on the shared branch whenever it does. None of them depends on any intermediate state being broken, and the first four are each already documented elsewhere in this playbook as something to work around:

- **Base churn — concurrency only.** N slices merging as they land means every live slice's base moves under every other live slice. The scar is already here: the phantom-deletion false alarm that burned a review cycle, and the standing discipline of anchoring every divergence check and every review diff to a **fork point** rather than the tip — a discipline that exists precisely because the tip moves. An epic branch bounds that churn to the epic's own slices instead of the epic's slices plus every other session's traffic.
- **The integration gate signal — concurrency only.** *Gate the integrated whole* calls the `^2` diff non-empty when a sibling branch merged in between — which under parallel dispatch is the ordinary case, not an edge one. The shared branch then routinely carries a tree no gate has run, covered only by N interleaved partial gates. An epic branch converges once and gates the whole thing once, which is the signal you actually wanted.
- **Revert granularity.** An epic that turns out wrong is N separate merges to unpick from the branch everyone else forks from, against one merge to revert.
- **Cross-slice seam review.** *The PR review loop* requires diffing both halves of a contract seam against each other before merging either. That is materially easier while both halves are still converging on a branch you control than once each has landed on the shared one — and halves that land in slice 1 and slice 4 are a seam however far apart in time those two merges are.
- **One arc, N releases.** In a project where shipped content must move a version, every merge into the integration branch is a release — so N slices merging there is N versions for one coherent change, on top of making the version file and the changelog a hotspot every slice has to touch. *Observed on the arc that shipped 3.15.0 in this repo.* `AGENTS.md` requires any PR touching shipped content to move `.claude-plugin/plugin.json`'s `version` and add a matching `CHANGELOG.md` heading, and `.github/workflows/ci.yml`'s `version-bump` job enforces it — but only on a PR whose base is `main`. That arc's three slices merging into `main` directly would each have needed their own bump, colliding on both files, and would have shipped three versions for one change; converging on an epic branch made it one release, and the epic → `main` PR still faced the bump check in one shot. That `if:` condition was written knowing this — its own comment says the epic → main PR *"is itself a PR into main… so the whole arc's accumulated content is still checked in one shot"* — so the CI already assumed this topology while the rule that produces it was still keyed on fan-out.

**Two of those five are artifacts of concurrency and genuinely do not apply to a sequentially-dispatched arc — conceded here rather than left for a reader to catch.** With one live slice at a time no sibling's base moves under anything, so base churn is zero; and conflict-free sequential merges come back empty on the `^2` check every time, so the shared branch is never left carrying an ungated tree. **The other three hold whatever the dispatch order is.** An arc that turns out wrong is still N merges to unpick, a seam is still a seam, and N merges into the branch a project releases from are still N releases — which is why the rule is stated over multi-slice work rather than over fan-out. *The failure this prevents is a reader's, and it is why the accounting is written down instead of assumed: someone who notices that base churn cannot happen sequentially, and finds the section silent about it, concludes the rule was widened past its own argument — and the next edit narrows it back to the qualifier this one removed.*

None of this makes the branch free. *The cost* below is the bill, and the merge-back cadence that bounds it is mandatory — and load-bearing in proportion, because this default fires on every multi-slice arc.

**Neither rule is a slice count, and what still bounds Rule 2 is its subject rather than its width.** Counting slices measures how long a partial state sits on the branch, never whether that state is broken — a real five-slice run (cache invalidation, a UI gate, a query poll, a SQL predicate, a store guard) was independently shippable at every step, and every merge left the integration branch green and coherent. That is why a count can never answer Rule 1, and it is also why that run is now the clearest case *for* Rule 2 rather than against it: it answered Rule 1 "no" and wanted the branch anyway, because the costs above landed on the shared branch however green each intermediate state was. What bounds Rule 2 instead is what counts as multi-slice at all — **one change decomposed into slices**, which is the thing an epic branch exists to converge. A handful of unrelated one-slice fixes running side by side is not an epic and cuts nothing: that is branch traffic, not an arc, and there is no half-finished arc for a branch to hold.

**And it is still not "the integration branch is busy."** Other sessions' traffic is the opposite concern — isolating you from them rather than them from you — and in a multi-session shop it is near-permanently true, so as a standalone trigger it degenerates into "always". What Rule 2 keys on is *your own* arc, which begins and ends with this epic.

**Single-slice work never cuts an epic branch.** Neither rule can fire on it: one slice has no intermediate state to leave behind, cannot churn its own base, gates the tree it produced, is one merge to revert, and has no sibling to hold a contract seam with.

**`decompose` recommends; you decide and act.** It is the pass that grounds slices in real code and produces the seam map, so it is the one positioned to see whether two halves must land together — it says so in its breakdown. You cut the branch and point the slices at it. Same find/act split already established for contract seams. A decomposition that recommends nothing means no epic branch.

### The cost — conflicts are deferred and concentrated, and the mitigation is mandatory

Conflicts do not disappear. Today a slice author resolves a small collision against the integration branch while the code is still theirs and still fresh in mind. Behind an epic branch that collision instead accumulates until the epic lands, and whoever lands it resolves a bigger one, later, with less context. That is the whole bill, and it is why this is trigger-gated rather than the shape everything uses.

**The mitigation rides the tick you already run.** On the same wakeup tick that drains the gate queue and fast-forwards the local integration branch, merge the integration branch INTO the epic branch — merge, never rebase, same as everywhere else here. *Draining the gate queue* carries the exact commands, because that is where you will be when you run them. That keeps the drift bounded and surfaces each collision while the slice author who caused it is still live to resolve it. Skipping this cadence is precisely how the deferred conflict becomes the concentrated one.

### Docs land at the end — one closing slice, fed by a falsification ledger

**Docs describe an end state, and an epic's intermediate states are by construction never shipped** — that is what this branch is for. So a doc rewritten by slice 1 gets rewritten again by slice 3, and the intermediate version was true of nothing anyone ever saw. Doc files are also hotspots in a way source files usually are not: one chapter describes a mechanism four slices are each changing a quarter of, so four slices patching four sentences is four conflicts whose resolution is **semantic** — reconciling four partial accounts of one mechanism, which is the thing the person holding the merge is least equipped to do.

Deferring docs wholesale is not the answer either, because it breaks the forcing function that makes naming them worth anything: **the implementer is the only party that knows what its change actually falsified**, and deferred docs are docs that do not get written. So the two halves split rather than move together:

- **`decompose` still names the docs each slice falsifies**, slice by slice, at grounding time (`skills/decompose/SKILL.md` Step 1). That discipline does not move, and neither does deriving it from the diff rather than from a grep.
- **The slice's deliverable is an entry in the epic's falsification ledger, not the edit** — *"this change makes paragraph Y of `<doc>` false"* — reported in the same hand-back that already carries a per-doc verdict. **That is the rule for prose describing behaviour**; a **structural coordinate** the slice itself moved is fixed by the slice, under the coordinate carve-out below.
- **Two questions, not one — the second asks what the slice ADDED that no doc describes at all.** *What did this change make false?* is a question about a **difference**, so a slice that gates, guards or exposes a surface **no doc has ever described** answers it with *nothing* — correct, complete, and indistinguishable from the answer a slice gives when it genuinely touched no documented behaviour. So ask the second question of the same diff and put its answer in the same ledger, marked as **needing new prose** rather than a correction: *"this change adds `<surface>`, which no doc describes."* **A slice reporting "nothing falsified" is doing the first rule correctly** — the defect was never implementer diligence and no amount of it closes a gap in what the question can return, which is why this is a second question rather than a warning to look harder. **It bites hardest on the surfaces most worth documenting**, since new behaviour is the likeliest thing to have no prose about it yet. *The failure this prevents, observed: a five-slice epic added seven gates across two workspaces, and the two that produced no ledger entry from anyone were both on undocumented surfaces — one slice checked the chapter covering its area, correctly found that the chapter says only that the thing fires and never what it contains, and reported in as many words that its surface "has nothing to falsify and nothing to document". The closing slice then consumed a ledger that was accurate and short by exactly the entries nobody could write, with no signal that anything was missing, because from there an absent entry and a not-affected verdict look identical.*
- **The ledger is the epic's record, not a file in the tree.** A file every slice appends to is exactly the shared hotspot this whole arrangement exists to avoid. Accumulate the entries where the arc's state already lives: the per-increment comment on the umbrella issue, or the orchestration record when the arc has none (`skills/orchestrate/SKILL.md` §7).
- **One closing docs slice consumes the ledger — and derives its work from what the epic ADDED as well, never from the inherited entries alone.** Last in the wave map, depending on every other slice, writing against the final tree with the whole picture in view. **Both halves are one rule and landing only the producer's is worth nothing**: a second question nobody consumes leaves its entries sitting unanswered, and a consumer reading only what it inherited is blind to exactly the surfaces that question exists to surface — so the closing slice's brief says to derive its rows from the arc's landed diff, the gates and flags and endpoints and surfaces the epic added, and to **reconcile** that list against the ledger rather than substituting either for the other. *The failure this prevents, observed on the arc above: a dispatcher had to write that instruction into the closing slice's brief by hand — derive the rows from the gate list, not from the ledger — and it is the only reason one of the two undocumented surfaces was documented at all.*
- **The epic cannot close with a non-empty ledger.** Every entry is answered by the closing slice's PR, and the epic → integration PR does not open while any remain. **This one really is a precondition over the OPEN, where the green close-out gate below is a precondition over the MERGE** — a draft PR puts nothing on the shared branch, so a gate can be enqueued against one, while an outstanding ledger entry means the epic is not finished and there is nothing to open a close-out for yet. It is the thing that stops this becoming the deferred-docs failure.

**Three carve-outs.** A **docs-only slice** writes inline: it has nothing to defer to, and its diff *is* what the closing slice would otherwise be doing. And **single-slice work has no end of an epic** — its docs ship in the same PR as the behavior, exactly as they do today, which is the same reason this section opens by telling you to skip it unless you are running a multi-slice epic. The third is unlike those two in the case it reaches: neither of them can help a **code slice in the middle of a multi-slice epic**, which is exactly the shape this rule is written for.

**A structural coordinate — a file path, or a route literal sitting in the same clause as one — is fixed by the slice that moves it.** The line is testable rather than a matter of judgement, and this is the operative statement of it: **if a checker can tell the reference is stale without reading the sentence, the slice that broke it fixes it.** A coordinate qualifies because it names something the tree either has or does not — which is *why* a gate can enforce it mechanically, and why repointing one is a **rename, not a rewrite**: no two slices can hold conflicting accounts of which path a file now has, so the semantic conflict this whole arrangement defers against has nothing to attach to. Everything on the other side of that line is untouched — **prose describing behaviour still defers to the closing docs slice, ledger and all.**

**A renamed IDENTIFIER lands on the prose side of that line, and it is the case the nouns above do not settle by looking.** A function, a param, an exported symbol is neither a file path nor a route literal, so the rule already returns an answer — but it returns it by the **test**, not by the nouns, and the test is the part to apply: nothing resolves a bare identifier in running prose against the tree. A path either exists or it does not. A symbol name in a sentence may be the current API, a superseded one a migration note is deliberately quoting, or a hypothetical in an example, and separating those is exactly the reading-the-sentence the test excludes. So an identifier your slice renamed goes to the ledger — **the whole sentence, not the name on its own** — and it usually costs no entry at all, because a sentence that names an accessor is almost always also describing what the accessor does, which was going to the ledger regardless. **Where a repo's docs gate genuinely does resolve identifiers — a code fence it compiles, a docs build that imports the symbol — the same test returns the other answer and the slice fixes it inline**, under the ⛔ below like any other sanctioned edit. Read the test, not the list of nouns; the nouns are what the test has returned so far.

*The failure this prevents: an identifier swap does not read as prose, it reads as exactly the mechanical repoint this carve-out sanctions — so it gets made inline, silently, by an agent that believes it is complying, and lands in the half-corrected state the adjacent-fact test below exists for. And unlike a stale path it costs nothing to defer: no gate reds on it, and an epic's intermediate states are never shipped, so there is no reader to mislead in the meantime.*

⛔ **Repointing a coordinate is NOT licence to fix the paragraph around it.** You change the path and nothing else; the sentence containing it, and the section containing that, stay in the ledger. A slice that "while I'm here" rewrites the surrounding prose reintroduces exactly the semantic conflict the deferral exists to prevent — and does it wearing a sanctioned edit, which is strictly worse than the failure it started from, because a diff that is *supposed* to touch that file no longer looks wrong to anyone reviewing it. This boundary is what keeps the carve-out from swallowing the rule.

⚠️ **"Nothing else" is only half the instruction — before you land an inline fix, read the sentence you just edited for a fact YOUR OWN change moved.** The rule above forbids you from improving the paragraph; it does not licence you to leave a sentence you have half-corrected, and the two are different obligations. This one is narrow by construction: it fires on facts *your diff* falsified — a TTL, a limit, a default, an ordering — and on nothing else that happens to be wrong in that sentence, which stays the closing slice's exactly as before. **Where you find one there is exactly one move: fix both halves. Never land the half.** **Reverting your inline edit is not a second way to satisfy that, and the reason is this carve-out's own test.** Every inline edit this test can fire on is one a checker *compelled* — a coordinate repoint, or an identifier fix in a repo whose docs gate resolves identifiers — and the edit is admitted precisely *because* a checker can tell the reference is stale without reading the sentence. So undoing it hands that checker back exactly what it reds on, which is the red-before-your-own-work-is-evaluated this carve-out exists to escape, and no ordering escapes it because the closing docs slice is last by construction. Putting the sentence in the ledger does not rescue the revert either: the rule above already leaves that sentence there, so the ledger gains nothing it did not already have while the slice loses its own gate. **Nor is there a leftover case where reverting is harmless** — where no checker resolves the reference, the carve-out never sanctioned an inline edit in the first place, so this test has nothing to fire on. And the one move is always available to you: the fact is one your own diff moved, which makes you the only party that already knows its new value. *The failure this narrowing prevents: an implementer that reverts has followed a sanctioned instruction to the letter and hands back a clean slice, so the red arrives afterwards from the gate runner, on a PR whose diff contains nothing wrong — and it reads as a defect in the slice rather than as the rule contradicting itself.* The asymmetry is why this is an obligation rather than advice — an untouched sentence is uniformly stale and a reader discounts all of it, while a fresh coordinate beside a stale number reads as evidence someone checked, so the wrong half inherits the credibility of the right one, and the closing docs slice, arriving at a sentence that was visibly attended to, has the least reason of anyone to look at it again.

*The failure this prevents, observed: one slice renamed a settings-cache accessor and moved that cache's TTL from 15 seconds to 60. The doc sentence naming the accessor was swapped to the new name and left reading "15-second cache" — the identifier right, the number describing a mechanism that no longer existed. Nothing in the slice, the gate or the ledger pointed at it; it was caught in review, and only because the reviewer happened to know the TTL had moved in the same change. The dispatcher's workaround was to tell the closing docs slice by hand to read that paragraph fresh, "do not treat it as done and do not treat it as untouched" — written per-slice, and only because someone remembered.*

*The failure this prevents, observed: a wave-2 slice of a six-slice epic deleted four files, four docs cited those files by path, and the repo's docs gate — which validates that every file path cited in a doc resolves in the tree — went red at **step 1 of 6**. `format`, `check` and `test` never ran, so the slice got no signal at all about its own work; nothing was wrong with it. It could not pass its gate without editing a doc the rule forbade it to edit, and no ordering escapes that, because the closing docs slice is last by construction. Neither of the first two carve-outs reaches it. The cost is a full drained-gate round trip plus a fix-agent dispatch per affected slice, and it arrives looking like a defect in the slice rather than a gap in the convention — and waves 3–4 of that same epic delete more files the docs cite, so it recurs by construction rather than by accident.*

*The failure the deferral itself prevents runs both ways, which is why it is a split and not a deferral. Docs written per slice inside an epic are rewritten by a later slice and collide semantically in between, so the work is done twice and the merge is resolved by whoever has the least context for it. Docs merely postponed are written at the end by an agent that watched none of it happen, from a diff too large to read — which is how an epic ships a chapter describing neither the old mechanism nor the new one, with every gate green.*

### Mechanics

- **It gets its own worktree, like every other branch that is not the integration branch.** One governing rule covers the whole flow: **the main checkout holds the integration branch and nothing else, ever.** The epic branch is not a special case — it is a slice-shaped thing one level up, cut the same way:
  ```
  setup-worktree.sh <epic-branch> <integration-branch>
  git -C <epic-worktree> push -u origin <epic-branch>
  ```
  `setup-worktree.sh` creates the branch **and** its tree in one command and **never touches the main checkout** — which is why this *replaces* the old switch/push/switch-back ceremony rather than relocating it. You cannot forget to step off a branch you never stepped onto, so there is no second half to get wrong. **Push it**, or `origin/<epic-branch>` does not exist: invariant 2 has nothing to compare a slice worktree's `HEAD:` against, and `gh pr create --base <epic-branch>` has no base on GitHub to open against. *The failure this prevents runs on two levels. Structurally, parking the epic branch in the main checkout caps you at exactly **one** epic — one checkout, one HEAD — while Rule 2 above makes an epic branch the **default** for multi-slice work, so the flow reaches for a branch constantly whose mechanics permit one at a time. And it puts the epic on the one piece of shared mutable state this flow has (the ⚠️ in *Worktree creation*, which named the main checkout as exactly that and was then contradicted by this bullet). Observed: another session moved the main checkout off the epic branch while a close-out gate ran. The gate was fine; the verification that followed ran against a different release branch entirely and reported an absurd count of schema blocks and a missing migration. **Nothing errored.** It was caught only because the numbers were absurd — with a subtler change it would have reported a green "verified" against the wrong tree. The safe workaround people actually reached for was `setup-worktree.sh --existing <epic-branch>`, a worktree on the epic branch: the skill's own recovery tool was the right answer to a problem the skill created, which is the tell that the tool was the design all along.*
- **⛔ The epic branch's leaf must be unique across the whole epic — no slice may reuse it, and the helper now refuses rather than letting the reuse through.** The worktree path is `$WORKTREE_HOME/<project>/<branch-leaf>` and the leaf is everything past the last slash, so `epic/checkout-flow` and a slice `feat/checkout-flow` resolve to the **same directory**. That collision is impossible until the epic branch has a worktree; it is live from the moment it does. On the second call `setup-worktree.sh` asks only whether a worktree is already **registered at that path**, finds the epic's, prints `worktree already exists: <path>`, and **skips `git worktree add` entirely** — so the slice branch is never created. It then reads the branch back off the tree, finds the epic's where the slice's was asked for, and **stops**: both branch names and the shared leaf on stderr, a non-zero exit, and no `READY:` line at all. The likeliest slice to reach for the collision is the epic's own **closing docs slice** — its wrap-up has no more natural name than the epic's — so pick a leaf that slice would not want, or name it for what it does rather than for the epic. *The failure this prevents: **invariant 2 is structurally blind to this one**, which is why the refusal has to live in the helper rather than in the check. Invariant 2 has you compare the printed `HEAD:` against `git rev-parse origin/<base>` — and the tree you were handed is standing on `<base>` itself, so the two shas **match**. The one check built to catch a wrong tree cannot see this wrong tree, because it is the base's own; the helper stops first, so there is never a `HEAD:` line for invariant 2 to be fooled by. Which generalizes past this one case: **a `READY:` line is not by itself evidence that the branch was created — the helper's own branch-back check is what makes it so.** Still choose the epic's leaf so that no slice will want it; what changed is that forgetting now costs you one refused command instead of a whole dispatch that looks correct.* **And the branch-back check is not the last thing standing between a skipped `git worktree add` and a `READY:` line — read that sentence as naming what makes the line evidence about the BRANCH, not as an inventory of the refusals.** The ancestry check that follows it asks a different question of the same handed-back tree — whether it contains `<base>` — which is the state a tree on exactly the right branch can still be in, and is why *Worktree creation* says the helper automates part of invariant 2. Neither refusal retires that invariant: its comparison is for equality and against `origin/<base>`, and invariant 2 is where the two gaps that leaves are named.
- **The epic worktree is a merge point and a gate target, not a workspace — nobody codes in it.** It exists so the epic branch has somewhere to be fast-forwarded, merged into, and gated. Every line of the epic is written in a slice worktree and arrives by PR, so this tree should never have uncommitted changes in it. *The failure this prevents: a dirty tree blocks **both** of the jobs this worktree exists for, and neither failure surfaces where it was caused. The every-tick `merge origin/<integration-branch>` refuses to run over uncommitted changes, so the mandatory mitigation for the epic's one real cost silently stops happening and the deferred conflict goes back to being the concentrated one. And `merge-pr.sh` now fast-forwards the base **inside this tree** on every slice close-out, so it fails there too — mid-close-out, after the merge is already irreversible. Both land as a failure in somebody else's slice, naming a tree that slice never touched.*
- **A module-resolution failure in the epic worktree is a stale install until proven otherwise, not a defect in the merged code.** The bullet above keeps this tree fit for two jobs that are both *git* operations; its **dependencies** are a third thing that can fall behind the branch, and no git-shaped rule covers them. They can fall behind in any tree that **outlives the merges landing in it**, which is precisely what this one is for — while every slice worktree is cut once the code it needs already exists and so installs correctly by construction. **This is not the only such tree, and it is not the most exposed one:** the main checkout outlives every merge the arc makes, holds the integration branch for all of it, and is fast-forwarded by `merge-pr.sh` on every close-out without ever installing — so the same question is asked of it, immediately before the integration gate runs there (*Gate the integrated whole*). So ask that question before you read a line of the diff: the tick's install (*Draining the gate queue*) is what keeps this tree current, and what you are checking is whether one has run since the package arrived, not whether a slice broke its imports. *The failure this prevents, observed: a slice added a workspace package and merged into the epic branch; the epic worktree's install predated it, and the integration gate there came back `TS2307: Cannot find module` on five files across two apps. The natural reading of that shape — five files, two apps, one module nobody can find — is a slice that repointed its imports at a path which does not resolve, and it invites dispatching a fix agent against code that is already correct, or hunting a package-name typo that is not there. The install took 1.2 seconds and the gate went green. The cost was never the install; it was arriving at it as a diagnosis.*
- **A conflicted tick is resolved before you walk away from it — never left half-merged for the next tick to find.** The every-tick merge of the integration branch into the epic branch is *where the deferred conflict surfaces*; surfacing it early is the entire reason the cadence exists. So resolve it in the epic worktree, commit the merge, push, and only then carry on. *The failure this prevents, and it is a second reason this merge no longer runs in trunk: the old cadence ran `git -C <main-checkout> merge origin/<integration-branch>` while the main checkout was standing on the epic branch, so a conflict — again, the exact case the tick exists to produce — left the **shared** checkout wedged mid-merge, conflict markers in the tree and `MERGE_HEAD` set. Every other session's `pull --ff-only` against that checkout then failed, in a checkout none of them had touched, for a reason none of them could see from their own worktree. The mitigation for the epic's one cost was itself a shared-state hazard. In a worktree you own the same conflict is yours alone and blocks nobody — but only until you leave it there, because an unfinished merge in the epic worktree is precisely the dirty tree the bullet above is about.*
- **Its *prefix* is free; its leaf is not, and the marker ref beside it is the exact opposite of both.** Nothing anywhere reads an epic branch's **prefix** — no helper in this plugin's `bin/`, no step in this playbook: the branch is identified by what forks from it and PRs into it, never by what it is called, so whatever prefix a team likes is fine. Its **leaf** is a different matter now that it has a worktree, because `setup-worktree.sh` derives the directory name from it — hence the uniqueness rule above. That is a collision constraint, not a naming contract: no leaf carries meaning, one just has to be unlike the others. **`transient-red/<epic-slug>` in the next bullet is not free in the same way — its name IS the contract**, because the detector finds the window by looking for that exact ref; spell it as written. The two are one fact rather than two: the branch's name is free *because* the marker took the job of being found. *The failure this prevents: a reader who carries "the name is free" across to the marker spells that to taste too, and a marker under any other name is a window that never opens — which nothing reports, because a window that failed to open and a project that has none behave identically.*
- **Cut under Rule 1's primary trigger? Open the window in the same breath — the branch alone does not open it.** A Rule 2-only epic branch — one Rule 1 answered "no" — is isolation and nothing else: every intermediate state on it would ship, and it stays strictly gated. A Rule 1 primary epic branch is *knowingly red* until the last consumer migrates (*Transient-red window* below), and a project whose commit-time tooling relaxes for that window has to be able to tell the two apart. It cannot read your decomposition, so declare the window structurally — one marker ref, pushed beside the epic branch and never committed to:
  ```
  git -C <epic-worktree> branch transient-red/<epic-slug> <epic-branch>
  git -C <epic-worktree> push origin transient-red/<epic-slug>
  ```
  Run them from the epic's own worktree, in the same breath as the two commands above. Creating a ref needs no working tree at all — the `-C` here only picks the repo — so this is about not reaching back into a checkout you no longer have any reason to touch, not about where the ref ends up. Nothing forks from it and nothing merges into it; it exists to be **found**, by tooling running inside a slice worktree that has no other way to know. **It answers one question — is the window open — and it is never a fork point.** A detector that needs the branch's own footprint takes its merge-base against the **epic branch**, which is what the slices actually forked from and which moves under them every time the tick merges the integration branch in. *The failure this prevents: the marker is static by design, so anchoring a merge-base on it silently widens every slice's "owned" file set to include everything merged into the epic since it was cut — which fails closed, quietly tightening the relaxation as the epic runs, and looks exactly like slices getting sloppier.* *Transient-red window* below states what reads it and what it must not be keyed on instead.
- **Slices fork from it and PR into it.** `setup-worktree.sh <slice-branch> <epic-branch>`, and invariant 2 then compares the tree's printed `HEAD:` against `git rev-parse origin/<epic-branch>` rather than the integration tip — **fetch first and read the freshness count, exactly as invariant 2 says, because this is the base most likely to have moved since you last looked.** The epic branch advances on every slice close-out, which fast-forwards it inside its own worktree, and again on every tick that merges the integration branch into it and pushes — so a cached `origin/<epic-branch>` goes stale on this flow's own cadence rather than on some other session's, and it does so between waves you are yourself running. Each slice's brief names the epic branch as its PR base. *The failure this prevents: nothing tells you the epic branch moved, because the close-out that advanced it ran in a worktree that is not yours and left no signal in yours — so a slice cut against a cached tip forks from a base the epic has already left, and the first sign is either a conflict at merge on files the slice had no reason to touch, or a sibling's half of a contract seam silently missing from the tree the slice was built and gated against.*
- **A follow-up the epic surfaced is part of the epic, so it lands on the epic branch.** The follow-up-ownership rule (*Hard rules*) turns every leftover into a filed, linked item — a new issue, or a comment on the issue already carrying that failure, which needs no branch at all and so has nothing for this bullet to place; while the epic branch is live, a new issue's slice forks from and PRs into the **epic branch** like any other slice of the arc, and that issue links to the arc's umbrella — or to the originating issue when the arc has none — rather than sitting loose. Only once the epic branch has merged back does a still-open follow-up re-target the integration branch. *The failure this prevents: the epic branch exists so the shared branch only ever sees the epic finished — routing a follow-up straight to the integration branch bypasses precisely the isolation the branch was cut for, and delivers the epic's leftovers to the shared branch piecemeal while the epic itself is still converging.*
- **Per-slice close-out needs no change, and leaves the main checkout where it found it.** `merge-pr.sh <n>` reads the base off the PR itself (`baseRefName`) and drives every later step from it — the mergeability preflight, the merge, and bringing the local base branch up to the merged tip in the main checkout. So a slice PR based on the epic branch closes out identically: worktree torn down, real merge commit into the epic branch, local epic branch advanced to the merged tip. No argument, flag or hand-run step to add, and nothing to switch back afterwards — the helper never switches the main checkout at all. What the epic branch having its own worktree changes is only **which** of the helper's three sync paths runs: the epic branch is now checked out, in that worktree, on every single slice merge, so the helper fast-forwards it **inside that worktree** (`merge --ff-only`, which can only ever move it forward) instead of moving its ref from outside — `git branch -f` refuses to move a branch any worktree is standing on. It then verifies the main checkout is still on the branch, and at the commit, it started on, exactly as before. The headline claim holds and gets **stronger**: this close-out now leaves not just the checkout's HEAD but every local branch in it untouched.
- **The bullet above is scoped to the steps the helper performs; the one it cannot do is the step an epic changes — not when it runs, but what happens when it is skipped.** Closing the issues the work resolved is that step, and *Merge & cleanup* already names it as the one that silently goes missing. An epic branch withdraws its only fallback, for every slice of the arc at once and for the arc's whole life: a slice PR bases on the epic branch rather than on the repository's **default** branch, so its closing keyword is inert — then, and later when the epic merges back (*Merge & cleanup* carries those mechanics and stays the only place they are explained). In a project whose integration branch simply **is** the default branch — this repo, and the shape most work here runs in — that flips at the moment the branch is cut: outside an epic the keyword fires and the hand-close is a harmless no-op, so the board moves whether or not anybody remembers the step; inside one the hand-close is the entire mechanism, on every slice merge. **So while an epic runs the board is not the arc's progress record — the umbrella body is**, rewritten every cycle (`skills/orchestrate/SKILL.md` §7). Read progress there, and where the board has fallen behind, catch it up to what has actually merged into the epic branch, never ahead of it. *The failure this prevents: mid-epic a dispatcher reads a board on which nothing has closed all day and reaches for one of two wrong conclusions. Either the work has not landed — it has, onto a branch no issue tracks — and slices that already merged get re-dispatched. Or hand-closing is overdue and the arc's issues get closed now to catch up, which is the worse branch: §7 counts the tracker in its termination check, so an issue closed ahead of its slice is a false "done" in the exact artifact the loop reads back to decide whether it is finished.*
- **A change to `.agents/worktree.json` is another thing this branch holds open for the arc's whole life: the config-read window ends at THIS branch's close-out, not at the slice merge inside it.** A slice that changes that file merges into the epic branch, which is not the branch the helper's lookup lands on, so that merge exercises nothing — and every worktree the arc cuts afterwards is still provisioned the old way, with the hand-application falling to you. *Worktree creation* is the authoritative copy of all of it: the lookup, the routes that do not get round it, the remedy, and the dispatcher's standing obligation. What is here is only which merge ends the window when there is an epic branch. *The failure this prevents: off an epic branch the window closes at the slice's own merge, so a reader carrying that reading onto one stops hand-applying after a single wave of an arc that has waves left to cut — and nothing reports it, because a worktree provisioned from the old config is not broken, only wrong later.*
- **Close-out is at most one gate plus one ordinary PR — and the ledger has to be empty before either** (*Docs land at the end* above; the closing docs slice is the last slice, so "the last slice merges" below includes it). Once the last slice merges, merge the integration branch into the epic one final time **in the epic's own worktree**, then **open the epic → integration PR as a DRAFT and enqueue the gate against it**, naming the epic worktree as the ticket's worktree so the gate runs there rather than in a checkout something else might move. *The failure that ordering prevents is the observed one that moved the epic branch out of trunk in the first place: a gate and the verification that reads it are two steps, and between them another session moved the shared checkout. The gate itself was fine; the verification ran against a different release branch and reported numbers that happened to be absurd enough to notice. In the epic's own worktree there is no window — nothing else has a reason to touch that tree, so what you gate and what you then verify are the same tree by construction.*

  **The PR opens BEFORE the gate, and the rule that looks like it forbids that does not.** *Gate the integrated whole* states the precondition over the **merge**, not over the open: a draft PR puts nothing on the shared branch, because GitHub refuses to merge one and this flow already spends the draft flag as the interlock against merging an unread diff. Opening it first is what gives the ticket something to attach to, so this becomes the shape every other PR in the flow already has — draft PR, enqueue, runner gates and comments, then merge. *The failure the old order caused: the one gate whose tree no per-slice gate had ever seen was also the only gate in the flow with no ticket, no streamed log, no recorded verdict and no comment, so its result survived only as an exit status in the terminal of whoever ran it — which is the whole reason a hard rule about `EXIT=$?` and piped invocations had to exist for it at all.* Two consequences: **"once the fleet is quiet" stops being something you poll for**, since the queue serializes by construction; and where the project declares **no queue** there is nothing to enqueue to, so you gate the epic branch in its own worktree yourself and read its exit status (*Gate the integrated whole*), with the draft-PR-first ordering unchanged.

  Then merge it with `merge-pr.sh` like any other. That merge is the first thing the integration branch sees of the epic, and it is a complete one. **It is "like any other" in shape now and unlike any other only in authorship** — this is the one PR in the flow with no implementer behind it. It is a draft carrying a gate comment from the moment it opens, exactly as **Hard rules**' reading requires, so there is no exception here to explain any more; what there is no such thing as is a hand-back to promote, because nothing was built on the epic branch directly. You author it and then merge it. What stands in for the missing hand-back has already been spent — every slice was reviewed as its own draft PR, and the epic tip has just been through *Gate the integrated whole*, which when the merges produced a tree no per-slice gate has run is the one signal those gates structurally could not give.
- **This closing merge is the ONE merge in the flow a project may collapse, and it is an option a project declares — never a judgement anyone makes at merge time.** Every other merge here is a real merge commit with no opt-out. This one branch is scaffolding — cut for one arc, deleted at its end — so on a long-lived release branch a project may prefer one commit per arc to N slice merges plus a merge commit, and it says so up front by putting `"epicMerge": "squash"` in `<repo>/.agents/worktree.json` (*Per-project config*). `merge-pr` reads that key itself and picks the mode; there is nothing to pass it, nothing for an implementer or a dispatcher to decide for one PR, and no way to reach the squash from the command line. Read that the way this file's documented-suppression carve-out reads: the exception is real, and stating it precisely is what keeps the default absolute. **The default is `merge`, and it stays `merge` for every project that has never heard of the key.**
  - **Under `"squash"` the squash still requires BOTH conditions, and every unanswerable question falls back to `merge`.** (1) The PR's base is **not** the repository's default branch (`gh repo view --json defaultBranchRef`), and (2) the head branch has merged PRs into it (`gh pr list --base <head> --state merged`) — which *is* the definition of an epic branch rather than a proxy for one, since an epic branch is the branch an epic's slices PR'd into. A slice branch and a single-slice branch both answer zero, which is what keeps `slice → epic` and single-slice → integration real merge commits without needing a rule of their own. gh absent, offline, unauthenticated or rate-limited; a default branch that came back empty or unresolvable; a count of zero; a config that will not parse; a value that is not exactly `squash` — every one of them lands on `merge`. The asymmetry is the whole design: **a missed squash is cosmetic, a wrong squash is unrecoverable history.**
  - **So a project whose integration branch IS the default branch never squashes, even at this boundary — that is deliberate, not a bug.** This repo is such a project: declare `"epicMerge": "squash"` here and it correctly does nothing. Condition (1) is there because condition (2) is true of an integration branch too — it is the branch every slice of every arc PR'd into, so a long-lived one answers in the dozens — and on its own it would take a `release/x.y.z → main`/`dev` close-out and collapse an entire release branch, irreversibly, with the tree check passing and every signal reading like a clean close-out. Nothing distinguishes an integration branch merging into `main` from an epic branch merging into `main` except a branch-name prefix, and no prefix is ever the key for anything in this flow (*Transient-red window*). So the constraint is **enforced rather than advised**, and a project that would have been told to leave the setting alone now has that for free. *The failure this prevents, observed: the first version of this test asked only question (2), and the slice that shipped it found while proving the negative cases that a release branch answers it too (this repo's own #107) — the release-branch squash reproduces on the pre-fix helper, and nothing about it looks wrong until you go looking for the commits.*
  - **Both ports compare the key, the value, and the branch names CASE-SENSITIVELY.** `"epicMerge": "squash"` exactly — `"Squash"`, `"SQUASH"` and `"EpicMerge"` all mean `merge`, identically in bash and in PowerShell. *The failure this prevents, observed on this very pair before it shipped, and in both directions: PowerShell's `-eq` and its property lookup both ignore case by default, so the first `.ps1` draft squashed a config the `.sh` merged — and the same default on the branch comparison, where git refs are case-sensitive, made a base named `Main` in a repo whose default branch is `main` look like the same branch, so the `.ps1` merged where the `.sh` squashed. Two ports disagreeing about the same file on the same input, once in each direction: the exact class the `bin/` parity rule exists for, and the one shape a parity check comparing surface shape cannot see.*
  - **The squash path does not pass `--delete-branch`, and git's "not fully merged" warning is answered by a different instrument rather than waved through.** A squash commit has no second parent, so the epic branch is never an ancestor of the new integration tip and `git branch -d` reports it as not fully merged on **every** squashed close-out — expected, and carrying no information, because squash breaks ancestry by construction. The warning is a claim about ancestry; what actually has to be true is that *what landed is what was gated*, which is a question about **trees**, and a squash preserves the tree exactly. So `merge-pr` captures the epic tip **before** the merge and afterwards runs `git diff --quiet <epic tip> <squash commit>`. Empty ⇒ the integration branch holds, byte for byte, the tree the close-out gate ran on — and only then is the branch deleted, local and remote. Non-empty, or a comparison that could not be made at all, ⇒ the close-out **stops** with both copies of the branch intact and everything else already finished, so re-running resumes from exactly that check. This is **stronger** than the `^2` check it replaces, not a weaker stand-in: it compares the trees directly instead of inferring coverage from parentage.
  - **What the option costs, stated next to the switch: the arc's individual commits stop reaching the integration branch.** They are not destroyed — they live on the epic branch until it is deleted, and on GitHub in each slice's PR and its `refs/pull/*` ref — but after the close-out nothing local holds them, and `git blame` on the integration branch lands on the squash commit for every line the arc touched. That is the trade the key *is*, and it is why `merge` is the default rather than the recommendation.
- **Deleting the epic branch is automatic on the merge path and earned on the squash path — the marker is the one thing left by hand either way.** The epic → integration PR has the **epic branch as its head branch**, so `merge-pr.sh` on it treats the epic largely as it treats a slice: step 2 tears the epic worktree down, and on the merge path `--delete-branch` removes the branch, local and remote, with the never-delete-past-git's-"not merged"-warning guard applying exactly as it does to a slice branch — verify it is fully merged into the integration branch first, and STOP on the warning rather than forcing past it. On the squash path that warning fires unconditionally and says nothing, so the tree comparison in the bullet above is what stands in its place, and the delete happens only once that comparison has passed. Its slice branches are already gone, each deleted by `merge-pr.sh` as it merged, so the only thing the close-out leaves behind is the `transient-red/<epic-slug>` marker, if it has one — delete that yourself, and the window closes with it. *Leaving it behind is the one failure mode this design cannot self-heal: the ref outlives the epic that justified it, and the next unrelated slice to commit gets its compile check quietly relaxed against a window that closed weeks ago.*

## Dispatcher

### Dispatch
Decompose the increment into independent tasks. For each: create + **verify** a worktree (above), then **dispatch a plain implementer sub-agent** (no `isolation`) pointed at that worktree path — in parallel whenever the tasks are independent. Spin up as many worktrees/branches as the work needs; the gate doesn't bottleneck fan-out (implementers enqueue rather than gate).

**Rules that govern what you dispatch live in other passes of this pipeline — in `skills/orchestrate/SKILL.md` and in `skills/decompose/SKILL.md` — and are pointed at here rather than restated.** They bind you at dispatch time even when you were invoked directly and never opened either of those skills. *The failure a restatement would cause: the rule then lives in two places, the copies drift, and nothing tells a reader which one is stale — so whichever they happen to open wins by accident.*

- **Merge-surface ordering — `skills/orchestrate/SKILL.md` §5.** Work folded into a live arc is placed by **merge surface before slice cohesion**, and churn goes in a **serial wave** — one slice, nothing else in flight. What it means *here*: the wave you are about to cut worktrees for is your last chance to honour that placement, because once its worktrees exist nothing folded joins it. *The failure this prevents: a wide-footprint change dispatched alongside its neighbours merges textually clean and semantically wrong — git merges by line and cannot know two edits must compose — so every gate in the wave stays green.* This file's *Merging a shared hotspot* is the same hazard reached from the other end, and carries the remedy — read the merged region — for a wave that already holds one.

- **The bare-string verify rider — `skills/orchestrate/SKILL.md` §8.** A slice renaming an identifier that crosses a string boundary — a table, a route, a cache key, a config key, an env var, a feature flag — carries a bare-string sweep in its verify bar, written in at **grounding** time by `/pipeline:decompose`, not added at review. What it means *here* is one check before you cut the worktree: **a rename-shaped brief that reaches you without the rider is a gap to send back.** *The failure this prevents: a dispatcher invoked directly never read `orchestrate`, so a gap not caught here is not caught at all — and both checks an implementer actually runs, a typecheck and one targeted test file, are structurally blind to a renamed literal sitting in a fixture, so the slice reports green and the break lands.*

- **Ground a claim before you write it into a brief — `skills/decompose/SKILL.md` Step 1.** The whole pass binds you, not one rule inside it: grounding is written for the decomposer, and a brief you wrote yourself carries premises that pass never saw. What it means *here* is one reading per sentence that states something about the code as settled fact — a convention the repo is said to hold, a boundary said to stop somewhere, a file said to say a thing: **open it and read it, or write it down as an assumption to flag rather than as a fact.** Step 0 hands your implementer `skills/execute/SKILL.md` rather than the skill this rule lives in, so a false premise leaves this seat having met nothing that could catch it, and the first party to meet it is the one building on it. *The failure this prevents, observed six times across five arcs in one session and once more inside the arc that added this bullet: claims stated as settled fact that the tree contradicted — an isolation boundary said to stop at the repository edge, a convention that exists nowhere and had been pasted into briefs across three arcs, a file said to state a count where it enumerates and states none. Every one was caught downstream, by an implementer that chose to go and look; one reached the maintainer as evidence before it was corrected. The brief is the one artifact in this flow that nothing checks against the tree — a gate cannot test a premise, `skills/decompose/SKILL.md` Step 3's `Verify` field tests the work rather than the claims the work was commissioned from, and its closing check reads a brief's fields against **each other**, which a false premise satisfies perfectly while being wrong against the **tree**. So a premise nobody questions is indistinguishable from one that is true, and the implementer that does not happen to look has violated nothing.*

- **An enumeration you gathered is a claim that carries its cardinality — `skills/decompose/SKILL.md` Step 1's *An enumeration is a claim*.** It binds you because every list in the brief came out of a command *somebody* ran, and when you were invoked directly that somebody is you. What it means *here* is one question per enumerated list before you cut a worktree: **does it carry the count the unfiltered command returned, and did that command filter nothing?** No `head`/`tail` on the set, no `2>/dev/null` on a search, and an empty result read as an answer only once its exit status says the search actually ran. `skills/decompose/SKILL.md` Step 3's closing check cannot cover this and is not a substitute for it — that check reads a brief's fields against each other, and a short list names real files, in the right format, reconciling with every other field. *The failure this prevents: this file already bans the same shortcut one artifact over — a pipe on a gate, where it swallows the verdict — and the enumeration case is worse in the one way that matters, because a gate at least has an exit status to lose. `grep … | head -8` exits 0 on eight hits and on eighteen alike, so nothing is discarded and nothing is inverted; the short list simply reads as complete, in the brief, in your review of it, and in the implementer's hands.*

- **A verify bar that ships a command states its property in words too, and the command is checked against that property — `skills/decompose/SKILL.md` Step 3's `Verify` field.** It binds you because the rule is written for the decomposer while the bar in a brief you wrote yourself is **yours**, and Step 0 hands your implementer `skills/execute/SKILL.md` rather than the skill this rule lives in — so a defective bar written from here reaches nobody who has read the rule, and the first party to meet it is the one running it. What it means *here* is one reading per bar before you cut the worktree: **the command is the instrument, the sentence beside it is the property, and you read the one against the other on the case the slice is EXPECTED to produce** — never on the tree you are standing in, where a bar can pass today and mean nothing by the time anyone runs it. The `Verify` field carries the argument; read it there rather than from this sentence. *The failure this prevents, observed three times across two arcs in bars written from this seat: a bar asserting that no numbered section had been renumbered shipped a grep for `## N.` headings aimed at files that carry none. The instrument had zero instances on its target, so it could not fail — it comes back green carrying no information, and green is what this flow reads as a bar met. Each time it was the implementer that caught it, reporting that the bar could not fire rather than that it had passed, which is the one party with no say in what the bar said.*

- **Reconcile the brief's fields against each other before you hand it over — `skills/decompose/SKILL.md` Step 3's closing check.** It binds a brief however it was authored, and **a brief you wrote yourself is a field set exactly as an emitted slice is** — a fence, a verify bar, a brief, the conventions the slice inherits. What it means *here* is one pass over the brief before you dispatch, most sharply on the pair that lands in a dispatcher's hands most often: **does anything in the `Verify` bar require touching a file the `Do NOT touch` fences?** A bar that cannot be satisfied without breaching a fence is a brief to fix now, not a judgement to hand the implementer. This is the **authoring** end; the Implementer section's *A brief that contradicts ITSELF* is the **receiving** end — what an implementer does with one that got through — so the second does not cover the first, and a contradiction that reaches it is one this check already had its chance at. *The failure this prevents, observed on this repo's own 3.16.0 arc: a dispatcher-written brief fenced `skills/write-issue/SKILL.md` as do-not-touch while its verify bar required `grep -rn "in parallel" skills/` to surface no surviving trigger claim — and that file carried exactly such a claim, so the bar could not come back clean while the fence held. It landed correctly on luck twice over: the fence happened to carry a carve-out, and the implementer happened to exercise it and say so. Remove either and the brief has the three moves the closing check already enumerates, two of them silent — and a diff read afterwards cannot tell a bar that was dropped from one that was never load-bearing.*

**Pick the model tier per task — match cost to difficulty.** Pass `model: "sonnet"` to the Agent tool for the *bulk* of implementer dispatches: well-scoped, mechanical, or moderate work (wiring, UI from a clear spec, a route/op that mirrors an existing one, tests, a refactor with a known shape). Reserve `model: "opus"` for genuinely HARD slices: subtle algorithms, ambiguous or design-heavy work, tricky concurrency/lifecycle, security-sensitive code, or large cross-cutting changes where a wrong approach is expensive to unwind. When unsure, **start Sonnet** — a Sonnet PR you have to redirect is cheaper than Opus on routine work; escalate to Opus only if the task proves harder than scoped. Trade-off: the easier the model, the **more explicit the brief** must be — exact files, patterns to copy, hard do-not-touch boundaries, research-first steps. Clarity substitutes for model strength, so a Sonnet brief should read as near-deterministic steps, not "figure it out."

**Open every brief with "Step 0: invoke the `pipeline:execute` skill (via the Skill tool) and act as the IMPLEMENTER."** That is THIS skill — the agent then reads the generic implementer playbook from `skills/execute/SKILL.md`'s own *Implementer* section: scoped-check-not-full-gate, cheap-checks-during, the zero-warnings "don't be lazy" bar, push-draft-PR-enqueue-report, never-rebase / never-self-merge, and stop-and-report. **Do NOT re-paste any of that into the brief** — it's already in the skill the agent just loaded, and duplicating it bloats the brief and drifts out of sync.

⚠️ **A section named apart from the skill that holds it is a claim nothing can check — bind the two, or name the file.** The corpus's ordinary form does this by construction, in either of two shapes: *`skills/orchestrate/SKILL.md` §5*, the form this section's own dispatch rules use, names the file outright, and a possessive like *`/pipeline:decompose`'s GitHub write mechanics* binds the section to its skill in one phrase. Either way the reference carries its own referent and cannot disagree with anything. This line did not. It named a skill to invoke in one sentence and *the* Implementer *section* in the next, with the binding between them left implicit — and an implicit binding is one no reader and no check can test. *The failure this prevents, observed: the skill named here was `pipeline:orchestrate`, which has no* Implementer *section and opens by forbidding implementation outright, so a dispatcher following the line handed its implementer a skill whose first instruction bans the work the brief then assigns. Both outcomes are silent. An agent honouring the skill hands back a decomposition of the slice it was told to build; an agent honouring the brief builds it having loaded none of the playbook Step 0 exists to deliver — the dangerous one, because it looks exactly like a correct dispatch. The wrong name survived a rename that swapped the two skills' names wholesale, sat here across seven releases reading perfectly, was caught twice only by dispatchers who happened to be reading this surrounding section, and then passed straight through into two live briefs by one who trusted the line — which is what a rule stated this plainly invites.*

**This skill is written for you, the dispatcher — you are the one who has fully internalized it, and your job is to translate the parts implementers must execute correctly into their brief.** Step 0 ("invoke the `pipeline:execute` skill and act as the IMPLEMENTER") covers simple absolute prohibitions fine — never rebase, never self-merge — an agent either does or doesn't do those. It does NOT cover (a) a multi-step procedure that has one correct order and one wrong, silently-incomplete order with no error to flag the miss, or (b) a rule that overrides a harness-level default the agent would otherwise follow unprompted. Six items have exactly one of those two shapes, and you paste all of them into every brief close to verbatim rather than relying on Step 0 to carry them: the **commit-last ordering**, the **push-draft-PR-then-enqueue handoff**, and the **docs-in-the-same-PR rule** (shape a), and **no AI attribution**, the **no-full-suite-runs ban** and the **foreground-handoff rule** (shape b — the harness default is "verify your change by running the tests," which is exactly the instinct this workflow overrides, along with its near neighbour "await the check you just started before you commit"; never rebase / never self-merge need no reinforcement because no default pushes against them, but these fight a strong instinct and lose unless restated). Treat any future addition with either shape the same way — and **the count is stated here, beside the list, and nowhere else**: every other line reaching for this enumeration names it (*the items above*, *enumerated above*) instead of restating how many there are, so an addition here falsifies nothing anywhere and there is no sweep to get wrong. *The failure this prevents, observed here twice. The docs item was added in 1.8.0 and only this paragraph's number moved, so the gate-mode bullet went on reading "one of the four paste-verbatim items" while this one read five, and it shipped that way from 1.8.0 through 3.18.2. 3.19.0 fixed that by declaring this paragraph the authoritative count and requiring every citing line to move with it — and the commit that installed the rule broke it in its own diff, sweeping two citing lines and leaving a third, three lines below and sitting in the same hunk as a context line, reading "the five items above", where it stayed until 3.26.0. A stale count reads exactly as authoritative as a current one, nothing compares the two, and a dispatcher who trusts the low one pastes a short brief believing it complete — which is why the remote counts are gone rather than swept a second time. `AGENTS.md` states the general form.*

Your brief carries the **task-specific context the skill can't know**, plus the items above — keep the rest lean:
- **Step 0 skills.** Invoke `pipeline:execute` (as implementer), plus any framework reference skill the task touches — name it as an explicit first step, not "use it." For Trinity — **app = Solid, sidecar = Effect**: Effect-TS on the sidecar (services, layers, HTTP routes, typed errors) → "invoke the `frameworks:effect-v3` skill"; SolidJS UI on the app (`solid-js`, `@solidjs/router`, `@tanstack/solid-query`, Kobalte) → "invoke the `frameworks:solid` skill"; a full-stack slice → both. Sonnet agents won't reach for these on their own, so spell them out.
- **Dispatching into the repository that SHIPS these skills? Say which copy of them is authoritative.** Step 0 loads the **installed** plugin — whichever version is enabled in the plugin cache — and never the tree the implementer is standing in. In every other repository those two have nothing to do with each other and this never arises. In the repository that ships these skills they are one document at two versions, so Step 0 hands an implementer one version of the rules and the brief then asks it to edit another — and **the rules an arc has just shipped are the ones most likely to be missing from the copy it was handed**, so every release the arc lands widens the gap. You are the only party that knows which repository you are dispatching into, so this is one sentence in the brief: *the worktree's copy of these skills is the authoritative one — read the rule there, and where one looks wrong or missing, `diff` the installed copy against the worktree's and trust the worktree.* The Implementer section's *The copy you were handed is not the copy you are editing* is the other half, and neither binds alone. *The failure this prevents, observed twice and measured the second time: the enabled cache sat seven releases behind the worktree and differed from it by 42 lines in this file alone, while that same cache held three newer versions it was not using — so it is not even "the newest installed copy", and nothing in the flow reads or reports which one is enabled. Nothing errors either way: the agent loads a real skill, follows real rules, and produces work that satisfies them, and a hand-back reads identically whichever version they were. It also corrupts a sweep — an audit of the corpus for rules that disagree across files produced two candidate findings that were defects the worktree had already fixed, manufactured by the instrument rather than found by it.*
- **The task + the worktree.** What to build/fix, the assigned worktree's absolute path, and the concrete files/patterns to copy. The weaker the model, the more explicit — near-deterministic steps for Sonnet, not "figure it out."
- **A scratchpad of its own, provisioned by you and NAMED in the brief.** An implementer writes gate logs, captured exit statuses and intermediate output somewhere, and unless you say otherwise that somewhere is the scratchpad it inherited from you — the one every sibling in the wave inherited too, at exactly the moment they are all running. So give each dispatched implementer its own, the way you give it its own worktree: a subdirectory per slice is enough, because the point is only that the namespace is not shared. **Both halves are the rule, and provisioning one silently is worth nothing**: an implementer cannot tell a per-slice scratchpad from a shared one and has no reason to look, so the brief carries the path, says it is this slice's alone, and says to put every log and temp file under it. *The failure this prevents, observed: two implementers dispatched in parallel into isolated worktrees, exactly as this playbook prescribes, both inherited one scratchpad and both redirected gate output to a conventionally-named file. One log was truncated mid-run by the sibling's write; then a killed gate's non-zero exit line was appended to the OTHER implementer's log, so a log carried an exit status belonging to a different process. Nothing argued against it, because the two places this playbook reasons about isolation both miss the scratchpad by construction: **a worktree is only isolated if its dependencies are** is a claim about what is inside the repository, and `sharedResources` reaches outside it but only to what the **project's checks** touch, declared per project. A scratchpad is neither — it is where the **agent** writes about its own run, and it arrives from the harness rather than from the project — so no key names it and no rule reaches it. Both halves of the failure are silent, too: a truncated log and a short log are the same file, and an exit line is an exit line.*

  ⚠️ **Kill by exact pid, or not at all** — a caution to carry into the brief beside the path. A process-kill pattern broad enough to match the project's test command matches a sibling's in-flight run too, and that is how the collision above compounded: the implementer diagnosing it killed its sibling's gate.
- **Scope + hard do-not-touch boundaries.** The other slices'/phases' core files this task must NOT edit. Where a chapter covers your area but stops short of what you changed, that is this entry rather than a not-affected verdict.

Start from the repo's own doc set (`README.md`, `AGENTS.md`/`CLAUDE.md`, and any reference or docs directory the project keeps) plus anything the project's conventions name. Docs changes go in their own commit, separate from the behavior. - **Gate mode for this slice.** Gate mode decides **who runs the gate and when** — nothing else. The DEFAULT is: implementer runs only the scoped check, pushes, opens a draft PR, and enqueues — a runner does the authoritative gate later. Override ONLY when the slice is foundational/cross-cutting and you want it verified before it enters the queue (or when there's no dispatcher to drain): then tell the implementer to run the full `gate` itself, in the foreground, **post the result as a comment on its own PR**, and NOT enqueue.   ⚠️ **In in-line gate mode the verdict comment is NOT the hand-back — wait for the hand-back before you merge or tear down.** That covers a slice you put in override mode and every slice of a project that declares no queue at all, where *Per-project config* makes in-line gating the default. It does not establish that the implementer has stopped working, and the merge is the step that destroys the tree it may still be standing in. *The failure this prevents, observed: a PR carried a green verdict, so the dispatcher reviewed and merged, and the teardown ran while the implementer was still mid-turn filing its follow-ups. Nothing was lost — the code was pushed before the verdict was posted — but the merge raced a live agent instead of following its hand-back, and the implementer's report of it arrived after the tree it named had ceased to exist.*

  The other direction is a **caution rather than a rule**, because an implementer's state is knowable by asking it: the comment's absence does not establish that no gate has run. It is not evidence the other way either — a PR is gated only if it carries a gate comment — so what a bare PR licenses is a question to the agent and nothing else. *Observed: a PR had no comments and the dispatcher had separately killed a gate process in that worktree, so it concluded no gate had run and told the implementer its slice was accepted with no changes needed. The gate had run and had come back **red** on a genuine regression; the implementer pushed back, which is the only reason it surfaced. Both observations were true — the inference joining them was not.* That is *Draining the gate queue*'s **A PR with NO gate comment has not been gated** taken one step further out, not a second position beside it: there, a bare PR is not evidence of a **verdict**; here, it is not evidence about the **implementer** either. What differs is only the instrument that settles it — a queued project has the reconciling drain that bullet names, and in-line mode has no ticket to reconcile, so what settles it is asking the agent.

  For a DEFAULT-mode slice, paste the ban into the brief — this is one of the paste-verbatim items enumerated above, because it overrides the agent's built-in "verify by running the tests" instinct and gets rationalized around otherwise:

  > **No full-suite or whole-package test runs — by ANY invocation.** Your only test execution is a SINGLE targeted test file (`vitest run path/to/x.test.ts`). Do not run the full suite or any whole-package test run through any route: not `gate`, not `turbo run test`, not a raw `vitest`/`tsc` sweep, not a package `test` script. Backgrounding it does not make it compliant — launching a banned run with `run_in_background` (or `&`/`nohup`) is still running it, and is the classic stall: the suite churns, you end your turn, and the handoff never happens. The runner gates your PR after you enqueue; verification wider than one test file is its job, not yours.
- **Review pass for this slice — your call.** `/pipeline:review` is the implementer's own quality + correctness pass over its uncommitted diff (reuse / simplification / efficiency / altitude, plus correctness). It pays off on substantial work — a new module, non-trivial logic, a refactor with structure to tighten. On a trivial slice — a one-line fix, a copy/string tweak, a config bump, a mechanical rename — it has nothing to chew on, so it's noise, not safety. YOU hold the decomposition, so YOU decide per slice and say so in the brief: default substantial slices to a review pass, and tell trivial ones to skip it. State it explicitly either way — the decision sets the commit ordering below.
  ⚠️ **Name the pipeline skill, never a bare `/simplify`.** Claude Code ships a bundled skill by that name whose behavior is outside this plugin's control, and which has changed under running epics: it fans out its reviewers as **forks**, which inherit the caller's whole conversation — an implementer's brief, whose imperatives end in *commit, push, open a PR, enqueue the gate*. Reviewers then execute that brief. Observed across three consecutive slices of one epic: review agents applied fixes, ran the repo formatter at root, committed, pushed, opened the PRs and enqueued the tickets before the implementer got its turn back. `/pipeline:review` ships in this plugin, dispatches nothing, and never commits.
- **The commit ordering — set by the review decision above.** If the slice runs `/pipeline:review`, commit LAST: the pass acts only on the *uncommitted* working-tree diff, so anything committed early is invisible to it — it reports nothing against the clean part whether or not that code needed cleanup.   > **Review slice:** Do NOT commit as you go. Write the ENTIRE change in your worktree first — uncommitted. Cheap checks while you work are fine (format, a scoped lint/typecheck, a single targeted test file) but don't commit yet. When the code is done, run `/pipeline:review` over your full uncommitted diff — it is YOUR pass, run inline: it spawns nothing and commits nothing, and you decide which of its findings to apply. Then run the auto-formatter in WRITE mode (Trinity: `pnpm format`) over the tree, and THEN commit — in logical, self-contained blocks (a type + its plumbing, a behavior + its tests), never one giant commit and never as-you-go.

  > **Skip-review slice (trivial change):** Skip `/pipeline:review` — it has nothing to chew on here. Write the change, run the cheap checks, run the auto-formatter in WRITE mode (Trinity: `pnpm format`), and commit in logical, self-contained blocks (never one giant commit). Do NOT run it just to tick a box; the dispatcher judged it not worth the round-trip. And do NOT substitute the bundled `/simplify` for it.

  In both cases your commits are held to the cheap SCOPED check by the pre-commit hook (format-check + lint + typecheck — no build, no test suite); you do NOT run the full gate. The hook only *checks* formatting, it does not *fix* it — so run the formatter in write mode right before you commit, or an unformatted diff gets bounced.

- **The foreground-handoff rule — and unlike the ban above it goes in EVERY brief, whatever the gate mode.** The ban reaches only a run the implementer was never allowed to start; the stall that actually happens comes from a **permitted** check — the project's own `scopedCheck`, backgrounded, with the turn ended on it — and a permitted check exists in every gate mode. Shape (b): the harness default is to await a check's result before committing, so Step 0 does not carry it. This is about checks and commands, NOT about sub-agents you spawned: ending your turn while your own children run is a self-suspension the harness re-invokes, and it stays legitimate.

- **The push-draft-PR-then-enqueue handoff.** The implementer's wrap-up is a durable handoff, not a wait — this order is load-bearing because it's what makes a mid-flight death lose nothing. Substitute it here rather than passing the condition down: you already know which branch it is, and an implementer left to work it out is one that can send its PR at the wrong branch.

  **The block states the ORDER and NAMES the report's contents — it does not restate them, and that split is exactly what makes it a paste-verbatim item.** What Step 0 cannot carry is the sequence: push, draft PR, enqueue, hand back, with one correct order, one silently-incomplete wrong one, and no error anywhere to mark the miss. ### Dispatch in the background, then monitor for divergence
**Default to dispatching implementers in the background** (the Agent tool's `run_in_background: true`) rather than blocking on each one. This keeps you — the dispatcher — responsive: you get an automatic notification when an agent completes or opens its PR, AND you can poll the live worktrees mid-flight to catch a wandering agent *before* it burns a whole run going the wrong way. (Background dispatch is the Agent tool's own flag — this is NOT the banned `isolation: "worktree"`; you still make the worktree yourself via the helper and point a plain agent at it.)

**Poll every ~10 minutes for divergence** while agents run. Use `ScheduleWakeup` to self-pace the checks (≈600s is frequent enough to course-correct early; it is accepted outside `/loop` despite the mode its description's opening sentence names — `/pipeline:orchestrate` §2 carries why, and settles that the tick is required at all). Don't poll *only* for completion — that arrives as a notification for free; the point of polling is **early divergence detection**, with two cheap riders on the same tick: (a) check whether any slice opened a draft PR and enqueued, and (b) **drain the gate queue** (`drain`) so enqueued PRs get gated and carry their verdict without waiting for you to notice. Each tick, snapshot what files each agent is actually touching and compare against its assigned scope:

- **Snapshot against the FORK POINT (the merge-base), never HEAD and never the integration tip.** Compute the fork point ONCE per tick — `FP=$(git -C <wt> merge-base HEAD origin/<integration>)` (re-`fetch` first; the tip moves) — then `git -C <wt> --no-pager diff --stat $FP` for the full file scope, plus `git -C <wt> ls-files --others --exclude-standard` for untracked. `git diff --stat $FP` (working tree vs fork point) captures BOTH any already-committed blocks AND uncommitted work-in-progress in one shot — which is what you need, because implementers **commit LAST** (after the review pass), so mid-flight most of the work is still *uncommitted*; diffing the working tree against the fork point sees it regardless of whether it's been committed yet. Two traps, both of which have actually bitten us, so neither is hypothetical:
  - ⚠️ **Don't use `git diff --stat HEAD`** — that shows only *uncommitted* changes, so the moment an agent commits (it commits everything at the end) HEAD goes clean and the diff shows **nothing**, and you'll either think the agent is idle or reach for a range diff against the tip (the next trap). Use `git log --oneline $FP..HEAD` only to *list the commits*, never as your file-scope check.
  - ⚠️ **Don't use `git diff <integration>..HEAD` / `origin/<integration>..HEAD`** (two-dot against the tip). Once another PR merges into the integration branch *while this worktree is open*, that merged work shows up as **phantom additions/deletions** here and triggers a false divergence alarm — the merged PR's unrelated files look like this agent's edits. We hit exactly this: a poll two-dot-diffed against a tip that had just advanced, the unrelated merged PR's files appeared as the agent's, and a **perfectly in-scope agent was wrongly `TaskStop`ped** (then had to be resumed). The fork point never moves — anchor every scope check to `$FP`, same as the PR-review diff (below).
- **What counts as divergence:** editing another task's / another phase's **core source files** (e.g. a "types only" task editing the resolver, or a backend task building UI). **What does NOT count:** compile-driven ripples from the task's own change — exhaustive `switch`/enum/interface/config entries a new member forces, a one-line badge to keep an exhaustive UI match compiling, and `+1`-line fixture edits across many `*.test.ts` files (even ones in another area) from adding a field to a shared type. Spell out this divergence/not-divergence line in the wakeup prompt so the check is mechanical, not a re-judgement each time.
- **Check substance, not just the file count.** Staying in scope ≠ doing it right — a diffstat tells you *where* the agent is editing, not *whether the approach is correct*. On any slice with real design subtlety, periodically **read the actual diff of the 2–3 highest-risk files** (`git -C <wt> --no-pager diff $FP -- <file>`, anchored to the same fork point as the diffstat — NOT `HEAD`, which would omit the committed blocks), not just `--stat`, and confirm the agent is following the intended approach (or genuinely improving on it). **Grep the diff for the specific anti-patterns the brief banned** (e.g. a forbidden call leaking into the wrong layer: `git -C <wt> diff $FP -- <files> | grep -nE '<bannedSymbols>'`). A wrong-but-in-scope approach is exactly what file-counting misses, and catching it mid-flight saves a whole wasted run. Keep it light — the risk files, not the entire diff. **And in a prose-shaped repo a diffstat measures nothing at all** — not scope, not magnitude. Where the unit of change is a paragraph, lines-changed correlates with nothing in either direction: one changed line can be a rewritten 400-word rule and two hundred can be a mechanical rename. *The failure this prevents, observed on this repo's own PRs: a reviewer read a 29-line diff carrying six rules as suspiciously thin at roughly five lines each, in a file where a single bullet runs to 400 words — the density was right and the arithmetic was measuring line wrapping. The misread runs the other way just as easily, and that direction merges: a large diffstat reads as thorough work and buys a pass on actually reading it.*
- **⛔ Confirm the alarm against `$FP` BEFORE you `TaskStop` — whatever channel the alarm arrived on.** The fork-point discipline above is written for the diff *you* run on the tick, but the alarm that actually reaches you is usually a fragment from somewhere else: a screenshot the user pastes, a line in the agent's own hand-back, a filename that looks wrong in a notification. **A fragment carries no base, and the DIRECTION of a change cannot be read off a hunk.** A hunk rewriting `b` back to `a` is byte-identical whether the agent is diverging into a backwards rename or **reverting an out-of-scope forward one** — only `git -C <wt> show $FP:<file>` separates them, because only the fork point says what that symbol was before this agent touched it. Read the fork-point state of the specific symbol, then decide. *The failure this prevents: a dispatcher `TaskStop`ped a healthy agent on a pasted diff fragment that was the agent cleaning up after itself — 380 of its renames were correct, and the 10 that looked backwards WERE the revert. The costs are asymmetric by an order of magnitude: confirming is one `git show`, and cutting wrong throws away the run, needs a resume, and spends the user's trust in every later call you make.*
- **If an agent diverged** (out of scope OR on a wrong approach) **and you have confirmed it against `$FP` per the bullet above**: `TaskStop` it, then **dispatch a fresh plain agent into the SAME worktree path** with a tighter brief — explicit *do-not-touch* boundaries naming the files/areas it strayed into (or the wrong pattern to avoid), and an instruction to revert the bad edits. Don't try to course-correct a still-running agent mid-stream; stop-and-replace is cleaner.
- **If an agent opened its draft PR + enqueued, or genuinely finished:** stop rescheduling for that one and move into the drain + PR review loop + merge below. ("Finished" means the PR is open — not merely that a turn-end notification arrived; see the next bullet for why those differ.)
- **⛔ Don't mistake a legitimate nested sub-agent wait for a stall — cutting in wastes real work and infuriates the user.** An implementer that spawned children of its own ends its turn while they run, and its **completion notification fires even though it is mid-wait, not done**. The tell: an uncommitted full worktree, no PR yet, and the agent's own hand-back saying it is awaiting sub-agents it spawned. That is a **self-suspension, not a stall** — the harness re-invokes it automatically when its children finish, so `TaskStop`ping OR resuming it mid-wait throws away the in-flight work and forces a restart. **Leave it alone and let it come back on its own.** Budget the window: on a substantial slice, expect NO PR for the first couple of ticks and do not read that as failure. Only escalate to the stall-recovery resume (next bullet) when it is genuinely stuck — the worktree byte-for-byte unchanged across **two consecutive ticks**, no live children, AND the agent not reporting a wait **on sub-agents it spawned** — never merely because a PR hasn't appeared inside one 10-minute tick. (This over-eager cutting was a recurring, real complaint: the fix is patience, not a faster poll.) **That last conjunct is narrow on purpose, because the other kind of reported wait IS the stall.** A hand-back saying it is waiting on a **check or command it started** — *"I'll pause here and wait for the scoped-check monitor notification before committing"* — is not a self-suspension: what it is waiting on is a process, not a child agent, so nothing re-invokes it, and every other tell reads identically (full worktree, no PR, turn ended). **Resume it.** *The failure this prevents, observed on a single-slice run against `trinity-ai-labs/trinity` (PR #4798): the implementer had backgrounded `pnpm check` — the project's `scopedCheck`, which it is allowed to run — and ended its turn with the whole change complete and uncommitted. Against the unnarrowed conjunct that agent WAS reporting a wait, so the rule as written instructed the dispatcher not to resume a genuinely stalled implementer, while the gate runner claimed the ticket and spent the claim refusing a dirty tree. Everywhere else this gap reached, the playbook merely failed to produce the right action; here it produced the wrong one.* The Implementer section's *Never background a check and end your turn on it* is the rule that stops it happening; this is how you recognise it when it does.
- **⚠️ But a wait on *review* sub-agents is now an ALARM, not a self-suspension — this inverted.** `/pipeline:review` runs **inline and spawns nothing**, so an implementer reporting that it is waiting on reuse / simplification / efficiency / altitude review agents did not run this plugin's pass. It ran the bundled `/simplify`, whose reviewers fork — and a fork inherits the implementer's whole brief, whose imperatives end in *commit, push, open a PR, enqueue the gate*, which those reviewers then carry out. Treat that phrasing as a signal to go look at the worktree, not to wait: check whether anything committed, pushed, or opened a PR that the implementer did not decide on. Fix it by naming `/pipeline:review` in the brief (see the review-pass bullet above), not by waiting longer.
- **A task that FAILS with "Agent stalled: no progress for Ns (stream watchdog did not recover)" is an INFRA stall, not a behavioural one.** The model made no bad choice — its stream died mid-turn. Nothing is lost: the worktree (including uncommitted work) persists, and a resume message to the SAME agent restores its full context from the transcript AND delivers any notifications that queued while it was down. Resume it firmly, restating where it was and the exact remaining finish-order (… → scoped check → review pass → commit blocks → push → draft PR → enqueue → report) plus "if you stall again, committed+pushed work is durable — resume from the furthest completed step." These stalls can cluster (one epic saw every parallel implementer hit one within an hour); each costs one resume, never a redispatch. The same resume verb also un-sticks a *genuine* behavioural stall (turn ended, worktree full, no PR — **and** none of the legitimate-self-suspension signals above) — but confirm it's actually stuck before resuming, because that description also fits an agent legitimately paused on **sub-agents it spawned**. It does NOT fit an agent that says it is waiting on a check it backgrounded — that one is the stall itself, and it is a resume (bullet above).

Carry forward a one-line note of each agent's last-known on-scope file set in the next wakeup prompt, so a sudden jump in surface area is obvious tick-over-tick.

### Draining the gate queue
On each `ScheduleWakeup` tick (the *same* timer you already run for divergence), run `drain` (Trinity: `pnpm gate:drain`) from the main checkout. One pass re-delivers any verdict a previous pass decided but failed to post, then claims queued tickets and, for each, runs the full `gate` in that ticket's worktree behind the slim machine-wide slot, then comments the verdict on the PR — a pass on green, the failing tail on red — and leaves it draft either way. It is a one-shot pass — it drains what's queued and exits — so the tick re-invokes it.

- **Size the drain to the fan-out — with ONE slice in flight it is near-dead weight on the tick.** This rider is shaped for a fan-out, where several slices enqueue at unpredictable times and draining steadily beats letting the queue pile up behind a serialized gate. A single slice enqueues once and hands back immediately after, and **that hand-back is a notification you get for free** — so drain on the hand-back, and let the tick's drain cover only the case the notification cannot: the agent dying between `enqueue` and handing back. Leave it on the tick either way (an empty queue drains in seconds), but never let its presence there stand in for the divergence check. *The failure this prevents: a dispatcher that has come to read the tick as "the drain timer" runs the drain, sees an empty queue, and files the tick as done without diffing a single worktree — keeping the half that costs nothing to skip and dropping the half that costs a whole run.*
- **A full drain can be long** (each ticket is one serialized full gate), so bound a big queue with `drain --max N` per tick, and back it with the harness `run_in_background` flag if you would rather not hold the turn open for it. **What its completion is NOT is a signal about your own tickets — never wait on it.** A pass loops until the *queue* is empty and the queue is machine-wide, so while other sessions keep enqueuing, that exit lands whenever their tickets run out, which can be hours after yours settled. And the bullet below against stacking a second drain on a live one makes the other road just as ordinary: your ticket is gated by another session's runner, and then there is no completion event of yours in this session at all. Don't fire a drain and abandon the loop either way. *The failure this prevents: a drain's exit is neither necessary nor sufficient for the thing a dispatcher is actually waiting for, and it is silent in both directions — you sleep through a verdict that landed twenty minutes ago, or you wake on an exit that gated somebody else's tickets and read it as news about your wave.* The signal that IS yours is the ledger watch in *Wait on your own tickets settling — one Monitor over the queue's ledger* below.
- **Multiple dispatchers may drain concurrently — "is a second drain safe?" and "is a second drain useful?" are different questions with different answers.** Safe, yes, by construction (atomic-rename claims, dead-claimant reclaim), so concurrent drains from *different* dispatchers are fine and expected; you don't coordinate, you both just drain. On a machine-wide queue that guarantee is load-bearing rather than incidental, which is why a runner waits on a held slot instead of refusing. Useful, no: stacking more drains from *the same* dispatcher buys nothing, because one pass loops until the queue is empty. So **one drain per tick**, riding the divergence timer, and never a second on top of one already running — and when you want to know the queue's state rather than work it, that is `drain --status`, not another drain. `skills/setup/references/gate-queue.md` invariant 9 carries the mechanism and the incident behind it.
- **"Is the queue contended?" and "is this gate advancing?" are different questions, and `--status` answers only the first.** The process list is the wrong instrument: `pgrep gate-runner`, or an elapsed clock off it, answers "is a process there" — never the question asked, because a runner gating a ticket and a runner blocked on another session's slot are the same live process with the same growing elapsed time. A waiting runner may already be announcing the contention — invariant 9 has it print the holder on a failed acquire — but onto its own stderr, and that runner is the backgrounded process two bullets up. Correct, recorded, and in the wrong process, which is why the read-only mode is the load-bearing half. What `--status` answers is **ownership** — queue depth, which tickets are claimed by which runner, who holds the slot — and its counts are two facts, not one: `queue: 0` says nothing is starved, `processing: N` across N distinct pid suffixes says every claim is owned, that suffix being the ticket-to-process join key `ps` cannot give you. No queue state answers **movement**: the queue records that a ticket is claimed, never how far along its gate is. For that, read the gate's own children inside that ticket's worktree — the build and test processes it spawned. Counts plus live children is the pair that yields "step 3 of 6, in `<package>`". The same instrument already governs the other actor — see the stalled-implementer test in *Dispatch in the background, then monitor for divergence*: read the work, not the clock. The drain is the one place that lesson was never applied. *The failure this prevents: a dispatcher read ~26 minutes of elapsed runner time as a stall when it was a claim held behind another session's gate — the process list cannot separate the two, and the announcement that would have said so sat in a backgrounded process nobody was reading.*
- **And on a runner that predates invariant 9, `--status` does not fail — it DRAINS.** `/pipeline:setup` scaffolds the queue INTO a project and the project owns it from there, so a project scaffolded before invariant 9 has a runner that never implemented the mode, and the unrecognised flag falls through to an ordinary drain pass. Observed: an operator ran `drain --status`, got `drained 0 ticket(s)`, and caught it only because the output *shape* was wrong — nothing errored, and nothing would have. That inverts the instruction above on exactly the projects most likely to still be running an old runner: the rule added to stop a dispatcher reaching for an unwanted drain is what fires one, while it is trying not to. **Read a `--status` whose output looks like a drain as evidence that it WAS one.** The portable instrument is the queue directory, portable precisely because every transition is a filesystem rename by construction: `ls` over `<queue-root>/<project>/queue` and `<queue-root>/<project>/processing` gives the same two counts and the same pid suffixes, claims nothing, and contends for nothing. `skills/setup/references/gate-queue.md` invariant 9 obliges a runner without the mode to reject the flag rather than fall through, but a project scaffolded before that carries no such guarantee and the flag alone cannot tell you which you are holding. *The failure this prevents: the obvious remedy for the misread above — "just run `--status`" — silently IS another drain wherever the mode was never implemented, so the dispatcher arrives at the mistake invariant 9 documents by following the instruction added to prevent it.*
- **Don't hand-run `gate` on top of a live drain — and in a project whose runner takes every ticket there is nothing left to hand-run.** The runner already serializes gates one-at-a-time behind the slot; launching your own concurrent `gate` re-creates the saturation the slot exists to prevent. Let the runner be the only thing gating. The two gates a dispatcher used to launch itself — the mid-arc integration gate and the epic's close-out gate — are both enqueued now (*Gate the integrated whole*), so on a runner that takes both tickets this is a case that cannot arise rather than one you have to remember. **That is also what removes a pre-flight nobody had.** Slot contention is invisible until you have already committed to a gate: a waiting runner announces the holder only on a *failed acquire*, onto its own stderr, in the backgrounded process nobody is reading — and the only other way to ask is `--status`, which on a runner scaffolded before invariant 9 silently drains. So the careful version of "check who holds the slot before gating by hand" was itself a hazard; not gating by hand dissolves the question instead of answering it.

  ⚠️ **On a runner that predates the PR-less ticket the case comes back, for the mid-arc gate alone, and the dissolved question comes back with it** (*Gate the integrated whole*, at *A runner scaffolded before the PR-less ticket REJECTS it*). That fallback is precisely this bullet's shape — a hand-run gate in a project that has a queue — so the pre-flight the paragraph above retires is one you are back to needing, on the projects least able to answer it: run the gate when nothing is draining, never on top of a live one, and establish that by **reading the queue directory** rather than by asking `--status`, which on that same vintage of runner is itself a drain. *The failure this prevents: the two instruments for "is anything draining" are the two this file already records as unreliable, and the reasoning that retired the question assumed the hand-run gate was gone — so a dispatcher arriving here from the refusal finds a bullet that says its situation cannot happen.*
- **A worktree whose ticket has not SETTLED is FROZEN — don't mutate it, don't remove it. The test is the ticket's existence, never whether a gate is observably running.** Queued and unclaimed freezes the tree exactly as processing does, because a claim is an atomic rename and can land between the moment you check and the moment your fix agent makes its first edit — so a ticket in *any* non-terminal state, `queue/` or `processing/` alike, is a live hazard. The runner gates *inside that ticket's worktree*, so anything that changes the tree mid-gate makes the verdict meaningless: the gate tests a tree that no longer exists, then posts its result against whatever HEAD is current when it finishes. Observed failure: a drain was already running when the dispatcher reviewed the diff and dispatched a fix agent into that same worktree; the agent committed at 22:34:37, and the gate — a ~2m20s run — posted `✓ passed` at 22:34:38. Green, against code no gate had ever seen. Since a gate comment is exactly the evidence this workflow reads as "gated", trusting it would have merged untested code. Wait for the ticket to settle — its verdict comment on the PR, either direction, or its arrival in `done/` when there is no PR to comment on — before you dispatch a fix agent, remove the worktree, or touch anything inside it. This is *why* the review order below is review-first-then-drain.

  ⚠️ **The queued window is the NORMAL state, not a rare one — it is exactly where a slice sits the moment its implementer hands back**, which is precisely when *The PR review loop* sends you to dispatch a fix agent. Two individually correct instructions compose into it: the handoff enqueues *before* it hands back, and *Review BEFORE you drain, never after* deliberately leaves the ticket in the queue while you read the diff. So the state this rule is most often read in is the one an "is a gate running" reading does not cover, and checking `processing/` is not checking anything. *The failure this prevents, observed: a dispatcher who had read this rule checked `processing/`, found its ticket absent from it, and dispatched a fix agent into a worktree whose ticket sat queued. A runner claimed it mid-edit and refused — the tree carried uncommitted tracked files, so a gate there would have judged a tree no commit held. Nothing was damaged, and that is the shallowest reading available: the refusal came from the runner's own uncommitted-files detector, which is a property of one project's queue rather than of this rule. A queue without that detector gates the moving tree and posts a verdict indistinguishable from any other — naming a SHA that may still match the PR head, so the "compare the comment's SHA against the head" check passes too, and the false green survives every reading this flow has.*
- **A red ticket is dispatcher feedback, not lost work.** The PR stays a draft with the failure commented. Read it, dispatch a fix agent into that same worktree, and the fix re-pushes and re-enqueues. Nothing is stranded. (Safe here precisely because the ticket has already resolved — the gate is no longer running in that tree.)
- **A PR with NO gate comment has not been gated — never treat it as red.** The comment is the whole reading: a pass comment is green, a failure comment is red, and no comment means the gate never reported. Do not dispatch a fix agent against a bare PR — there is no failure to fix. A queue that records its verdicts (invariant 7 in the gate-queue reference) self-heals this on the next drain, which reconciles undelivered verdicts before claiming anything, so **run the drain and look again** before concluding anything. If it is still bare after a reconcile, the gate genuinely never ran: re-enqueue it. Observed on a real slice — a runner claimed a ticket, ran a full gate, and retired it with nothing posted; the PR sat with no verdict for 37 minutes until it was re-enqueued and gated a second time.
- **Reconcile the local integration branch on every tick — the cheap backstop for a dropped sync.** Even though `merge-pr.sh` fast-forwards the local integration branch at merge time, a hand-run merge or an interrupted close-out can leave it behind the remote, and the next worktree would then fork off a stale HEAD. On the same tick as the drain, run one anchored fast-forward against the main checkout: `git -C <main-checkout> fetch origin && git -C <main-checkout> pull --prune --ff-only` (a no-op when already current). It's idempotent and near-instant, so any missed post-merge sync self-heals within one poll instead of poisoning the next dispatch.
- **Sweep for outstanding parked work on the same tick — both places it can be.** Agents park under a named ref, so the first call is the authoritative one, and the second only catches work that reached the shared stack anyway:
  ```sh
  git for-each-ref --format='%(refname) %(contents:subject)' refs/pipeline-stash
  git stash list --format='%gd %gs' | grep -F 'pipeline-stash/'
  ```
  Run either against the main checkout and it covers every live worktree at once: both namespaces live in the repo's common gitdir, not in a tree (*Hard rules* carries the park/restore commands and the marker format that make an entry attributable). While agents are live a hit is context for the divergence check — whose it is, and whether that slice is parked mid-turn. **When the fleet is quiet a hit is a defect to chase, not noise to ignore**: it means an implementer ended its turn with work its own worktree teardown will not carry. A named ref at least says whose it was and restores with one `git stash apply`; a stack entry left behind after its tree is gone is one nobody can attribute well enough to pop safely, which is the asymmetry the named ref exists for.
- **Running an epic branch? Merge the integration branch into it on this same tick — in the epic's own worktree.** Nothing to do when there is no epic branch, which is most of the time. When there is one:
  ```
  git -C <epic-worktree> fetch origin
  git -C <epic-worktree> merge origin/<integration-branch>
  git -C <epic-worktree> push origin <epic-branch>
  ( cd <epic-worktree> && <install> )
  ```
  Merge, never rebase. This is the mandatory mitigation for the epic branch's one real cost — deferred and concentrated conflicts (see *The epic branch*) — and it only stays cheap while the slice authors are still live to resolve what it surfaces. The push is what puts the merged base where the slice worktrees fetch it from; without it the drift is reconciled only in the epic's own tree and every live slice still forks off the old epic tip. Nothing here touches the main checkout, so this bullet no longer depends on the reconcile above having run and no longer has a step to undo. A conflict is the tick doing its job — resolve it, commit, and push before you walk away (*The epic branch* → *Mechanics*).

  **That fourth line is the project's own `install`, and it runs UNCONDITIONALLY — but never while that tree has an unsettled ticket.** `install` is already a config key (*Per-project config*), so this is the same command `setup-worktree.sh` ran when the tree was cut, and a project that declares none — this repo is one — has nothing to run, making the step a no-op rather than an error. It belongs on this tick for the reason *The epic branch* → *Mechanics* gives: the epic worktree's dependencies fall behind the branch it holds the same way its git state does, and this is the tick that already exists to keep it current. The one thing that defers it is the rule the section already states, applied unchanged: an install rewrites the tree's dependencies wholesale, which is a strictly larger mutation than the edits *A worktree whose ticket has not SETTLED is FROZEN* bans — so if that tree has a ticket outstanding in any non-terminal state, **queued as much as claimed**, whether from a drain or from a gate you enqueued against it yourself, wait for it to settle and install on the next tick. *The failure this prevents: the epic worktree's own close-out ticket sits queued from the moment you enqueue it until a runner claims it, and this tick fires on a timer that knows nothing about either — so a rule keyed on a gate being observably live licenses the largest mutation in the flow during exactly the window the enqueue just opened.*

  **The conditional version is the trap, and it is the one that looks cheaper.** Keying the install to the cadence merge's own diff — `git diff --name-only ORIG_HEAD..HEAD` against the project's lockfile and workspace manifest — misses the very case that produces the failure, because a new package does not arrive through this merge at all. It arrives through a **slice close-out**: `merge-pr.sh` fast-forwards the epic branch inside this same worktree on every slice merge (*The epic branch* → *Mechanics*), and a fast-forward sets `ORIG_HEAD` too, so that range is unreliable from both directions — it misses what the close-outs brought in, and names as new whatever the last close-out happened to move past. A conditional that actually held would have to compare the tree's *installed* state against the branch, which means an **install stamp**: a new `.agents/worktree.json` key plus matching changes to `setup-worktree.sh` **and** `setup-worktree.ps1`, under the frozen helper contract (`AGENTS.md` → *The frozen helper contract*). Weigh the two failure modes rather than the two runtimes. The stamp's is a missed trigger, which silently reintroduces this exact bug and looks like nothing at all; the unconditional install's is the 1.2 seconds the report measured, on a tick already dominated by serialized gate runs.

  *The failure this prevents, observed: a slice created a workspace package, registered it in the workspace manifest and updated the lockfile, and its PR merged into the epic branch — while the epic worktree's `node_modules`, installed when that tree was cut at the start of the epic, still had no link for it. The integration gate run in that tree failed on five files across two apps with `TS2307: Cannot find module`, with no code defect anywhere, and a 1.2s `pnpm install --frozen-lockfile` there turned it green. Nothing about the worktree looked wrong while it was in that state: `git status` was clean, and the tree it held was exactly the branch it was supposed to be holding.*

### Wait on your own tickets settling — one Monitor over the queue's ledger
The bullet above says what a drain's exit is not. This is the signal that actually belongs to you: **one persistent `Monitor`, armed once per wave, polling the gate queue's `done/` ledger and emitting one line per settlement that belongs to this wave.** Arm it in the same breath as the wave's dispatch, beside the divergence tick, and it is what lets you stop spending ticks on "has anything been gated yet".

**The wave is the unit — not the ticket.** One watch per in-flight ticket looks tidier and breaks the first time a PR needs work: a fix agent re-pushes and **re-enqueues**, so a ticket exists that no per-ticket watch was ever armed for. Anything keyed to the set of tickets live at arm time is stale the moment the wave moves. Key on the wave's **branches** instead — the same set the divergence tick already carries — and every re-enqueue is covered for free.

**Scope on the fields the ticket is guaranteed to carry, and emit on SETTLED rather than on a verdict.** `skills/setup/references/gate-queue.md` pins the enqueue shape as `{ branch, worktreePath, prNumber, prUrl, mode }`. The verdict facts invariant 7 requires — the outcome, the exit code, the failing tail, the gated SHA, whether the report was delivered — are specified there as *facts the ticket carries*, not as key names, so their spelling belongs to each project's runner. So the watch reads `branch`, plus `prNumber` for the handle it prints, and nothing else; you read the verdict off the ticket and the PR once you are awake. *The failure this prevents is the one the two `--status` bullets above record in another guise: an instrument written against the project it was born on, correct there and silently wrong on a project scaffolded earlier — and a watch that never fires is indistinguishable from a wave that has not settled yet.*

**Watch the ledger, not the PR.** A verdict exists in `done/` before it exists as a comment, and invariant 7 is exactly the rule that lets those two come apart: the runner records the verdict on the ticket *before* it attempts to post, so a failed post leaves a settled ticket whose comment never landed. *The failure this prevents is recorded a few bullets up — a PR that sat with no verdict for 37 minutes after a runner had gated it and retired the ticket with nothing posted.* A watch on the PR comment sleeps straight through that; a watch on the ledger wakes on it, and waking is what gets the reconciling drain run — a pass that posts a verdict already decided and never re-gates. *A PR with NO gate comment has not been gated* is the reading to apply once you are awake.

**The shape.** Poll the ledger, remember the ticket files you have already reported, and print one line per new arrival whose `branch` is in the wave:

```sh
DONE="<queue-root>/<project>/done"        # the ledger; the gate-queue reference has the layout
SEEN=$(mktemp)                            # the seen set, one ticket path per line
find "$DONE" -name '*.json.*' > "$SEEN"   # prime: what is already there is history
while true; do
  find "$DONE" -name '*.json.*' | while IFS= read -r t; do
    if grep -qxF "$t" "$SEEN"; then continue; fi
    b=$(jq -r '.branch' "$t" 2>/dev/null)   # unreadable now; retried next pass
    if [ -z "$b" ]; then continue; fi
    echo "$t" >> "$SEEN"
    case "$b" in
      feat/slice-a|feat/slice-b)            # this wave's branches, exactly as enqueued
        echo "settled: $b  PR $(jq -r '.prNumber // "none"' "$t")" ;;   # PR-less ticket: the branch is the handle
    esac
  done
  sleep 5
done
```

Every part of that shape is load-bearing, and it opens on the shell you will actually paste it into — the harness runs a `Monitor` command in the session's shell, which on macOS is **zsh** by default. **The seen set is a FILE, and never a shell string the loop appends each ticket path into**: in zsh a `[` immediately after a parameter expansion — `$var[` — opens an array subscript, so a string accumulator written the obvious way makes the shell evaluate a ticket path as a math expression, and the watch dies with `bad math expression: operand expected` before it ever reaches the loop. **And the ledger is enumerated with `find`, never with a bare glob**: zsh's default `nomatch` makes an unmatched `"$DONE"/*.json.*` a fatal error rather than a literal, so a watch armed while `done/` is still empty — the ordinary state at the start of a wave on a fresh queue — dies for a second reason, and it dies before the kind of `[ -e "$t" ]` guard that makes a bare glob safe under POSIX `sh` ever gets to run. Being a file rather than a variable is also what lets the loop body sit on the right-hand side of a pipe, since the subshell's writes reach the parent where a variable's would be discarded with it. *The failure both of those prevent is the one this whole subsection exists to stop, and* Silence from this watch means nothing settled *spells it out: a watch that dies at arm time produces exactly that silence, its one error notification arrives at arm time and scrolls past, and after it a dead watch and a wave with nothing settling are indistinguishable — which is the state a dispatcher arms this instrument to get out of.* **Prime the seen set before the loop** — `done/` is a durable ledger holding every settlement this machine has made and not yet pruned, so an unprimed watch replays that whole archive as this wave's news on its first pass. **Dedupe on the ticket file, never on the branch** — a branch that goes red, takes a fix agent, and re-enqueues settles twice, and the second settlement is the one you are waiting for. (Read the JSON, not the filename: the claim suffix `done/` keeps is a runner's PID, not a ticket identity you can parse a branch out of.) And **read the ticket before you mark it seen**, which is why the append sits below the `jq` rather than above it — a ticket caught mid-write is unreadable for one pass, so marking it first retires it unreported, where reading first simply lets it come round again.

**A few seconds is the right interval, and it is not the tick's question.** Each poll is a local directory listing plus a small JSON read, so running it often costs nothing — where the ~10-minute cadence in *Dispatch in the background, then monitor for divergence* is a cadence for reading **worktrees**, which is expensive and is answering something else entirely. **So do not put this on that tick, and do not give it that tick's period.** The tick keeps its one job and its two riders; this is a separate instrument, not a third rider. *The failure this prevents is the one the drain rider already names: a dispatcher that comes to read the tick as a list of commands to run stops diffing worktrees, and the divergence check is the half of the tick whose skipping costs a whole run.*

**Silence from this watch means nothing settled — never that the wave is healthy.** It fires on arrival in `done/` in both directions, because a red settles exactly as a green does and a red is dispatcher feedback you want at once. What it structurally cannot see is a ticket that never settles: a runner that dies mid-gate has its ticket reclaimed back to `queue/` (invariant 2) and re-gated later, which is not a settlement and produces no event, and a ticket nobody ever drains produces none either. So this is a wake-up, not a liveness check — the divergence tick stays the thing that notices a wave that has stopped moving, and the queue directory (or `--status`, with the caveat in *Draining the gate queue*) stays the thing that says where a ticket actually is.

**⛔ This is a DISPATCHER instrument, and an implementer must never arm one.** Sitting under `## Dispatcher` is not the scoping — this sentence is. The Implementer section's *Never background a check and end your turn on it* forbids precisely this shape for an implementer, and nothing here softens it by so much as a word. The asymmetry is structural rather than a matter of rank: an implementer has a **durable handoff** — push, draft PR, enqueue — which is what makes the wait unnecessary there, and the ticket it just enqueued is by design somebody else's to watch. A dispatcher has no handoff to end on; it holds the merge decision the settlement feeds, so it is the one party in the run for whom that event is not somebody else's business. Read the two together and they agree: *the implementer's turn ends at the hand-back, and the dispatcher's turn is what the hand-back hands to.* And *Dispatch in the background, then monitor for divergence*'s stall-recognition bullet is unchanged by this — it reads a wait reported in an **implementer's hand-back** as a stall to resume, which is still right, because that agent has a handoff it has not made; a dispatcher's own watch is not a hand-back and was never in that bullet's scope. *The failure this prevents: read as a general licence to wait on a process, this subsection repeals the foreground rule for the role that cannot afford it, and the behaviour it would license is the observed run where a complete change sat uncommitted behind a backgrounded `scopedCheck` with no commit, no push, no PR and no ticket.*

**Tear it down at close-out with `TaskStop`.** The queue cannot tell you when your wave is over: the last settlement is not the end of it, because a red settles too and the wave ends when you have merged — a decision you make, which nothing on disk can see. That is why the watch has no exit condition of its own and why `persistent: true` is right; the counterpart is that its lifetime is yours to end. *The failure this prevents: a watch left armed past its wave scopes on branches that no longer settle, so it goes quiet — and quiet from this watch is indistinguishable from a wave with nothing settling yet, which is the same ambiguity the coverage rule above warns about, arriving through a watch you forgot instead of a ticket that stalled.*

### The PR review loop
Each implementer opens **its own draft PR** back to the branch its worktree was cut from — the integration branch, or the epic branch when the epic has one; the runner comments the gate's verdict on it. That comment is the gate signal, and it is all the gate can tell you — the PR stays draft until *you* merge it, because marking it ready is your signature that you read the diff. So **review each PR and actually read the code involved**, not just the agent's summary or the green comment. Read the diff: verify correctness, that it does what the issue/plan intended, that the scope is right, and scrutinize anything the agent flagged or where it went wider than the planned files. A green gate and a confident agent report are necessary but **not sufficient** — the merge decision is yours and must be grounded in the actual changed code.

**A hand-back report is evidence about its own half and hearsay about the other.** An implementer can tell you what it built; it cannot tell you what its counterpart now expects, because it never saw the counterpart. So for any pair the decomposition flagged as a **contract seam** — one slice produces a shape another consumes — reading each diff on its own is not review, it is two half-reviews. **Diff both halves against each other before merging either**, and check the specific thing: the shape the producer now emits against the shape the consumer now reads. **And where that shape is a status, flag or state value, the two halves agreeing on it is not the whole check — read what the consuming side DOES with it.** A consumer that only filters is safe; one whose read drives an action is where the break is, because the action may be computed from a snapshot taken before the producer's value could exist. Both PRs will be green — each gate only ever exercised one side. *The failure this prevents: perfectly file-disjoint slices, zero merge conflicts, and several genuine cross-slice breaks that no single PR's gate or hand-back could have surfaced.* When the producer has merged and the consumer has not, the consumer's next re-gate catches it; when they merge in the same drain, nothing does.

**Review BEFORE you drain, never after.** Reviewing is where you decide whether the code changes, so draining first is both wasted (a full serialized gate burned on code you're about to replace) and *unsafe*: the fix agent you dispatch next would edit a worktree with a gate still running in it, which produces a green that corresponds to no commit (see *Draining the gate queue*). The order per PR is: implementer hands back a **draft PR + an enqueued ticket** → **you read the diff first** → needs changes? dispatch the fix agent **now**, before any drain — it re-pushes and re-enqueues → re-review → only once the code is final do you drain, so the gate verdict corresponds to the exact commit you're going to merge. Then verify that correspondence explicitly before merging: compare the SHA the gate comment names against the PR's current head, since a verdict that predates the last push describes a tree the PR no longer carries.

**Review the implications, not just the brief.** A PR can match its slice's brief, pass its own gate, and stay perfectly in scope — and still be wrong once it lands among its siblings. Read for *second-order* effects, not only local correctness: (1) **cross-slice composition** — when two slices each own one half of a contract (slice A stamps a header, slice B reads that header for the credential; one slice renames/derives a field, another consumes it), confirm the halves still agree *on the merged branch*, even though the files are disjoint. (2) **shared global state** — a change that's correct in isolation can be silently defeated by a process-wide cache, singleton, or memo it didn't author (does that cache key on the value you just made per-tenant, or globally?). (3) **emergent interactions** — a fix that corrects one path can expose or shift a neighbor's behavior (tightening identity makes a queue correctly *wait* instead of mis-running; a now-required field surfaces a caller nobody listed). File-disjointness buys *textual* independence, never *semantic* independence — so the review asks "what does this imply for everything it touches indirectly?", not just "does it match the brief?". When a second-order effect is load-bearing, go read the shared dependency yourself (the cache, the consumer, the sibling's half) rather than assuming it composes.

**And the spot check you run to test a claim is an instrument, not a verdict — read the dependency at the level production reaches it.** Calling a module's function directly, below whatever preprocessing its real callers go through, is evidence about that function and not about the pipeline, so a correction you send on that basis is a claim of exactly the same kind as the one you are correcting. Check the call path before you send it, and read a push-back that answers with a call path as the work rather than as resistance to review. *The failure this prevents, observed while auditing the fix for this very defect: a dispatcher doubted a corrected comment, called the consumer's matcher itself to check, and told the implementer the comment was false — the preprocessing step sat a layer above what it had called, the comment was true, and the implementer that pushed back with the call path was right. The same error, in the opposite role, twenty minutes apart. That is the strongest evidence available that "call the real consumer" cannot be left to either party's judgement, and it is why the instrument is named in the verify bar at grounding time (`skills/decompose/SKILL.md` → `Verify`) rather than argued about here — a reviewer who improvises the instrument reproduces the defect it is reviewing, and its correction arrives carrying a reviewer's authority.*

**Check the docs before you flip it ready — every PR, not just the ones that look documentation-shaped.** The implementer's report carries a per-doc verdict; read it against the diff rather than accepting it, because the implementer can only report on docs it thought to look at. Ask the question yourself from the diff: what does this change make true, or stop being true, for someone who reads the docs instead of the code? Then check that the docs saying otherwise are in this PR. A missing docs commit is a fix-agent round trip, not a merge blocker to argue about — but it is caught *here*, because after the merge the only thing that surfaces it is a user acting on something that stopped being true. **The failure mode to watch for is your own:** if you scoped a doc out of the brief, you did it from the plan rather than from the diff, so re-derive it now from what actually changed. That is exactly how a stale README ships — not because the implementer skipped it, but because it was told not to look.

**The review pass's rejected findings are addressed to YOU and reach you by one route only — read them, and read a hand-back that carries none against your own brief before you read it as a clean pass.** `/pipeline:review` runs inline inside the implementer, so its `Rejected` list — each finding that implementer considered and deliberately did not act on — is written for the reviewer of this PR, and the hand-back is its only way here. `skills/review/SKILL.md`'s Output section names that reader itself — *the dispatcher reviewing your PR has no way to tell the difference* — which is you, holding this diff. A rejection you disagree with is a fix-agent round trip; one you agree with is the cheapest evidence in the run that the diff was reasoned about rather than typed, and it is evidence no gate and no diff can produce. **When the list is absent, the blank is two different facts wearing one face, and you are the only party who can tell them apart** — a slice you told to skip the pass has no findings by construction and the blank is correct, while a slice that ran it and forwarded nothing is indistinguishable from one whose pass raised nothing, which is the exact indistinguishability that list exists to remove. So check the review decision you made in the brief, then read the silence: correct where you skipped it, a round trip where you did not. *The failure this prevents: the pass runs inside the implementer, so the only agent that read why the list is written is the one whose turn ends before you look — and a finding rejected on a reasoning you would have overruled is, from here, byte-identical to a finding nobody ever raised.*

**A report that names unfinished work hands YOU the next move, not the user.** A hand-back is allowed — required, even — to say what it did not land. The item stops with you: your moves are a fix agent into that same worktree, a resume message to the same implementer, or a filed and linked issue folded into the wave plan (*Hard rules* — the follow-up-ownership rule binds you exactly as it binds the implementer, and *The epic branch* says which branch the follow-up targets while one is live). **Forwarding the list to the user is the same defect one level up**, and it is worse from here: you are the only party in the run holding the decomposition, the sibling slices, and the wave plan the item has to be placed against, so a triage you decline is a triage nobody in the run can do. *The failure this prevents: a close-out summary reading "the implementer flagged X, Y and Z for follow-up" ends the run with three untracked defects and a user who has to reconstruct the whole slice to triage them — while every artifact in the run, the green gate and the merged PR included, says the work is done.*

**Two artifacts of every PR sit outside the diff — the commit messages and the PR body — and attribution is the one thing that lives in exactly those two. Read both before you flip it ready.** `git diff` shows the code and shows neither, so nothing you read *for* the diff can catch attribution and it has to be its own read — the gate judges a tree, the docs check works from the diff, the SHA comparison works from a comment, and not one of them opens either artifact. Read for the **class** and not for the strings any brief happened to name — a trailer, line, footer or URL naming Claude, the assistant, the model, the harness, or the session the work ran in — because the harness's set is extended from outside any repository's control, without notice, so the brief that briefed this implementer may have been written before the form it was handed mid-run existed. **A clean PR body and a PR body nobody opened are the same blank page, which is why this is a read you perform rather than an absence you notice** — nothing about compliance reports itself, and there is no artifact anywhere whose presence would tell you the question was asked. **The one PR where you are both author and reviewer is the one that most needs this**: the epic → integration close-out has no implementer behind it (*The epic branch* → *Mechanics*), so no brief ever carried the ban to the party that wrote its body, and that party is you. Timing is the whole value of catching it here: before the merge this is a fix-agent round trip on a branch nothing else has been built on, and after it a trailer is permanent history in a flow that never rebases, while a PR body in a public repository has already been published. *The failure this prevents, observed: the harness began emitting a session-id commit trailer and a bare session URL mid-run, announcing that they replaced earlier attribution guidance. The implementer reasoned from the enumerated ban it had been given, correctly concluded the URL was not on it, and kept it; the URL shipped into a public repository's PR body and was removed by hand, by a dispatcher that happened to notice. The brief-side wording is fixed and is still one party's judgement at one moment — this is the second reader every other implementer output already has.*

**Diff against the merge-base, not the integration tip.** The integration branch advances *while a worktree is open* (other agents' PRs merging in parallel), so `git diff <integration-branch>..HEAD` shows the OTHER work's additions as phantom **deletions** in this PR — a clean change then looks like it ripped out unrelated code, and you'll raise a false alarm. Always diff the fork point: `git -C <wt> diff $(git merge-base HEAD origin/<integration>)..HEAD` (re-`fetch` first — the tip moves). Confirm by test-merging the current base in: if the "deleted" files come back as *additions*, the PR never touched them. This bit us once — burned a review cycle chasing a "destructive deletion" that was just the base having moved.

If it needs changes, **dispatch a fix agent into that same worktree** — but only once that worktree's ticket has SETTLED, or was never enqueued. **Not "once no gate is running in it":** a ticket sitting **queued and unclaimed** freezes the tree exactly as a claimed one does, and queued is the state a slice is in the moment its implementer hands back — which is this step, reached from a review you were told to run *before* draining. So the check that feels sufficient here, looking for a live gate, is the one that structurally cannot see the hazard: the claim is an atomic rename and lands between your look and the agent's first edit. *The failure this prevents: a gate that judges a moving tree posts a verdict indistinguishable from any other — and on a SHA that may still match the PR head, so the SHA comparison **Review BEFORE you drain, never after** closes on passes as well, and nothing left in the flow can catch it.* *Draining the gate queue* carries the operative rule and the observed failure. Once the ticket has settled the fix agent re-pushes and re-enqueues, and the runner re-gates. Iterate until the PR is good and green. Only when satisfied do you **merge and clean up** — and the *order* matters because of worktrees (see next section): the implementer has already pushed everything, so you **remove the worktree first**, then merge with `gh pr merge --merge --delete-branch`.

**In in-line gate mode your satisfaction is not the only precondition on this step — the implementer's hand-back is.** A gate comment there was posted by the agent itself, before its hand-back and through a channel you are already watching, so it says a gate finished and nothing about whether that agent is still working — and this step is the one that tears down the tree it may still be standing in. *Dispatch* → **Gate mode for this slice** carries the rule, both directions of the misreading, and the observed failure; wait for the hand-back before you remove the worktree or merge.

### Merging a shared hotspot — `mergeable` ≠ correct
When several slices edited the **same function or structure** (a control loop's `tick()`, a reducer, a registry, an exhaustive switch — anything the decomposition flagged as a *shared hotspot*), a clean auto-merge is **not** proof of correctness. Git merges by line: two slices that added code in *different* spots produce `mergeable: MERGEABLE` with no conflict markers — but git has no idea the two additions must **compose**. The recurring failure shape: a structure has sibling branches that must stay **twins** (e.g. two "parked → freeze every kill-clock" branches), each slice added its new clock's freeze-line only to the branches that existed *when it forked*, and the merge silently leaves the newer branch missing it — textually clean, behaviorally a reaper that kills a healthy job. **The integration gate won't catch it** unless a test exercises that exact cross-slice interaction, which is precisely the case nobody wrote.

So whenever a merge — auto-clean OR conflicted — touches a structure 2+ slices edited: **open the merged region and read it; do not trust `mergeable`.** Diff the parallel-edited siblings against *each other* — whatever should be parallel (twin branches, every case of a switch, all handlers of an event, the reducer vs the renderer) must have received the **same** treatment from each slice. Honor the **shared invariant** the decomposition handed you, if any. Fix drift forward as a small, clearly-messaged merge-reconcile commit, then re-verify the interaction — enqueue an integration gate, PR-less if the merged tree has no PR (*Gate the integrated whole*), and run one directly only where there is no queue to put it in **or a runner that refuses the PR-less ticket** — two conditions, because a project with a working queue can still be the second (*Gate the integrated whole*). Resolve actual conflicts by **merging the branch's own PR base into it, in its worktree** (`git fetch && git merge origin/<the PR's base>`, keep BOTH concerns) — never rebase. Merge the base the PR actually targets, not the integration branch by reflex: for a slice based on an epic branch those are different branches, and merging the integration branch straight into the slice drags in commits the epic has not converged on, defeating the isolation the epic branch is there for. Then push and `gh pr merge`. And if you park the tree to clear it for a resolve, **this is the moment the shared stack costs the most** — a conflicted merge is reached at exactly the point where several worktrees are guaranteed to be live and pushing onto it, so the entry on top when you come back is the least likely to be yours of any moment in the run. Park under your own named ref instead (*Hard rules*); if you are recovering something already on the stack, re-match it by marker first and never pop blind. Two more conflict-resolution hazards from the field: (1) **lockfile conflicts between sibling PRs are never hand-merged** — take the base's side (`git checkout --theirs pnpm-lock.yaml`), regenerate with the package manager (`pnpm install --no-frozen-lockfile`) so it reconciles ALL merged packages, verify the scoped check, and commit that; (2) **git happily commits leftover conflict markers once the file is staged** — `git add` marks a path resolved whether or not it is, so after ANY conflict edit (especially a scripted one) run `git diff --check` or grep for `<<<<<<<` BEFORE committing; a botched scripted resolution has shipped markers into a pushed branch exactly this way. This bit us twice in one governor epic: two separate textually-clean auto-merges each dropped a parked-state freeze-line, either of which would have reaped a healthy queued job.

### On the gate — the runner gates; you read the diff
**The RUNNER runs `gate` once per PR — that IS the gate.** `gate` is the HEAVY full suite: build + the entire test run, serialized behind the slim machine-wide slot (`scripts/gate-slot.mjs` for Trinity) so concurrent gates can't saturate the box. Implementers don't run it (their commits are held only to the cheap scoped check by the pre-commit hook), and release-branch PRs typically get no CI — so the runner's drained gate is what stands in for CI.

**Per-PR, the dispatcher reads the diff — it does NOT hand-re-run the heavy gate.** The runner's green comment is the per-PR signal; don't duplicate it. Re-gate — **by enqueuing it**, which for a merged tree with no PR is a PR-less ticket (*Gate the integrated whole*), and by hand only where there is no queue or the runner refuses that ticket — only for a genuine reason: the runner never got to a ticket, or a **merge integrates branches that weren't tested together** (one integration gate on the merged result). That second one is not a judgment call — it is `git diff --name-only <merge>^2 <merge>` coming back non-empty, and an empty answer means the merged result is the tree the gate already ran (*Gate the integrated whole* below). Even then prefer the minimum — the affected/changed tests over the whole suite where possible. Your always-on job is reading the **diff**; heavy re-gating is conditional.

**A stale slot self-heals; you rarely touch it.** The slot's holder-PID is liveness-checked, so a crashed gate's slot is stolen by the next drain within a poll, and a runner that dies mid-gate has its ticket reclaimed and re-gated. There is no "strangling orphan" for you to clear by hand and no lock dir to `rm` — the queue and slot handle their own dead work. (If you ever do need to forcibly stop a runner's gate, clear its worktree via `remove-worktree.sh <leaf>`, which signals the processes; never `rm` the slot dir out from under a possibly-live holder.)

### Reading a gate result — verify the WHOLE failure set, and read the comment, not the flags
Two misreads have shipped a red integration branch and closed an epic on top of it. Both are structural and cheap to avoid — internalize them before you ever conclude "green" or merge. A third runs the opposite way and costs the opposite thing: reading an **environmental** red as N code defects, which spends whole runs debugging innocent diffs. The bullet on a PR that arrives without `--draft` is the adjacent bug they make easy to wave through. **All of it is about reading a verdict somebody else POSTED.** A gate you ran yourself has none to read at the moment you need one — you are the party who produces it, if anyone does — so its **exit status** is the reading instead (*Gate the integrated whole* below). Naming that boundary is load-bearing rather than tidy: this section is thorough enough to look complete, so a dispatcher standing in front of a gate log it produced itself finds nothing here that fits its situation and falls back on whatever the shell said — which is how a piped gate's exit 0 got read as green.

**Two counts moved when the flow started enqueueing its own gates, and they moved by DIFFERENT amounts — say which one you mean.** In a project with a queue, the epic's close-out gate and the mid-arc integration gate are both enqueued now (*Gate the integrated whole*). So: **paths that produce no durable record at all go 3 → 1.** A hand-run gate is the only one that writes no streamed log, no ticket and no ledger entry, and it is left in **two** places rather than one: a project that declares no queue, where an override-mode slice is the whole of it, and a queued project whose runner refuses the PR-less ticket, where the mid-arc integration gate alone falls back to it (*Gate the integrated whole*). **Paths that produce no PR comment go 3 → 2.** The close-out gains one, on the very PR the verdict is about; a PR-less integration ticket does not and never will, because there is no PR; and an override-mode slice's comment is one the agent *writes* rather than one it reads. So the mid-arc gate does not leave this section's scope — what changes is what you read: **the verdict on its ticket in `done/`, not a shell's exit status.** *The failure this prevents is letting either count stand for the other. Read as "everything is commented now", a dispatcher waits on a comment that will never arrive against a PR that does not exist — and "settled with no comment" is the queue's own signal for a failed post (`skills/setup/references/gate-queue.md`, Reporting), so the wait presents as a delivery problem and the natural remedy, another reconciling drain, retries a post nobody was ever owed.*

- **A gate spans every workspace — read every package's result, never one package's summary.** `gate` runs the task-runner across ALL packages (Trinity: trinity, trinityailabs.com, cf, api-types). A `Failed: <pkg>#test` line plus a non-zero exit is **RED**, even when the *first* package's summary you happen to see looks like only the known baseline. Concluding "green-modulo-baseline" (see the transient-red window below) from one package's `Test Files N failed` line — without confirming the failing SET across *every* package is exactly the baseline — is precisely how a real regression in a *second* package rides through to merge. When you assert green-modulo-baseline, enumerate the failing files across all packages and match them to the baseline set by name; a `cache miss, executing …` line for a package whose *result* you never saw is a signal to go read that result, not to assume it passed. (This actually happened: a slice was merged "green-modulo-baseline" off its trinity summary while its trinityailabs.com suite was red — the data-layer regression only surfaced at the epic's integration gate.)

- **Several worktrees red at the same moment, with infrastructure-shaped errors, is ONE shared resource before it is N code defects — and it is the same instrument as the bullet above, pointed one level out.** That one says the failure set spans every package, so don't stop at the first summary; this one says the failure set can span every *worktree*, so don't read a simultaneous multi-slice red as N independent verdicts. They compose: widen within a gate, then widen across gates. **The tell is the shape of the errors, not their count** — deadlocks, unique-constraint violations, lock timeouts, "address already in use", a fixture another run truncated, a cache another run evicted — and the confirmation is that the *same* named resource appears in failures on branches whose diffs have nothing to do with each other. Check `sharedResources` (*Per-project config*) before you dispatch a single fix agent: an entry with `"isolatedBy": null` means the flow already knows these runs collide, and a missing key means nobody ever asked, which is not the same as no. Re-gate the branch **alone** to separate the two — a red that survives in isolation is a code defect, one that evaporates was the race — and where it was the race, the move is to narrow the wave, not to touch a diff. *The failure this prevents, observed twice from opposite directions. Three reviewers dispatched while a gate was live produced 605 spurious failures and then 151, and the implementer got it right only by calling it environmental rather than "fixing" its branch. And in a repo that had already solved this, commenting out the single line that gave each worktree its own database reproduced it exactly — 116 failures, then 121, deadlocks throughout, every one of them naming the one shared database. The default response to a red is to debug the diff, and that response is not merely wasted here: the slice that lost the race is the one that looks guilty, so the "fix" lands in whichever innocent branch happened to be second.*

- **The gate comment is the only evidence a gate ran — a PR's flags are not.** Trust exactly two signals that a gate is actually green: a runner-drained **`gate ✓ passed`** comment, or an override-mode agent's own gate comment on its PR reporting a full green with zero failures — and on the close-out/integration slice, independently re-run the previously-red files yourself before you believe it. Nothing else attests to a gate, and an empty PR conversation means nothing has. Read the comment and its failure set; the draft flag is about review, not about the suite.

- **An implementer that opens its PR without `--draft` is a bug you act on, not a formatting slip.** The ready flag means "a dispatcher read this diff and is merging it", and `merge-pr.sh` is the only thing that should ever set it — so a PR that arrives non-draft is claiming a review that never happened and is sitting in the merge-eligible state without one. Put it back to draft (`gh pr ready --undo`), then gate and review it like any other.

### Transient-red window (schema-first / all-or-nothing epics)
When a foundational change lands first — a NOT-NULL schema swap, a required interface field, a renamed module — it makes `gate` impossible to get fully green branch-wide until every consumer migrates. A full-green gate is **unattainable mid-epic BY DESIGN**; holding slices to it just paralyzes progress.

**Put this window on an epic branch.** An epic in this shape is the primary trigger for one (*The epic branch* above), and this section is the reason: the window has to exist somewhere, and the only real choice is whether it sits on the branch every other session cuts its worktrees from. On an epic branch it does not — the integration branch stays shippable throughout and sees the epic only as the single merge at the end, so nobody else forks off a knowingly-red base. Read the rest of this section as describing the **epic branch** when the epic has one, and the integration branch when it does not.

**The window is a fact on disk, not a note in a plan — declare it or it does not exist.** `decompose` flags which slices live in the window and you read a drained ticket's red against that flag, but both of those are judgments made by something that can read prose. A project's **commit-time** tooling cannot. Where a repo relaxes its pre-commit compile check for exactly this window — forgiving diagnostics that all point at files the branch never touched, while holding the branch's own files to the full bar — the only thing it can consult from inside a slice worktree is the ref graph. So the marker ref from *The epic branch* above is the contract, and it is deliberately the whole contract: `transient-red/<epic-slug>` exists ⇔ the window is open, and deleting it at close-out closes the window with nothing to unwind.

**Two things a detector must not key on instead, both of which look right — and the one rule behind both.** Not the **epic branch itself** — Rule 2 cuts one on multi-slice width alone, so there is an epic branch on *every* multi-slice arc including all the ones where every intermediate state is green, and a relaxation keyed on `epic/*` would silently start forgiving sibling breakage that is real on every one of those. And not `integration/*` — this playbook's opening reserves "integration branch" for the shared branch and says it never means anything else, so a detector keyed on that word is reading a level of the hierarchy that was never the window's home. **Generally: no branch-name prefix is ever the key.** The epic branch's prefix is read by nothing (*The epic branch* → *Mechanics*), so a detector keyed on it is keyed on taste, and tooling that has to ask "is this an epic branch" answers it with a dedicated ref of its own — the way this marker does — never with a prefix match. *The failure this prevents: a prefix match reads a name nothing else in the flow reads, so it agrees with the branch only for as long as whoever cut it happens to pick that prefix — and it fails silently in both directions, calling the window closed on an epic that has one open and open on an epic that does not. The other half of the cost is invisible from here: a prefix already carrying meaning somewhere else in the project quietly acquires a second reader, and renaming a branch to satisfy this detector re-scopes that one too.*

**Confirm it actually fires before you dispatch the first slice.** A window that failed to open and a project that never had one are byte-for-byte indistinguishable: nothing errors, nothing warns, and every slice just takes the strict path as though that were the design. So the evidence is only ever evidence you went and asked for. From inside the first slice's worktree — where the tooling actually runs, not from the main checkout — confirm the marker is visible (`git for-each-ref refs/heads/transient-red refs/remotes/origin/transient-red` naming the ref you pushed) and that the project's own detector agrees the window is open. One check, once per epic. *The failure this prevents: a detector and a flow can disagree about where the window lives — the detector looking for one ref, the flow having pushed another — and neither side reports the disagreement, so every slice pays full strict-path friction for a relaxation the repo believes it has.*

In that window a drained ticket's gate will exit non-zero on the pre-existing baseline failures until every consumer migrates, and the runner will comment that failure on the PR. That's expected, **not** a real block. Read the runner's output as: the compile half (typecheck + lint) is GREEN, the task's OWN new/affected tests are GREEN, and there are NO failures beyond the baseline SET that pre-dated this task on its fork point (file + test names, not a count — fixing one stale test and breaking a new one keeps the count identical but is still a regression; the absolute count drifts between tasks forked at different tips and as consumers migrate). If it clears that bar, merge it with `merge-pr.sh` on that bar rather than a green exit — the merge is where you record having read it, and a red comment you have *judged* is not a blocker, only a verdict you have to read carefully.

### Gate the integrated whole — conditional on what the merge actually produced
Each branch was gated against *its own fork point*, blind to the other slices, so the branch that now carries all of them together **may** be carrying a tree no gate has ever run. May — and the merge itself tells you which. Every merge this check reads makes a real merge commit, so every one of them has a second parent — with the single exception the closing-merge paragraph below takes up, an epic → integration merge in a project that declared `"epicMerge": "squash"` (*The epic branch* → *Mechanics*), where there is no `^2` to read and a different instrument answers instead. After each of the rest:

```
git diff --name-only <merge-commit>^2 <merge-commit>
```

**Non-empty ⇒ the merge produced content no gate has seen**, and the merged result needs ONE `gate` run — **enqueued** in a project whose runner takes the ticket, and run by hand where there is no queue or the runner refuses it (*Enqueue it rather than running it*, below). Exactly two things cause it: a **conflict resolution**, whose resolved tree is new content by definition; and a **sibling branch that merged in between**, where this branch was cut before it and gated without it — the parallel case the reasoning above is really about.

**Empty ⇒ the merge's tree is byte-identical to the branch tip the gate already ran on**, so re-running executes the same tree for the same answer. A run that cuts every worktree from the current tip and merges sequentially without conflicts comes back empty on every merge and needs no dedicated integration gate at all.

The failure this prevents runs both ways, which is why it's a check and not a rule. On a monorepo whose full gate is ~10 minutes, an unconditional close-out gate spends that every epic to re-execute a tree that was already gated — a real cost paid for zero information. And "the last slice was green, so the epic is green" spends nothing and is wrong the moment two slices ran in parallel, which is this flow's *default* dispatch shape.

Two things the empty answer does **not** buy you:

- **It proves the tree was *run*, not that the run was *green*.** In the transient-red window above, slices merge on a green-modulo-baseline judgment rather than a green exit — so an epic tip can be byte-identical to a tree that was never observed fully green. Skipping needs both halves: the merge added nothing **and** the gate it inherits was an actual green. When the last slice merged on judgment, the close-out gate is the first real green signal there has ever been, and it runs.
- **It governs re-running the suite, nothing else.** It says nothing about the merged *code*: a shared hotspot still gets its merged region read by hand (*Merging a shared hotspot* above), because the semantic drift that section describes is invisible to a green gate and equally invisible to an empty diff.

**Re-derive the merged tip's derived artifacts before you gate it — and do that whether the `^2` diff came back empty or not.** An artifact whose correct contents are a function of the whole tree rather than of any one branch — a ratchet ledger, a backlog a checker regenerates, a generated type, an unimported-exports manifest — is the thing per-slice gates structurally could not have covered: each slice was correct about its own files, and the artifact derives from all of them. Run the project's own regenerator against the merged tip and commit what it writes, or send the delta back as a fix. `skills/decompose/SKILL.md`'s `Derives` field names these per slice, so the list comes with the breakdown rather than being reconstructed here. *The failure this prevents: two slices edit disjoint files, each is individually correct, and the artifact is right on neither branch — no textual conflict at either merge, so nothing stops. The `^2` check does not catch it either: a sequential conflict-free run answers empty on every merge, and staleness that was already committed is not content a merge introduced. The gate then passes on a tree whose ledger disagrees with its own source, and the next increment grounded off that tip inherits it as ground truth.*

**Install the tree you are about to gate — unconditionally, and the main checkout is a tree like any other.** This gate runs against the merged tip of the integration branch, which is the **main checkout**: the longest-lived tree in the flow, fast-forwarded by `merge-pr.sh` on every close-out without ever installing, while other sessions merge `package.json` and lockfile changes onto that branch continuously. Run the project's `install` (*Per-project config*) there immediately before the gate — the same command `setup-worktree.sh` runs when it cuts a tree, and a no-op in a project that declares none, this repo included. **The conditional version is the trap:** you cannot tell from the merge's own diff whether a dependency arrived, because that fast-forward means every range you might compare against is unreliable in both directions. The diagnostic order is *The epic branch* → *Mechanics*' rule applied to this tree: **on an integration gate a module-resolution failure is a stale install until proven otherwise** — install and re-run before reading a line of the diff. *The failure this prevents, observed on `trinity-ai-labs/trinity` gating a merged tip on `release/0.4.0`: another session had merged a subpath export into `shared/utils` while the branch was open, the main checkout's `node_modules` predated that merge, and the gate came back `TS2307: Cannot find module 'shared-utils/sqlite-timestamp'` at step 5 of 6 — on code that was entirely correct. The shape of that error invites dispatching a fix agent against a correct tree, which is the same cost the epic worktree's rule names: arriving at the install as a diagnosis rather than as a step. The install took 1.4 seconds and the gate then passed 6/6. It fails the other way too, and worse: a stale install that still happens to resolve returns a green on a tree the current dependencies would have rejected.*

**Enqueue it rather than running it — the tree has no PR, and the ticket shape admits that.** In a project whose runner takes the ticket this gate goes in as a **PR-less ticket**: `enqueue --branch <branch> --worktree <worktree>`, with no `--pr-number` and no `--pr-url` (`skills/setup/references/gate-queue.md`, the ticket shape). A runner claims it, gates that worktree behind the machine-wide slot, and settles it into `done/` with the verdict written on the ticket; the only step it skips is the comment, because there is no PR to put one on. So **you read the verdict off the ticket**, not off a shell's exit status, and the ledger watch already armed for the wave sees it settle by `branch` (*Wait on your own tickets settling — one Monitor over the queue's ledger*; a PR-less ticket carries no `prNumber`, so print the branch as its handle). Then fire **one** drain and react only if the ticket is still sitting unclaimed in `queue/` a couple of polls later — do not pre-flight whether a runner is already draining, because the two instruments for that question are the ones this file records as unreliable (a process list cannot separate gating from blocked-on-a-slot, and `--status` silently drains on a runner scaffolded before invariant 9), while a second drain is idempotent and safe by construction. *The failure this prevents is what a hand-run gate here costs, observed: a dispatcher launched one into a fleet with two live runners, two tickets processing and one queued, without checking. The slot serialized it correctly and nothing went wrong — but the slot produced that outcome and the process that led to it did not, and on a hand-run gate that distinction leaves nothing behind for anyone to notice. Enqueued, there is no pre-flight to remember and no reason to invoke a drain runner just to ask a question: the queue serializes by construction, so "once the fleet is quiet" stops being something anyone polls for.*

**A runner scaffolded before the PR-less ticket REJECTS it with a usage error, and the hand-run gate is the sanctioned fallback there too — not only where the project declares no queue.** `/pipeline:setup` scaffolds the queue **into** a project and the project owns it from there, so a project scaffolded before `prNumber`/`prUrl` became optional has a runner that still requires them, and the enqueue above exits non-zero on a missing-required-field usage error naming both. **Every fallback clause in this file is keyed on a condition that case does not satisfy** — the project *has* a queue, and that queue works correctly for every ticket a PR is attached to — so a dispatcher reading them is pushed away from the hand-run gate by an instruction that is emphatic about it (*The durable gate queue*: in a project whose runner will take them, no gate is run by hand) and toward an enqueue that cannot accept the ticket. That is why the clauses now name **two** conditions rather than one. Run the gate yourself in that worktree, capture its own exit status (*Where you do run a gate yourself*), and say in the close-out that this verdict has no ticket behind it. **Only the mid-arc gate is reachable this way**: the epic's close-out gate sits behind a draft PR and therefore always has a `--pr-number` to carry, so it enqueues on any runner.

*The two halves of that rollout fail in OPPOSITE directions, and the safe one is the one that strands you.* `skills/setup/references/gate-queue.md` invariant 9 records the sibling half — a `--status` flag an older runner does not recognise **silently drains**, which is dangerous precisely because it looks like it worked; *Draining the gate queue* carries what that costs a dispatcher. A PR-less enqueue on an older runner does the opposite: it exits non-zero and does nothing, so no tree is mis-gated, no gate run is spent and no verdict is invented. What it costs instead is a dispatcher stopped mid-close-out with the sanctioned route refused and — until this paragraph — no other one the file admitted, which is the failure this prevents. **Read a usage error naming `prNumber` and `prUrl` as the runner's age, not as a defect in your invocation**, and do not re-type the command with invented PR fields: a ticket pointed at a PR the tree does not have sends a real verdict to a real PR that no gate on that PR ever produced, which is the one outcome worse than having no route at all.

**Where you do run a gate yourself, capture the gate's OWN exit status, never a pipeline's.** `pnpm gate > gate.log 2>&1; echo "EXIT=$?"`, then read the log — not `pnpm gate | tail`, whose status is `tail`'s, because a shell reports the exit code of a pipeline's **last** command. A gate you run yourself posts no comment, so that status is the whole verdict, and every natural way to shorten a long gate log throws it away while still printing the output that makes you feel you have read it. Report the `EXIT=` line itself rather than a summary of the log: a green you cannot quote is one nobody can check. **This is the reading for a gate nobody drained, and in a project with a queue that is now almost none of them** — both gates this section used to have you run by hand are enqueued above, on a runner that takes their tickets. What is left is two cases. A project that declares no `enqueue` and no `drain` at all (*Per-project config*), where every gate is hand-run: a slice in **override gate mode**, and this section's own two gates where there is no queue to put them in. And, **in a project whose queue works**, the mid-arc integration gate by itself, where the runner refuses the PR-less ticket (*A runner scaffolded before the PR-less ticket REJECTS it*) — the one case in which this reading is needed by a dispatcher who has every reason to believe it does not apply to them. There an implementer's or a dispatcher's own reading of that status *becomes* the comment everything downstream trusts (*Implementer*). **`set -o pipefail` is not the fix to reach for** — it is shell-specific, off by default in every shell these commands are typed into, and a rule that depends on an option being set somewhere else fails silently in exactly the case it was added for; a redirect and `$?` work everywhere and show their own working. *The failure this prevents, observed twice in one day by two independent dispatchers reaching for the same shortcut. One ran the integration gate as `cd <epic-worktree> && pnpm gate 2>&1 | tail -30` and the harness reported exit 0 — `tail`'s. The gate had failed at step 5 of 6 (`Failed: trinity#typecheck, trinityailabs.com#typecheck`), and it was caught only because the output happened to be read line by line; the exit status agreed with "green" throughout, and the next step would have been grounding the following wave on a tree that did not compile. The other gated two epic close-outs with `sh scripts/check.sh 2>&1 | tail -3`. Those were genuinely green, so nothing came of it — which is the danger rather than a mitigating detail: from a piped status a pass and a failure are byte-identical, so every run that happens to land on green teaches that the shortcut is fine.* **And `| grep`, the one that feels like diligence rather than a shortcut, is worse than the others: it does not discard the verdict, it INVERTS it.** `gate | grep -i failed` exits 0 exactly when it found a failure and non-zero when the gate was clean — so the status now reports red as green and green as red, and the reading that looks most careful is the one that is wrong in both directions.

**On an epic branch, apply the check to the closing merge too — it is the one merge that is usually non-empty.** A gate on the epic tip is not a gate on what lands: the integration branch moved while the epic ran, so `epic → integration` combines two histories nothing has tested together. The fix is ordering, not another gate — before the close-out gate, merge the integration branch INTO the epic one last time (the same merge the tick already runs, *The cost* above; that cadence buys this, not just bounded conflicts). Then the epic already contains everything the integration branch has, the gate covers the exact tree the closing merge will produce, and that merge's `^2` diff comes back empty. Skip the cadence and it won't, and the gate moves to *after* the closing merge, on the shared branch, where a cross-slice break is found only once every slice has already landed on it.

**And when that closing merge is a squash, the same reasoning has a consequence: the cadence stops being advisory.** A squash commit has no second parent, so there is no `^2` to read at all — the tree comparison `merge-pr` runs takes its place (*The epic branch* → *Mechanics*), and it is stronger, comparing the gated epic tip against what landed rather than inferring coverage from parentage. What changes for you is the *enforcement*, not the check. Those two trees are equal **only** if the final `merge origin/<integration>` into the epic actually ran before the gate, so on the squash path a skipped cadence does not surface as a non-empty diff you were free not to look at — it surfaces as a **failed comparison that blocks the branch delete**, and the close-out stops there with both copies of the branch intact. *The failure this prevents: on the merge path the `^2` diff is a signal a dispatcher can read and shrug at, and skipping the cadence costs only that the close-out gate ran on a tree the closing merge then changed. Under squash the cadence is what makes the tree comparison answerable at all — so the cheapest way to hit that failure is to treat the cadence as a nicety, and the one place it is guaranteed to be noticed is after the merge is already irreversible.*

That ordering is the whole point of which branch the gate runs on. On an epic branch the failure surfaces while the integration branch has seen none of the epic, and the fix is one more slice PR into the epic; without one, it surfaces on the branch every other session cuts worktrees from. A failure that first appears here is a real cross-slice interaction the per-PR gates *structurally could not* catch (none of them saw the others) — fix it forward, don't rationalize it away. Independent-green is necessary; *integrated*-green is what actually ships. **On an epic branch a green gate is the precondition for MERGING the epic → integration PR — not for opening it.** What finally puts the whole change set on the shared branch is the merge, and a **draft** PR puts nothing anywhere: GitHub refuses to merge one, and this flow already spends the draft flag as the interlock against merging an unread diff. So the PR opens first, as a draft, and the gate is enqueued against it (*The epic branch* → *Mechanics*). *The failure the other statement caused: read as a precondition over the open, it forced the one gate whose tree no per-slice gate had ever seen to run with nothing to attach a ticket to — no log, no ledger entry, no comment, and a verdict surviving only as an exit status in one terminal, on the least-observed gate in the flow.*

### Merge & cleanup — one command, because the sync is the step that gets dropped
The steps below have exactly one correct order, and syncing the local integration branch is the one with **no forcing feedback** — every visible signal after the merge (`✓ Merged`, branch deleted, PR closed) says "done", so it's silently skipped, and the miss only surfaces later when the *next* worktree is cut from a stale HEAD. So **default to the helper, which does all of them but the last, atomically: `merge-pr.sh <pr-number>`** — plus the mergeability preflight the list below has you run by hand before its first step. It resolves the main checkout + the PR's base/head branches, confirms GitHub can actually merge the PR before anything irreversible happens, tears down the worktree, marks the PR ready and immediately `gh pr merge --merge --delete-branch`es it, and — anchored to the main checkout regardless of your cwd — brings that local base branch up to the merged tip. (The one PR it merges any other way is an epic → integration close-out in a project that declared `"epicMerge": "squash"`, which it decides from that project's config before anything irreversible happens and finishes with a tree check in place of the delete — *The epic branch* → *Mechanics*. Every other PR, in every project, takes the sentence above unchanged.) It does that **without ever switching the checkout**, via one of **three** sync paths picked by where the base actually is: the main checkout is standing on it → `merge --ff-only` there; a **linked worktree** is standing on it → `merge --ff-only` **inside that worktree**, which is the ordinary path for every slice PR of an epic now that the epic branch lives in one; nothing is standing on it → move the **ref** (`fetch` + `branch -f`), which needs no working tree. All three only ever move the branch forward, so none can discard a commit, and none opens a window for another session to land in or leaves anything to switch back afterwards. It then verifies the checkout is still on the branch, and at the commit, it was on when the run started — the alarm the shared-main-checkout hazard above calls for. When the fast-forward inside a linked worktree cannot proceed, the helper stops and names **which** worktree and **why** — commits the local branch carries that the remote does not, or a working tree not clean enough to fast-forward — rather than forcing the ref or reporting a sync that did not happen. Running it *is* the approval: the ready flip lives one line above the merge precisely so a PR can never sit around wearing a review it has outgrown. It's idempotent (a re-run finishes a half-done close-out) and it's the reason a hand-run sync can't get dropped: don't split these steps back out by hand unless the helper can't handle a case.

**Of the steps below, the one the helper cannot do is closing the issues the work resolved — and it is the one that silently goes missing.** `merge-pr.sh` knows the PR, not which issues it settled — and whether GitHub closes them on its own turns on where that PR was based. Closing keywords in a PR description "are interpreted only when the pull request targets the repository's **default** branch. If the pull request targets **any other branch**, then these keywords are ignored, **no links are created**, and merging the PR has no effect on the issues." **The predicate is the PR's base against the repo's DEFAULT branch — not "integration or epic branch", which stands in for it only where the two are different branches.** A slice PR based on an epic branch is genuinely inert, and so is any PR based on an integration branch that is not the default one. But a project whose integration branch simply **is** `main` — this repo and both sibling skills repos are that shape — has nothing between a PR and the default branch unless an epic branch is standing there, so every PR that is not a slice of an epic bases on the default branch, and there the keyword is **live**. Where the base is not the default branch the keyword **does not fire later either**: it belongs to a PR whose base was never the default branch, and nothing re-evaluates it when the integration branch eventually merges. (The one that *does* fire later is a closing keyword in a **commit message**, when that commit reaches the default branch — a different mechanism, delayed by the whole life of the release branch, and not a plan.) So close them yourself, in the same breath as the merge — **unchanged by any of this, because the hand-close is the one action that is correct under both readings**: a no-op when GitHub has already closed them, and the whole mechanism when it has not. Learning that keywords sometimes fire is not learning that this step is sometimes skippable. **Which issues you close here, and therefore when any given issue closes, turns on a different question from the one above: what did THIS PR settle.** The issues this PR settled close at this merge; an issue no single increment settles — an umbrella, or an arc whose next cycle is still to run — closes when the arc does, which is `skills/orchestrate/SKILL.md` §7's termination check and not this step. *The failure this prevents, observed: a dispatch brief asserted that during an epic no issue closes for the epic's whole life and they all close together at the end, and instructed an implementer to write that into this file. It is false — the hand-close runs at each slice merge inside an epic exactly as it does outside one — and it was caught only because the implementer read this section end to end before writing. A brief is the artifact this corpus is read into most often and the one nothing gates.*
```sh
gh api -X PATCH repos/{owner}/{repo}/issues/<n> -f state=closed
gh api repos/{owner}/{repo}/issues/<n>/comments -f body='Fixed in #<pr> (merged into <base>).'
```
REST rather than `gh issue close`, for the reason `skills/decompose/SKILL.md`'s *GitHub write mechanics* gives: the high-level `gh issue` writes go through GraphQL and hit rate limits exactly when you are closing a batch of them. *The failure this prevents, observed: nine issues, every one genuinely complete, every one named with `Closes #<n>` in a PR that merged clean — all nine still open at close-out, found by accident because somebody happened to list what was outstanding. Nothing errors, the keyword sits in the PR body looking like it worked, and the board diverges from the tree for as long as the release branch lives.*

**And the inverse is the half no rule here covered — the one that can actually bite: where the base IS the default branch, a closing keyword is LIVE, so do not write one into a slice PR while its arc is still running.** Single-slice work never cuts an epic branch, so in a project whose integration branch is `main` such a PR goes straight to the default branch, and `Closes #<n>` in its body fires the instant it merges. **That is the right moment only if this one PR settles the whole issue** — and an increment is not an arc: `orchestrate` grounds one horizon per cycle, so an arc can run several cycles whose increments are each a single slice, cutting no epic branch and basing every one of those PRs on the default branch. A keyword written into the first of them closes the issue while the cycles after it are still outstanding, and the same shape reaches an umbrella that a sub-issue's PR happens to name. `skills/orchestrate/SKILL.md` §7 treats the tracker as part of termination, so an issue closed early is a false "done" in exactly the artifact the loop reads back to decide whether it is finished. Reference the issue without the keyword — `Refs #<n>` — and close it by hand when the ARC closes rather than at this merge, since this PR did not settle it (the question above). What closes it is `skills/orchestrate/SKILL.md` §7's termination check, not the per-merge step above. *The failure this prevents is the mirror of the one above and strictly worse, because the two leave opposite residue. A hand-close that got skipped leaves an open issue, which any later sweep of what is outstanding can still find — that is how the nine were found. A keyword that fired early leaves nothing to find: the issue is closed, the board reads finished, the arc's own termination check agrees, and the only thing that disagrees is work still running against it.*

**The teardown comes before the merge, so the helper checks the merge is possible before the teardown.** The branch lives in a linked worktree, and **git refuses to delete a branch that's checked out in a worktree** (`cannot delete branch 'X' used by worktree …`), so `gh pr merge --delete-branch` would error on the local-branch step if the worktree still existed — the order below is load-bearing and stays. What that order costs is that the two irreversible steps run *before* the one that can fail: a PR whose base moved under it fails at the merge with `GraphQL: Pull Request has merge conflicts`, and without a preflight that leaves no worktree to resolve the conflict in and a PR marked ready with no review behind it. So `merge-pr.sh` asks GitHub whether the PR is mergeable **first**, and a `CONFLICTING` answer stops it cleanly — worktree intact, PR still draft — naming the fix. Two consequences for you: a conflict now costs you a resolve rather than a recovery, and if the merge fails anyway (GitHub computes mergeability asynchronously, so a just-pushed PR can answer `UNKNOWN` and the helper falls through rather than blocking) the helper puts the draft flag back on its way out, and its message tells you to re-attach a tree with `setup-worktree.sh --existing <head-branch>`. Resolve a conflict by **merging the base in, in the branch's worktree** (`git fetch origin && git merge origin/<the PR's base>` — the branch the PR actually targets, which for an epic's slice is the epic branch, not the integration branch) — never rebase — then push, re-gate, and re-run `merge-pr.sh`.

If you ever run the close-out by hand (helper unavailable, or an edge it can't cover), do it in this exact sequence, every time — and check `gh pr view <n> --json mergeable` yourself before step 1, since by step 2 the worktree is gone:
1. **Confirm the ticket is done before you tear down.** The runner gates in the ticket's worktree, so don't remove a worktree whose ticket is still `queue`/`processing` — wait until its gate has resolved (its verdict comment is on the PR). Removal is one half of the frozen-worktree rule; **editing** it mid-gate is the other and is just as damaging — see *Draining the gate queue*. Then **remove the worktree — always via the helper:** `remove-worktree.sh <branch-leaf>` (or the absolute path). **Do not use `git worktree remove` directly.** Plain `git worktree remove` evicts the directory but does NOT signal any running processes — so a gate running in it survives as an orphan. The helper kills all processes rooted in the worktree first — via `lsof` + `pgrep`, escalating SIGTERM → SIGKILL — then removes the worktree. On Windows it instead scans `Win32_Process` command lines and kills the matching process trees with `taskkill /T /F`, since neither `lsof` nor `pgrep` exists in Git Bash and there is no SIGTERM to escalate from; it also prints a notice that open-handle enumeration was **skipped** (the `lsof +D` half has no built-in Windows equivalent), so a removal that fails on a locked file has a stated cause rather than looking like a mystery. Nothing is lost — it's all pushed — and this frees the branch so it can be deleted.
2. **Mark the PR ready, then merge with branch deletion:** `gh pr ready <n>` immediately followed by `gh pr merge --merge --delete-branch` — the flip is your review approval, so it belongs against the commit you are merging this second, not earlier in the sequence. Real merge commit (never squash), and with the worktree gone `--delete-branch` cleanly removes BOTH the local and remote branch. Skipping `--delete-branch` is what let merged `origin/*` branches pile up indefinitely (they did: dozens accumulated). Verify it's fully merged first; STOP on git's "not yet merged to HEAD" warning. **If the merge fails after you flipped it, flip it back** (`gh pr ready <n> --undo`) — a non-draft PR that isn't being merged right now is a bug, and here it would be one wearing a review the merge never earned.

  **The one PR this step reads differently is an epic → integration close-out in a project that declared `"epicMerge": "squash"`** — the exception in full at *The epic branch* → *Mechanics*, including both conditions it depends on, so check them there before doing this by hand rather than deciding from the branch's name. **The hand-run form is `gh pr merge <n> --squash`, and it is NOT `--squash --delete-branch`:** the branch has to outlive the merge so what landed can be compared against what was gated. Then `git diff --quiet <the epic tip you captured BEFORE the merge> <the squash commit>` — capture that sha first, because after the squash the PR no longer points at a branch anything will hold for you — and delete the branch, local and remote, **only** if that comes back empty. Git's "not yet merged" warning fires here on every squashed close-out and is answered by that comparison rather than overridden by you; if the comparison does not pass, or you could not make it, stop and leave both copies of the branch alone. This is the whole reason to prefer `merge-pr.sh`: it captures the tip, compares, and refuses to delete on a mismatch, in one command with no step you can drop.
3. **Sync the local base branch — anchored to the MAIN checkout, never `&&`-chained, and without switching if you can avoid it.** `gh pr merge` advances the branch only on the *remote*; the local copy in the main checkout does NOT move, and syncing it is what keeps the next worktree from forking off a stale HEAD. When the base is **not** what the main checkout is standing on, move the ref and leave the checkout alone — `git -C <main-checkout> fetch origin` then `git -C <main-checkout> branch -f <base> origin/<base>` — for the reason the shared-main-checkout hazard gives: switching a checkout other sessions share is what corrupted a release branch. When the base **is** the checked-out branch there is nothing to switch, so: `git -C <main-checkout> pull --prune --ff-only`. ⚠️ Do NOT hand-run the old `git checkout <integration> && git pull` form: with no `-C` anchor it assumes your shell is in the main checkout, but the dispatcher's cwd is usually inside a worktree — there `git checkout <integration>` fails with `already used by worktree at …`, and the `&&` swallows the `git pull` so the sync silently never happens (this is exactly the "merged but never synced" bug). Anchoring every call with `-C` is what makes the step survive being run from anywhere, and is why the helper above can't drop it.
4. **Close the issues the work resolved** — the step named above that the helper cannot do, in full: GitHub will not do it for a PR based on anything but the default branch, and no keyword you wrote will do it later.

**When this close-out ends the whole arc rather than one increment, one arc-level question is still owed and it is answered in writing — `skills/orchestrate/SKILL.md` §7: did the arc surface a defect or gap in the pipeline itself?** It binds a dispatcher invoked directly exactly as it binds the loop, which is why it is pointed at here rather than left where only the loop would read it, and it is asked **per arc, never per increment** — asked five times in an evening it becomes noise and gets tuned out, which is worse than not asking. Read the bar and the "none found" rule there; this file does not carry a second copy.

**And one arc-level action, on the same cadence and for a different reason: where the project declares `reclaim` (*Per-project config*), run its `report` here.** Every worktree the arc cut has by now been torn down, and each one that ran a check left behind whatever its `sharedResources` mechanism created — named after a path that no longer exists. Per arc, never per increment, and the reason is not noise: an arc's waves overlap, so a mid-arc run reports resources belonging to slices still live and invites exactly the wrong conclusion about them. **Run `report`; never `drop` on your own judgement.** A drop is the maintainer's call on the maintainer's box, for the same reason a merge is not yours to approve — and it is barred outright while any ticket is outstanding — queued as much as claimed — by the frozen-worktree rule (*Draining the gate queue*), because a queued ticket names a worktree whose resources a runner is about to need. *The failure this prevents runs both ways. Skipped, the resources accumulate silently for as long as the machine lives, which is the whole reason the key exists. Run as a drop instead, on a report you did not have to read, it deletes a live worktree's database mid-gate — and a missed reclaim is a disk-space cost, while a wrong one is unrecoverable.*

## Implementer

**First action, before any other command: `cd` into your assigned worktree and prove you're really there** — `git rev-parse --show-toplevel` must print the assigned path and `git branch --show-current` the assigned branch; if either mismatches, STOP and report rather than proceed. Run every subsequent command from inside the worktree — a relative path or a stray `cd` back to a main checkout is how edits land in the wrong tree. Work only in the assigned worktree (absolute paths), match surrounding style, and follow the project's conventions — its `briefConventions` (from `<repo>/.agents/worktree.json`) and its `AGENTS.md`. (For Trinity — **app = Solid, sidecar = Effect**: invoke the `frameworks:effect-v3` skill for any Effect-TS code on the sidecar, and the `frameworks:solid` skill for any SolidJS UI code on the app — `solid-js`, `@solidjs/router`, `@tanstack/solid-query`, Kobalte; build forward-only — pre-launch, no backwards-compat shims; comments explain the mechanism, no issue/PR/version/plan refs.)

**The copy you were handed is not the copy you are editing — where your slice edits the corpus it is reading, the worktree's copy is the authoritative one.** Step 0 loaded these skills from the **installed** plugin, whichever version is enabled in the plugin cache, and that is not the tree you have just proved you are standing in. In every other repository the two have nothing to do with each other and this never arises; in the repository that ships these skills they are one document at two versions, and **the rules an arc has just shipped are the ones most likely to be missing from the copy you were handed**. So read a governing rule out of the worktree before you act on it, and where one looks wrong, absent, or contradicted by what the tree plainly does, `diff` the two copies rather than concluding the tree is broken — a discrepancy is the cache being old, not the tree being wrong. Say in your hand-back which copy you read the rules from. *The failure this prevents: nothing errors. You load a real skill, follow real rules and produce work that satisfies them — the previous version's — and the hand-back, the diff and the gate all read the same either way. Observed: a sweep of this corpus for rules that disagree across files produced two candidate findings that were defects the worktree had already fixed, manufactured by the instrument rather than found by it; it was caught partway through and redone against the worktree.* This is the version-skew test in *File your follow-ups BEFORE you hand back* arriving one artifact earlier — there, a closed issue is a fact about the tracker rather than about the tree the failure was observed in; here, the same gap is in the rules themselves.

**The flow is: write all the code → update the docs it changed → (`/pipeline:review` if this slice warrants it) → commit → push → draft PR → enqueue the gate → hand back.** Write the whole change in your worktree, running *cheap* checks as you work: format, a scoped lint/typecheck (via `scopedCheck` or `turbo run <task> --filter=<pkg>` for lint/typecheck breadth — never raw `tsc`/`eslint`, which bypass the shared cache), and a **single targeted test file run directly** (`vitest run path/to/x.test.ts`). That single file is the widest test execution you get. **Any test run wider than one file — a whole package or the whole suite — is the gate's job, not yours, and is banned by ANY invocation:** not `gate`, not `turbo run test`, not a raw `vitest` sweep, not a per-package `test` script. The cached-runner rule is about *how* to run lint/typecheck breadth, not a license to run suites — routing a suite run through turbo doesn't make it allowed.

**Docs are part of the change, not a follow-up.** Before you hand back, write down the user-visible behavior your change adds, removes or alters, then find the docs describing *that behavior* and bring them in line — the repo's `README.md`, its `AGENTS.md`/`CLAUDE.md`, and any reference or docs directory it keeps, plus whatever its conventions name. **Search by the behavior, not by the vocabulary you introduced:** prose written for a user describes a feature in plain language and contains none of your new identifiers, so grepping for your own new terms comes back empty and reads as "nothing to update" — which is how a doc goes stale while every check stays green. Docs go in their own commit, separate from the behavior, and every doc you looked at gets a one-line verdict in your hand-back report. Nothing in the gate can catch a stale doc, so the report is the only record that the question was asked at all.

**A comment you rewrite or relocate is a claim you are re-asserting — check it before you reword it.** Prose that asserts what *other* code does is the one defect class nothing here can scan for. A duplicate, an unimported export, a type that disagrees with its schema — every class this flow's checks catch is a disagreement between two artifacts a tool can compare. A comment asserting a code path is prose against behavior, and the only thing that finds it is someone reading the claim and going to look. So when your change touches a comment that says what happens elsewhere — *the route parses this with X*, *callers must call Y first*, *this is enforced in Z* — open that code and confirm it still does that **before** you rewrite the sentence. **A claim that turns out false is a FINDING, not a wording bug**: report it, and file it (*A follow-up is yours*) when fixing it is not this slice's job. Never quietly correct it into accurate prose. This is a different rule from the one governing how a comment is written — present-tense mechanism, no archaeology; that one is about the wording, this one is about whether the wording is TRUE, and a comment can be flawless by the first and describe a function call that does not exist. *The failure this prevents, observed: a schema module's doc block described a two-step validation the route performed — the route did only step one, and never had done step two. Tracing every consumer showed the refined schema was never parsed in production at all, so an invariant that was declared twice and refined twice had never executed anywhere, while a comment described its enforcement in working code. It surfaced by accident, from a slice rewriting that block for an unrelated naming fix that happened to check the claim first. The tidy rewrite is the worst outcome available: it documents a bug as the design and removes the last thing that could have led anyone to look, because a wrong comment and a right one are indistinguishable in review — and the wrong one is load-bearing in the worst way. It is why nobody looked.*

**On a slice of an epic your brief inverts the last step, and only that step: record what you falsified, don't rewrite it.** The entry — *"this change makes paragraph Y of `<doc>` false"* — goes in your report, and one closing docs slice writes against the final tree (*The epic branch* → *Docs land at the end*, which is also where the carve-outs are). Everything before it is unchanged: you still derive the list from the behavior you changed rather than from your own new vocabulary, and you still report a verdict per doc. *The failure this prevents: read as "docs are somebody else's problem on an epic", it becomes the deferred-docs failure — you are the only party who will ever know what your diff falsified, and an entry you did not write is one the closing slice cannot answer.*

**And the ledger takes TWO entries, not one — the second is what your change ADDED that no doc describes at all.** *What did this change make false?* is a question about a difference, so a surface no doc has ever described returns *nothing* from it — honestly, completely, and indistinguishably from the answer you give when you touched no documented behaviour. **Reporting "nothing falsified" is doing the first rule correctly and says nothing whatever about the second**, so answer both: beside each falsification entry, record what you added that has no prose anywhere, marked as **needing new prose** rather than a correction — *"this change adds `<surface>`, which no doc describes."* Derive it the same way, from the behavior your diff adds rather than from your own new vocabulary; and where a chapter covers your area but stops short of what you changed — it says the thing fires, never what it now contains — that is this entry and not a not-affected verdict. *The failure this prevents: you are the only party who will ever stand in front of this diff, and the closing docs slice cannot ask a question about a surface it does not know exists — so an undocumented surface with no entry stays undocumented, which lands hardest on new behaviour precisely because new behaviour is the likeliest thing to have no prose about it yet.*

**The inversion covers prose, not coordinates — a path you moved, you repoint, in this PR.** A file path your slice moved or deleted, or a route literal sitting in the same clause as one, is yours to fix here even though the doc is otherwise the closing slice's: a checker can tell it is stale without reading the sentence, so a repo whose docs gate validates path citations reds on it at its FIRST step and your own `format`, `check` and `test` never run — you get no signal about your own work, and there is no ordering that escapes it, because the closing docs slice is last by construction. **Change the path and stop there.** The sentence around it is prose, so it goes in the ledger like everything else, and rewriting it while you happen to have the file open is precisely the semantic conflict the deferral exists to prevent (*The epic branch* → *Docs land at the end*, the coordinate carve-out, which carries the argument and the observed failure). **A renamed identifier is not a coordinate and does not come with you** — a function, a param, an exported symbol reads like the same mechanical swap, but no checker resolves one in prose, so the whole sentence goes in the ledger and the name goes with it. **And "stop there" is not "leave it half-right": before you land the repoint, read that sentence for a fact your OWN change moved** — a TTL, a limit, a default — and where you find one, **fix both halves. That is the only move**: reverting the repoint hands your docs gate back the stale path it reds on, and the sentence sits in the ledger with or without the revert, so undoing it costs you your own gate and buys the closing slice nothing. Never a fresh path beside a stale number: the half you corrected is what persuades the closing slice the rest was checked.

**Whether you run `/pipeline:review` is the dispatcher's call, made per slice in your brief** — it's worth its round-trip on substantial work and pure noise on trivial changes. If the brief says to run it (the default for substantial slices), do NOT commit as you go: keep the whole change uncommitted, and when the code is done run `/pipeline:review` over your *full uncommitted* working-tree diff (reuse / simplification / efficiency / altitude, plus correctness), decide which findings to apply, and ONLY then commit. If the brief says to skip it — or you're a direct implementer with no dispatcher and the change is plainly trivial (a one-liner, a copy/config tweak, a mechanical rename) — skip it and commit in logical blocks as the work lands.

⛔ **`/pipeline:review`, never the bundled `/simplify`.** They are not interchangeable and the difference is not cosmetic. The bundled skill fans its reviewers out as **forks**, and a fork inherits your entire conversation — including this brief, whose imperatives end in *commit, push, open a draft PR, enqueue the gate*. Its reviewers read that as their task list and carry it out: observed across three consecutive slices of one epic, review agents applied fixes, ran the repo formatter at root, committed, pushed, opened the PRs and enqueued the gate tickets before the implementer that spawned them got its turn back. `/pipeline:review` is inline — it spawns nothing and commits nothing, and every decision about what goes in stays yours. If you catch yourself about to spawn review sub-agents, or waiting on any, you are running the wrong pass: stop and check what they did to your worktree.

⚠️ **Why commit last when you DO review:** the pass acts on the *uncommitted* working-tree diff. Anything you've already committed is invisible to it — so if you commit as you go, the earlier blocks never get reviewed, and against a fully-committed (clean) tree it sees an empty diff, finds nothing, and silently does nothing while reporting that there was nothing to act on. The review simply never happens. Keeping everything uncommitted until after the pass is what makes it actually cover the whole change. (A skip-review slice has no such constraint — commit as the blocks land.) **And holding a change uncommitted for a whole slice is exactly where the urge to `git stash` shows up — to get a clean tree for a check, or to park the work while you sync a base. Park it under your own named ref rather than onto the shared stack**: `git stash create` + `git update-ref refs/pipeline-stash/<branch-leaf>/<epoch>`, restored with `git stash apply --index` on that same name (*Hard rules* carries the four commands and the caveats). Nothing else in the repo can renumber, pop or clear it, so getting the work back is a lookup rather than a guess about what is on top.

**Always format in write mode right before committing.** The scoped check runs format-*check* (Trinity: `pnpm format` in write mode vs. the check inside `pnpm check`) — the pre-commit hook verifies formatting, it does not fix it. So run the auto-formatter over your tree as the last thing before `git commit`; then the hook's format-check passes on the first try instead of bouncing you on whitespace you never saw. Cheap, and it removes a whole class of surprise commit denials.

**Formatter output is always committed, never reverted.** When the auto-formatter (or the gate, which runs it) rewrites a file, commit the result — do not revert it as "out of scope." Formatting of the files *you* changed folds into your change; formatting of files *unrelated* to your change (a pre-existing non-canonical file the formatter normalized) goes in its OWN `chore(format)` commit. And when you run the full gate yourself (override mode), it formats *in your worktree* — so on green you CAN and SHOULD commit whatever it wrote and push, rather than re-running the slow gate to re-verify formatting (pure prettier writes can't break a check/test that already passed). The one thing you must never do is throw formatter output away: a reverted format is drift left on the branch for the next agent to trip over.

**You do NOT run the full gate — and the ban is on the WORK, not the command name.** The heavy build+test gate runs later, in a runner, drained from the queue — not by you. Your commits are held only to a cheap **scoped check** (`scopedCheck` = format-check + lint + typecheck; no build, no test suite), and the agentic pre-commit hook already enforces it on every `git commit` — so a commit that would fail the scoped check is denied and you fix it and re-commit. That's the entire quality bar you personally clear. Never run the full suite or any whole-package test run **by any invocation** — not `gate`, not `turbo run test`, not a raw `vitest` sweep, not a package `test` script; renaming the route doesn't unban the run. **Backgrounding it is still running it:** launching a banned run with `run_in_background` (or `&`/`nohup`) does not satisfy "don't wait" — it violates "don't run," burns the box the slot exists to protect, and is the classic stall shape (suite churns in the background, you end your turn, the handoff never happens). Your instinct to verify your change by running the tests is exactly the default this workflow overrides: verification wider than one test file is the runner's job, and your PR gets it after you enqueue. Never wait on a gate, and **never mark your own PR ready — in any mode, on any result.** That flag is the dispatcher's signature that it read your diff, and you cannot sign it for them. (Exception, and it covers only *who runs the gate*: ONLY if the dispatcher's brief — or the user dispatching you directly — **explicitly** put this slice in **override gate mode**: then run the full `gate` yourself once, in the foreground, post the result as a comment on your own PR, leave the PR a draft, and do NOT enqueue. **Capture that gate's own exit status, never a pipeline's** — `gate > gate.log 2>&1; echo "EXIT=$?"`, then read the log, never `gate | tail` — and quote the `EXIT=` line in the comment you post. *Gate the integrated whole* carries the argument; what is different here is the stake. Your reading of that status **is** the comment, and the comment is the one thing this flow treats as evidence a gate ran — so a piped invocation does not merely mislead you, it manufactures a green verdict for every reader downstream. On a project with no queue that is every slice rather than a rare grant (*Per-project config*). You never grant yourself this exception — not because the change feels risky, not because you suspect nobody is draining. If you genuinely believe no runner will ever gate your PR, say so in your hand-back report; don't run the gate.)

**Never background a check and end your turn on it — and this rule is keyed to the HANDOFF, because the ban above is keyed to the run and so cannot reach a check you are allowed to run.** That paragraph is scoped to a *banned* run, which is exactly why an implementer backgrounding its `scopedCheck` reads it correctly and concludes it is not about them. The stall shape does not care which run it was: the turn ends, the handoff never happens, and the dispatcher's only signal is the phrasing of your hand-back. So the rule is stated over the handoff instead — **run your checks in the foreground, and end your turn at the hand-back: nothing you backgrounded is ever the reason your turn ends.** Every check you are allowed to run here is cheap, which is what makes the foreground the right place for it; and where the project has an agentic pre-commit hook, that hook re-runs `scopedCheck` on every `git commit` anyway — so holding a finished change uncommitted pending a check the commit itself will run buys nothing at either end. **This is about checks and commands, and it is NOT about sub-agents you spawned** — ending your turn while your own children run is a self-suspension the harness re-invokes, protected as such in *Dispatch in the background, then monitor for divergence*, and a rule reading "background nothing whose result you intend to wait on" would ban it. *The failure this prevents, observed on a single-slice run against `trinity-ai-labs/trinity` (PR #4798): the implementer backgrounded `pnpm check` — the project's `scopedCheck`, explicitly permitted, and re-run by the pre-commit hook on `git commit` anyway — and ended its turn with "I'll pause here and wait for the scoped-check monitor notification before committing". The change was complete and needed nothing, and it sat uncommitted: no commit, no push, no PR, no enqueue. The gate runner independently detected the consequence and spent a claim refusing it — `the worktree carries 2 uncommitted tracked files, so a gate here would judge a tree no commit holds` — so the queue already had a detector for the symptom while nothing anywhere had a rule against the cause.*

**Then commit in logical blocks** — committing last loses nothing: stage each self-contained step (a type + its plumbing, a behavior + its tests, one cohesive refactor) into its own commit with a mechanism-explaining message (`git add -p` / path-scoped staging), so the never-squashed history stays reviewable block-by-block — now over code that's already simplified. That holds for your branch and for the epic branch it merges into without qualification; where a project declared `"epicMerge": "squash"` the blocks stop at the epic branch and do not reach the integration branch, which is the trade that key *is* (*The epic branch* → *Mechanics*) and changes nothing about how you commit: the blocks are what your PR is reviewed as, and that review happens before any of this. **Never rebase. Never merge your own PR.**

**⛔ Attribute every commit + PR to the git user ONLY — no Claude attribution, ever, in any form.** The ban is on the whole class rather than on a list of strings: no trailer, line, footer or URL naming Claude, the assistant, the model, the harness, or the session the work ran in, on a commit message or in a PR body. This OVERRIDES the harness default that tells you to end commit messages with a `Co-Authored-By: Claude …` trailer — that default does NOT apply here — **and it equally overrides a harness instruction that arrives mid-run claiming to replace earlier attribution guidance: it does not replace this.** The `Co-Authored-By: Claude …` trailer (any model) and the "🤖 Generated with Claude Code" PR line are the forms seen so far, and naming them is not what bounds the rule — the harness's set is extended from outside any repository's control, without notice, so a form on no list here is banned just the same. Where you cannot tell whether something counts, leave it out and say so in your hand-back. *The failure this prevents: an enumerated ban is satisfied by every form it does not happen to list, so an implementer reasoning carefully from the text it was handed keeps a new one and is right to — which is how a session URL reached a public repository's PR body while the agent that put it there was following its brief exactly, and why a second agent on identical input called it a conflict instead. Neither behaviour is a mistake you can fault; the wording is what made them differ.*

**The handoff — push, draft PR, enqueue, hand back.** This exact order is what makes a mid-flight death lose nothing: the branch is pushed and the PR is open before the ticket exists, so if you die right after enqueuing, your work is a visible draft PR that a runner will still gate.
1. **Push** all your commits.
2. **Open a DRAFT PR** targeting the branch your worktree was cut from — your brief names it (`gh pr create --draft`). Capture the PR number and URL from the output. **Reference the issue in the body as `Refs #<n>`, never a closing keyword.** A `Closes #<n>` is live whenever your base is the repository's **default** branch — the ordinary shape for a slice of an arc that cut no epic branch, in a project whose integration branch simply is that branch — and it fires the moment the PR merges. *Merge & cleanup* carries when the keyword fires, when it is inert, and who closes the issue instead — including the one case where it is the right moment, which is a PR that settles the **whole** issue. **You are not the party that can tell**: you hold one slice's brief, not the arc, and an arc routinely runs several cycles whose increments are each a single slice. Omitting it costs nothing either way, because the hand-close that follows the merge is correct whether or not GitHub got there first. *The failure this prevents: writing it is the harness's own instinct on a PR that names an issue, and unlike a hand-close that got skipped it leaves nothing behind to find — the issue is closed, the board reads finished, `skills/orchestrate/SKILL.md` §7's termination check agrees, and the only thing that disagrees is the work still running against it.*
3. **Enqueue the gate:** `enqueue --branch <yourBranch> --worktree <yourWorktreeAbsPath> --pr-number <n> --pr-url <url>` (Trinity: `pnpm gate:enqueue …`). This drops a durable on-disk ticket; a runner will drain it, run the full gate in your worktree, and comment the verdict on your PR — a pass on green, the failing tail on red. The PR stays a draft either way. (In override gate mode there is no ticket: you ran the gate yourself, so you post that comment on your own PR and skip this step.)
4. **Hand back** — report the PR URL, files changed, scoped-check result, tests touched, **the per-doc verdict** (every doc you checked, each marked updated or not-affected-because — never a bare "docs reviewed", which is indistinguishable from not having looked), **every follow-up you filed** (issue number and one line on what it covers — see below; a follow-up named but not filed is not a follow-up), **the review pass's applied and rejected findings where the slice ran one** (`skills/review/SKILL.md`'s Output section writes that `Rejected` list *for the dispatcher reviewing your PR*, and this hand-back is its only route there; a finding you considered and deliberately did not act on is a decision rather than a doubt, so *anything ambiguous* does not reach it. *The failure this prevents: that pass runs inline, so the agent that read why the list exists is you — and complying with the letter of this enumeration still drops it, silently, because a rejected finding you never forwarded is indistinguishable from one the pass never raised, which is the exact indistinguishability the list was written to remove*), and anything ambiguous. You're done; you do NOT wait for the gate.

**File your follow-ups BEFORE you hand back — a bullet in a report is not a follow-up.** *Hard rules* states the rule and what a follow-up becomes; three things about it are yours specifically. **The filing happens inside this turn**, because you are the cheapest place in the whole flow for it: the worktree is open, the install is paid for, and the change that caused the item is in front of you, where a later session has to rebuild all three before it can start reading. **And the create call is not the first move — the failure you are about to file may already have a number.** `skills/write-issue/SKILL.md`'s *Before you file, search what is already filed* is that search: keyed on the failure shape rather than on your own words, over closed issues as well as open, and returning an outcome that is not always a new issue — an open issue already carrying this failure takes the observation as a comment instead, and a closed one makes the item a regression **only where the fix that closed it is present in the copy you read**. Absent from that copy, what you have is version skew rather than a finding and you file nothing; where you cannot establish which, you say that rather than pick. You are the only party who can run that check, because you are the one standing in the copy the failure was observed in. Run it here for the same reason the filing happens here. **The link names what surfaced it — and under an umbrella that is TWO acts, not one.** The body backlink is the first — `Follows #<N>`, or `Part of #<umbrella>` — so the item is findable from the arc it came out of. The **native** link is the second, it goes on in the same breath rather than as a follow-on step, and it is `gh api -X POST repos/{owner}/{repo}/issues/<umbrella>/sub_issues -F sub_issue_id=<child's DATABASE id>`. ⚠️ **That field is the child's database id (`.id`, e.g. `5261102081`), NOT its issue number** — take it from the create call's own response, or `gh api repos/{owner}/{repo}/issues/<n> --jq .id`. The two are different fields on the same object and both are plain integers, so nothing about the value's shape tells them apart, and passing the number returns a bare `404 Not Found` that reads as *"this endpoint doesn't exist"* rather than *"wrong id"* — which is how the step gets abandoned by an agent that believes it checked whether the API was there. **Native-link a containment relation only:** `Part of #<umbrella>` is containment and takes both links, while a bare `Follows #<N>` on a plain issue is provenance — the arc it came out of, not a whole it is a part of — and takes the body backlink alone, because in this corpus a sub-issue is a piece of the parent's remaining plan (`skills/orchestrate/SKILL.md` §7 makes an umbrella's body exactly that) and hanging a follow-up natively off a finished standalone issue asserts that issue is unfinished without it. `skills/decompose/SKILL.md`'s *Umbrella + sub-issues* is the authoritative copy of the call, and carries the other trap and the writer-side argument; what is here is the minimum you need in hand to do it without leaving this file, because nothing puts that skill in front of you at the moment you are filing. And **it goes in your report by number**, not as prose: an issue you filed and did not name is one the dispatcher cannot fold into the plan. *The failure this prevents: "flagged for follow-up: X, Y, Z" reads as thoroughness and is indistinguishable from it, while the items themselves stop existing the moment your turn ends — nothing in the gate, the PR, or the dispatcher's review can tell they were ever raised.*

*The failure the native half prevents, observed: five implementer-filed follow-ups on one six-slice epic, every one carrying a correct `Part of #<umbrella>` body backlink and not one natively linked — the shape of a rule being followed rather than skipped, because the rule the implementer had said backlink and stopped there. The cost lands on whoever arrives at that follow-up next. `skills/decompose/SKILL.md` Step 1 opens with one `/parent` call that resolves the umbrella definitively and reads **nothing but the native link**, so on a child of a markdown-only umbrella it 404s and drops the arriving agent onto the eight-candidate timeline search and its disambiguator. **The umbrella checklist line `skills/write-issue/SKILL.md`'s *Follow-up linking* mandates is not a substitute for the native link**, and reading it as one is the easy mistake here: it is the artifact that fallback disambiguates on, so it makes the expensive path resolve rather than making the cheap one available at all — the arc that produced the item stays reachable, and only by an agent that has already paid for the fallback.*

**An issue you file from behind a fence SAYS SO, on its own line in the body: `Filed from behind a fence: <the fenced path>`** — **and where the failure is already filed and your observation goes onto that issue as a comment instead, the line goes on the comment, in the same fixed form.** What it marks is how far *your* reading got, and that is unchanged by which artifact carries it. **Read the fence before you conclude that filing is what you have to do** — `skills/decompose/SKILL.md`'s `Do NOT touch` field is where this case is dispositioned, and a fence that grants you the fix is the only thing that can grant it, since you may not widen your own. Where it IS silent you have one move when you find something untrue inside it: you cannot change the thing, so you report it — and the report you write from there is weaker than the one you would have written with your hands on the file. The mechanism is not carelessness and no amount of diligence removes it: **an agent that can edit verifies by editing** — it changes the thing and watches what breaks — **and an agent that can only report verifies by reading, to the depth a report needs rather than the depth a change needs.** Afterwards the two artifacts are indistinguishable, so a report written from a glance is trusted exactly like one written from a diff, and the line is the only thing that tells them apart. Write it beside the backlink — or at the head of the comment, where there is no backlink to sit beside — and write it as the fixed form above rather than a phrasing of your own: `skills/orchestrate/SKILL.md` §4 is the consumer, and it keys on that line to treat the issue's claims as unverified premises before any of them becomes a slice — a marker nothing reads is decoration, and a rule with no marker to key on is unreachable. **It is not a disclaimer and it does not lower the bar on what you file**: ground the claim as far as reading takes you, exactly as you would otherwise, then mark how far that was. *The failure this prevents, observed: four slices each found something untrue inside a file their brief fenced, and each filed. Three of the four could not be closed as written — one reported a constant naming a file as dead when the constant was dead and the file was live, read and written by a module one directory over and outside the fence; one's acceptance grep under-counted its own subject, naming five sites as the whole set where a hyphen-tolerant pattern found eight across seven files; one offered deleting a branch as its first reading and could not reach the fallbacks below it to establish whether they covered the same case, which they did not. The first one's false half then propagated: a later issue inherited it verbatim as a premise and stacked a second wrong claim on top, and neither its author nor the dispatcher re-checked either half. An issue saying a thing is already gone is the most reliable way to ensure nobody looks at it again.*

**Don't be lazy — leave the tree cleaner than you found it, and commit out-of-scope fixes separately.** Your job is not "make the assigned change and stop the instant the scoped check stops *erroring*." A check that exits green but still prints warnings is NOT done. Actively fix every lint warning, type warning, and error you hit or that your own change surfaces — even when it is technically out of scope: the residual unused imports a file is left with after you move its code to a sibling, a path-keyed lint allowlist (sanctioned-git / ambient-identity / ambient-network rules) that must follow the relocated code to its NEW file path, a stray nit in a file you only opened to read. The bar is **zero warnings and zero errors on every file your change touches.** **Isolate each such opportunistic / out-of-scope fix in its OWN commit** with a clear mechanism-explaining message (e.g. a `chore(lint): prune imports the split left unused` commit, kept separate from the `refactor: split …` commits) — so it stays independently reviewable and the dispatcher can keep or drop it without untangling it from the task. Never silently fold an unrelated fix into a task commit, and never hand back a "green" PR that still carries warnings for someone else to clean up. (If a surfaced fix is genuinely large, risky, or a behavior change, still isolate it in its own commit AND call it out in your report — don't bury it, and don't skip it.) **And the bar has a floor as well as a ceiling: what you cannot fix here, you FILE.** Residue too large or too risky to land in this slice does not become the user's by virtue of being left behind — it becomes a linked issue (*File your follow-ups before you hand back*, above). The two halves are one rule at two sizes: what fits, you fix here in its own commit; what doesn't, you file and link. A warning left behind and a follow-up left unfiled fail identically — the next agent finds the residue and no record that anyone ever saw it.

**And when you improve a bar without reaching it, leave a residual you can COUNT.** A partial fix is often the right call — the honest whole fix is too big for this slice, and landing the improvement beats landing nothing. What makes it a stopping point rather than a fudge is the *shape* of what is left: one blanket escape hatch replaced by three named assertions is finishable, because they can be grepped, counted and filed; the same improvement expressed as a slightly narrower escape hatch is not, because nothing separates what you reasoned about from what merely survived. So the leftover is a named cast, a listed exception carrying its reason, a ledger entry — never a widened type or a general suppression that happens to be smaller than the last one. Then file it, with the count in the issue. *The failure this prevents: a partial fix with an implicit residual is indistinguishable from a complete one, so nobody ever finishes it, and the next reader cannot tell which parts were decided from which were merely tolerated.* `skills/decompose/SKILL.md`'s scaffolding-and-teardown rule is the same instinct at planning scale — a ratchet is a countable residual with a slice already booked to drive it to zero.

**⛔ Never game a guardrail — fix the cause, not the number.** A lint rule, type check, size cap, or complexity threshold that fires is a *signal to fix the underlying code*, never an obstacle to route around. If a file trips a max-lines cap, **split it** — extract a cohesive module and re-export it from the barrel so consumers are untouched; do NOT shave comments, compact readable code, or nudge to one-line-under to sneak past. That ships *worse* code that merely passes — the exact opposite of what the check is for. Never silence a rule to go green: no bare `eslint-disable` / `oxlint-disable`, no `@ts-ignore` / `@ts-expect-error`-to-hush, no widening a type to `any`, no deleting the assertion the check flagged. Never sacrifice clarity — a dropped explanatory comment, a mangled refactor — to hit a metric. **Zero warnings AND zero errors on every file you touch is the bar** — a warning is not a lesser class you may leave behind: where the gate lints at `--max-warnings=0` a warning IS a hard failure, and even where it isn't yet, you still fix it. The only acceptable path to green is fixing what the guardrail pointed at; anything else gets caught and bounced at review. If the honest fix is genuinely too big for this slice, STOP and hand it back (see below) — do not paper over it.

**The one carve-out — a DOCUMENTED suppression, for when the flagged construct IS the intended behavior.** That is rare, and it is never "the check is wrong": it is that the thing the rule points at is the feature, so there is no cause to fix and "fix the cause instead of suppressing" has nothing to point at. (This plugin's own `bin/setup-worktree.ps1` is one — it suppresses `PSAvoidUsingInvokeExpression` on a single function, because a project's `install` config value is a command *line* (`pnpm install --frozen-lockfile`, possibly with a pipe) that must be **interpreted** rather than spawned as an argv, exactly as the bash sibling's `eval "$INSTALL_CMD"` does. Deleting it turns CI red; spawning an argv instead breaks every project whose install command carries a flag.) A suppression you ADD is permitted then, and ONLY when **all four** of these hold — it is gaming the moment any one of them fails:

- **Narrowest scope the tool allows** — one function, or one line. Never file-wide, and never a settings-file or config exclusion that switches the rule off repo-wide: a global exclusion is indistinguishable from deleting the check.
- **A written justification in place, through the tool's own mechanism** where one exists — `SuppressMessageAttribute`'s `Justification=`, a `// eslint-disable-next-line <rule> -- <reason>` — never a bare disable comment. This is the load-bearing condition, and the reason is the diff: a justification-bearing suppression puts a claim in front of a reviewer who can reject it, while a bare `// eslint-disable-next-line` asserts nothing and so cannot be argued with. Invisible to review is exactly what gaming looks like, which is why the mechanism matters and not just your intent.
- **The justification says why the flagged construct is correct HERE** — what the code does and why that is the behavior wanted. "Noisy rule", "false positive", "the check is wrong" are not justifications; they are the claim this carve-out exists to refuse. If you can't write the sentence without arguing with the check, you don't have an exception — you have the fix you were avoiding.
- **You call it out in your hand-back report** — file, rule, and the one-line reason — so it is reviewed at merge rather than discovered later by someone who has to reconstruct why it is there. A suppression nobody flagged is a suppression nobody reviewed, and gets bounced at review even when the other three hold.

**An EXISTING suppression is not yours to re-justify, and not yours to delete for compliance.** These four conditions test a suppression you are introducing; one that was already in the file when you opened it is the previous author's claim, already reviewed on the PR that added it. If you think it fails a condition, say so in your report and leave it — removing it is a behavior change you were not asked for, and load-bearing suppressions are exactly the ones a green-at-any-cost instinct removes first.

Nothing here softens the prohibitions two paragraphs up — a bare disable with no reason, widening to `any`, deleting the assertion the check flagged, shaving comments to duck a max-lines cap, nudging one line under a threshold. None of them can satisfy the four conditions, because for none of them is there a correct-construct claim to write down. **The failure this carve-out prevents:** an implementer who reads the rule as an unqualified absolute and then opens a repo that correctly violates it has two bad options — delete a load-bearing suppression to comply, or conclude the rule is violated in the repo that ships it and stop trusting it at all. A rule with an undocumented exception doesn't get followed carefully; it gets ignored wholesale. Stating the exception precisely is what keeps the default absolute.

**If you get stuck, hand back a reviewable artifact — never spin or die silently.** A blocker, an ambiguity you can't resolve, a scoped check you can't get green, or running low on room all mean the same thing: STOP and give the dispatcher something it can act on. Commit-push and open a **draft PR** with what you have (and enqueue it if it's far enough along to gate); if you can't even do that, hand back a complete report of your worktree state — what's done, what's broken, the exact error/blocker, and the decision you need. Partial-but-clean beats stuck-and-silent (e.g. land the solid part and flag the rest). **Never leave a dirty worktree with no PR and no report, and never leave a committed-but-unpushed branch — push and open a DRAFT PR so the dispatcher inherits a reviewable, mergeable artifact rather than invisible work trapped in your worktree.**

⚠️ **This sanctions handing back when you are BLOCKED — never handing back work you simply did not do.** It is the narrow rule, and read as the broad one it becomes "list what is left and stop", which is exactly the defect the follow-up-ownership rule names. The test is mechanical and takes a second: **if you can still act on it, it is not a blocker.** You can fix it — do that, in its own commit. You cannot fix it here but you can describe it — file and link it as a follow-up. Only what you can do neither of those to is what this paragraph is for. *The failure this prevents: a hand-back reporting a blocker and a hand-back reporting an unfinished intention look identical on the dispatcher's side — both are prose naming work that did not land — so a paragraph that legitimizes the first, read loosely, launders the second.*

**A missing input is a hand-back, not a value to invent — and this is the one that will NOT feel like being stuck.** The paragraph above covers blockers you can see. This covers the opposite: your brief needs an id, a key, an owner, a path, a version — something that identifies a real thing — and the thing does not exist yet, or you cannot reach it from where you are. Nothing is erroring. You can produce a value of the right *shape*, and everything downstream will accept it: the types are satisfied, the scoped check is green, the tests pass, the PR reads clean. **That is precisely the failure.** A fabricated identifier does not fail loudly at review; it records the wrong fact, permanently and quietly, and every guardrail you have confirms it. So when the input names something real and you cannot obtain the real one, STOP and report exactly that — what you needed, why it was not available where you stand, and what the dispatcher must decide (dispatch it later, hoist a wave-0 slice, or hand you the value). *The failure this prevents: an implementer that could not obtain an owning identifier at the point its slice ran, declined to synthesize one, and reported the gap — where a plausible substitute would have passed every check while silently attributing the work to the wrong thing.* Shape-correct and fact-wrong is the hardest defect class to find later, because nothing about it looks broken.

⚠️ **Narrow in the same way, and for the same reason: this covers an input that names a real thing you cannot obtain — not a decision you would rather not make.** A gap that an existing pattern, `AGENTS.md`, or a plainly obvious default already settles is not a missing input at all: adopt the answer, write the assumption down in your report, and move on. `skills/decompose/SKILL.md`'s *Step 2 — Validate the plan and fill the gaps* is the canonical statement of that split — fill what the grounding already answers, escalate only what it genuinely cannot — and it binds every role here, not just `decompose`. *The failure this prevents: escalating a settled question spends a user turn on something the repo already says, and each one teaches the next reader to route around a rule that fires too often — so the escalation that actually matters, the fabricated-identifier one this paragraph exists for, arrives already discounted.*

**Evidence that contradicts your brief is a finding you report, and producing it IS the job.** A brief is written from the plan, one step further from the code than you are standing: by the time you are in the worktree you can read the thing it describes, and sometimes it is not what the brief says it is. Follow the source and say so — plainly, in your report, naming what the brief asserted and what the code actually does. **Do not make the stated thing compile.** This is the stronger form of `decompose`'s `Assumes X (existing pattern in <file>); flag if wrong`, which only ever covers what a dispatcher *labelled* as an assumption; the damage comes from what a brief states as settled fact, because an implementer does not challenge a coordinate presented as established. *The failure this prevents: the incentive runs the wrong way unless this is said out loud. Contradicting the brief reads as scope creep and costs a paragraph to defend, while implementing the assertion is cheap and comes back green — so the dispatcher's error becomes your output with a gate's endorsement on top, and the brief stays the only record that anyone ever believed it. An implementer that overturns a false assertion with evidence has done more of the job than one that merely satisfied it, not less.* **A correction that arrives from your reviewer is a claim of the same kind.** A dispatcher reading your PR is standing one step further from the code than you are, exactly as the brief's author was — and a correction it reached by calling a module directly is evidence about that module, not about the path production takes. Answer it with the call path; where it is right, say so and fix it. (*The PR review loop* carries the reviewer's half of this, and the run where a reviewer made this exact error while auditing the fix for it.)

**A brief that contradicts ITSELF is the same finding, and the shape to watch for is a boundary that forbids the verify bar the same brief demands.** A `Do NOT touch` is written to fence production code; a verify bar routinely needs the *test* file beside it, in the directory that glob names. A fence over a directory covers behaviour and not the tests under it unless the brief says otherwise, so the ordinary case resolves itself — take the test file, and **say in your hand-back that you did**, since a diff landing inside a fenced directory is exactly what the dispatcher's divergence check is watching for and it cannot read your reasoning off the paths. Where the brief *does* say otherwise, or names the test file outright, and the bar still needs that file, the two halves genuinely contradict and you have three moves of which two are silent. Drop the test and the bar evaporates with nothing to mark it. Breach the fence and you do the thing the fence existed to prevent, which on a security or authorization boundary is the entire hazard your slice was scoped around. The third — parking the assertion somewhere else — is the one that looks most like compliance and can be worth nothing, since an assertion placed outside the module it is about is exactly as green as one placed correctly. **You do not get to widen your own fence and you do not get to quietly narrow your own bar**, so this is a report, not a judgement call: name the file the assertion needs, the instruction that forbids it, and hand the choice back to whoever wrote both. *The failure this prevents: nothing errors on any of the three moves, and a diff read afterwards cannot tell a verify bar that was dropped from one that was never load-bearing — so the resolution that costs you the least is also the one nobody can audit.* `skills/decompose/SKILL.md`'s `Do NOT touch` field is where the contradiction is supposed to be settled before it ever reaches you; this is what to do with the ones that get through.

**A brief that asks you to derive something from a source you cannot reach is the same finding wearing a different shape, and the silent move here is transcription, not one of the three above.** `skills/decompose/SKILL.md` Step 3's closing check now names this as its own pair: a `Brief` that says *derive X from Y* is unsatisfiable when Y does not resolve from where your worktree sits, however real Y is elsewhere in the tree. The compliant-looking move is not to skip, breach, or park — it is to write down, by hand, the values the derivation would have produced. That output can be entirely correct, the slice green, the diff clean, and the brief's false premise never contradicted anywhere, which is exactly what makes it the most dangerous of the four. **A derivation you had to satisfy by transcription is a finding you report, whatever the output looks like** — name the source, where it actually sits, and why it does not resolve from here, rather than silently hand-writing the values and moving on. *The failure this prevents, observed: a slice told to derive its field set from a map on the wrong side of a workspace boundary did exactly that, correctly, and the premise surfaced only because the dispatcher happened to read the diff.*

**An enumeration a brief hands you is a FLOOR on what your change must reach, and one that comes back short is a FINDING — never evidence that you have misread your own scope.** The consumers, the call sites, the declarations of a chain: every such list came out of a command *somebody* ran, and `skills/decompose/SKILL.md` Step 1's *An enumeration is a claim* is why a list cannot vouch for its own length. Read the argument there rather than a copy of it here; what is yours is what to do standing in the tree with a set bigger than the brief's. **The list is the floor on reach and the `Do NOT touch` fence is the ceiling on edit** — two different fields, and the second is the one that governs your hands: **land** the member the list missed where no boundary covers it, **stop and report** where a fence or a sibling's `Owns` does, and **report it either way**, because every other slice in the wave was sized against that list. The Dispatcher section's *Scope + hard do-not-touch boundaries* is the authoring end of the same pair — your brief is supposed to arrive carrying this sentence, and this is what to do when it does not. **This is not the finding *A brief that contradicts ITSELF* names, and that rule structurally cannot reach it**: a short enumeration lists real files, in the right format, reconciling with every other field the brief carries, so the brief is internally perfectly consistent and there is nothing in it to contradict; the claim is false against the **tree**, and nothing you can read off the brief alone will say so. **And your own enumerations are held to the identical bar, whether or not anybody handed you one:** the greps you run to find what your change must touch are the same claim made by you, so take the count from the command that filtered nothing before you treat the set as your scope. A direct implementer — one entered by being told to *build / fix / implement* a specific thing, with no dispatcher and no brief — authors every enumeration in its slice itself, and this half is the only statement of the rule that reaches it. *The failure this prevents runs the same way at both ends and is silent at both. Told nothing, the one party actually standing in the tree reads its own nineteenth hit as evidence it has misread the boundary and discards the answer — and where the brief skipped the sentence, or where there is no brief at all, there is nothing anywhere for it to check that reading against; the short set simply becomes the change.*

**A measured value your brief hands you is a cross-check, never your baseline — re-measure it here, and report your delta against YOUR number.** A test count, a timing, a row count, a file count, a hit count from a sweep: the dispatcher gathered it somewhere, and *somewhere* is routinely a different tree from yours — a slice's own hand-back rather than the tip, one branch's total quoted as a merged one, a figure taken before the last two merges landed. So measure it yourself before you change anything, and where the two differ, **yours wins**, because it is the only one taken in the tree the work is being done in. Say so plainly rather than substituting it silently. **This is not the fork-point rule below**: that one settles what a measurement is taken *against*, and this one settles *whose* measurement wins when there are two. **Where the brief hands down a number and does NOT say which one wins, name that gap in your hand-back rather than adjudicating it on your own** — a rule that settles a disagreement is worth something only while it predates the disagreement, and arriving afterwards it is indistinguishable from either party defending its own figure, with nothing available to separate them. *The failure this prevents: an implementer that takes a handed-down baseline as its own and measures higher afterwards reports a phantom regression, or spends a run hunting a break it never caused — and the dispatcher is the party least able to catch it, because the number looks authoritative precisely because it wrote it down. The Dispatcher section's* A measured value you did not measure in THIS tree *is the authoring end of this pair; this is what to do when a brief reaches you without it.*

**Before you report a NEGATIVE from your verify bar, measure it against the FORK POINT — never your own last commit, and never `HEAD`.** *X is unchanged*, *no new Y*, *that grep comes back empty*: each is a claim about a difference, so it is worth exactly as much as the base it was taken from. `git merge-base HEAD origin/<base>` is that base — the tree as it stood before your slice existed. Your own previous commit is not: it is **inside** the change you are asserting about, so a claim checked against it is a claim about a fragment of your own work and comes back true whatever the work did. `HEAD` is worse than either, because it shows only uncommitted changes and goes clean the moment you commit, at which point the claim holds against nothing at all. **Where the honest answer is narrower than the bar's phrasing — the output is unchanged *for a caller who has not opted in*, rather than unchanged — report the narrow one and say which it is**; *A brief that contradicts ITSELF* above is why the wording is not yours to quietly widen or narrow. **This is not the trap the dispatcher's two fork-point rules guard, and blurring them costs you both**: theirs is a baseline that **moves** — the integration tip advancing under an open worktree, so a sibling's merged work reads as this branch's phantom deletions — while yours is one that is too **close**. `skills/decompose/SKILL.md`'s `Verify` field carries the argument and the observed failure; this is the same rule at the end that runs the check. *The failure this prevents: nothing downstream can separate a negative measured from the fork point from one measured from your previous commit — both arrive as a single confident sentence in a hand-back, and the second is true by construction, so it clears the bar, survives the gate, and reads in review exactly like the check that was actually performed.*

**A verify bar's command is an INSTRUMENT and the sentence beside it is a PROPERTY — a command that could not have fired is a finding, not a pass.** Every rule above is about a bar you cannot satisfy; this one is about the bar you satisfy trivially. An instrument **narrower** than its property fails a correct slice, and you find out, because you are stuck. One that is **wider** — or that has **no instances at all** on the files it names, a grep for a construct the target does not contain — comes back green carrying no information, and green is what this flow reads as a bar met, so nothing after you can tell it from a sweep that ran and found the target clean. So before you report a bar green, ask whether its command could have gone red at all on the tree you are standing in; where it could not, **report that the instrument could not fire, and name the property you read it as standing for**, rather than reporting the bar passed. `skills/decompose/SKILL.md` Step 3's `Verify` field carries the argument and the observed failures; what is yours is that you are the first party to run the thing and the last that can see it did not run. *The failure this prevents: your other two moves are both silent — obey an instrument you can see is wrong and nothing in the diff afterwards says why, or declare the bar met on your own reading of what it obviously meant and nothing records that you substituted your judgement for the bar. Every instance this corpus has recorded was caught here rather than by the seat that wrote the bar, which is the one seat with no say in what the bar said.*

## Hard rules (both roles)

- **⛔ Implementers never run the full suite — by any invocation, foreground or background; they enqueue it.** The heavy build+test gate runs one-at-a-time in a runner drained from the durable queue, behind a slim machine-wide slot. An implementer's quality bar is the cheap scoped check (enforced by the pre-commit hook) plus at most a single targeted test file; its wrap-up is push → draft PR → enqueue. The ban is extensional — it covers `gate`, `turbo run test`, raw `vitest` sweeps, and package `test` scripts alike — and **backgrounding a banned run (`run_in_background`, `&`, `nohup`) is still running it**, not a way to comply with "don't wait." The only exception is override gate mode, which is reached two ways: a slice **explicitly** put there by the dispatcher's brief (or the dispatching user) — never self-granted — **or a project that declares no `enqueue` and no `drain` at all, where *Per-project config* makes gating in-line the DEFAULT rather than a grant.** Either way the implementer runs `gate` itself once, in the foreground, and comments the result on its own draft PR; on a queueless project the wrap-up above therefore ends at that comment rather than at `enqueue`, because that command does not exist there. Those two readings are settled in *Per-project config*'s no-`enqueue`/`drain` bullet and in the Implementer section's *You do NOT run the full gate*, which stay authoritative — this clause exists only so that reading this bullet alone cannot contradict them. *The failure this prevents: an implementer on a queueless project comes to this section for absolutes and, from a bullet whose sole exception was an explicit grant it never received, derives both that it may not gate at all and that its handoff is a command the project does not define — which is exactly the run **Per-project config** predicts ending with committed work and no handoff. The plugin's own repo is one of those projects, which is where the gap surfaced.* Never hand-run a `gate` concurrently with a live drain — the runner already serializes gates; a concurrent one re-creates the saturation the slot prevents. **This ban is keyed to the run, so it structurally cannot reach a check the implementer is ALLOWED to run — the companion rule keyed to the handoff is the Implementer section's *Never background a check and end your turn on it*, which is the authoritative copy.** Read the scope and the observed failure there rather than here: two statements of one rule drift, and nothing marks which one is stale.
- **⛔ Never use the Agent tool's `isolation: "worktree"` param or any auto worktree provisioner.** Make worktrees only via `setup-worktree.sh`, verify HEAD, then dispatch a plain agent. (See worktree section.)
- **⛔ The three `trinity-ai-labs` skills repos — `market-skills`, `orchestration-skills`, `framework-skills` — are PR-only, never a direct push to `main`, docs and CHANGELOG included.** Each ships to installs pinned by `.claude-plugin/plugin.json`'s `version`, so a change here reaches users exactly as any other repo's does; and in a repo whose product is prose, the diff is the only review artifact there is, because no gate can tell whether a rule is *correct*. A direct push spends the review record to save a worktree.
- **⛔ Only the merge marks a PR ready — the flag is the reviewer's signature, never a gate verdict.** `draft → ready` means "a dispatcher read this diff and is merging it", so the only thing that sets it is `merge-pr.sh` in the same breath as `gh pr merge`. Implementers never set it, in any gate mode; the gate never sets it, in either direction — it comments its verdict and leaves the PR draft. That gives one reading that holds everywhere: **a PR is gated iff it carries a gate comment**, and a non-draft PR that isn't being merged right now is a bug. Keeping the flip adjacent to the merge is what stops `ready` from going stale — a flip set earlier survives the next push and then vouches for a diff nobody read.
- **Never squash-merge; merge + clean up + sync as one step.** Prefer `merge-pr.sh <pr-number>`, which does the whole close-out atomically (tear down worktree → real merge commit → fast-forward the local integration branch). If you merge by hand, use a real merge commit (`gh pr merge --merge --delete-branch`), never `--squash` — squashing flattens the individual commits we keep. **One carve-out exists and it is defined in full at *The epic branch* → *Mechanics*, which is the authoritative copy:** an epic branch's own collapse back into the integration branch, in a project whose `.agents/worktree.json` declares `"epicMerge": "squash"`, when that integration branch is not the repository's default branch. Read the two conditions and the tree check there before acting on it; what belongs here is the shape of the exception rather than its mechanics — **it is an option a project declares, never a judgement anyone makes at merge time, and never something an implementer or a dispatcher decides for one PR.** Nothing else in this flow is ever squashed, the default is `merge` everywhere, and a project that has not declared the key has no exception at all. Always pass `--delete-branch` so the remote branch is removed on merge instead of accumulating — but **remove the worktree first** (see Merge & cleanup), or `--delete-branch` errors trying to delete a branch still checked out in a worktree. **And always finish with the local integration-branch sync**, anchored to the main checkout (`git -C <main-checkout> pull --prune --ff-only`) — never the unanchored `git checkout <integration> && git pull`, whose `&&` silently swallows the pull when your cwd is inside a worktree, leaving the branch merged-on-remote but stale locally and the next worktree forked off a stale HEAD.
- **Do NOT rebase.** Rebasing rewrites history. Default to plain merge commits everywhere: integrating parallel worktree branches, a branch falling behind the integration branch, resolving overlap between two PRs — MERGE, never rebase. If two parallel branches touch the same file, resolve it at MERGE time (merge one, then merge the other and fix conflicts in the merge), not by rebasing one onto the other. Never instruct a sub-agent to rebase. Only rebase when there's a specific, unavoidable reason AND it's worth rewriting history — rare; when in doubt, merge.
- **⛔ Park work under a named ref of your own — never on `refs/stash`, and never blind-pop what is already there.** `refs/stash` is a **stack addressed by position**: the main checkout and every linked worktree of a repo push onto and pop off the *same* one, `git stash list` in any tree lists every other tree's entries indistinguishably from its own, and `stash@{n}` renumbers on every push and every drop anywhere in the repo. Nothing about an entry identifies its owner either — git's auto-generated `WIP on <branch>: <sha> <msg>` subject is identical for two agents on one branch, and for one agent resumed after a stall. **A named ref removes that whole class instead of policing it, and it is the documented mechanism rather than a trick:** `git stash create` "create[s] a stash entry (which is a regular commit object) and return[s] its object name, **without storing it anywhere in the ref namespace**", and `git stash apply`'s argument "may be any commit that looks like a commit created by `stash push` or `stash create`".
  - **Park it — the ref exists before anything is discarded, which is the entire safety property.** `create` saves; it does not clear. You clear the tree yourself, afterwards:
    ```sh
    REF="refs/pipeline-stash/<branch-leaf>/<epoch>"
    SHA=$(git stash create "<why you are parking>")   # a commit — touches no stack
    git update-ref "$REF" "$SHA"                      # saved, and named
    git checkout -- .                                 # only now clear the tree
    ```
  - **Restore it by that name:** `git stash apply --index "$REF"` (the `--index` restores the staged/unstaged split too), then `git update-ref -d "$REF"`. **`git stash pop` is stack-only and refuses a named ref** — `error: '<ref>' is not a stash reference` — because it has nothing to drop from a reflog it never wrote. Apply-then-delete is the two-step equivalent and it fails safe: a conflicted apply leaves the ref intact, so the work is still parked while you sort it out.
  - **What that buys is the whole failure at once.** Nothing renumbers it, so there is no index to re-resolve and no window in which to be wrong. No other tree's `push`, `pop`, `drop` or **`clear`** can reach it. The name carries its owner, so work that outlives a turn stays attributable. And `git for-each-ref refs/pipeline-stash` enumerates every tree's parked work in one call from anywhere in the repo — the sweep on the dispatcher's tick (*Draining the gate queue*) reads exactly this.
  - **The namespace is a plain global one — `refs/pipeline-stash/…` — and NOT `refs/worktree/…`, which is the trap that looks like the better answer.** `refs/worktree/*` is git's own per-worktree namespace and it genuinely is private per tree (two worktrees hold that same ref name pointing at different commits, and `git worktree`'s REFS section says those refs "are not shared"), so it reads as purpose-built for exactly this. **It is not gc-safe from outside its own tree, and the mechanism is the same sentence that makes it attractive.** A gc keeps everything reachable from the refs *the invoking worktree can see*, and a sibling's per-worktree refs are precisely the ones it cannot: verified on git 2.50.1, a linked worktree's `refs/worktree/park` is absent from the main checkout's `git rev-list --all` while present in its own, so **`git gc --prune=now` run in the main checkout deletes the object** — leaving the ref resolving to nothing, `git fsck` reporting `invalid sha1 pointer`, and the next repack dying on `fatal: bad object`. (The main checkout *can* read it deliberately, through the documented `worktrees/<name>/refs/worktree/…` path; being reachable on request is not the same as being in the root set.) A ref in a global namespace is in every tree's root set and survives the same gc untouched. *The failure this prevents: gc runs on its own schedule, fired by whatever any tree happens to be doing, so parked work is simply gone when its agent comes back for it — and because the ref still resolves, the symptom presents as a broken `apply` rather than as a collected object, which sends the debugging somewhere else entirely.*
  - **A shared namespace is not a shared stack, which is the objection to have ready.** `refs/pipeline-stash/*` is repo-wide exactly as `refs/stash` is; what made the stack dangerous was never the directory but the **addressing** — a positional handle that renumbers under you, and a `pop` that takes whatever is on top. A ref addressed by `<branch-leaf>/<epoch>` has neither: no other tree can name it by accident, and nothing consumes it implicitly. Keep out of git's own reserved namespaces (`refs/heads`, `refs/tags`, `refs/remotes`, `refs/notes`, `refs/replace`, `refs/original`, `refs/bisect`, `refs/worktree`, `refs/rewritten`); everything else under `refs/` is free.
  - **What parking there costs, and it is worth knowing before you park.** It is invisible to `git stash list`, `git stash show` and `git stash drop`, which only ever read `refs/stash` and its reflog — and therefore invisible to the stash panel of every IDE and git GUI, which read the same thing. So a human who goes looking for their agent's parked work in the UI will not find it; the ref is the only handle, which is why it goes in your hand-back if it somehow outlives your turn. The flip side is durability: a ref outside `refs/heads`/`refs/remotes`/`refs/notes` gets no reflog by default, so no expiry clock ticks on it and the commit lives until someone deletes the ref — better than a buried stack entry, which survives only as a reflog entry subject to `gc.reflogExpireUnreachable` (30 days by default). It also never leaves the machine: default push and fetch refspecs cover `refs/heads/*` only, so a custom namespace is local unless someone writes an explicit refspec. **Durable and unsweepable is exactly why the tick sweeps it** (*Draining the gate queue*) — refs nobody owns accumulate silently, and a parked commit that outlives the epic that made it is dead weight in the ref store with no one left who knows what it was.
  - **What `create` does NOT capture is untracked files, and it will not tell you.** It records tracked changes only, and it **silently accepts and ignores `-u`**: `git stash create -u` returns a commit with no untracked parent where `git stash push -u` produces one, and the docs give `create` no options at all. Nothing is destroyed — `git checkout -- .` leaves untracked paths alone — but they are not in the parked commit, so anything new that must travel with the change gets `git add`ed first, or committed if it belongs on the branch anyway.
  - **The fallback, for anything already on the stack — and never a blind pop.** A human's stashes live on `refs/stash`, and so does any entry an older agent left; both are untouchable unless you can name them. So every `pop`, `apply` and `drop` against the stack carries an explicit ref you re-matched one command earlier, and **an argument-less `git stash pop` is never correct in this flow** — not immediately after your own push, and not when `git stash list` comes back with exactly one entry. **That single-entry case is the one that gets rationalized and it is the weakest evidence on the list**: the list is repo-wide, so "one entry" means one across the main checkout and every live worktree at the instant you looked, and the gap between your two commands is precisely when a sibling tree pushes. If you do push there, push with a marker — `git stash push -m "pipeline-stash/<branch-leaf>/<epoch>: <short purpose>"` — and re-resolve it immediately before you touch it, never from an index you stored earlier in the turn:
    ```sh
    MARK='pipeline-stash/<branch-leaf>/<epoch>'
    REF=$(git stash list --format='%gd %gs' | grep -F -- "$MARK" | cut -d' ' -f1)
    N=$(git stash list --format='%gs' | grep -c -F -- "$MARK")
    ```
    `N` is the decision, not `REF`: **exactly one** → `git stash pop "$REF"`; **zero, or two or more → STOP and report.** Never fall back to `stash@{0}`, and never pick one of several — your entry not being where you left it means something else moved the stack, and that is the moment to hand back rather than to guess. *The failure this prevents: this rule is not broken on purpose, it is broken by habit. `git stash pop` is one of the most automatic commands there is and it is correct in a single-checkout repo, so the instinct arrives already justified and never reaches the paragraph above.*
  - **Never `git stash clear`, and never drop an entry you did not create.** `clear` destroys every other worktree's entries and the human's in one command, with no confirmation and no UI-level recovery — `git fsck --unreachable` only, and only until the next gc. It cannot touch a named ref, which is half the reason to park there.
  - **Never end a turn with parked work of yours still around.** Restore it or delete it before you hand back; if you truly cannot, name the exact ref and the restore command in your report. A named ref is at least attributable forever, where an orphaned stack entry whose worktree is later torn down is one nobody can ever safely pop.

  *The failure this prevents: in a repo with the main checkout and two slice worktrees all live — this flow's default dispatch shape, not an edge case — all three had stashed, and a bare `git stash pop` in one slice worktree applied the main checkout's stash into the slice and dropped it from the stack. The human's WIP was gone from where they left it and sitting silently in an agent's worktree, and nothing errored. Every property above is aimed at that one run: parking under a named ref is why it cannot happen, and the fallback is what to do when you are standing on the shared stack anyway.*
- **⛔ The quality pass is `/pipeline:review` — never the bundled `/simplify` — it is the dispatcher's per-slice call, and WHEN it runs, commit LAST.** Use this plugin's own skill: it runs inline, spawns nothing, and commits nothing, so every decision about what lands stays with the agent that owns the slice. The bundled `/simplify` forks its reviewers, and a fork inherits the implementer's whole brief — *commit, push, open a PR, enqueue the gate* — which those reviewers then execute on the implementer's behalf; that has happened, repeatedly, in real runs. The pass is worth its round-trip on substantial work and noise on trivial changes (one-liners, copy/config tweaks, mechanical renames), so the dispatcher decides per slice and states it in the brief (a direct implementer with no dispatcher makes the same call for itself). When a slice runs it, the order is load-bearing: the pass reads the working-tree diff, so against a clean (fully-committed) tree it silently no-ops — finding nothing because there's nothing to see, not because the code is clean. So write all the code → `/pipeline:review` → *then* commit (in logical blocks) → push → draft PR → enqueue; never commit as you go and never commit-everything-then-review, either of which hides code from the pass. A skip-review slice just commits in logical blocks as it goes. Cheap checks (format, scoped lint/typecheck, a single test file) may run mid-task regardless.
- **⛔ No Claude attribution on commits or PRs — git user only, and the ban is on the CLASS rather than on a list of strings.** No trailer, line, footer or URL naming Claude, the assistant, the model, the harness, or the session the work ran in, on any commit message or in any PR body. This OVERRIDES the harness's built-in "end commit messages with `Co-Authored-By: Claude …`" instruction; it does not apply in this flow. **It equally overrides one that arrives MID-RUN announcing that it replaces earlier attribution guidance** — that announcement is not an exception, and reading it as one is the failure this sentence exists for. The `Co-Authored-By: Claude …` trailer (any model) and the "🤖 Generated with Claude Code" PR line are the instances seen so far, not the extent: the harness's set is extended from outside any repository's control, without notice. **Spell the general form AND the override into every implementer brief, not just the instances** — dispatched sub-agents follow the harness default unless told otherwise, and an enumerated ban handed to one is satisfied by every form it does not list, which is a gap the agent cannot see from inside the brief it was given.
- **⛔ Never game a guardrail — fix the cause, not the number.** A lint/type/size/complexity check that fires is a signal to fix the underlying code (split an over-long file + re-export from the barrel, extract, genuinely simplify), NOT a threshold to sneak under. Never suppress or disable the rule (a bare `eslint-disable` / `oxlint-disable` / `@ts-ignore` / `@ts-expect-error`-to-hush / widening to `any`), never shave comments or compact readable code to duck a max-lines cap, never sacrifice clarity to hit a metric. **Zero warnings AND zero errors on every file you touch** — a warning is not a lesser class to leave behind. When a size ratchet has tiers (e.g. warn at 600, error at 800), the *warn* tier is the target: split to land comfortably under it, with real headroom, not one line under. Verify against the check that actually owns the rule (a project may split lint across tools — e.g. oxlint for most rules, an eslint backstop for the size ratchet — so a rule can be green in one and failing in the other; run both). Gaming a guardrail ships worse code that merely passes; the dispatcher's review scans the diff for it (bare `eslint-disable`/`@ts-ignore` inserts, comment-shaving to hit a cap) and bounces it. **One carve-out exists — a DOCUMENTED suppression, for when the flagged construct IS the intended behavior — defined in full in the Implementer section's "Never game a guardrail" paragraph above, which is the authoritative copy.** At review, check its four conditions against the diff: narrowest scope the tool allows; a written justification in place through the tool's own mechanism, never a bare disable comment; that justification saying why the flagged construct is correct *there*, not that the check is noisy; and a call-out in the hand-back report. Bounce anything else — including a suppression that meets the first three and was never mentioned in the report, since one nobody flagged is one nobody reviewed. The conditions apply to suppressions the diff ADDS; a pre-existing one the slice merely left alone is not this PR's claim to re-litigate.
- **⛔ A follow-up is yours until it concretely requires the user — file it, link it, fold it into the run.** The work your change creates or reveals — the residual cleanup, the doc it made stale, the second call site, the missing test, the rename you started — belongs to whoever surfaced it, in both roles. For each one you do not land in this PR: **look before you create** — `skills/write-issue/SKILL.md`'s *Before you file, search what is already filed* decides whether there is a new body to write at all, since an open issue already carrying that failure takes the observation as a comment, and a closed one makes the item a regression only where the fix that closed it is present in the copy you read — version skew rather than a finding where it is absent, and an explicit *cannot tell* where neither is established — then write it up as a real issue with `/pipeline:write-issue`, **link it** to the originating issue or umbrella — **and under an umbrella that is two links, not one: the body backlink AND the native `sub_issues` POST**, whose call, database-id trap and containment condition are in the Implementer section's *File your follow-ups BEFORE you hand back*, the authoritative copy — **decompose it** with `/pipeline:decompose` if it is more than one slice, and **fold it into the orchestration** — a new slice in the current run, or an explicitly-deferred tracked item. It becomes an artifact in the pipeline, never a bullet in a hand-back that reads like progress. The **only** sanctioned hand-off to the user is a genuine fork — a design decision with no house answer, or a product call the codebase and conventions cannot settle — asked the way `skills/decompose/SKILL.md`'s *Step 2 — Validate the plan and fill the gaps* already prescribes for every gap in this pipeline: in plain chat, one question at a time, with your recommendation and why. An existing pattern, `AGENTS.md`, or a plainly obvious default settles most gaps — adopt it, state the assumption, move on. *The failure this prevents: a hand-back listing "flagged for follow-up: X, Y, Z" is indistinguishable from thorough work, and it converts the agent's job into the user's backlog. Each punted item costs a triage decision they have no context to make, and every one of them is cheaper to handle in the worktree that is already open, already installed, and already holds the change that caused it than in any later session that has to rebuild all three. Untracked, it is not a follow-up at all — it is a defect with a polite name.*
- **Branch from the branch the work converges on, never `main`.** That is the **epic branch** when a multi-slice epic has cut one (*The epic branch* — single-slice work never cuts one), and the **active integration branch** otherwise. A PR targets the same branch its worktree was cut from, so the two can never disagree. That includes a follow-up the work itself surfaced: it converges where the arc that produced it does, so while an epic branch is live it targets the **epic branch** too (*The epic branch*). That is the case that most often escapes this rule, because a follow-up feels like new work rather than like part of the arc that produced it.
- **Never delete a branch past git's "not merged" warning** — verify fully merged into the target first. **The one place that refusal is overridden is not an exemption from this rule; it is the same question answered by a different instrument.** On a squashed epic → integration close-out the warning fires *every single time* and carries no information, because a squash commit has no second parent and the epic branch is therefore never an ancestor of the new tip — ancestry is broken by construction, not by anything going wrong. What has to be true instead is that what landed is what was gated, which is a question about **trees**: `merge-pr` compares the epic tip it captured before the merge against the squash commit, and deletes only when that comes back empty. Both `only`s are load-bearing and neither travels: **only** on that path, and **only** after that comparison has passed — the stop on a failed comparison *is* the guard `git branch -d` would otherwise have been, not a formality standing between the check and the delete. Everywhere else, including every slice branch and every merge-path epic branch, the warning means exactly what it says and you STOP. *The failure this prevents is the habit, not the command: an agent that learns to wave a not-fully-merged warning through carries that reading to the merge path, where the warning is the only thing standing between a delete and losing an unmerged branch — so the exception has to arrive as a substitute check that must pass, never as permission to ignore a warning.*
- **⛔ Don't bypass the shared build cache — run tasks through the runner.** Cache-eligible tasks (test, typecheck, lint) must go through the task-runner — the project's `scopedCheck`/`gate`, or `turbo run <task> --filter=<pkg>` — NOT the raw binary (`vitest`, `tsc`, `eslint`) and NOT a per-package script that shells straight to it (`pnpm --filter <pkg> test` when that script is a bare `vitest run`). A direct run always goes cold — locally *and* in the drained gate — and never populates the cache for the next machine/CI. The only sanctioned direct-binary run is a **single targeted test file**. If a project's `AGENTS.md` documents the raw form as the whole-package default, that's a leak to fix, not a pattern to copy into briefs.

**Why this shape:** integration branch as the merge point, isolated worktrees per task, clean up after merge. The heavy gate is decoupled from the flaky sub-agent that produced the change — implementers enqueue a durable ticket and hand back; robust dispatchers drain the queue and gate one-at-a-time — so a dying agent never strands committed work and a wide fan-out never serializes on a lock. We preserve real merge history rather than flattening it via squash or rebase — with one boundary a project may opt to collapse, the epic branch's own merge back into the integration branch, which is scaffolding rather than history (*The epic branch* → *Mechanics*). Skipping the post-merge local sync leaves the local integration branch behind the remote, so the next worktree gets cut from a stale HEAD.
