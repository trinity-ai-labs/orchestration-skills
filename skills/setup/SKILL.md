# setup — onboard a repo onto the pipeline

`/pipeline:execute` — the pass `/pipeline:orchestrate` invokes to ship each increment — cuts a worktree per task and expects each project to declare how it builds, checks, and gates itself. That declaration is `<repo>/.agents/worktree.json`. This skill writes it, and scaffolds the gate queue when the project wants one.

**The artifacts live in the project, not in this plugin.** The plugin stays markdown plus four thin helpers, each shipped in both shells; the repo gets its own `worktree.json` and its own queue scripts, which it then owns and evolves. Two projects' queues *should* be allowed to diverge — one may grow transient-red baseline handling the other never needs.

## Why an unconfigured repo is worse than an obviously-broken one

`setup-worktree.sh` does not fail when config is missing. It prints a note **to stderr** and cuts a bare worktree — no env symlinks, no `node_modules`. **Where the project has an install step**, an implementer dispatched into that worktree then fails its checks for reasons that look like code bugs, and burns a run before anyone notices the real cause. A zero-dependency project escapes that particular failure — a bare worktree is the only kind it has — but not the rest of it: with no config, the gate command, the conventions, and the framework skills are all things the dispatcher has to guess, and a guessed gate is one that passes while testing nothing. Treat "no config" as a hard stop, not a warning.

## Step 0 — Decide how much of this the repo actually needs

Most repos are not Trinity-shaped. Adopting machinery a project doesn't need is a cost, not a safety net — decide the tier first and say which you picked.

| Tier | Looks like | Config |
|---|---|---|
| **No flow at all** | A scratch or single-author repo with nothing to isolate and no check to run — you edit `main` and push | No `worktree.json` needed. Say so and stop |
| **Worktrees + a check** | Isolation is useful, but the check runs in seconds. This plugin's own repo is one | `gate` == `scopedCheck`; no `enqueue`/`drain`. Often no `install` and no `envFiles` either |
| **Worktrees + gate + queue** | The gate takes minutes, saturates the box, and several tasks run in parallel | The full set |

**`gate` and `scopedCheck` being the same command is a normal, correct answer.** It means the repo has one authoritative check and no separate heavy tier. Don't invent a heavier gate to fill the key — a fabricated `gate` is a command that either doesn't exist or tests nothing.

**A repo with no queue is normal too.** Omit `enqueue` and `drain`, and the implementer runs the check itself and comments the result on its own draft PR — `/pipeline:execute` reads their absence as "this project gates in-line". The PR is still a draft at hand-back; only who runs the gate changes.

Keys you have no honest value for are **left out**, never guessed. A markdown repo has no `install` and no `envFiles`; writing `"install": "npm install"` into it produces a worktree setup that fails every time.

**One key breaks that rule, and only because for it an empty value is an answer rather than a blank: `sharedResources`.** Everywhere else, absent and empty mean the same thing to every reader. There they mean opposite things — a missing key says nobody asked what the checks touch outside the worktree, `[]` says somebody asked and the answer was nothing — and a dispatcher reads the second as licence to fan out. So write `[]` when you have established there is nothing, and leave the key out only when you genuinely could not ask. *The failure this prevents: "no honest value, so leave it out" is the correct instinct applied to the one key where it destroys the finding — the two files are byte-identical apart from four characters, and the tested answer is the one that goes missing.*

## Onboarding a polyrepo workspace

If the target is a **containing folder of sibling repos** rather than a repo — no `.git` at the root, several child directories that each have one — you are setting up a workspace. Write `.agents/workspace.json` at that root, plus a `.agents/worktree.json` inside each member.

**The workspace manifest is a derived artifact, not source.** The containing folder is a local convention: its name, and which members are cloned, differ per machine. So it is normal and correct that the manifest is untracked and gets **regenerated** by running this skill at the root on each new machine — the same way nobody syncs `node_modules`. Don't invent a meta-repo to hold it.

That only holds if regeneration is faithful, which puts the weight on where each field comes from:

| Field | Derive it from |
|---|---|
| `members` | The child directories that contain a `.git` |
| `integrationBranch` | The branch the members are actually on — they share one because they release together |
| `branchPrefixes` | The workspace's own `CLAUDE.md`/`AGENTS.md` branch policy |
| `crossRepoContracts` | **The workspace's own docs.** A "cross-project sync" section that says which repo generates an artifact and which repos hold copies is the contract, stated by the people who built it |
| `briefConventions` | The conventions in those same docs that every member shares |

**Never infer a contract from resemblance.** Noticing that three repos contain an identical `generated.d.ts` and concluding one owns it is a guess. When a guess is wrong, contract closure — the rule that stops a task changing a contract owner without the repos that consume it — silently stops protecting anything, and the drift surfaces only after both sides have merged. If the docs don't state the ownership, say so and leave `crossRepoContracts` empty rather than filling it speculatively. An absent contract degrades to "no closure", which is honest; a wrong one is a safety property that looks present and isn't.

**Ask about the preferences, don't derive them.** Whether a member is `"default": false` — skipped unless named — is a judgement about how the team works, not a fact about the repos. Default to including everything and say which member looks like a candidate (a marketing site beside an app), rather than deciding for them.

Then verify by cutting a real task: `setup-workspace.sh --dry-run <branch>` shows the resolved member set, including anything closure pulls in. If a contract is declared, confirm that naming the owner alone pulls its consumers in — that is the check that the manifest actually does its job.

## Step 1 — Ground the repo. Never guess a command.

Every value you write must come from something you read. Guessing produces a config that looks right and gates nothing.

- **Package manager** — from the lockfile (`pnpm-lock.yaml`, `package-lock.json`, `yarn.lock`, `bun.lockb`), not from what's popular.
- **Scripts** — read `package.json` (`scripts`), or the `Makefile`/`justfile`/`Taskfile` for non-JS repos. Find what actually exists.
- **The real gate** — read CI (`.github/workflows/*.yml`). Whatever CI runs before merge IS the gate; if the repo has no CI, the gate is the broadest local command that builds and tests.
- **The scoped check** — the cheap subset with no build and no test suite (typically format-check + lint + typecheck). If a single script already composes them, use it; otherwise compose one and say so.
- **Env files** — the gitignored files tests and builds read. `git check-ignore` over candidates, then confirm they exist in the main checkout. **Record paths only** — the config is committed, so a value would leak a secret.
- **Conventions** — read `AGENTS.md` / `CONTRIBUTING.md`. These belong in `briefConventions` only if they live nowhere else; a convention already in `AGENTS.md` should stay there and be pointed at, not copied.

**And a value you must ASK for, because no file in the repo can tell you it: what does the gate touch that lives OUTSIDE the worktree?** A lockfile names dependencies, `package.json` names scripts, CI names the gate — none of them names the Postgres instance the suite migrates, the Redis the queue tests flush, the cache directory two runs share, or the fixed port an e2e run binds. Ask it in those words, then ask the follow-up that turns the answer into something testable: **does each worktree already get its own, and what makes that happen?** Write both into `sharedResources` — the resource, and the mechanism plus the entry point it sits at — and write `[]` when the honest answer is that the checks touch nothing outside their own tree. *The failure this prevents: this is a key that cannot be ground, so a pass that only reads files produces a config where the values it could read all trace to something and this one is silently absent — and absence here is not the safe reading (`skills/execute/SKILL.md` → *Per-project config*). Nothing errors, because the failure is a repo whose worktrees are declared parallel and are not.*

**Then the third part of that same question, in the same breath, because it only exists where the second had an answer: what DROPS what that mechanism creates, once the worktree is gone?** A mechanism that gives each worktree its own database, keyspace or cache directory creates one per worktree and removes none — `remove-worktree` takes the tree and knows nothing the tree made. Where the project already has a sweep, its two commands become `reclaim` (`skills/execute/SKILL.md` → *Per-project config* carries the shape and the rules such a command has to satisfy, and Step 2's `sharedResources` note carries the marker its resources need to be sweepable at all). Where it has none — which is the common answer — **that is a gap you hand back, not a command you invent**: you declare, you never provision, and a `reclaim` naming a script nobody wrote is a delete command that fails or, worse, one that does not. And where every entry is `null` or non-durable — a fixed port cannot leak — there is nothing to ask and the key is simply absent. *The failure this prevents: the second question's answer reads as the finished story — the worktrees are isolated, the claim is falsifiable, Step 4 proves it — while what it has actually established is that every worktree this project ever cuts leaves a resource behind. It costs one sentence while the maintainer is in the conversation, and it is otherwise found months later as a full disk by somebody with no idea what named any of them.*

**And a value you must ask for that is not a fact about the repo at all — it is CONSENT, which is why no file anywhere could hold it: when a run finds a defect in the *pipeline itself*, may it open an issue about that in the pipeline's own public repository?** That is `upstreamFindings`, and it is the purer case of the rule `sharedResources` falls under. That one is at least something a determined reader could dig out of a test bootstrap; this one is a decision, and a lockfile, a CI config and an `AGENTS.md` are equally incapable of containing one. Onboarding is also the only moment the project's owner is reliably in the conversation, which is the argument the `sharedResources` ask already makes for itself. **Put it about the PROJECT** — not the machine, not the person typing — so it is asked once per repo and put again if the repo changes hands. *The failure this prevents: absence is a settled no rather than an open question (`skills/orchestrate/SKILL.md` §7), so a pass that never asks produces a valid config, a working project, and no error anywhere — which is exactly why nothing catches it. What is lost is not a broken repo but a choice nobody was offered: an owner who would have said yes is never asked, and the channel stays empty for a reason invisible from both ends of it.*

**Give them what they need to decide, and take it from `skills/orchestrate/SKILL.md` §7 rather than from memory.** Three things: the target repository is **public**; a finding keeps the shape of the failure, the counts and the conclusion, and never keeps a file path, a symbol, a route, a branch name, a client name or a home directory; and the close-out **says out loud** when it has filed, naming the issue and the repository, so a filing is never something they learn about afterwards. **Name the repository rather than describing it** — resolve it from the `repository` field in the plugin's own manifest, `.claude-plugin/plugin.json`, which ships beside these skills — because nobody can consent to publishing somewhere unnamed. §7 argues each of those; read it there and point at it rather than pasting a summary beside it, which is a second copy that drifts. *The failure this prevents: a yes given without knowing the tracker is public is not consent to anything, and afterwards it is indistinguishable from one given in full knowledge — the config records the answer and nothing records what was understood.*

⚠️ **Do not make it easy to say yes.** The person answering is frequently not the person whose code a later finding will be about, so an ask that arrives already arguing for itself — *this helps every other install*, *it costs you nothing*, *you want to help, right?* — extracts a yes that was never theirs to give. Put the question, give those facts flat, and say that no is a complete answer needing no reason. That is the same asymmetry §7 names when it says opt-in is consent to **file** and never consent to **disclose**: whoever answers cannot review every future filing, and is frequently not the person it will be about. *The failure this prevents: a leading ask and a neutral one write the same key into the same file, so nothing downstream can tell a decision from a nudge — while the cost of the wrong one lands on a colleague who was never in the conversation.*

**Write `true` only on an explicit yes; on anything else — a no, a maybe, silence, or nobody to ask — OMIT the key.** That is the ordinary rule — *keys you have no honest value for are left out* — rather than an exception to it, and saying so is the point: the one key where an empty value beats omission is `sharedResources`, Step 0 carries both the rule and that exception, and a reader fresh from the exception will reach for it here. It does not transfer. There, absence means nobody asked and `[]` means somebody did, so the two say different things; here absence and *asked, declined* both mean no, and an explicit `false` disambiguates nothing while implying the file distinguishes them. **This plugin's own `examples/worktree.json` carries `"upstreamFindings": false` and is not a counter-example** — a template's job is to show every key that exists, and Step 2 sends you to it for a complete file. *The failure this prevents: copied out of that template by a pass that never put the question, a `false` records a decided no that nobody decided — and it is byte-identical to one an owner chose. The runtime answer is the same either way, which is exactly what hides the harm: the copied value immunises the project against ever being asked again, by a later reconcile, by a later setup run, or by a human reading the file, every one of which reads it as an answer already given.*

For a monorepo, note which commands live at the **root** and which are per-package — a root-only script run from a subpackage reports "no such script", which is a wrong-directory error that agents reliably misread as a missing feature.

## Step 2 — Write `.agents/worktree.json`

| Key | Read by | Source it from |
|---|---|---|
| `envFiles` | `setup-worktree.sh` | Gitignored env paths that exist in the main checkout |
| `install` | `setup-worktree.sh` + skills | The lockfile's package manager, frozen/CI form |
| `env` | `setup-worktree.sh` | Shared build-cache dirs; `${VAR:-default}` so an existing value wins |
| `gate` | skills | What CI runs before merge |
| `scopedCheck` | skills | The no-build, no-test subset |
| `sharedResources` | skills | **The maintainer's answer, not a file's** — what the checks touch outside the worktree, and the mechanism that gives each worktree its own. `[]` when there is nothing; see Step 1 |
| `reclaim` | skills | `{report, drop}` — the project's own sweep for resources whose worktree is gone. **Omit it** unless `sharedResources` has an entry that creates something durable AND the project already has the commands; see Step 1 |
| `enqueue` / `drain` | skills | Step 3 — **omit both if the project has no queue** |
| `format` | skills | The formatter in *write* mode |
| `frameworkSkills` | skills | `{skill, when}` per area, from the deps actually imported |
| `briefConventions` | skills | Only what `AGENTS.md` doesn't already say |
| `upstreamFindings` | skills | **Consent, not a fact about the repo** — the answer to Step 1's ask about filing pipeline findings upstream. `true` on an explicit yes, **omit it** on anything else, including a decided no; see Step 1 |
| `epicMerge` | `merge-pr.sh` + `.ps1` | The project's own history policy — **omit it** unless a long-lived release branch wants one commit per arc, and omit it outright if the integration branch is the repo's default branch, where it does nothing |

Keep `briefConventions` short. It is not a place to restate the orchestration protocol — "don't run the full gate", "enqueue then hand back", "never rebase", the transient-red reading and the formatter rule are all in `/pipeline:execute` already and are identical for every project. Duplicating them there means two copies that drift, and the copy agents read is the one no human ever opens. Point at `AGENTS.md`; state only the gotchas that would otherwise cost a run.

**`sharedResources` is a claim you then have to falsify, which is what fixes its shape.** Each entry is `{resource, isolatedBy}`: `resource` names the thing, and `isolatedBy` names the project's own mechanism *and the entry point it sits at*, or an explicit `null` — `null` declares a resource that is shared and stays shared, which is a real answer and the one Step 4 has nothing to test. Write the entry point down rather than "handled in the test config", because the entry point is the part a later reader has to check and the part that is most often wrong: it has to be one **every** invocation reaches, since this flow's verify bars routinely have an implementer run a targeted test file directly, so a mechanism hung off the `gate` command isolates only the runs launched through it. **You declare; you never provision.** Do not write a setup script, a lifecycle hook, or anything this plugin would call — placement belongs to the project for the reason just given, and a hook that isolates only what the plugin invokes isolates the wrong set. **And where the mechanism creates something DURABLE, the entry has to record how the resource is MARKED, not only how it is named.** Two halves, and the first is a bug rather than a feature: the path goes into the name via `git rev-parse --path-format=absolute --show-toplevel` and never via `$PWD`, which spells a symlinked entry differently and hands one worktree two databases — check that where you read the mechanism, because it is wrong in the tree far more often than it is wrong in the config. The second is the mark itself, written onto the resource as it is created — `COMMENT ON DATABASE`, a key in the keyspace, a file in the directory — carrying that same absolute path, which is the only thing that ever lets a resource be attributed back to a worktree and the only thing `reclaim`'s sweep will consider. A mechanism that marks nothing is not a config gap: it is a change to the project's own bootstrap, so **write down what is missing and hand it back**, exactly as you would a missing sweep. `/pipeline:execute`'s *Per-project config* carries the three-state reading of the key, both of those rules with the failures behind them, and what the sweep itself has to satisfy.

**`epicMerge` is the only key in that table read by a helper other than `setup-worktree`**, which is why its `Read by` cell names a different pair of scripts than every other script-read row. `"merge"` is the default; every value but the exact lowercase `"squash"` means `merge`, in both ports, which compare the key and the value case-sensitively. It governs exactly one merge — an epic branch collapsing back into the integration branch it was cut from — and **only when that integration branch is not the repository's default branch**. So a project where those are the same branch can declare `"squash"` and correctly see nothing happen, which makes "omit it there" a structural fact rather than a convention someone has to remember, and a harder reason to leave it out than any preference about commit counts. Default to omitting the key: write it only when the project has a long-lived release branch, actually wants one commit per arc on it, and has said so. `/pipeline:execute`'s *The epic branch* → *Mechanics* carries both conditions and the trade the option makes.

See `examples/worktree.json` in this plugin for a complete file.

## Step 3 — The gate queue (only if the project wants one)

The queue exists so implementers never run the heavy gate: they push, open a draft PR, enqueue a durable ticket, and hand back, while dispatchers drain the queue one gate at a time. It buys three things — no gate lock for a wide fan-out to serialize on, no thundering herd of concurrent builds, and no way for a dying agent to strand committed work.

**Not every project needs it.** A repo whose gate takes seconds, or that no one fans out across, is better off with no queue at all: omit `enqueue`/`drain`, and the implementer runs the gate itself and comments the result on its own draft PR. Say which you chose and why. Adding a queue to a repo that doesn't need one is pure ceremony.

If it does want one, scaffold the three scripts into the project and add their `package.json` entries. **Read `references/gate-queue.md` before writing a line of it** — the correctness of the whole thing rests on a few invariants (atomic-rename claims, PID liveness, re-entrant slot) that are easy to get subtly wrong and whose failure mode is a green gate against code no gate ever saw.

### Already has a queue? Reconcile it — report the delta, never rewrite

*Scaffold* has one branch, and it is the case this skill is otherwise blind to. Every other trigger here is an **absence** — no config, a helper warning, a dispatcher refusing. This one is a **presence**: the three scripts are already there, so the project is not onboarding, it is possibly *behind*. The ownership split that makes this design right — the repo owns and evolves its own queue — is the same split that guarantees no signal ever crosses back when the reference gains an invariant.

So when the scripts already exist, read them against the invariants in `references/gate-queue.md` and hand back a **per-invariant delta**: implemented, absent, or not determinable by reading. That third verdict is a real answer rather than a hedge — give it with the command you would have to run to settle it.

- **Report, never rewrite.** Two projects' queues *should* be allowed to diverge, and an overwrite cannot tell a deliberate divergence from a stale one, so it destroys both. The output is a list a maintainer decides on, one invariant at a time — this pass edits nothing.
- **Read the code, never a version stamp.** A stamp recorded at scaffold time looks like the cheap version of this and does not work, because **an invariant can be partly already true on the day it ships**: the reference is written from implementations that already exist, and says so in its first paragraph. Invariant 9 is the worked example — its announcement half (an `onWait` that prints the slot holder on a failed acquire) was already implemented in a real project before the invariant was written, while its read-only `--status` half was genuinely new. A stamp answers "current" or "behind" and both are wrong here: bumped on partial adoption it says current, left alone it says behind on an invariant nine-tenths satisfied. Neither one names the single missing clause, which is the only part that ever caused drift.
- **The half-recognised invariant is exactly what a human re-read misses.** A maintainer re-reading invariant 9 recognises their own runner in most of it and concludes they are current. The delta is worth writing down *because* most of what it checks comes back implemented — that is what makes the remainder invisible without it.

*The failure this prevents: a project onboards once, the reference gains invariants over the following months, and no signal ever reaches that project. Every invariant it does implement still holds, so the queue keeps working, nothing errors, and nothing looks stale. It surfaces only when a dispatcher follows a newer instruction assuming a mode the runner never had — observed as `drain --status` falling through to a full drain on a pre-invariant-9 runner, symptom `drained 0 ticket(s)`, caught only because the output shape looked wrong. Re-running setup on that repo would not have closed the gap; it would have returned a successful verification report.*

## Step 4 — Verify it, don't assert it

A config that parses is not a config that works. Prove each layer:

⚠️ Every helper named below ships as both `<name>.sh` and `<name>.ps1`. Use the extension your shell tool can run: on native Windows with no Git for Windows, Claude Code hands you the **PowerShell tool** and there is no bash at all, so the `.sh` is not a script that fails — it is a command that does not exist, and the error reads as a broken plugin rather than a wrong extension. Both take the same arguments and print the same output, so the verification below is otherwise identical.

1. **The reader agrees.** `setup-worktree.sh <branch> <base>` (or `setup-worktree.ps1`) in the repo, then confirm each declared env file is **present** in the new worktree and deps are installed — not that the command exited 0. Present, not necessarily symlinked: on Windows a real symlink needs Developer Mode or an elevated shell, so the helper falls back to a **copy** and says so on stderr. That is a working setup, not a broken one — the only thing it costs is that a later edit to the main checkout's env file will not propagate, which the helper's own warning spells out.
2. **HEAD is right.** `git -C <wt> rev-parse HEAD` equals the base tip.
3. **The gate command exists.** Run the *scoped* check for real. Don't run the full gate just to prove it resolves — `<pm> run <script> --help` or the script listing is enough.
4. **The queue round-trips**, if you scaffolded one: enqueue a ticket, drain it, confirm the ticket reached `done/` and the PR carries the gate's verdict comment. A queue that enqueues but never drains is worse than none — work vanishes into a directory nobody reads. **Then exercise the read-only mode too — `drain --status` — and confirm it reports the state and claims nothing** (queue depth and in-flight claims unchanged, no ticket moved). The round-trip alone is the happy path and never invokes that mode, so it comes back green on a runner that does not implement it; and an unrecognised flag falling through to a full drain is indistinguishable from a working mode until you read the output shape. That is the check invariant 9's rejection requirement exists to make possible — a runner without the mode must say so rather than drain. **Then invariant 9's other half — a blocked acquire names the holder — which you verify by READING the output, because there is nothing here to assert on.** Enqueue two tickets rather than one, and while the first is gating start a second drain and read *its* output: it must name who holds the slot, what that holder is gating, and since when, before it waits. This is the one place a second concurrent drain is the point rather than the mistake `skills/execute/SKILL.md`'s drain rider warns about — it is safe by construction (invariants 1–8), and it is the only posture the announcement is legible from at all, since it goes to the waiting runner's own stderr and an observer is by definition some other process. A silent wait and an announced one exit the same way after the same elapsed time, which is exactly the asymmetry invariant 9 exists to break, so a green exit records nothing. And if the gate finishes too fast for two drains to overlap, say you could not produce the contention rather than that the check passed — an overlap you never achieved is not a check that came back green. **Then the PR-less enqueue, which the round trip is structurally blind to: enqueue a ticket with no `--pr-number`/`--pr-url` and read what comes back.** The round trip above has a PR by construction — its closing assertion is a comment on one — so it stays green whether the runner accepts a PR-less ticket, refuses it cleanly, or accepts it and then tries to comment on a PR that was never named. Two outcomes are legible and **either one is a pass**, because they are the two sides of a rollout and what this check establishes is which side the project's runner is on. Either the ticket is **claimed, gated and settled into `done/` with the verdict on the ticket and no post attempted** — parse the JSON in `done/` rather than reading the exit code or the filename (*Queue layout* in `references/gate-queue.md`), and confirm the enqueue-time undeliverable flag is on the ticket, because without it a settled ticket carrying no comment is byte-for-byte the failed post *Reporting* flags for a human — **or** the enqueue is **refused with a non-zero exit and a message naming the missing fields**, which is what `references/gate-queue.md` requires of a runner scaffolded before those fields became optional. What neither of them is, is a green exit that says neither: that is the third state and the expensive one — the runner took the ticket, spent a full serialized gate, and filed the result as a delivery failure, the one classification invariant 8 refuses to prune and no retry can ever clear, so the cost lands on a human reading a flagged ticket for a gate that did exactly what it was asked to. A refusal is a pass here and a **delta for the handoff**: that runner is on the older side of the contract, so the dispatcher's mid-arc integration gate (`skills/execute/SKILL.md`'s *Gate the integrated whole*) cannot be enqueued against it and gets run by hand with no ticket and no ledger entry until the project widens its enqueue — say so where you report the queue rather than filing the check green and moving on. And if you could not produce the case — no gateable tree, or the ticket never reached a drain — say you could not produce it rather than that the check passed.
5. **Two worktrees, gated at once — the only place the FULL gate earns a run here, and only when `sharedResources` declares an `isolatedBy`.** Item 3 deliberately refuses to run the full gate to prove a command resolves; this is the opposite case, because the claim under test is not "the command works" but "these two runs do not collide", and that is unobservable in one run. Cut a second worktree off the same base, start the real `gate` in both, and let them overlap. Green in both is the answer. A red is what you are here for: read it before you read either diff, since the tell is infrastructure-shaped — a deadlock, a unique-constraint violation, a lock timeout, a port already in use, a fixture the other run truncated — and both worktrees hold the same untouched base, so a code defect is not on the table. Then confirm the isolation is real rather than lucky by **reversing it**: disable the mechanism at the entry point the config names, re-run the same overlap, and confirm the collision reproduces. And if the runs finish too fast to overlap, say you could not produce the contention rather than that the check passed — an overlap you never achieved is not a check that came back green. Where an entry has **no** `isolatedBy` there is no claim to falsify: record the project as not parallel-safe and say so in the handoff, which is what `/pipeline:execute` reads before it sizes a wave. *The failure this prevents: a declared claim nobody tests is documentation, and this one is documentation that reads as a safety property — every downstream reader treats the entry as evidence the worktrees are isolated, and the first thing that disagrees is a fan-out in production use.*
6. **Tear down** the verification worktrees with `remove-worktree.sh` (or `remove-worktree.ps1`) — both of them, if item 5 cut a second. **What the teardown does not reach is now a check rather than a caveat, and it runs on BOTH sides of that teardown**, where the project declares a `reclaim`. So take the baseline **before you remove anything**: with the verification worktrees still standing, run `reclaim`'s `report` and confirm their resources come back **live**. That is the half a broken sweep fails, and skipping it makes the whole check worthless — a sweep that calls everything dead and a correct one are the same output when you only look after. Then remove the worktrees and run `report` again: the same resources, and only those, have moved to **dead**, while every worktree still standing — the main checkout included — keeps its own on the live side. Read the counts rather than the verdict: considered, in-scope, live, dead, with the live/dead split moving between the two runs and *considered* unchanged. **Then stop.** The resources are still there and that is correct — `report` deletes nothing, and running `drop` is the maintainer's call on the maintainer's box, so say what is outstanding and hand them the command rather than running it. **Two things this does not establish, and say both:** the cross-clone case — another clone, or another machine sharing the same database host, whose live resources a sweep must call out of scope rather than orphaned — cannot be produced here, and nothing mechanical checks the scope rule anywhere; and where the project declared **no** `reclaim`, there is nothing to run, so report plainly that anything the mechanism created is still there, named after a path that no longer exists, and that nothing sweeps it. *The failure this prevents: a sweep is trusted the moment it exists, and the only cheap way to see one that is wrong is to watch it change its answer about a resource whose worktree you just removed — which you can only do if you asked it before you removed it.*

## Step 5 — Land it as a reviewable change

Commit the config (and the queue scripts) to the project and open a PR the way that repo normally does. In a workspace this applies to each member's `.agents/worktree.json`; the workspace manifest itself has no repo to land in, which is expected — it is regenerated, not shared. Say that plainly rather than leaving someone wondering why one file went uncommitted.

One exception where committing straight to the integration branch is correct, and say so in the message:

- **The project has an install step.** A repo with no config still cuts a worktree — `setup-worktree.sh` warns on stderr and makes a **bare** one — but bare means no `node_modules`, so every check inside it fails for reasons that read as code bugs rather than as a missing config, and the run burns before anyone reads the stderr note. Writing the config *from* such a worktree is what this exception prevents.

A **zero-dependency** project is not covered by it. A bare worktree there is fully functional — nothing to install, nothing to symlink — so the config lands through a normal PR like any other change. This plugin's own repo is the worked example: it had no `.agents/worktree.json`, `setup-worktree.sh` cut it a working worktree anyway, and the config reached `main` as a reviewed PR. Claiming the flow can never bootstrap itself would have made that PR look like a rule violation.

**That exception is about the FIRST config. A later CHANGE to one is a different case, and it is not a second exception.** This pass is the likeliest producer of such a slice, because it writes the file every later `envFiles` entry, `install` change or new key is a change *to*. Such a slice gets a perfectly good worktree and still cannot exercise its own change: `setup-worktree` reads the **main checkout's working copy** of `.agents/worktree.json`, so every worktree cut anywhere is provisioned from the pre-change file until the change reaches that copy, and neither pushing the branch nor cutting a second worktree off it alters that. **Which merge puts it there is the part to get right — on a multi-slice arc it is the epic's close-out and not the slice's own.** Verify it by applying the effect by hand in the worktree and **saying in the hand-back that the config path itself was never exercised**. Do **not** reach into the main checkout to make the helper see it early — that is the one thing that would work, and it is rejected in `/pipeline:execute`'s *Worktree creation*, which carries the argument for all of this. **Read the property as the one Step 4 stands on rather than as a bug**: Step 4 proves this pass's own config by cutting a real worktree *before* anything is committed, and it can only do that because the helper reads the working tree Step 2 wrote the file into. *The failure this prevents: a config change ships green having tested everything except itself, with nothing in the diff, the gate or the hand-back to tell it apart from one that was verified.*

## What setup does NOT do (hard boundaries)

- **No guessed commands.** Every value traces to a file you read. If you genuinely cannot determine the gate, write the config without `gate` and say so — a missing key is honest, a wrong one is a gate that passes while testing nothing.
- **No secrets.** `envFiles` carries paths. Never inline a value, never read the env files to "check" them.
- **No provisioning, and no reclaiming either.** You record what the checks touch outside the worktree, how the project isolates it, and what the project already has to sweep it; you do not build the isolation, you do not write the sweep, and you do not add a hook for this plugin to call. A `reclaim` naming a command nobody wrote is worse than an absent key, because the absent key reads as the open gap it is. The mechanism has to sit at an entry point every invocation reaches, which is inside the project's own bootstrap, so anything written here would isolate a strictly smaller set than the flow actually runs — and it would do it while looking like the whole answer. Declare it, verify it in Step 4, and hand the gap back where there is one.
- **No feature work, no slicing, no dispatch.** You configure the repo and stop. Running the work is `/pipeline:orchestrate`'s loop — it grounds each increment through `/pipeline:decompose` and ships it through `/pipeline:execute`.
- **Don't scaffold a queue into a project that doesn't want one.**

**Handoff:** report the config, what each value was derived from, whether you scaffolded a queue, and the verification results. Then:

> **Ready to run the pipeline.** `<repo>` is configured — hand an idea to `/pipeline:write-issue` to file it, or hand a plan you already have straight to `/pipeline:orchestrate`.
