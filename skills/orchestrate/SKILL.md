# Orchestrate — release-branch worktree workflow

Our main dev workflow: we work off an integration branch (for Trinity, `release/x.x.x` — discover the active one with `git branch --list 'release/*'` / the current branch; never hardcode a version). For each task we cut a git worktree, do the work there, commit, push, and open a PR back into the integration branch. The heavy build+test gate does NOT run in the worktree that produced the change — the implementer **enqueues** it and durable orchestrators **drain** it (see *The durable gate queue* below). After a PR merges we **sync the local integration branch first**, then clean up the merged branch and its worktree.

**Two branch levels, and only one of them is always there.** The **integration branch** is the shared one every task merges into and every worktree forks from — that is what `integration branch` means everywhere in this playbook, and it never means anything else. Above it sits one optional level: an **epic branch**, cut from the integration branch, that a multi-slice epic's slices fork from and PR into so the shared branch never carries the epic half-finished. It exists only when an epic's intermediate states are unshippable — *The epic branch* below states the trigger, which is narrow. Most work never cuts one, and everything in this playbook reads the same when there isn't one.

This is project-agnostic. The per-project specifics — which env files to symlink, the install command, the gate command, the docs fast-path, and the conventions to bake into briefs — live in a config the tooling reads (see *Per-project config* below), not in this playbook.

**Default to planning for parallelization.** Given a batch of work, the first move is to decompose it into independent tasks that can run concurrently in their own worktrees — don't default to doing everything sequentially yourself. Spin up as many worktrees/branches as the work needs. Because implementers don't run the heavy gate themselves (they enqueue it), a wide fan-out doesn't serialize on a gate lock — fan out as wide as the work is genuinely independent.

## First: which role are you?

Before acting, decide whether you are the **orchestrator** or an **implementer** — they behave very differently.

- **ORCHESTRATOR** when the user asks you to *orchestrate / coordinate* work, to *complete or work a GitHub issue*, to *execute a plan*, or hands you a batch of tasks. You are the coordinator. **Do NOT write the implementation yourself.** You decompose the work, create + verify worktrees, dispatch an implementer sub-agent into each (in parallel when independent), then run the review loop, **drain the gate queue**, and merge. You hold the plan, the reviews, the gate runs, and the merges — not the file edits.

- **IMPLEMENTER** when you are a dispatched sub-agent, or the user *directly tells you to implement / build / fix* a specific thing. You do the actual code in your assigned worktree, pass a cheap scoped check, push, open a **draft** PR, **enqueue the gate**, and hand back. **You do not run the full gate, you do not mark your own PR ready, and you do not merge your own PR** — a runner gates it and comments the verdict, and the orchestrator reads the diff, marks it ready, and merges. The ready flag is the reviewer's signature, so it has no override carve-out: in every gate mode your PR is a draft when you hand it back.

## Per-project config

The worktree tooling is generic; each project declares its specifics in **its own repo** at `<repo>/.agents/worktree.json`. The helper reads `envFiles`, `env`, and `install` from it; you read the rest (`cat <repo>/.agents/worktree.json`) to learn the gate, the framework skills, and the brief conventions.

Config lives in the repo — not in your home directory — so it travels with the clone, works under any checkout directory name, and is reviewed in the same PR as the change that alters it. **No config → STOP and say so.** The helper will happily cut a bare worktree (no env symlinks, no `node_modules`) and only warn on stderr; an implementer dispatched into that worktree then fails its checks for reasons that look like code bugs. Don't dispatch into a config-less repo — get the file written first. Keys:

- `envFiles` — gitignored env files to symlink from the main checkout into each worktree.
- `install` — install command run inside a new worktree (worktrees don't share `node_modules`).
- `gate` — the heavy full gate (build + test). This is what the RUNNER runs against a queued PR's worktree; implementers do NOT run it (they enqueue it). It's also what a human runs for a manual full check.
- `scopedCheck` — the cheap, unlocked check an implementer's commits are held to (format-check + lint + typecheck; no build, no test). For Trinity this is `pnpm check`, and the agentic pre-commit hook already enforces it on every commit.
- `enqueue` / `drain` — how an implementer enqueues its PR for gating, and how the orchestrator drains the queue. For Trinity: `pnpm gate:enqueue` and `pnpm gate:drain`. **Both absent means the project has no queue** — see below.

⚠️ **Not every project is queue-shaped, and two config readings change the whole flow.** Check them before dispatching:

- **No `enqueue`/`drain`** → this project gates in-line. The implementer runs `gate` **itself**, in the foreground, and posts the result as a comment on its own **draft** PR — that is override gate mode, and here it is the *default* rather than something you grant. The PR is still a draft when it hands back, exactly as in queued mode; only who ran the gate changes. Do not tell an implementer to enqueue against a project with no queue: the command doesn't exist, and the run ends with committed work and no handoff.
- **`gate` == `scopedCheck`** → the project has one authoritative check and no separate heavy tier. There is nothing for a runner to add, so don't build a queue around it or split briefs into "cheap" and "full" bars that are the same command.

A repo can also be small enough to want none of this — a scratch repo with nothing to isolate. Absence of a config is a signal to ask, not to improvise one.
- **Gate mode** (optional, per-project) — a project may offer a lighter gate for a prose-only slice (Trinity: `--mode docs` → the runner gates with `pnpm docs:gate` instead of the full `pnpm gate`). The mode is a property of the *ticket*, set at enqueue — **never inferred from the branch name**, since a rename must not silently change how a PR is gated. Treat it as a **speed choice, not a workaround**: every worktree gets a real install, so a light-mode slice that turns out to touch code just enqueues in the default mode and faces the full gate. Nothing to install by hand, nothing to except.

  ⚠️ **Never give a worktree a shared `node_modules`.** An earlier version of this tooling had a docs fast path that skipped the install and symlinked the main checkout's `node_modules` — saving ~8s and letting prettier resolve. It cost far more than it bought: the worktree couldn't face the full gate (so a whole light-gate *mode* existed to compensate), and its escape hatch — "if the slice touches TypeScript, run a real install by hand" — resolved **through the symlink** and recreated the *main checkout's* `node_modules` underneath every other live worktree and any gate running at that moment. The script that created the symlink even warned "never run `pnpm install` against this symlink" while the project config instructed exactly that. The result was a red on an unrelated branch that nobody could reproduce, because the cause was a directory being swapped mid-run rather than anything in a commit. **A worktree is only isolated if its dependencies are.** Pay the install.
- `frameworkSkills` — `{skill, when}` pairs naming the framework skill each area opens with, so a brief can say "invoke the `frameworks:solid` skill as Step 0" without you guessing the stack.
- `briefConventions` — project conventions to bake into every dispatched implementer brief (compat policy, comment style, test-invocation rules, etc.).
- `format` — the auto-formatter in *write* mode, run right before committing (the scoped check only format-*checks*).

The config's `env` map is exported before the install runs — most usefully a **shared build cache** for a monorepo (turbo/nx/bazel): `"env": {"TURBO_CACHE_DIR": "${TURBO_CACHE_DIR:-$HOME/.cache/<project>-turbo}"}` lets a fresh worktree's gate **replay** tasks another checkout already built (near-instant on unchanged packages) instead of running cold every time. A remote cache (a shared HTTP/S3 backend the runner declares in its config — e.g. turbo's `remoteCache.apiUrl`) extends the same replay *across machines and CI*. ⚠️ **A cache var must live where NON-INTERACTIVE shells read it.** The gate runner, the `drain` pass, and dispatched implementer agents all run in non-interactive shells — a var set only where an interactive shell reads it reaches your terminal but *not* the fleet, so the shared cache silently never applies to gated PRs and every drain runs cold. The config's `env` map covers the install step; this covers the gate. In zsh that means `~/.zshenv`, NOT `~/.zshrc`. On **Windows there is no equivalent file**: persist a real user environment variable instead (`setx VAR value`, or System Properties → Environment Variables), which every later process inherits regardless of shell — PowerShell's `$PROFILE` is interactive-only and is therefore the exact same trap as `~/.zshrc`. (This is a real trap we hit: the 287x cache speedup showed up in the terminal but not in a single gated worktree until the export moved to `~/.zshenv`.)

**Go through the task-runner, never around it.** A shared cache only helps commands that actually invoke the runner (turbo/nx/bazel): the project's `scopedCheck` and `gate` do, by construction. Invoking the underlying binary **directly** — `vitest`, `tsc`, `eslint` — or running a per-package script that shells straight to it (e.g. `pnpm --filter <pkg> test` when that package's `test` script is a bare `vitest run`) **bypasses the cache entirely and always runs cold**, both locally and in the drained gate, and never *populates* the cache for anyone else either. So steer every whole-package / whole-suite run that is *supposed to happen* — the runner's drained gate, an orchestrator's integration gate, an override-mode slice — to the cached runner command (`turbo run <task> --filter=<pkg>`, or the project's own `scopedCheck`), and say the same in briefs and the project's `AGENTS.md`. (This is a routing rule, not a permission: for a default-mode implementer, whole-package/whole-suite *test* runs are banned outright — see the Implementer section — so "route it through turbo" never applies to them.) Reserve a direct-binary run for a **single targeted file** (`vitest run path/to/x.test.ts`), where wrapping one file in a whole-task cache entry is pointless overhead. If the project's `AGENTS.md` still documents the raw-binary form as the default for a whole package, that's a leak — fix the doc, don't propagate it into briefs.

To onboard a new project, add `<repo>/.agents/worktree.json` declaring the keys above and commit it — one PR, reviewed like any other change. Read the repo's `AGENTS.md`, its package scripts, and its CI to fill in the commands rather than guessing them.

## Polyrepo workspaces

Some projects are a **containing folder of sibling repos** rather than one repo — an API, its clients, an admin panel, a marketing site, all released together. The folder itself is not a git repo, so every helper that resolves the repo from CWD fails at its root.

A workspace declares itself with `.agents/workspace.json` at that root:

- `integrationBranch` — the branch every member shares (they release together; that's what makes it a workspace).
- `members` — the repos, as names or `{path, default}`. A member with `"default": false` is skipped unless named — for the one repo the others rarely change with.
- `crossRepoContracts` — the shared artifacts (generated types, notification payloads, translations) and which repo owns each. This is the polyrepo form of the shared-hotspot problem: the owning side must land first, and the consumer regenerates rather than hand-edits.
- `briefConventions` — conventions shared by every member, so five repos don't each restate the same branch policy.

**One task gets one worktree per repo, laid out like the workspace:**

```
setup-workspace.sh <branch> [repo ...]
setup-workspace.sh <branch> --exclude <repo,repo>
```

→ `$WORKTREE_HOME/<workspace>/<branch-leaf>/<repo>/`, using the **same branch name in every member** so the PRs are visibly one change. Mirroring the layout is the point: relative paths between repos still resolve and both stacks run side by side, which is what a change spanning an API and its client actually needs. Each member is provisioned through `setup-worktree.sh`, so it still gets its own `.agents/worktree.json` treatment.

**Name the repos a task touches.** Every repo you cut is an install you pay for, so the default set is a floor, not a target. `--exclude` is for when a task touches most of the workspace and you want to drop one.

**What changes for you as orchestrator:**

- **Verify HEAD in every member**, not just one. A polyrepo's integration branch is a convention, and one repo lagging is the normal failure.
- **Order merges by contract.** A slice that changes a contract and its consumer is two PRs with a mandatory order — the owning repo lands first. Nothing enforces this; you do.
- **Each member gates itself.** There are as many queues as repos, so per-repo green says nothing about the pair. Treat the cross-repo pair the same way you treat a multi-slice epic: independently green is necessary, integrated-green is what ships.

A repo inside a workspace also gets its plain `setup-worktree.sh` worktrees namespaced under the workspace, because bare polyrepo names (`api`, `client`, `admin`) collide across unrelated projects in a flat worktree home.

## Worktree creation (both roles depend on this being done right)

**⛔ HARD BAN — the Agent tool's `isolation: "worktree"` parameter (and ANY harness / auto worktree provisioner) is FORBIDDEN. Never use it.** It (a) creates the worktree under `.claude/worktrees/agent-*` (violates invariant 1 below) and (b) repeatedly seeds it at a STALE base — far behind the integration tip (observed ~1000+ commits behind, a previous-minor-version commit) — which has burned us over and over (agents waste cycles re-basing, or stale code silently leaks in). There is exactly ONE way to make a worktree: the helper script below, then **verify HEAD yourself**, THEN dispatch a plain agent (no `isolation`) pointed at that worktree path.

**Helper script — `setup-worktree.sh`** (ships in this plugin's `bin/`, which Claude Code puts on your shell tool's `PATH` while the plugin is enabled — so it's a bare command, no path prefix, alongside its siblings `merge-pr.sh` / `remove-worktree.sh`). It auto-detects the project and reads that project's `.agents/worktree.json`, so it works the same for any repo.

⚠️ **Pick the extension from the shell tool you were actually handed, not from habit.** Every helper ships twice: `<name>.sh` for the **Bash tool**, `<name>.ps1` for the **PowerShell tool**. A session on native Windows with no Git for Windows installed gets the PowerShell tool and has **no bash at all** — so `setup-worktree.sh` there is not a script that fails, it is a command that does not exist, and the error reads as a broken or missing plugin rather than as a wrong extension, which sends the whole run off diagnosing the wrong thing. The rule: **if the only shell tool you have is PowerShell, call `setup-worktree.ps1` / `remove-worktree.ps1` / `merge-pr.ps1` / `setup-workspace.ps1`; otherwise call the `.sh`.** Arguments, environment variables, the `READY:` line, and exit codes are identical either way, so nothing else in this playbook changes — and `scripts/check.sh` in this repo enforces that they stay identical.

Usage: `setup-worktree.sh <branch> <base>` — both **required**. Run it from **anywhere inside the target repo** (the root, a subdirectory, a monorepo subpackage, or even a linked worktree — it walks up to the repo's common gitdir). If cwd isn't inside the repo, prefix `REPO=/path/to/repo`.
- `<branch>` = full name of the branch to create (any prefix: `feat/…`, `fix/…`, `refactor/…`, `docs/…`); the worktree dir is named after the segment past the last slash (`feat/toasts-top-right` → `toasts-top-right`).
- `<base>` = the branch to fork from, with **no default** (integration branches roll over often, so a hardcoded default just goes stale); it errors early with a `git fetch` hint if `<base>` isn't a local ref yet.

**Recovery form — `setup-worktree.sh --existing <branch>`** attaches a worktree to a branch that already exists, instead of creating one. Reach for it when a **branch outlived its tree**: a `merge-pr.sh` that failed at the merge after tearing the worktree down, a tree removed by hand or lost to a cleanup, a branch you need to pick back up after its close-out was interrupted. It takes **no base** — an existing branch's base is whatever it already forked from, so there is nothing for a second argument to mean. If only `origin/<branch>` survives (the local branch is deleted on every successful merge), it recreates a local branch tracking the remote and attaches to that; if the branch doesn't exist at all it **stops** rather than creating one, because the fallback would silently fork off whatever HEAD it found. Everything downstream is identical to a fresh worktree — env symlinks, the config's `env`, a real install — so a re-attached tree can face the gate like any other.

⚠️ **It is a flag, never an inference — do not reach for it just because the branch exists.** Attaching to a pre-existing branch when you meant to fork off `<base>` is the stale-base seeding this whole section warns about hardest, and it arrives silently: the tree is real, the install is real, and only its HEAD is wrong. Use the two-argument form for new work, always.

⚠️ **Every helper resolves its target repo from your CWD** (or an explicit `REPO=`). Running `merge-pr.sh <n>` while your shell sits in a *different* repo's checkout operates on THAT repo — observed failure: it switched an unrelated main checkout off its integration branch onto the default branch and attempted to merge *that repo's* PR `<n>` (same number, wrong project; only luck — the PR was long merged — kept it a no-op). When orchestrating across multiple repos, `cd` into the target repo immediately before EVERY helper invocation, and treat an unexpected "behind by thousands of commits" line in helper output as a wrong-repo alarm: stop and verify before anything else runs. (`merge-pr.sh` also self-guards now: it refuses when the PR's head branch is unknown to the resolved repo, and when an already-merged PR has no worktree/local branch left to close out — `MERGE_PR_FORCE=1` overrides the latter.)

It creates the worktree at `$WORKTREE_HOME/<project>/<branch-leaf>`, symlinks the config's `envFiles`, and runs `install` — automating invariants 1, 3, 4 below. Every branch is treated the same, docs included: a worktree always gets its own install, so it is always self-contained and can face any check the project has. It finishes by printing two lines on stdout — `READY: <path>` and then `HEAD: <sha>`, the commit the tree actually landed on, which is what invariant 2 has you compare.

`WORKTREE_HOME` defaults to `~/.worktrees`, **except on Windows, where it defaults to `%LOCALAPPDATA%\wt`** — a worktree path there carries a whole dependency tree (`…/<repo>/node_modules/.pnpm/<pkg>@<version>/…`), and from `~/.worktrees` that routinely exceeds Windows' 260-character `MAX_PATH`, which surfaces as an install failing on some deeply nested filename rather than on the length. Setting `WORKTREE_HOME` yourself still overrides it everywhere. Two more Windows-only notes worth knowing before you read a worktree's stderr as a code bug: `setup-worktree.sh` warns when `git config core.longpaths` is unset (the same MAX_PATH ceiling, from git's side), and it warns when an env file was **copied** rather than symlinked — Git Bash's `ln -s` silently copies unless Windows Developer Mode is on, and a copy is a snapshot, so later edits in the main checkout stop reaching the worktree.

**The four invariants** (the helper covers 1, 3, 4 — step 2 is always on you):
1. The worktree lives under `$WORKTREE_HOME/<project>/`, **never** under `.claude/worktrees`.
2. **Verify its HEAD == the base tip BEFORE dispatching any agent** — compare the `HEAD: <sha>` line the helper just printed against `git rev-parse origin/<base>` (e.g. `origin/release/x.x.x`), or re-read it yourself with `git -C <worktree> rev-parse HEAD`. The helper prints the sha but does **not** verify it for you — sync the base first, then check. A mismatch means STOP and fix the base; do not dispatch. Read the sha, never the `READY: … off <base>` text: that says what was *asked for*, and this invariant exists for the case where what you got is something else.
3. Env files are symlinked into the worktree (they aren't carried over automatically).
4. Deps are installed (worktrees don't share `node_modules`, and the gate can't run without them).

## The durable gate queue

The heavy gate (`gate` = build + full test suite) is expensive and CPU-saturating: running several concurrently across worktrees stacks builds and vitest/workerd forks until the box thrashes. So implementers never run it — they enqueue a durable ticket and hand back, and orchestrators drain the queue and gate one at a time. This keeps the wait off the implementer entirely and makes a mid-flight death impossible to lose work to:

- **Implementers never run the full gate.** They get their code to a cheap **scoped check** (format-check + lint + typecheck; the pre-commit hook enforces this on every commit), commit, push, open a **draft PR**, then **enqueue** a durable gate request (`enqueue`) and hand back. The work is pushed and the PR is open before the ticket exists, so an implementer death after enqueue strands nothing — worst case the work sits as a visible draft PR.
- **Orchestrators drain the queue.** On each tick a runner (`drain`) claims a queued ticket, runs the gate its declared mode selects (`gate`, or a project's lighter gate for a prose-only ticket — see *Gate mode* above) **one at a time** in that ticket's worktree behind a slim machine-wide slot, then comments the verdict on the PR — a pass on green, the failing tail on red — and leaves the PR draft either way. Multiple orchestrators can drain the same queue safely: every state transition is an atomic rename that exactly one runner wins, and a runner that dies mid-gate has its in-flight ticket reclaimed and re-gated (the gate is idempotent).

The consequences ripple through everything below: there's no gate lock for implementers to wait on, no thundering herd of concurrent gates, and no way for a dying agent to strand committed work. Fan out freely; drain steadily; the queue + draft PRs make lost work structurally impossible.

## The epic branch

**Skip this section unless you are running a multi-slice epic whose intermediate states are unshippable.** Single-slice work — one fix, one feature, one PR — never cuts an epic branch, and nothing else in this playbook changes when there isn't one.

An **epic branch** is a branch cut from the integration branch that an epic's slices fork from and PR into, gated as a whole once they have all landed, then merged back to the integration branch in one ordinary PR. It is the same shape as the integration branch, one level down: the epic converges there instead of on the shared branch, so the shared branch only ever sees the epic finished.

### The trigger is one question — and it is not slice count

> **Does any intermediate state leave the integration branch in a condition you would not ship?**

If no intermediate state does, there is no epic branch: the slices merge into the integration branch as they land, exactly as they do today.

- **Primary — the epic is only correct as a whole.** A foundational change whose consumers must all follow it: a NOT-NULL schema swap, a required interface field, a renamed module. Every state between the foundation landing and the last consumer migrating is unshippable. This is exactly the shape *Transient-red window* below describes, and the case this branch exists for — the window has to sit somewhere, and an epic branch is what keeps it off the branch everyone else forks from. It is still a recommendation you weigh, not an automatic cut: a small foundational change whose consumers all land in the same afternoon may not be worth the branch.
- **Secondary — a contract seam.** `decompose` emits a producer → consumer map naming the shape one slice emits and another reads. Two halves of one contract landing separately means the branch is wrong in between — the primary condition arriving by a different route.

**Two conditions contribute and are never sufficient on their own.** Both are routinely true of runs that want no epic branch at all, so either one taken alone converts the trigger into a default:

- **Slice count.** It measures how long a partial state sits on the branch, never whether that state is broken. A real five-slice run — cache invalidation, a UI gate, a query poll, a SQL predicate, a store guard — was independently shippable at every step, and every merge left the integration branch green and coherent. A count-based trigger would have fired and bought nothing.
- **An integration branch busy with other sessions.** That is the opposite concern — isolating you from them, rather than them from you — and in a multi-session shop it is near-permanently true, so as a standalone trigger it degenerates into "always".

**`decompose` recommends; you decide and act.** It is the pass that grounds slices in real code and produces the seam map, so it is the one positioned to see whether two halves must land together — it says so in its breakdown. You cut the branch and point the slices at it. Same find/act split already established for contract seams. A decomposition that recommends nothing means no epic branch.

### The cost — conflicts are deferred and concentrated, and the mitigation is mandatory

Conflicts do not disappear. Today a slice author resolves a small collision against the integration branch while the code is still theirs and still fresh in mind. Behind an epic branch that collision instead accumulates until the epic lands, and whoever lands it resolves a bigger one, later, with less context. That is the whole bill, and it is why this is trigger-gated rather than the shape everything uses.

**The mitigation rides the tick you already run.** On the same wakeup tick that drains the gate queue and fast-forwards the local integration branch, merge the integration branch INTO the epic branch — merge, never rebase, same as everywhere else here. *Draining the gate queue* carries the exact commands, because that is where you will be when you run them. That keeps the drift bounded and surfaces each collision while the slice author who caused it is still live to resolve it. Skipping this cadence is precisely how the deferred conflict becomes the concentrated one.

### Mechanics

- **It lives in the main checkout**, like the integration branch itself, and it is **pushed and then stepped off** in the same breath:
  ```
  git -C <main-checkout> switch -c <epic-branch> <integration-branch>
  git -C <main-checkout> push -u origin <epic-branch>
  git -C <main-checkout> switch <integration-branch>
  ```
  Worktrees are only ever for slice work — never cut one for the epic branch. Neither of the last two commands is optional. **Push it**, or `origin/<epic-branch>` does not exist: invariant 2 has nothing to compare a slice worktree's `HEAD:` against, and `gh pr create --base <epic-branch>` has no base on GitHub to open against. **Switch back**, or you have left the main checkout parked on the epic branch — and the every-tick reconcile (`git -C <main-checkout> pull --prune --ff-only`, *Draining the gate queue*) takes no branch argument, so it follows whatever is checked out. Parked on the epic branch it silently stops fast-forwarding the integration branch for the epic's whole duration, and the next worktree cut for anything else forks off a stale HEAD — the exact failure that reconcile exists to prevent, reintroduced by the section that is supposed to change nothing for everyone else.
- **Slices fork from it and PR into it.** `setup-worktree.sh <slice-branch> <epic-branch>`, and invariant 2 then compares the tree's printed `HEAD:` against `git rev-parse origin/<epic-branch>` rather than the integration tip. Each slice's brief names the epic branch as its PR base.
- **Per-slice close-out needs no change.** `merge-pr.sh <n>` reads the base off the PR itself (`baseRefName`) and drives every later step from it — the mergeability preflight, the merge, and the fast-forward of the local branch in the main checkout. So a slice PR based on the epic branch closes out identically: worktree torn down, real merge commit into the epic branch, local epic branch fast-forwarded to the merged tip. No argument, flag or hand-run step to add. **One thing to do after it, though:** syncing the base means checking it out, so the helper leaves the main checkout sitting on whatever branch the PR targeted — the epic branch, here. Switch it back (`git -C <main-checkout> checkout <integration-branch>`) for the same reason the two commands above do, and expect to keep doing it: this is the third path that parks the main checkout on the epic branch, and the every-tick reconcile follows whatever it finds checked out.
- **Close-out is one gate plus one ordinary PR.** Once the last slice merges and the fleet is quiet, run ONE `gate` on the epic branch (*Gate the integrated whole* below), then open a normal PR from the epic branch into the integration branch and merge it with `merge-pr.sh` like any other. That merge is the first thing the integration branch sees of the epic, and it is a complete one.
- **Delete the epic branch after that merge, never before** — and the never-delete-past-git's-"not merged"-warning guard applies to it exactly as to a slice branch: verify it is fully merged into the integration branch first, and STOP on the warning rather than forcing past it. Its slice branches are already gone, each deleted by `merge-pr.sh` as it merged, so the epic branch is the last thing left to clean up.

## Orchestrator

### Dispatch
Decompose the batch into independent tasks. For each: create + **verify** a worktree (above), then **dispatch a plain implementer sub-agent** (no `isolation`) pointed at that worktree path — in parallel whenever the tasks are independent. Spin up as many worktrees/branches as the work needs; the gate doesn't bottleneck fan-out (implementers enqueue rather than gate).

**Pick the model tier per task — match cost to difficulty.** Pass `model: "sonnet"` to the Agent tool for the *bulk* of implementer dispatches: well-scoped, mechanical, or moderate work (wiring, UI from a clear spec, a route/op that mirrors an existing one, tests, a refactor with a known shape). Reserve `model: "opus"` for genuinely HARD slices: subtle algorithms, ambiguous or design-heavy work, tricky concurrency/lifecycle, security-sensitive code, or large cross-cutting changes where a wrong approach is expensive to unwind. When unsure, **start Sonnet** — a Sonnet PR you have to redirect is cheaper than Opus on routine work; escalate to Opus only if the task proves harder than scoped. Trade-off: the easier the model, the **more explicit the brief** must be — exact files, patterns to copy, hard do-not-touch boundaries, research-first steps. Clarity substitutes for model strength, so a Sonnet brief should read as near-deterministic steps, not "figure it out."

**Open every brief with "Step 0: invoke the `pipeline:orchestrate` skill (via the Skill tool) and act as the IMPLEMENTER."** The agent then reads the generic implementer playbook from the *Implementer* section itself — scoped-check-not-full-gate, cheap-checks-during, the zero-warnings "don't be lazy" bar, push-draft-PR-enqueue-report, never-rebase / never-self-merge, and stop-and-report. **Do NOT re-paste any of that into the brief** — it's already in the skill the agent just loaded, and duplicating it bloats the brief and drifts out of sync.

**This skill is written for you, the orchestrator — you are the one who has fully internalized it, and your job is to translate the parts implementers must execute correctly into their brief.** Step 0 ("invoke the `pipeline:orchestrate` skill and act as the IMPLEMENTER") covers simple absolute prohibitions fine — never rebase, never self-merge — an agent either does or doesn't do those. It does NOT cover (a) a multi-step procedure that has one correct order and one wrong, silently-incomplete order with no error to flag the miss, or (b) a rule that overrides a harness-level default the agent would otherwise follow unprompted. Five items have exactly one of those two shapes, and you paste all five into every brief close to verbatim rather than relying on Step 0 to carry them: the **commit-last ordering**, the **push-draft-PR-then-enqueue handoff**, and the **docs-in-the-same-PR rule** (shape a), and **no AI attribution** and the **no-full-suite-runs ban** (shape b — the harness default is "verify your change by running the tests," which is exactly the instinct this workflow overrides; never rebase / never self-merge need no reinforcement because no default pushes against them, but this one fights a strong instinct and loses unless restated). Treat any future addition with either shape the same way.

Your brief carries the **task-specific context the skill can't know**, plus the five items above — keep the rest lean:
- **Step 0 skills.** Invoke `orchestrate` (as implementer), plus any framework reference skill the task touches — name it as an explicit first step, not "use it." For Trinity — **app = Solid, sidecar = Effect**: Effect-TS on the sidecar (services, layers, HTTP routes, typed errors) → "invoke the `frameworks:effect-v3` skill"; SolidJS UI on the app (`solid-js`, `@solidjs/router`, `@tanstack/solid-query`, Kobalte) → "invoke the `frameworks:solid` skill"; a full-stack slice → both. Sonnet agents won't reach for these on their own, so spell them out.
- **The task + the worktree.** What to build/fix, the assigned worktree's absolute path, and the concrete files/patterns to copy. The weaker the model, the more explicit — near-deterministic steps for Sonnet, not "figure it out."
- **Scope + hard do-not-touch boundaries.** The other slices'/phases' core files this task must NOT edit. This is the part only you hold from the decomposition; the skill cannot supply it.
- **Project conventions for this slice.** The relevant bits of the project's `briefConventions` (`<repo>/.agents/worktree.json`) and `AGENTS.md` — compat policy, comment style. (Trinity: pre-launch forward-only, no backwards-compat shims; comments explain the mechanism.)
- **Docs ship in the same PR as the behavior.** Stale docs throw no error and fail no gate — the slice goes green, the PR merges, and the miss surfaces later as a user reading something that stopped being true. That silence is why this is a paste-verbatim item rather than something Step 0 can carry: an implementer that never considered the docs and one that considered them and found nothing produce identical output. Naming the docs YOURSELF in the brief is not enough and is the trap — you are working from the plan, not from the diff, so a doc you concluded was clean stays clean by assumption. Make the implementer derive it from what it actually changed. Paste this into every brief:

  > **Update the docs in this PR, and report what you checked.** Before you hand back, write down the user-visible behavior your change adds, removes, or alters — then find the docs that describe *that behavior* and bring them in line. Search by the behavior, NOT by the vocabulary your change introduced: a README describing a feature in plain language contains none of the new identifiers, so grepping for your own new terms returns nothing and reads as "no docs affected". Start from the repo's own doc set (`README.md`, `AGENTS.md`/`CLAUDE.md`, and any reference or docs directory the project keeps) plus anything the project's conventions name. Docs changes go in their own commit, separate from the behavior. In your hand-back report, list every doc you checked with a one-line verdict each — updated, or not-affected-because — and never just "docs reviewed". A doc you decided needs no change is a decision on the record; silence is indistinguishable from never having looked.
- **Gate mode for this slice.** Gate mode decides **who runs the gate and when** — nothing else. The DEFAULT is: implementer runs only the scoped check, pushes, opens a draft PR, and enqueues — a runner does the authoritative gate later. Override ONLY when the slice is foundational/cross-cutting and you want it verified before it enters the queue (or when there's no orchestrator to drain): then tell the implementer to run the full `gate` itself, in the foreground, **post the result as a comment on its own PR**, and NOT enqueue. Both modes end identically — a draft PR carrying a gate comment — because whether the diff was *read* is your call, not the gate's, and you record it by merging. For a DEFAULT-mode slice, paste the ban into the brief — this is one of the four paste-verbatim items, because it overrides the agent's built-in "verify by running the tests" instinct and gets rationalized around otherwise:

  > **No full-suite or whole-package test runs — by ANY invocation.** Your only test execution is a SINGLE targeted test file (`vitest run path/to/x.test.ts`). Do not run the full suite or any whole-package test run through any route: not `gate`, not `turbo run test`, not a raw `vitest`/`tsc` sweep, not a package `test` script. Backgrounding it does not make it compliant — launching a banned run with `run_in_background` (or `&`/`nohup`) is still running it, and is the classic stall: the suite churns, you end your turn, and the handoff never happens. The runner gates your PR after you enqueue; verification wider than one test file is its job, not yours.
- **Simplify pass for this slice — your call.** `/simplify` is a real quality pass (reuse / simplification / efficiency / altitude cleanups) that costs a round-trip and only pays off on substantial work — a new module, non-trivial logic, a refactor with structure to tighten. On a trivial slice — a one-line fix, a copy/string tweak, a config bump, a mechanical rename — it burns that round-trip to report "nothing actionable," so it's noise, not safety. YOU hold the decomposition, so YOU decide per slice and say so in the brief: default substantial slices to a simplify pass, and tell trivial ones to skip it. State it explicitly either way — the decision sets the commit ordering below.
- **The commit ordering — set by the simplify decision above.** If the slice runs `/simplify`, commit LAST: `/simplify` acts only on the *uncommitted* working-tree diff, so anything committed early is invisible to the pass — it reports "nothing actionable" against the clean part whether or not that code needed cleanup. If the slice skips simplify, there's nothing to hold the tree open for, so commit in logical blocks as the work lands. Paste the matching block into the brief:

  > **Simplify slice:** Do NOT commit as you go. Write the ENTIRE change in your worktree first — uncommitted. Cheap checks while you work are fine (format, a scoped lint/typecheck, a single targeted test file) but don't commit yet. When the code is done, run `/simplify` over your full uncommitted diff and fold its fixes in. Then run the auto-formatter in WRITE mode (Trinity: `pnpm format`) over the tree, and THEN commit — in logical, self-contained blocks (a type + its plumbing, a behavior + its tests), never one giant commit and never as-you-go.

  > **Skip-simplify slice (trivial change):** Skip `/simplify` — it has nothing to chew on here. Write the change, run the cheap checks, run the auto-formatter in WRITE mode (Trinity: `pnpm format`), and commit in logical, self-contained blocks (never one giant commit). Do NOT run `/simplify` just to tick a box; the orchestrator judged it not worth the round-trip.

  In both cases your commits are held to the cheap SCOPED check by the pre-commit hook (format-check + lint + typecheck — no build, no test suite); you do NOT run the full gate. The hook only *checks* formatting, it does not *fix* it — so run the formatter in write mode right before you commit, or an unformatted diff gets bounced.

- **The push-draft-PR-then-enqueue handoff.** The implementer's wrap-up is a durable handoff, not a wait — this order is load-bearing because it's what makes a mid-flight death lose nothing. Paste this into every brief (unless this slice is in override gate mode, above), substituting the literal branch name you cut this slice's worktree from — the integration branch, or the epic branch when the epic has one. Substitute it here rather than passing the condition down: you already know which branch it is, and an implementer left to work it out is one that can send its PR at the wrong branch.

  > After committing: **push your branch, then open a DRAFT PR** targeting `<base-branch>`. THEN enqueue the gate: `enqueue --branch <yourBranch> --worktree <yourWorktreeAbsPath> --pr-number <n> --pr-url <url>` (get the PR number/url from the `gh pr create` output). THEN hand back — report the PR URL, files changed, scoped-check result, tests touched, and anything ambiguous. Do NOT run the full gate, do NOT wait for it, do NOT mark your own PR ready — a runner gates it and comments the verdict, and the orchestrator marks it ready as it merges. Never leave committed work unpushed and never leave a pushed branch without a draft PR + an enqueued ticket.

- **No AI attribution.** The harness's default is to add a `Co-Authored-By: Claude …` trailer and a "🤖 Generated with Claude Code" PR line; this workflow overrides that default. Paste this into every brief:

  > No AI attribution: no `Co-Authored-By: Claude` trailer on any commit, no "Generated with Claude Code" line in the PR body. Attribute solely to the configured git user.

### Dispatch in the background, then monitor for divergence
**Default to dispatching implementers in the background** (the Agent tool's `run_in_background: true`) rather than blocking on each one. This keeps you — the orchestrator — responsive: you get an automatic notification when an agent completes or opens its PR, AND you can poll the live worktrees mid-flight to catch a wandering agent *before* it burns a whole run going the wrong way. (Background dispatch is the Agent tool's own flag — this is NOT the banned `isolation: "worktree"`; you still make the worktree yourself via the helper and point a plain agent at it.)

**Poll every ~10 minutes for divergence** while agents run. Use `ScheduleWakeup` to self-pace the checks (≈600s is frequent enough to course-correct early). Don't poll *only* for completion — that arrives as a notification for free; the point of polling is **early divergence detection**, with two cheap riders on the same tick: (a) check whether any slice opened a draft PR and enqueued, and (b) **drain the gate queue** (`drain`) so enqueued PRs get gated and carry their verdict without waiting for you to notice. Each tick, snapshot what files each agent is actually touching and compare against its assigned scope:

- **Snapshot against the FORK POINT (the merge-base), never HEAD and never the integration tip.** Compute the fork point ONCE per tick — `FP=$(git -C <wt> merge-base HEAD origin/<integration>)` (re-`fetch` first; the tip moves) — then `git -C <wt> --no-pager diff --stat $FP` for the full file scope, plus `git -C <wt> ls-files --others --exclude-standard` for untracked. `git diff --stat $FP` (working tree vs fork point) captures BOTH any already-committed blocks AND uncommitted work-in-progress in one shot — which is what you need, because implementers **commit LAST** (after simplify), so mid-flight most of the work is still *uncommitted*; diffing the working tree against the fork point sees it regardless of whether it's been committed yet. Two traps, both of which have actually bitten us, so neither is hypothetical:
  - ⚠️ **Don't use `git diff --stat HEAD`** — that shows only *uncommitted* changes, so the moment an agent commits (it commits everything at the end) HEAD goes clean and the diff shows **nothing**, and you'll either think the agent is idle or reach for a range diff against the tip (the next trap). Use `git log --oneline $FP..HEAD` only to *list the commits*, never as your file-scope check.
  - ⚠️ **Don't use `git diff <integration>..HEAD` / `origin/<integration>..HEAD`** (two-dot against the tip). Once another PR merges into the integration branch *while this worktree is open*, that merged work shows up as **phantom additions/deletions** here and triggers a false divergence alarm — the merged PR's unrelated files look like this agent's edits. We hit exactly this: a poll two-dot-diffed against a tip that had just advanced, the unrelated merged PR's files appeared as the agent's, and a **perfectly in-scope agent was wrongly `TaskStop`ped** (then had to be resumed). The fork point never moves — anchor every scope check to `$FP`, same as the PR-review diff (below).
- **What counts as divergence:** editing another task's / another phase's **core source files** (e.g. a "types only" task editing the resolver, or a backend task building UI). **What does NOT count:** compile-driven ripples from the task's own change — exhaustive `switch`/enum/interface/config entries a new member forces, a one-line badge to keep an exhaustive UI match compiling, and `+1`-line fixture edits across many `*.test.ts` files (even ones in another area) from adding a field to a shared type. Spell out this divergence/not-divergence line in the wakeup prompt so the check is mechanical, not a re-judgement each time.
- **Check substance, not just the file count.** Staying in scope ≠ doing it right — a diffstat tells you *where* the agent is editing, not *whether the approach is correct*. On any slice with real design subtlety, periodically **read the actual diff of the 2–3 highest-risk files** (`git -C <wt> --no-pager diff $FP -- <file>`, anchored to the same fork point as the diffstat — NOT `HEAD`, which would omit the committed blocks), not just `--stat`, and confirm the agent is following the intended approach (or genuinely improving on it). **Grep the diff for the specific anti-patterns the brief banned** (e.g. a forbidden call leaking into the wrong layer: `git -C <wt> diff $FP -- <files> | grep -nE '<bannedSymbols>'`). A wrong-but-in-scope approach is exactly what file-counting misses, and catching it mid-flight saves a whole wasted run. Keep it light — the risk files, not the entire diff.
- **If an agent diverged** (out of scope OR on a wrong approach): `TaskStop` it immediately, then **dispatch a fresh plain agent into the SAME worktree path** with a tighter brief — explicit *do-not-touch* boundaries naming the files/areas it strayed into (or the wrong pattern to avoid), and an instruction to revert the bad edits. Don't try to course-correct a still-running agent mid-stream; stop-and-replace is cleaner.
- **If an agent opened its draft PR + enqueued, or genuinely finished:** stop rescheduling for that one and move into the drain + PR review loop + merge below. ("Finished" means the PR is open — not merely that a turn-end notification arrived; see the next bullet for why those differ.)
- **⛔ Don't mistake a `/simplify` pass (or ANY nested sub-agent wait) for a stall — it isn't, and cutting in wastes real work and infuriates the user.** `/simplify` fans out its OWN review sub-agents (reuse / simplification / efficiency / altitude) and legitimately takes **several minutes** — a `~5 min` pass is normal, not slow. While it runs, the implementer's turn ends and its **completion notification fires even though it is mid-pass, not done**. The tell is unmistakable: an uncommitted full worktree, no PR yet, and the agent's own hand-back saying it is *awaiting its simplify review agents* (or any sub-agent it spawned). That is a **self-suspension, not a stall** — the harness re-invokes the implementer automatically when its children finish, so `TaskStop`ping OR resuming it mid-pass throws away the in-flight review work and forces the whole pass to restart. **Leave it alone and let it come back on its own.** Budget the window: on a substantial slice, expect NO PR for the first couple of ticks and do not read that as failure. Only escalate to the stall-recovery resume (next bullet) when it is genuinely stuck — the worktree is byte-for-byte unchanged across **two consecutive ticks**, there are no live children, AND the agent is not reporting a wait — never merely because a PR hasn't appeared inside one 10-minute tick. (This over-eager cutting was a recurring, real complaint: the fix is patience, not a faster poll.)
- **A task that FAILS with "Agent stalled: no progress for Ns (stream watchdog did not recover)" is an INFRA stall, not a behavioural one.** The model made no bad choice — its stream died mid-turn. Nothing is lost: the worktree (including uncommitted work) persists, and a resume message to the SAME agent restores its full context from the transcript AND delivers any notifications that queued while it was down. Resume it firmly, restating where it was and the exact remaining finish-order (… → scoped check → simplify → commit blocks → push → draft PR → enqueue → report) plus "if you stall again, committed+pushed work is durable — resume from the furthest completed step." These stalls can cluster (one epic saw every parallel implementer hit one within an hour); each costs one resume, never a redispatch. The same resume verb also un-sticks a *genuine* behavioural stall (turn ended, worktree full, no PR — **and** none of the legitimate-self-suspension signals above) — but confirm it's actually stuck before resuming, because that description also fits an agent legitimately paused on its own sub-agents.

Carry forward a one-line note of each agent's last-known on-scope file set in the next wakeup prompt, so a sudden jump in surface area is obvious tick-over-tick.

### Draining the gate queue
On each `ScheduleWakeup` tick (the *same* timer you already run for divergence), run `drain` (Trinity: `pnpm gate:drain`) from the main checkout. One pass re-delivers any verdict a previous pass decided but failed to post, then claims queued tickets and, for each, runs the full `gate` in that ticket's worktree behind the slim machine-wide slot, then comments the verdict on the PR — a pass on green, the failing tail on red — and leaves it draft either way. It is a one-shot pass — it drains what's queued and exits — so the tick re-invokes it.

- **A full drain can be long** (each ticket is one serialized full gate). For a big queue, either bound it (`drain --max N` per tick) or run the drain with the harness `run_in_background` flag and treat its completion as a resume signal. Don't fire it and then abandon the loop.
- **Multiple orchestrators may drain concurrently** — that's safe by construction (atomic-rename claims, dead-claimant reclaim). You don't coordinate; you both just drain.
- **Don't hand-run `gate` on top of a live drain.** The runner already serializes gates one-at-a-time behind the slot; launching your own concurrent `gate` re-creates the saturation the slot exists to prevent. Let the runner be the only thing gating.
- **A worktree with a ticket in flight is FROZEN — don't mutate it, don't remove it.** The runner gates *inside that ticket's worktree*, so anything that changes the tree mid-gate makes the verdict meaningless: the gate tests a tree that no longer exists, then posts its result against whatever HEAD is current when it finishes. Observed failure: a drain was already running when the orchestrator reviewed the diff and dispatched a fix agent into that same worktree; the agent committed at 22:34:37, and the gate — a ~2m20s run — posted `✓ passed` at 22:34:38. Green, against code no gate had ever seen. Since a gate comment is exactly the evidence this workflow reads as "gated", trusting it would have merged untested code. Wait for the ticket to resolve — its verdict comment on the PR, either direction — before you dispatch a fix agent, remove the worktree, or touch anything inside it. This is *why* the review order below is review-first-then-drain.
- **A red ticket is orchestrator feedback, not lost work.** The PR stays a draft with the failure commented. Read it, dispatch a fix agent into that same worktree, and the fix re-pushes and re-enqueues. Nothing is stranded. (Safe here precisely because the ticket has already resolved — the gate is no longer running in that tree.)
- **A PR with NO gate comment has not been gated — never treat it as red.** The comment is the whole reading: a pass comment is green, a failure comment is red, and no comment means the gate never reported. Do not dispatch a fix agent against a bare PR — there is no failure to fix. A queue that records its verdicts (invariant 7 in the gate-queue reference) self-heals this on the next drain, which reconciles undelivered verdicts before claiming anything, so **run the drain and look again** before concluding anything. If it is still bare after a reconcile, the gate genuinely never ran: re-enqueue it. Observed on a real slice — a runner claimed a ticket, ran a full gate, and retired it with nothing posted; the PR sat with no verdict for 37 minutes until it was re-enqueued and gated a second time.
- **Reconcile the local integration branch on every tick — the cheap backstop for a dropped sync.** Even though `merge-pr.sh` fast-forwards the local integration branch at merge time, a hand-run merge or an interrupted close-out can leave it behind the remote, and the next worktree would then fork off a stale HEAD. On the same tick as the drain, run one anchored fast-forward against the main checkout: `git -C <main-checkout> fetch origin && git -C <main-checkout> pull --prune --ff-only` (a no-op when already current). It's idempotent and near-instant, so any missed post-merge sync self-heals within one poll instead of poisoning the next dispatch.
- **Running an epic branch? Merge the integration branch into it on this same tick — and step back off it.** Nothing to do when there is no epic branch, which is most of the time. When there is one, run this *after* the reconcile above (it merges the ref that fetch just moved):
  ```
  git -C <main-checkout> checkout <epic-branch>
  git -C <main-checkout> merge origin/<integration-branch>
  git -C <main-checkout> push origin <epic-branch>
  git -C <main-checkout> checkout <integration-branch>
  ```
  Merge, never rebase. This is the mandatory mitigation for the epic branch's one real cost — deferred and concentrated conflicts (see *The epic branch*) — and it only stays cheap while the slice authors are still live to resolve what it surfaces. The push is what puts the merged base where the slice worktrees fetch it from; without it the drift is reconciled only in the main checkout and every live slice still forks off the old epic tip. The final `checkout` is not tidiness: the reconcile bullet above takes no branch argument and pulls whatever is checked out, so a main checkout left parked on the epic branch stops fast-forwarding the integration branch from the next tick onward.

### The PR review loop
Each implementer opens **its own draft PR** back to the branch its worktree was cut from — the integration branch, or the epic branch when the epic has one; the runner comments the gate's verdict on it. That comment is the gate signal, and it is all the gate can tell you — the PR stays draft until *you* merge it, because marking it ready is your signature that you read the diff. So **review each PR and actually read the code involved**, not just the agent's summary or the green comment. Read the diff: verify correctness, that it does what the issue/plan intended, that the scope is right, and scrutinize anything the agent flagged or where it went wider than the planned files. A green gate and a confident agent report are necessary but **not sufficient** — the merge decision is yours and must be grounded in the actual changed code.

**A hand-back report is evidence about its own half and hearsay about the other.** An implementer can tell you what it built; it cannot tell you what its counterpart now expects, because it never saw the counterpart. So for any pair the decomposition flagged as a **contract seam** — one slice produces a shape another consumes — reading each diff on its own is not review, it is two half-reviews. **Diff both halves against each other before merging either**, and check the specific thing: the shape the producer now emits against the shape the consumer now reads. Both PRs will be green — each gate only ever exercised one side. *The failure this prevents: perfectly file-disjoint slices, zero merge conflicts, and several genuine cross-slice breaks that no single PR's gate or hand-back could have surfaced.* When the producer has merged and the consumer has not, the consumer's next re-gate catches it; when they merge in the same drain, nothing does.

**Review BEFORE you drain, never after.** Reviewing is where you decide whether the code changes, so draining first is both wasted (a full serialized gate burned on code you're about to replace) and *unsafe*: the fix agent you dispatch next would edit a worktree with a gate still running in it, which produces a green that corresponds to no commit (see *Draining the gate queue*). The order per PR is: implementer hands back a **draft PR + an enqueued ticket** → **you read the diff first** → needs changes? dispatch the fix agent **now**, before any drain — it re-pushes and re-enqueues → re-review → only once the code is final do you drain, so the gate verdict corresponds to the exact commit you're going to merge. Then verify that correspondence explicitly before merging: compare the SHA the gate comment names against the PR's current head, since a verdict that predates the last push describes a tree the PR no longer carries.

**Review the implications, not just the brief.** A PR can match its slice's brief, pass its own gate, and stay perfectly in scope — and still be wrong once it lands among its siblings. Read for *second-order* effects, not only local correctness: (1) **cross-slice composition** — when two slices each own one half of a contract (slice A stamps a header, slice B reads that header for the credential; one slice renames/derives a field, another consumes it), confirm the halves still agree *on the merged branch*, even though the files are disjoint. (2) **shared global state** — a change that's correct in isolation can be silently defeated by a process-wide cache, singleton, or memo it didn't author (does that cache key on the value you just made per-tenant, or globally?). (3) **emergent interactions** — a fix that corrects one path can expose or shift a neighbor's behavior (tightening identity makes a queue correctly *wait* instead of mis-running; a now-required field surfaces a caller nobody listed). File-disjointness buys *textual* independence, never *semantic* independence — so the review asks "what does this imply for everything it touches indirectly?", not just "does it match the brief?". When a second-order effect is load-bearing, go read the shared dependency yourself (the cache, the consumer, the sibling's half) rather than assuming it composes.

**Check the docs before you flip it ready — every PR, not just the ones that look documentation-shaped.** The implementer's report carries a per-doc verdict; read it against the diff rather than accepting it, because the implementer can only report on docs it thought to look at. Ask the question yourself from the diff: what does this change make true, or stop being true, for someone who reads the docs instead of the code? Then check that the docs saying otherwise are in this PR. A missing docs commit is a fix-agent round trip, not a merge blocker to argue about — but it is caught *here*, because after the merge the only thing that surfaces it is a user acting on something that stopped being true. **The failure mode to watch for is your own:** if you scoped a doc out of the brief, you did it from the plan rather than from the diff, so re-derive it now from what actually changed. That is exactly how a stale README ships — not because the implementer skipped it, but because it was told not to look.

**Diff against the merge-base, not the integration tip.** The integration branch advances *while a worktree is open* (other agents' PRs merging in parallel), so `git diff <integration-branch>..HEAD` shows the OTHER work's additions as phantom **deletions** in this PR — a clean change then looks like it ripped out unrelated code, and you'll raise a false alarm. Always diff the fork point: `git -C <wt> diff $(git merge-base HEAD origin/<integration>)..HEAD` (re-`fetch` first — the tip moves). Confirm by test-merging the current base in: if the "deleted" files come back as *additions*, the PR never touched them. This bit us once — burned a review cycle chasing a "destructive deletion" that was just the base having moved.

If it needs changes, **dispatch a fix agent into that same worktree** — but only once that worktree has no gate running in it (its ticket is unqueued or already resolved); never into a tree the runner is mid-gate on. It re-pushes and re-enqueues, and the runner re-gates. Iterate until the PR is good and green. Only when satisfied do you **merge and clean up** — and the *order* matters because of worktrees (see next section): the implementer has already pushed everything, so you **remove the worktree first**, then merge with `gh pr merge --merge --delete-branch`.

### Merging a shared hotspot — `mergeable` ≠ correct
When several slices edited the **same function or structure** (a control loop's `tick()`, a reducer, a registry, an exhaustive switch — anything the decomposition flagged as a *shared hotspot*), a clean auto-merge is **not** proof of correctness. Git merges by line: two slices that added code in *different* spots produce `mergeable: MERGEABLE` with no conflict markers — but git has no idea the two additions must **compose**. The recurring failure shape: a structure has sibling branches that must stay **twins** (e.g. two "parked → freeze every kill-clock" branches), each slice added its new clock's freeze-line only to the branches that existed *when it forked*, and the merge silently leaves the newer branch missing it — textually clean, behaviorally a reaper that kills a healthy job. **The integration gate won't catch it** unless a test exercises that exact cross-slice interaction, which is precisely the case nobody wrote.

So whenever a merge — auto-clean OR conflicted — touches a structure 2+ slices edited: **open the merged region and read it; do not trust `mergeable`.** Diff the parallel-edited siblings against *each other* — whatever should be parallel (twin branches, every case of a switch, all handlers of an event, the reducer vs the renderer) must have received the **same** treatment from each slice. Honor the **shared invariant** the decomposition handed you, if any. Fix drift forward as a small, clearly-messaged merge-reconcile commit, then re-verify the interaction (enqueue an integration gate, or run one directly once the fleet is quiet). Resolve actual conflicts by **merging the branch's own PR base into it, in its worktree** (`git fetch && git merge origin/<the PR's base>`, keep BOTH concerns) — never rebase. Merge the base the PR actually targets, not the integration branch by reflex: for a slice based on an epic branch those are different branches, and merging the integration branch straight into the slice drags in commits the epic has not converged on, defeating the isolation the epic branch is there for. Then push and `gh pr merge`. Two more conflict-resolution hazards from the field: (1) **lockfile conflicts between sibling PRs are never hand-merged** — take the base's side (`git checkout --theirs pnpm-lock.yaml`), regenerate with the package manager (`pnpm install --no-frozen-lockfile`) so it reconciles ALL merged packages, verify the scoped check, and commit that; (2) **git happily commits leftover conflict markers once the file is staged** — `git add` marks a path resolved whether or not it is, so after ANY conflict edit (especially a scripted one) run `git diff --check` or grep for `<<<<<<<` BEFORE committing; a botched scripted resolution has shipped markers into a pushed branch exactly this way. This bit us twice in one governor epic: two separate textually-clean auto-merges each dropped a parked-state freeze-line, either of which would have reaped a healthy queued job.

### On the gate — the runner gates; you read the diff
**The RUNNER runs `gate` once per PR — that IS the gate.** `gate` is the HEAVY full suite: build + the entire test run, serialized behind the slim machine-wide slot (`scripts/gate-slot.mjs` for Trinity) so concurrent gates can't saturate the box. Implementers don't run it (their commits are held only to the cheap scoped check by the pre-commit hook), and release-branch PRs typically get no CI — so the runner's drained gate is what stands in for CI.

**Per-PR, the orchestrator reads the diff — it does NOT hand-re-run the heavy gate.** The runner's green comment is the per-PR signal; don't duplicate it. Re-gate (by re-enqueuing, or running `gate` yourself once the fleet is quiet) only for a genuine reason: the runner never got to a ticket, or a **merge integrates branches that weren't tested together** (one integration gate on the merged result). Even then prefer the minimum — the affected/changed tests over the whole suite where possible. Your always-on job is reading the **diff**; heavy re-gating is conditional.

**A stale slot self-heals; you rarely touch it.** The slot's holder-PID is liveness-checked, so a crashed gate's slot is stolen by the next drain within a poll, and a runner that dies mid-gate has its ticket reclaimed and re-gated. There is no "strangling orphan" for you to clear by hand and no lock dir to `rm` — the queue and slot handle their own dead work. (If you ever do need to forcibly stop a runner's gate, clear its worktree via `remove-worktree.sh <leaf>`, which signals the processes; never `rm` the slot dir out from under a possibly-live holder.)

### Reading a gate result — verify the WHOLE failure set, and read the comment, not the flags
Two misreads have shipped a red integration branch and closed an epic on top of it. Both are structural and cheap to avoid — internalize them before you ever conclude "green" or merge. The third bullet is the adjacent bug they make easy to wave through:

- **A gate spans every workspace — read every package's result, never one package's summary.** `gate` runs the task-runner across ALL packages (Trinity: trinity, trinityailabs.com, cf, api-types). A `Failed: <pkg>#test` line plus a non-zero exit is **RED**, even when the *first* package's summary you happen to see looks like only the known baseline. Concluding "green-modulo-baseline" (see the transient-red window below) from one package's `Test Files N failed` line — without confirming the failing SET across *every* package is exactly the baseline — is precisely how a real regression in a *second* package rides through to merge. When you assert green-modulo-baseline, enumerate the failing files across all packages and match them to the baseline set by name; a `cache miss, executing …` line for a package whose *result* you never saw is a signal to go read that result, not to assume it passed. (This actually happened: a slice was merged "green-modulo-baseline" off its trinity summary while its trinityailabs.com suite was red — the data-layer regression only surfaced at the epic's integration gate.)

- **The gate comment is the only evidence a gate ran — a PR's flags are not.** Trust exactly two signals that a gate is actually green: a runner-drained **`gate ✓ passed`** comment, or an override-mode agent's own gate comment on its PR reporting a full green with zero failures — and on the close-out/integration slice, independently re-run the previously-red files yourself before you believe it. Nothing else attests to a gate, and an empty PR conversation means nothing has. Read the comment and its failure set; the draft flag is about review, not about the suite.

- **An implementer that opens its PR without `--draft` is a bug you act on, not a formatting slip.** The ready flag means "an orchestrator read this diff and is merging it", and `merge-pr.sh` is the only thing that should ever set it — so a PR that arrives non-draft is claiming a review that never happened and is sitting in the merge-eligible state without one. Put it back to draft (`gh pr ready --undo`), then gate and review it like any other.

### Transient-red window (schema-first / all-or-nothing epics)
When a foundational change lands first — a NOT-NULL schema swap, a required interface field, a renamed module — it makes `gate` impossible to get fully green branch-wide until every consumer migrates. A full-green gate is **unattainable mid-epic BY DESIGN**; holding slices to it just paralyzes progress.

**Put this window on an epic branch.** An epic in this shape is the primary trigger for one (*The epic branch* above), and this section is the reason: the window has to exist somewhere, and the only real choice is whether it sits on the branch every other session cuts its worktrees from. On an epic branch it does not — the integration branch stays shippable throughout and sees the epic only as the single merge at the end, so nobody else forks off a knowingly-red base. Read the rest of this section as describing the **epic branch** when the epic has one, and the integration branch when it does not.

In that window a drained ticket's gate will exit non-zero on the pre-existing baseline failures until every consumer migrates, and the runner will comment that failure on the PR. That's expected, **not** a real block. Read the runner's output as: the compile half (typecheck + lint) is GREEN, the task's OWN new/affected tests are GREEN, and there are NO failures beyond the baseline SET that pre-dated this task on its fork point (file + test names, not a count — fixing one stale test and breaking a new one keeps the count identical but is still a regression; the absolute count drifts between tasks forked at different tips and as consumers migrate). If it clears that bar, merge it with `merge-pr.sh` on that bar rather than a green exit — the merge is where you record having read it, and a red comment you have *judged* is not a blocker, only a verdict you have to read carefully.

### Gate the integrated whole before you close — N green PRs ≠ a green epic
Each branch was gated against *its own fork point*, blind to the other slices; the branch that now carries all of them together has been gated by *no one*. So a multi-slice epic is NOT done when every PR is individually merged-green. The close-out is: once the last slice merges and the fleet is quiet, run ONE `gate` (directly, or enqueue a ticket for it) on **the branch the slices merged into — the epic branch when there is one, the integration branch when there isn't** — and require it GREEN (modulo a known pre-existing baseline) BEFORE declaring the work done or closing the issue.

Which branch that is decides where a cross-slice break gets found. On an epic branch this gate runs while the integration branch has still seen none of the epic, so the failure surfaces outside the branch other sessions are cutting from, and the fix is one more slice PR into the epic. Without one, the same failure is found *on* the shared branch, after every slice has already merged into it. Either way, a failure that first appears here is a real cross-slice interaction the per-PR gates *structurally could not* catch (none of them saw the others) — fix it forward, don't rationalize it away. Independent-green is necessary; *integrated*-green is what actually ships. **On an epic branch this gate is also the precondition for the epic → integration PR**: that PR is what finally puts the whole change set on the shared branch, so it does not open until this gate is green.

### Merge & cleanup — one command, because the sync is the step that gets dropped
The four steps below have exactly one correct order, and step 3 (sync the local integration branch) is the one with **no forcing feedback** — every visible signal after the merge (`✓ Merged`, branch deleted, PR closed) says "done", so it's silently skipped, and the miss only surfaces later when the *next* worktree is cut from a stale HEAD. So **default to the helper that does all four atomically: `merge-pr.sh <pr-number>`.** It resolves the main checkout + the PR's base/head branches, confirms GitHub can actually merge the PR before anything irreversible happens, tears down the worktree, marks the PR ready and immediately `gh pr merge --merge --delete-branch`es it, and — anchored to the main checkout regardless of your cwd — fast-forwards that local base branch. Running it *is* the approval: the ready flip lives one line above the merge precisely so a PR can never sit around wearing a review it has outgrown. It's idempotent (a re-run finishes a half-done close-out) and it's the reason a hand-run sync can't get dropped: don't split these steps back out by hand unless the helper can't handle a case.

**The teardown comes before the merge, so the helper checks the merge is possible before the teardown.** The branch lives in a linked worktree, and **git refuses to delete a branch that's checked out in a worktree** (`cannot delete branch 'X' used by worktree …`), so `gh pr merge --delete-branch` would error on the local-branch step if the worktree still existed — the order below is load-bearing and stays. What that order costs is that the two irreversible steps run *before* the one that can fail: a PR whose base moved under it fails at the merge with `GraphQL: Pull Request has merge conflicts`, and without a preflight that leaves no worktree to resolve the conflict in and a PR marked ready with no review behind it. So `merge-pr.sh` asks GitHub whether the PR is mergeable **first**, and a `CONFLICTING` answer stops it cleanly — worktree intact, PR still draft — naming the fix. Two consequences for you: a conflict now costs you a resolve rather than a recovery, and if the merge fails anyway (GitHub computes mergeability asynchronously, so a just-pushed PR can answer `UNKNOWN` and the helper falls through rather than blocking) the helper puts the draft flag back on its way out, and its message tells you to re-attach a tree with `setup-worktree.sh --existing <head-branch>`. Resolve a conflict by **merging the base in, in the branch's worktree** (`git fetch origin && git merge origin/<the PR's base>` — the branch the PR actually targets, which for an epic's slice is the epic branch, not the integration branch) — never rebase — then push, re-gate, and re-run `merge-pr.sh`.

If you ever run the close-out by hand (helper unavailable, or an edge it can't cover), do it in this exact sequence, every time — and check `gh pr view <n> --json mergeable` yourself before step 1, since by step 2 the worktree is gone:
1. **Confirm the ticket is done before you tear down.** The runner gates in the ticket's worktree, so don't remove a worktree whose ticket is still `queue`/`processing` — wait until its gate has resolved (its verdict comment is on the PR). Removal is one half of the frozen-worktree rule; **editing** it mid-gate is the other and is just as damaging — see *Draining the gate queue*. Then **remove the worktree — always via the helper:** `remove-worktree.sh <branch-leaf>` (or the absolute path). **Do not use `git worktree remove` directly.** Plain `git worktree remove` evicts the directory but does NOT signal any running processes — so a gate running in it survives as an orphan. The helper kills all processes rooted in the worktree first — via `lsof` + `pgrep`, escalating SIGTERM → SIGKILL — then removes the worktree. On Windows it instead scans `Win32_Process` command lines and kills the matching process trees with `taskkill /T /F`, since neither `lsof` nor `pgrep` exists in Git Bash and there is no SIGTERM to escalate from; it also prints a notice that open-handle enumeration was **skipped** (the `lsof +D` half has no built-in Windows equivalent), so a removal that fails on a locked file has a stated cause rather than looking like a mystery. Nothing is lost — it's all pushed — and this frees the branch so it can be deleted.
2. **Mark the PR ready, then merge with branch deletion:** `gh pr ready <n>` immediately followed by `gh pr merge --merge --delete-branch` — the flip is your review approval, so it belongs against the commit you are merging this second, not earlier in the sequence. Real merge commit (never squash), and with the worktree gone `--delete-branch` cleanly removes BOTH the local and remote branch. Skipping `--delete-branch` is what let merged `origin/*` branches pile up indefinitely (they did: dozens accumulated). Verify it's fully merged first; STOP on git's "not yet merged to HEAD" warning. **If the merge fails after you flipped it, flip it back** (`gh pr ready <n> --undo`) — a non-draft PR that isn't being merged right now is a bug, and here it would be one wearing a review the merge never earned.
3. **Sync the local integration branch — anchored to the MAIN checkout, never `&&`-chained.** `gh pr merge` advances the branch only on the *remote*; the local integration branch in the main checkout does NOT move, and syncing it is what keeps the next worktree from forking off a stale HEAD. Run it anchored so cwd can't defeat it: `git -C <main-checkout> checkout <integration>` then, as a **separate** command, `git -C <main-checkout> pull --prune --ff-only`. ⚠️ Do NOT hand-run the old `git checkout <integration> && git pull` form: with no `-C` anchor it assumes your shell is in the main checkout, but the orchestrator's cwd is usually inside a worktree — there `git checkout <integration>` fails with `already used by worktree at …`, and the `&&` swallows the `git pull` so the sync silently never happens (this is exactly the "merged but never synced" bug). The two-command, `-C`-anchored form is why the helper above can't drop it.
4. **Close the issue yourself if the work resolved one — GitHub will NOT auto-close it.** Auto-close only fires when a PR with a `Closes #N` keyword merges into the **default branch** (`main`). Our PRs merge into the **integration branch**, so a linked issue stays open regardless of keywords — and in practice the PRs only cross-reference (`#N`) rather than use a closing keyword anyway, so no close link even exists. After merging, `gh issue close <N> --comment "Fixed in #<pr> (merged into <integration>)."` for each issue the merged work resolved. (Don't wait for the eventual integration→`main` merge to sweep them — close them now so the issue tracker reflects reality.)

## Implementer

**First action, before any other command: `cd` into your assigned worktree and prove you're really there** — `git rev-parse --show-toplevel` must print the assigned path and `git branch --show-current` the assigned branch; if either mismatches, STOP and report rather than proceed. Run every subsequent command from inside the worktree — a relative path or a stray `cd` back to a main checkout is how edits land in the wrong tree. Work only in the assigned worktree (absolute paths), match surrounding style, and follow the project's conventions — its `briefConventions` (from `<repo>/.agents/worktree.json`) and its `AGENTS.md`. (For Trinity — **app = Solid, sidecar = Effect**: invoke the `frameworks:effect-v3` skill for any Effect-TS code on the sidecar, and the `frameworks:solid` skill for any SolidJS UI code on the app — `solid-js`, `@solidjs/router`, `@tanstack/solid-query`, Kobalte; build forward-only — pre-launch, no backwards-compat shims; comments explain the mechanism, no issue/PR/version/plan refs.)

**The flow is: write all the code → update the docs it changed → (`/simplify` if this slice warrants it) → commit → push → draft PR → enqueue the gate → hand back.** Write the whole change in your worktree, running *cheap* checks as you work: format, a scoped lint/typecheck (via `scopedCheck` or `turbo run <task> --filter=<pkg>` for lint/typecheck breadth — never raw `tsc`/`eslint`, which bypass the shared cache), and a **single targeted test file run directly** (`vitest run path/to/x.test.ts`). That single file is the widest test execution you get. **Any test run wider than one file — a whole package or the whole suite — is the gate's job, not yours, and is banned by ANY invocation:** not `gate`, not `turbo run test`, not a raw `vitest` sweep, not a per-package `test` script. The cached-runner rule is about *how* to run lint/typecheck breadth, not a license to run suites — routing a suite run through turbo doesn't make it allowed.

**Docs are part of the change, not a follow-up.** Before you hand back, write down the user-visible behavior your change adds, removes or alters, then find the docs describing *that behavior* and bring them in line — the repo's `README.md`, its `AGENTS.md`/`CLAUDE.md`, and any reference or docs directory it keeps, plus whatever its conventions name. **Search by the behavior, not by the vocabulary you introduced:** prose written for a user describes a feature in plain language and contains none of your new identifiers, so grepping for your own new terms comes back empty and reads as "nothing to update" — which is how a doc goes stale while every check stays green. Docs go in their own commit, separate from the behavior, and every doc you looked at gets a one-line verdict in your hand-back report. Nothing in the gate can catch a stale doc, so the report is the only record that the question was asked at all.

**Whether you run `/simplify` is the orchestrator's call, made per slice in your brief** — it's a quality pass worth its round-trip on substantial work and pure noise on trivial changes. If the brief says to simplify (the default for substantial slices), do NOT commit as you go: keep the whole change uncommitted, and when the code is done run the `/simplify` skill over your *full uncommitted* working-tree diff (reuse / simplification / efficiency / altitude cleanups — quality only, not bug-hunting), fold the fixes in, and ONLY then commit. If the brief says to skip it — or you're a direct implementer with no orchestrator and the change is plainly trivial (a one-liner, a copy/config tweak, a mechanical rename) — skip `/simplify` and commit in logical blocks as the work lands; don't run it just to report "nothing actionable."

⚠️ **Why commit last when you DO simplify:** `/simplify` acts on the *uncommitted* working-tree diff. Anything you've already committed is invisible to it — so if you commit as you go, the earlier blocks never get simplified, and against a fully-committed (clean) tree `/simplify` sees an empty diff, finds nothing, and silently does nothing while reporting "nothing actionable." The review simply never happens. Keeping everything uncommitted until after simplify is what makes the pass actually cover the whole change. (A skip-simplify slice has no such constraint — commit as the blocks land.)

**Always format in write mode right before committing.** The scoped check runs format-*check* (Trinity: `pnpm format` in write mode vs. the check inside `pnpm check`) — the pre-commit hook verifies formatting, it does not fix it. So run the auto-formatter over your tree as the last thing before `git commit`; then the hook's format-check passes on the first try instead of bouncing you on whitespace you never saw. Cheap, and it removes a whole class of surprise commit denials.

**Formatter output is always committed, never reverted.** When the auto-formatter (or the gate, which runs it) rewrites a file, commit the result — do not revert it as "out of scope." Formatting of the files *you* changed folds into your change; formatting of files *unrelated* to your change (a pre-existing non-canonical file the formatter normalized) goes in its OWN `chore(format)` commit. And when you run the full gate yourself (override mode), it formats *in your worktree* — so on green you CAN and SHOULD commit whatever it wrote and push, rather than re-running the slow gate to re-verify formatting (pure prettier writes can't break a check/test that already passed). The one thing you must never do is throw formatter output away: a reverted format is drift left on the branch for the next agent to trip over.

**You do NOT run the full gate — and the ban is on the WORK, not the command name.** The heavy build+test gate runs later, in a runner, drained from the queue — not by you. Your commits are held only to a cheap **scoped check** (`scopedCheck` = format-check + lint + typecheck; no build, no test suite), and the agentic pre-commit hook already enforces it on every `git commit` — so a commit that would fail the scoped check is denied and you fix it and re-commit. That's the entire quality bar you personally clear. Never run the full suite or any whole-package test run **by any invocation** — not `gate`, not `turbo run test`, not a raw `vitest` sweep, not a package `test` script; renaming the route doesn't unban the run. **Backgrounding it is still running it:** launching a banned run with `run_in_background` (or `&`/`nohup`) does not satisfy "don't wait" — it violates "don't run," burns the box the slot exists to protect, and is the classic stall shape (suite churns in the background, you end your turn, the handoff never happens). Your instinct to verify your change by running the tests is exactly the default this workflow overrides: verification wider than one test file is the runner's job, and your PR gets it after you enqueue. Never wait on a gate, and **never mark your own PR ready — in any mode, on any result.** That flag is the orchestrator's signature that it read your diff, and you cannot sign it for them. (Exception, and it covers only *who runs the gate*: ONLY if the orchestrator's brief — or the user dispatching you directly — **explicitly** put this slice in **override gate mode**: then run the full `gate` yourself once, in the foreground, post the result as a comment on your own PR, leave the PR a draft, and do NOT enqueue. You never grant yourself this exception — not because the change feels risky, not because you suspect nobody is draining. If you genuinely believe no runner will ever gate your PR, say so in your hand-back report; don't run the gate.)

**Then commit in logical blocks** — committing last loses nothing: stage each self-contained step (a type + its plumbing, a behavior + its tests, one cohesive refactor) into its own commit with a mechanism-explaining message (`git add -p` / path-scoped staging), so the never-squashed history stays reviewable block-by-block — now over code that's already simplified. **Never rebase. Never merge your own PR.**

**⛔ Attribute every commit + PR to the git user ONLY — no Claude attribution, ever.** This OVERRIDES the harness default that tells you to end commit messages with a `Co-Authored-By: Claude …` trailer — that default does NOT apply here. Do NOT add a `Co-Authored-By: Claude …` trailer (any model) to commit messages, and do NOT add a "🤖 Generated with Claude Code" line to PR bodies. Keep messages clean and attributed solely to the configured git user.

**The handoff — push, draft PR, enqueue, hand back.** This exact order is what makes a mid-flight death lose nothing: the branch is pushed and the PR is open before the ticket exists, so if you die right after enqueuing, your work is a visible draft PR that a runner will still gate.
1. **Push** all your commits.
2. **Open a DRAFT PR** targeting the branch your worktree was cut from — your brief names it (`gh pr create --draft`). Capture the PR number and URL from the output.
3. **Enqueue the gate:** `enqueue --branch <yourBranch> --worktree <yourWorktreeAbsPath> --pr-number <n> --pr-url <url>` (Trinity: `pnpm gate:enqueue …`). This drops a durable on-disk ticket; a runner will drain it, run the full gate in your worktree, and comment the verdict on your PR — a pass on green, the failing tail on red. The PR stays a draft either way. (In override gate mode there is no ticket: you ran the gate yourself, so you post that comment on your own PR and skip this step.)
4. **Hand back** — report the PR URL, files changed, scoped-check result, tests touched, **the per-doc verdict** (every doc you checked, each marked updated or not-affected-because — never a bare "docs reviewed", which is indistinguishable from not having looked), and anything ambiguous. You're done; you do NOT wait for the gate.

**Don't be lazy — leave the tree cleaner than you found it, and commit out-of-scope fixes separately.** Your job is not "make the assigned change and stop the instant the scoped check stops *erroring*." A check that exits green but still prints warnings is NOT done. Actively fix every lint warning, type warning, and error you hit or that your own change surfaces — even when it is technically out of scope: the residual unused imports a file is left with after you move its code to a sibling, a path-keyed lint allowlist (sanctioned-git / ambient-identity / ambient-network rules) that must follow the relocated code to its NEW file path, a stray nit in a file you only opened to read. The bar is **zero warnings and zero errors on every file your change touches.** **Isolate each such opportunistic / out-of-scope fix in its OWN commit** with a clear mechanism-explaining message (e.g. a `chore(lint): prune imports the split left unused` commit, kept separate from the `refactor: split …` commits) — so it stays independently reviewable and the orchestrator can keep or drop it without untangling it from the task. Never silently fold an unrelated fix into a task commit, and never hand back a "green" PR that still carries warnings for someone else to clean up. (If a surfaced fix is genuinely large, risky, or a behavior change, still isolate it in its own commit AND call it out in your report — don't bury it, and don't skip it.)

**⛔ Never game a guardrail — fix the cause, not the number.** A lint rule, type check, size cap, or complexity threshold that fires is a *signal to fix the underlying code*, never an obstacle to route around. If a file trips a max-lines cap, **split it** — extract a cohesive module and re-export it from the barrel so consumers are untouched; do NOT shave comments, compact readable code, or nudge to one-line-under to sneak past. That ships *worse* code that merely passes — the exact opposite of what the check is for. Never silence a rule to go green: no bare `eslint-disable` / `oxlint-disable`, no `@ts-ignore` / `@ts-expect-error`-to-hush, no widening a type to `any`, no deleting the assertion the check flagged. Never sacrifice clarity — a dropped explanatory comment, a mangled refactor — to hit a metric. **Zero warnings AND zero errors on every file you touch is the bar** — a warning is not a lesser class you may leave behind: where the gate lints at `--max-warnings=0` a warning IS a hard failure, and even where it isn't yet, you still fix it. The only acceptable path to green is fixing what the guardrail pointed at; anything else gets caught and bounced at review. If the honest fix is genuinely too big for this slice, STOP and hand it back (see below) — do not paper over it.

**The one carve-out — a DOCUMENTED suppression, for when the flagged construct IS the intended behavior.** That is rare, and it is never "the check is wrong": it is that the thing the rule points at is the feature, so there is no cause to fix and "fix the cause instead of suppressing" has nothing to point at. (This plugin's own `bin/setup-worktree.ps1` is one — it suppresses `PSAvoidUsingInvokeExpression` on a single function, because a project's `install` config value is a command *line* (`pnpm install --frozen-lockfile`, possibly with a pipe) that must be **interpreted** rather than spawned as an argv, exactly as the bash sibling's `eval "$INSTALL_CMD"` does. Deleting it turns CI red; spawning an argv instead breaks every project whose install command carries a flag.) A suppression you ADD is permitted then, and ONLY when **all four** of these hold — it is gaming the moment any one of them fails:

- **Narrowest scope the tool allows** — one function, or one line. Never file-wide, and never a settings-file or config exclusion that switches the rule off repo-wide: a global exclusion is indistinguishable from deleting the check.
- **A written justification in place, through the tool's own mechanism** where one exists — `SuppressMessageAttribute`'s `Justification=`, a `// eslint-disable-next-line <rule> -- <reason>` — never a bare disable comment. This is the load-bearing condition, and the reason is the diff: a justification-bearing suppression puts a claim in front of a reviewer who can reject it, while a bare `// eslint-disable-next-line` asserts nothing and so cannot be argued with. Invisible to review is exactly what gaming looks like, which is why the mechanism matters and not just your intent.
- **The justification says why the flagged construct is correct HERE** — what the code does and why that is the behavior wanted. "Noisy rule", "false positive", "the check is wrong" are not justifications; they are the claim this carve-out exists to refuse. If you can't write the sentence without arguing with the check, you don't have an exception — you have the fix you were avoiding.
- **You call it out in your hand-back report** — file, rule, and the one-line reason — so it is reviewed at merge rather than discovered later by someone who has to reconstruct why it is there. A suppression nobody flagged is a suppression nobody reviewed, and gets bounced at review even when the other three hold.

**An EXISTING suppression is not yours to re-justify, and not yours to delete for compliance.** These four conditions test a suppression you are introducing; one that was already in the file when you opened it is the previous author's claim, already reviewed on the PR that added it. If you think it fails a condition, say so in your report and leave it — removing it is a behavior change you were not asked for, and load-bearing suppressions are exactly the ones a green-at-any-cost instinct removes first.

Nothing here softens the prohibitions two paragraphs up — a bare disable with no reason, widening to `any`, deleting the assertion the check flagged, shaving comments to duck a max-lines cap, nudging one line under a threshold. None of them can satisfy the four conditions, because for none of them is there a correct-construct claim to write down. **The failure this carve-out prevents:** an implementer who reads the rule as an unqualified absolute and then opens a repo that correctly violates it has two bad options — delete a load-bearing suppression to comply, or conclude the rule is violated in the repo that ships it and stop trusting it at all. A rule with an undocumented exception doesn't get followed carefully; it gets ignored wholesale. Stating the exception precisely is what keeps the default absolute.

**If you get stuck, hand back a reviewable artifact — never spin or die silently.** A blocker, an ambiguity you can't resolve, a scoped check you can't get green, or running low on room all mean the same thing: STOP and give the orchestrator something it can act on. Commit-push and open a **draft PR** with what you have (and enqueue it if it's far enough along to gate); if you can't even do that, hand back a complete report of your worktree state — what's done, what's broken, the exact error/blocker, and the decision you need. Partial-but-clean beats stuck-and-silent (e.g. land the solid part and flag the rest). **Never leave a dirty worktree with no PR and no report, and never leave a committed-but-unpushed branch — push and open a DRAFT PR so the orchestrator inherits a reviewable, mergeable artifact rather than invisible work trapped in your worktree.**

**A missing input is a hand-back, not a value to invent — and this is the one that will NOT feel like being stuck.** The paragraph above covers blockers you can see. This covers the opposite: your brief needs an id, a key, an owner, a path, a version — something that identifies a real thing — and the thing does not exist yet, or you cannot reach it from where you are. Nothing is erroring. You can produce a value of the right *shape*, and everything downstream will accept it: the types are satisfied, the scoped check is green, the tests pass, the PR reads clean. **That is precisely the failure.** A fabricated identifier does not fail loudly at review; it records the wrong fact, permanently and quietly, and every guardrail you have confirms it. So when the input names something real and you cannot obtain the real one, STOP and report exactly that — what you needed, why it was not available where you stand, and what the orchestrator must decide (dispatch it later, hoist a wave-0 slice, or hand you the value). *The failure this prevents: an implementer that could not obtain an owning identifier at the point its slice ran, declined to synthesize one, and reported the gap — where a plausible substitute would have passed every check while silently attributing the work to the wrong thing.* Shape-correct and fact-wrong is the hardest defect class to find later, because nothing about it looks broken.

## Hard rules (both roles)

- **⛔ Implementers never run the full suite — by any invocation, foreground or background; they enqueue it.** The heavy build+test gate runs one-at-a-time in a runner drained from the durable queue, behind a slim machine-wide slot. An implementer's quality bar is the cheap scoped check (enforced by the pre-commit hook) plus at most a single targeted test file; its wrap-up is push → draft PR → enqueue. The ban is extensional — it covers `gate`, `turbo run test`, raw `vitest` sweeps, and package `test` scripts alike — and **backgrounding a banned run (`run_in_background`, `&`, `nohup`) is still running it**, not a way to comply with "don't wait." The only exception is a slice **explicitly** put in override gate mode by the orchestrator's brief (or the dispatching user) — never self-granted — where the implementer runs `gate` itself once, in the foreground, and comments the result on its own draft PR. Never hand-run a `gate` concurrently with a live drain — the runner already serializes gates; a concurrent one re-creates the saturation the slot prevents.
- **⛔ Never use the Agent tool's `isolation: "worktree"` param or any auto worktree provisioner.** Make worktrees only via `setup-worktree.sh`, verify HEAD, then dispatch a plain agent. (See worktree section.)
- **⛔ The three `trinity-ai-labs` skills repos — `market-skills`, `orchestration-skills`, `framework-skills` — are PR-only, never a direct push to `main`, docs and CHANGELOG included.** Each ships to installs pinned by `.claude-plugin/plugin.json`'s `version`, so a change here reaches users exactly as any other repo's does; and in a repo whose product is prose, the diff is the only review artifact there is, because no gate can tell whether a rule is *correct*. A direct push spends the review record to save a worktree.
- **⛔ Only the merge marks a PR ready — the flag is the reviewer's signature, never a gate verdict.** `draft → ready` means "an orchestrator read this diff and is merging it", so the only thing that sets it is `merge-pr.sh` in the same breath as `gh pr merge`. Implementers never set it, in any gate mode; the gate never sets it, in either direction — it comments its verdict and leaves the PR draft. That gives one reading that holds everywhere: **a PR is gated iff it carries a gate comment**, and a non-draft PR that isn't being merged right now is a bug. Keeping the flip adjacent to the merge is what stops `ready` from going stale — a flip set earlier survives the next push and then vouches for a diff nobody read.
- **Never squash-merge; merge + clean up + sync as one step.** Prefer `merge-pr.sh <pr-number>`, which does the whole close-out atomically (tear down worktree → real merge commit → fast-forward the local integration branch). If you merge by hand, use a real merge commit (`gh pr merge --merge --delete-branch`), never `--squash` — squashing flattens the individual commits we keep. Always pass `--delete-branch` so the remote branch is removed on merge instead of accumulating — but **remove the worktree first** (see Merge & cleanup), or `--delete-branch` errors trying to delete a branch still checked out in a worktree. **And always finish with the local integration-branch sync**, anchored to the main checkout (`git -C <main-checkout> pull --prune --ff-only`) — never the unanchored `git checkout <integration> && git pull`, whose `&&` silently swallows the pull when your cwd is inside a worktree, leaving the branch merged-on-remote but stale locally and the next worktree forked off a stale HEAD.
- **Do NOT rebase.** Rebasing rewrites history. Default to plain merge commits everywhere: integrating parallel worktree branches, a branch falling behind the integration branch, resolving overlap between two PRs — MERGE, never rebase. If two parallel branches touch the same file, resolve it at MERGE time (merge one, then merge the other and fix conflicts in the merge), not by rebasing one onto the other. Never instruct a sub-agent to rebase. Only rebase when there's a specific, unavoidable reason AND it's worth rewriting history — rare; when in doubt, merge.
- **⛔ Whether to run `/simplify` is the orchestrator's per-slice call — and WHEN it runs, commit LAST.** Simplify is a quality pass worth its round-trip on substantial work and noise on trivial changes (one-liners, copy/config tweaks, mechanical renames), so the orchestrator decides per slice and states it in the brief (a direct implementer with no orchestrator makes the same call for itself). When a slice simplifies, the order is load-bearing: `/simplify` reads the working-tree diff, so against a clean (fully-committed) tree it silently no-ops — finding "nothing actionable" because there's nothing to see, not because the code is clean. So write all the code → `/simplify` → *then* commit (in logical blocks) → push → draft PR → enqueue; never commit as you go and never commit-everything-then-simplify, either of which hides code from the pass. A skip-simplify slice just commits in logical blocks as it goes. Cheap checks (format, scoped lint/typecheck, a single test file) may run mid-task regardless.
- **⛔ No Claude attribution on commits or PRs — git user only.** This OVERRIDES the harness's built-in "end commit messages with `Co-Authored-By: Claude …`" instruction; it does not apply in this flow. Never add a `Co-Authored-By: Claude …` trailer (any model) to a commit, nor a "🤖 Generated with Claude Code" line to a PR body. Attribute solely to the configured git user. Spell this out in every implementer brief — dispatched sub-agents follow the harness default unless told otherwise.
- **⛔ Never game a guardrail — fix the cause, not the number.** A lint/type/size/complexity check that fires is a signal to fix the underlying code (split an over-long file + re-export from the barrel, extract, genuinely simplify), NOT a threshold to sneak under. Never suppress or disable the rule (a bare `eslint-disable` / `oxlint-disable` / `@ts-ignore` / `@ts-expect-error`-to-hush / widening to `any`), never shave comments or compact readable code to duck a max-lines cap, never sacrifice clarity to hit a metric. **Zero warnings AND zero errors on every file you touch** — a warning is not a lesser class to leave behind. When a size ratchet has tiers (e.g. warn at 600, error at 800), the *warn* tier is the target: split to land comfortably under it, with real headroom, not one line under. Verify against the check that actually owns the rule (a project may split lint across tools — e.g. oxlint for most rules, an eslint backstop for the size ratchet — so a rule can be green in one and failing in the other; run both). Gaming a guardrail ships worse code that merely passes; the orchestrator's review scans the diff for it (bare `eslint-disable`/`@ts-ignore` inserts, comment-shaving to hit a cap) and bounces it. **One carve-out exists — a DOCUMENTED suppression, for when the flagged construct IS the intended behavior — defined in full in the Implementer section's "Never game a guardrail" paragraph above, which is the authoritative copy.** At review, check its four conditions against the diff: narrowest scope the tool allows; a written justification in place through the tool's own mechanism, never a bare disable comment; that justification saying why the flagged construct is correct *there*, not that the check is noisy; and a call-out in the hand-back report. Bounce anything else — including a suppression that meets the first three and was never mentioned in the report, since one nobody flagged is one nobody reviewed. The conditions apply to suppressions the diff ADDS; a pre-existing one the slice merely left alone is not this PR's claim to re-litigate.
- **Branch from the branch the work converges on, never `main`.** That is the **epic branch** when a multi-slice epic has cut one (*The epic branch* — the trigger is narrow, so most work has none), and the **active integration branch** otherwise. A PR targets the same branch its worktree was cut from, so the two can never disagree.
- **Never delete a branch past git's "not merged" warning** — verify fully merged into the target first.
- **⛔ Don't bypass the shared build cache — run tasks through the runner.** Cache-eligible tasks (test, typecheck, lint) must go through the task-runner — the project's `scopedCheck`/`gate`, or `turbo run <task> --filter=<pkg>` — NOT the raw binary (`vitest`, `tsc`, `eslint`) and NOT a per-package script that shells straight to it (`pnpm --filter <pkg> test` when that script is a bare `vitest run`). A direct run always goes cold — locally *and* in the drained gate — and never populates the cache for the next machine/CI. The only sanctioned direct-binary run is a **single targeted test file**. If a project's `AGENTS.md` documents the raw form as the whole-package default, that's a leak to fix, not a pattern to copy into briefs.

**Why this shape:** integration branch as the merge point, isolated worktrees per task, clean up after merge. The heavy gate is decoupled from the flaky sub-agent that produced the change — implementers enqueue a durable ticket and hand back; robust orchestrators drain the queue and gate one-at-a-time — so a dying agent never strands committed work and a wide fan-out never serializes on a lock. We preserve real merge history rather than flattening it via squash or rebase. Skipping the post-merge local sync leaves the local integration branch behind the remote, so the next worktree gets cut from a stale HEAD.
