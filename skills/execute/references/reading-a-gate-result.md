# Reading a gate result, and the transient-red window

Reference for `skills/execute/SKILL.md` → *Dispatcher*. **Read it the moment a verdict lands on a PR** — a green flag and a green gate are not the same claim, and one epic shape makes red the expected answer.

## Reading a gate result — verify the WHOLE failure set, and read the comment, not the flags
Two misreads have shipped a red integration branch and closed an epic on top of it. Both are structural and cheap to avoid — internalize them before you ever conclude "green" or merge. A third runs the opposite way and costs the opposite thing: reading an **environmental** red as N code defects, which spends whole runs debugging innocent diffs. The bullet on a PR that arrives without `--draft` is the adjacent bug they make easy to wave through. **All of it is about reading a verdict somebody else POSTED.** A gate you ran yourself has none to read at the moment you need one — you are the party who produces it, if anyone does — so its **exit status** is the reading instead (*Gate the integrated whole* below). Naming that boundary is load-bearing rather than tidy: this section is thorough enough to look complete, so a dispatcher standing in front of a gate log it produced itself finds nothing here that fits its situation and falls back on whatever the shell said — which is how a piped gate's exit 0 got read as green.

**Two counts moved when the flow started enqueueing its own gates, and they moved by DIFFERENT amounts — say which one you mean.** In a project with a queue, the epic's close-out gate and the mid-arc integration gate are both enqueued now (*Gate the integrated whole*). So: **paths that produce no durable record at all go 3 → 1.** A hand-run gate is the only one that writes no streamed log, no ticket and no ledger entry, and it is left in **two** places rather than one: a project that declares no queue, where an override-mode slice is the whole of it, and a queued project whose runner refuses the PR-less ticket, where the mid-arc integration gate alone falls back to it (*Gate the integrated whole*). **Paths that produce no PR comment go 3 → 2.** The close-out gains one, on the very PR the verdict is about; a PR-less integration ticket does not and never will, because there is no PR; and an override-mode slice's comment is one the agent *writes* rather than one it reads. So the mid-arc gate does not leave this section's scope — what changes is what you read: **the verdict on its ticket in `done/`, not a shell's exit status.** *The failure this prevents is letting either count stand for the other. Read as "everything is commented now", a dispatcher waits on a comment that will never arrive against a PR that does not exist — and "settled with no comment" is the queue's own signal for a failed post (`skills/setup/references/gate-queue.md`, Reporting), so the wait presents as a delivery problem and the natural remedy, another reconciling drain, retries a post nobody was ever owed.*

- **A gate spans every workspace — read every package's result, never one package's summary.** `gate` runs the task-runner across ALL packages (Trinity: trinity, trinityailabs.com, cf, api-types). A `Failed: <pkg>#test` line plus a non-zero exit is **RED**, even when the *first* package's summary you happen to see looks like only the known baseline. Concluding "green-modulo-baseline" (see the transient-red window below) from one package's `Test Files N failed` line — without confirming the failing SET across *every* package is exactly the baseline — is precisely how a real regression in a *second* package rides through to merge. When you assert green-modulo-baseline, enumerate the failing files across all packages and match them to the baseline set by name; a `cache miss, executing …` line for a package whose *result* you never saw is a signal to go read that result, not to assume it passed. (This actually happened: a slice was merged "green-modulo-baseline" off its trinity summary while its trinityailabs.com suite was red — the data-layer regression only surfaced at the epic's integration gate.)

- **Several worktrees red at the same moment, with infrastructure-shaped errors, is ONE shared resource before it is N code defects — and it is the same instrument as the bullet above, pointed one level out.** That one says the failure set spans every package, so don't stop at the first summary; this one says the failure set can span every *worktree*, so don't read a simultaneous multi-slice red as N independent verdicts. They compose: widen within a gate, then widen across gates. **The tell is the shape of the errors, not their count** — deadlocks, unique-constraint violations, lock timeouts, "address already in use", a fixture another run truncated, a cache another run evicted — and the confirmation is that the *same* named resource appears in failures on branches whose diffs have nothing to do with each other. Check `sharedResources` (*Per-project config*) before you dispatch a single fix agent: an entry with `"isolatedBy": null` means the flow already knows these runs collide, and a missing key means nobody ever asked, which is not the same as no. Re-gate the branch **alone** to separate the two — a red that survives in isolation is a code defect, one that evaporates was the race — and where it was the race, the move is to narrow the wave, not to touch a diff. *The failure this prevents, observed twice from opposite directions. Three reviewers dispatched while a gate was live produced 605 spurious failures and then 151, and the implementer got it right only by calling it environmental rather than "fixing" its branch. And in a repo that had already solved this, commenting out the single line that gave each worktree its own database reproduced it exactly — 116 failures, then 121, deadlocks throughout, every one of them naming the one shared database. The default response to a red is to debug the diff, and that response is not merely wasted here: the slice that lost the race is the one that looks guilty, so the "fix" lands in whichever innocent branch happened to be second.*

- **The gate comment is the only evidence a gate ran — a PR's flags are not.** Trust exactly two signals that a gate is actually green: a runner-drained **`gate ✓ passed`** comment, or an override-mode agent's own gate comment on its PR reporting a full green with zero failures — and on the close-out/integration slice, independently re-run the previously-red files yourself before you believe it. Nothing else attests to a gate, and an empty PR conversation means nothing has. Read the comment and its failure set; the draft flag is about review, not about the suite.

- **An implementer that opens its PR without `--draft` is a bug you act on, not a formatting slip.** The ready flag means "a dispatcher read this diff and is merging it", and `merge-pr.sh` is the only thing that should ever set it — so a PR that arrives non-draft is claiming a review that never happened and is sitting in the merge-eligible state without one. Put it back to draft (`gh pr ready --undo`), then gate and review it like any other.

## Transient-red window (schema-first / all-or-nothing epics)
When a foundational change lands first — a NOT-NULL schema swap, a required interface field, a renamed module — it makes `gate` impossible to get fully green branch-wide until every consumer migrates. A full-green gate is **unattainable mid-epic BY DESIGN**; holding slices to it just paralyzes progress.

**Put this window on an epic branch.** An epic in this shape is the primary trigger for one (*The epic branch* above), and this section is the reason: the window has to exist somewhere, and the only real choice is whether it sits on the branch every other session cuts its worktrees from. On an epic branch it does not — the integration branch stays shippable throughout and sees the epic only as the single merge at the end, so nobody else forks off a knowingly-red base. Read the rest of this section as describing the **epic branch** when the epic has one, and the integration branch when it does not.

**The window is a fact on disk, not a note in a plan — declare it or it does not exist.** `decompose` flags which slices live in the window and you read a drained ticket's red against that flag, but both of those are judgments made by something that can read prose. A project's **commit-time** tooling cannot. Where a repo relaxes its pre-commit compile check for exactly this window — forgiving diagnostics that all point at files the branch never touched, while holding the branch's own files to the full bar — the only thing it can consult from inside a slice worktree is the ref graph. So the marker ref from *The epic branch* above is the contract, and it is deliberately the whole contract: `transient-red/<epic-slug>` exists ⇔ the window is open, and deleting it at close-out closes the window with nothing to unwind.

**Two things a detector must not key on instead, both of which look right — and the one rule behind both.** Not the **epic branch itself** — Rule 2 cuts one on multi-slice width alone, so there is an epic branch on *every* multi-slice arc including all the ones where every intermediate state is green, and a relaxation keyed on `epic/*` would silently start forgiving sibling breakage that is real on every one of those. And not `integration/*` — this playbook's opening reserves "integration branch" for the shared branch and says it never means anything else, so a detector keyed on that word is reading a level of the hierarchy that was never the window's home. **Generally: no branch-name prefix is ever the key.** The epic branch's prefix is read by nothing (*The epic branch* → *Mechanics*), so a detector keyed on it is keyed on taste, and tooling that has to ask "is this an epic branch" answers it with a dedicated ref of its own — the way this marker does — never with a prefix match. *The failure this prevents: a prefix match reads a name nothing else in the flow reads, so it agrees with the branch only for as long as whoever cut it happens to pick that prefix — and it fails silently in both directions, calling the window closed on an epic that has one open and open on an epic that does not. The other half of the cost is invisible from here: a prefix already carrying meaning somewhere else in the project quietly acquires a second reader, and renaming a branch to satisfy this detector re-scopes that one too.*

**Confirm it actually fires before you dispatch the first slice.** A window that failed to open and a project that never had one are byte-for-byte indistinguishable: nothing errors, nothing warns, and every slice just takes the strict path as though that were the design. So the evidence is only ever evidence you went and asked for. From inside the first slice's worktree — where the tooling actually runs, not from the main checkout — confirm the marker is visible (`git for-each-ref refs/heads/transient-red refs/remotes/origin/transient-red` naming the ref you pushed) and that the project's own detector agrees the window is open. One check, once per epic. *The failure this prevents: a detector and a flow can disagree about where the window lives — the detector looking for one ref, the flow having pushed another — and neither side reports the disagreement, so every slice pays full strict-path friction for a relaxation the repo believes it has.*

In that window a drained ticket's gate will exit non-zero on the pre-existing baseline failures until every consumer migrates, and the runner will comment that failure on the PR. That's expected, **not** a real block. Read the runner's output as: the compile half (typecheck + lint) is GREEN, the task's OWN new/affected tests are GREEN, and there are NO failures beyond the baseline SET that pre-dated this task on its fork point (file + test names, not a count — fixing one stale test and breaking a new one keeps the count identical but is still a regression; the absolute count drifts between tasks forked at different tips and as consumers migrate). If it clears that bar, merge it with `merge-pr.sh` on that bar rather than a green exit — the merge is where you record having read it, and a red comment you have *judged* is not a blocker, only a verdict you have to read carefully.
