# Implementer

Reference for `skills/execute/SKILL.md`. **If you were handed a dispatch brief, THIS FILE is your instructions** — `skills/execute/SKILL.md` alone does not contain them, and its *Hard rules (both roles)* binds you on top of everything here. Read all of both before you write a line.

## The work — the tree you edit, the flow through it, and the commits

**First action, before any other command: `cd` into your assigned worktree and prove you're really there** — `git rev-parse --show-toplevel` must print the assigned path and `git branch --show-current` the assigned branch; if either mismatches, STOP and report rather than proceed. Run every subsequent command from inside the worktree — a relative path or a stray `cd` back to a main checkout is how edits land in the wrong tree. Work only in the assigned worktree (absolute paths), match surrounding style, and follow the project's conventions — its `briefConventions` (from `<repo>/.agents/worktree.json`) and its `AGENTS.md`. (For Trinity — **app = Solid, sidecar = Effect**: invoke the `frameworks:effect-v3` skill for any Effect-TS code on the sidecar, and the `frameworks:solid` skill for any SolidJS UI code on the app — `solid-js`, `@solidjs/router`, `@tanstack/solid-query`, Kobalte; build forward-only — pre-launch, no backwards-compat shims; comments explain the mechanism, no issue/PR/version/plan refs.)

**The copy you were handed is not the copy you are editing — where your slice edits the corpus it is reading, the worktree's copy is the authoritative one.** Step 0 loaded these skills from the **installed** plugin, whichever version is enabled in the plugin cache, and that is not the tree you have just proved you are standing in. In every other repository the two have nothing to do with each other and this never arises; in the repository that ships these skills they are one document at two versions, and **the rules an arc has just shipped are the ones most likely to be missing from the copy you were handed**. So read a governing rule out of the worktree before you act on it, and where one looks wrong, absent, or contradicted by what the tree plainly does, `diff` the two copies rather than concluding the tree is broken — a discrepancy is the cache being old, not the tree being wrong. Say in your hand-back which copy you read the rules from. *The failure this prevents: nothing errors. You load a real skill, follow real rules and produce work that satisfies them — the previous version's — and the hand-back, the diff and the gate all read the same either way. Observed: a sweep of this corpus for rules that disagree across files produced two candidate findings that were defects the worktree had already fixed, manufactured by the instrument rather than found by it; it was caught partway through and redone against the worktree.* This is the version-skew test in *File your follow-ups BEFORE you hand back* arriving one artifact earlier — there, a closed issue is a fact about the tracker rather than about the tree the failure was observed in; here, the same gap is in the rules themselves.

**The flow is: write all the code → update the docs it changed → (`/pipeline:review` if this slice warrants it) → commit → push → draft PR → enqueue the gate → hand back.** Write the whole change in your worktree, running *cheap* checks as you work: format, a scoped lint/typecheck (via `scopedCheck` or `turbo run <task> --filter=<pkg>` for lint/typecheck breadth — never raw `tsc`/`eslint`, which bypass the shared cache), and a **single targeted test file run directly** (`vitest run path/to/x.test.ts`). That single file is the widest test execution you get. **Any test run wider than one file — a whole package or the whole suite — is the gate's job, not yours, and is banned by ANY invocation:** not `gate`, not `turbo run test`, not a raw `vitest` sweep, not a per-package `test` script. The cached-runner rule is about *how* to run lint/typecheck breadth, not a license to run suites — routing a suite run through turbo doesn't make it allowed.

**Docs are part of the change, not a follow-up.** Before you hand back, write down the user-visible behavior your change adds, removes or alters, then find the docs describing *that behavior* and bring them in line — the repo's `README.md`, its `AGENTS.md`/`CLAUDE.md`, and any reference or docs directory it keeps, plus whatever its conventions name. **Search by the behavior, not by the vocabulary you introduced:** prose written for a user describes a feature in plain language and contains none of your new identifiers, so grepping for your own new terms comes back empty and reads as "nothing to update" — which is how a doc goes stale while every check stays green. Docs go in their own commit, separate from the behavior, and every doc you looked at gets a one-line verdict in your hand-back report. Nothing in the gate can catch a stale doc, so the report is the only record that the question was asked at all.

**A comment you rewrite or relocate is a claim you are re-asserting — check it before you reword it.** Prose that asserts what *other* code does is the one defect class nothing here can scan for. A duplicate, an unimported export, a type that disagrees with its schema — every class this flow's checks catch is a disagreement between two artifacts a tool can compare. A comment asserting a code path is prose against behavior, and the only thing that finds it is someone reading the claim and going to look. So when your change touches a comment that says what happens elsewhere — *the route parses this with X*, *callers must call Y first*, *this is enforced in Z* — open that code and confirm it still does that **before** you rewrite the sentence. **A claim that turns out false is a FINDING, not a wording bug**: report it, and file it (*A follow-up is yours*) when fixing it is not this slice's job. Never quietly correct it into accurate prose. This is a different rule from the one governing how a comment is written — present-tense mechanism, no archaeology; that one is about the wording, this one is about whether the wording is TRUE, and a comment can be flawless by the first and describe a function call that does not exist. *The failure this prevents, observed: a schema module's doc block described a two-step validation the route performed — the route did only step one, and never had done step two. Tracing every consumer showed the refined schema was never parsed in production at all, so an invariant that was declared twice and refined twice had never executed anywhere, while a comment described its enforcement in working code. It surfaced by accident, from a slice rewriting that block for an unrelated naming fix that happened to check the claim first. The tidy rewrite is the worst outcome available: it documents a bug as the design and removes the last thing that could have led anyone to look, because a wrong comment and a right one are indistinguishable in review — and the wrong one is load-bearing in the worst way. It is why nobody looked.*

**On a slice of an epic your brief inverts the last step, and only that step: record what you falsified, don't rewrite it.** The entry — *"this change makes paragraph Y of `<doc>` false"* — goes in your report, and one closing docs slice writes against the final tree (*The epic branch* → *Docs land at the end*, which is also where the carve-outs are). Everything before it is unchanged: you still derive the list from the behavior you changed rather than from your own new vocabulary, and you still report a verdict per doc. *The failure this prevents: read as "docs are somebody else's problem on an epic", it becomes the deferred-docs failure — you are the only party who will ever know what your diff falsified, and an entry you did not write is one the closing slice cannot answer.*

**And the ledger takes TWO entries, not one — the second is what your change ADDED that no doc describes at all.** *What did this change make false?* is a question about a difference, so a surface no doc has ever described returns *nothing* from it — honestly, completely, and indistinguishably from the answer you give when you touched no documented behaviour. **Reporting "nothing falsified" is doing the first rule correctly and says nothing whatever about the second**, so answer both: beside each falsification entry, record what you added that has no prose anywhere, marked as **needing new prose** rather than a correction — *"this change adds `<surface>`, which no doc describes."* Derive it the same way, from the behavior your diff adds rather than from your own new vocabulary; and where a chapter covers your area but stops short of what you changed — it says the thing fires, never what it now contains — that is this entry and not a not-affected verdict. *The failure this prevents: you are the only party who will ever stand in front of this diff, and the closing docs slice cannot ask a question about a surface it does not know exists — so an undocumented surface with no entry stays undocumented, which lands hardest on new behaviour precisely because new behaviour is the likeliest thing to have no prose about it yet.*

**The inversion covers prose, not coordinates — a path you moved, you repoint, in this PR.** A file path your slice moved or deleted, or a route literal sitting in the same clause as one, is yours to fix here even though the doc is otherwise the closing slice's: a checker can tell it is stale without reading the sentence, so a repo whose docs gate validates path citations reds on it at its FIRST step and your own `format`, `check` and `test` never run — you get no signal about your own work, and there is no ordering that escapes it, because the closing docs slice is last by construction. **Change the path and stop there.** The sentence around it is prose, so it goes in the ledger like everything else, and rewriting it while you happen to have the file open is precisely the semantic conflict the deferral exists to prevent (*The epic branch* → *Docs land at the end*, the coordinate carve-out, which carries the argument and the observed failure). **A renamed identifier is not a coordinate and does not come with you** — a function, a param, an exported symbol reads like the same mechanical swap, but no checker resolves one in prose, so the whole sentence goes in the ledger and the name goes with it. **And "stop there" is not "leave it half-right": before you land the repoint, read that sentence for a fact your OWN change moved** — a TTL, a limit, a default — and where you find one, **fix both halves. That is the only move**: reverting the repoint hands your docs gate back the stale path it reds on, and the sentence sits in the ledger with or without the revert, so undoing it costs you your own gate and buys the closing slice nothing. Never a fresh path beside a stale number: the half you corrected is what persuades the closing slice the rest was checked.

**Whether you run `/pipeline:review` is the dispatcher's call, made per slice in your brief** — it's worth its round-trip on substantial work and pure noise on trivial changes. If the brief says to run it (the default for substantial slices), do NOT commit as you go: keep the whole change uncommitted, and when the code is done run `/pipeline:review` over your *full uncommitted* working-tree diff (reuse / simplification / efficiency / altitude, plus correctness), decide which findings to apply, and ONLY then commit. If the brief says to skip it — or you're a direct implementer with no dispatcher and the change is plainly trivial (a one-liner, a copy/config tweak, a mechanical rename) — skip it and commit in logical blocks as the work lands.

⛔ **`/pipeline:review`, never the bundled `/simplify`.** They are not interchangeable and the difference is not cosmetic. The bundled skill fans its reviewers out as **forks**, and a fork inherits your entire conversation — including this brief, whose imperatives end in *commit, push, open a draft PR, enqueue the gate*. Its reviewers read that as their task list and carry it out: observed across three consecutive slices of one epic, review agents applied fixes, ran the repo formatter at root, committed, pushed, opened the PRs and enqueued the gate tickets before the implementer that spawned them got its turn back. `/pipeline:review` is inline — it spawns nothing and commits nothing, and every decision about what goes in stays yours. If you catch yourself about to spawn review sub-agents, or waiting on any, you are running the wrong pass: stop and check what they did to your worktree.

⚠️ **Why commit last when you DO review:** the pass acts on the *uncommitted* working-tree diff. Anything you've already committed is invisible to it — so if you commit as you go, the earlier blocks never get reviewed, and against a fully-committed (clean) tree it sees an empty diff, finds nothing, and silently does nothing while reporting that there was nothing to act on. The review simply never happens. Keeping everything uncommitted until after the pass is what makes it actually cover the whole change. (A skip-review slice has no such constraint — commit as the blocks land.) **And holding a change uncommitted for a whole slice is exactly where the urge to `git stash` shows up — to get a clean tree for a check, or to park the work while you sync a base. Park it under your own named ref rather than onto the shared stack**: `git stash create` + `git update-ref refs/pipeline-stash/<branch-leaf>/<epoch>`, restored with `git stash apply --index` on that same name (*Hard rules* carries the four commands and the caveats). Nothing else in the repo can renumber, pop or clear it, so getting the work back is a lookup rather than a guess about what is on top.

**Always format in write mode right before committing.** The scoped check runs format-*check* (Trinity: `pnpm format` in write mode vs. the check inside `pnpm check`) — the pre-commit hook verifies formatting, it does not fix it. So run the auto-formatter over your tree as the last thing before `git commit`; then the hook's format-check passes on the first try instead of bouncing you on whitespace you never saw. Cheap, and it removes a whole class of surprise commit denials.

**Formatter output is always committed, never reverted.** When the auto-formatter (or the gate, which runs it) rewrites a file, commit the result — do not revert it as "out of scope." Formatting of the files *you* changed folds into your change; formatting of files *unrelated* to your change (a pre-existing non-canonical file the formatter normalized) goes in its OWN `chore(format)` commit. And when you run the full gate yourself (override mode), it formats *in your worktree* — so on green you CAN and SHOULD commit whatever it wrote and push, rather than re-running the slow gate to re-verify formatting (pure prettier writes can't break a check/test that already passed). The one thing you must never do is throw formatter output away: a reverted format is drift left on the branch for the next agent to trip over.

**You do NOT run the full gate — and the ban is on the WORK, not the command name.** The heavy build+test gate runs later, in a runner, drained from the queue — not by you. Your commits are held only to a cheap **scoped check** (`scopedCheck` = format-check + lint + typecheck; no build, no test suite), and the agentic pre-commit hook already enforces it on every `git commit` — so a commit that would fail the scoped check is denied and you fix it and re-commit. That's the entire quality bar you personally clear. Never run the full suite or any whole-package test run **by any invocation** — not `gate`, not `turbo run test`, not a raw `vitest` sweep, not a package `test` script; renaming the route doesn't unban the run. **Backgrounding it is still running it:** launching a banned run with `run_in_background` (or `&`/`nohup`) does not satisfy "don't wait" — it violates "don't run," burns the box the slot exists to protect, and is the classic stall shape (suite churns in the background, you end your turn, the handoff never happens). Your instinct to verify your change by running the tests is exactly the default this workflow overrides: verification wider than one test file is the runner's job, and your PR gets it after you enqueue. Never wait on a gate, and **never mark your own PR ready — in any mode, on any result.** That flag is the dispatcher's signature that it read your diff, and you cannot sign it for them. (Exception, and it covers only *who runs the gate*: ONLY if the dispatcher's brief — or the user dispatching you directly — **explicitly** put this slice in **override gate mode**: then run the full `gate` yourself once, in the foreground, post the result as a comment on your own PR, leave the PR a draft, and do NOT enqueue. **Capture that gate's own exit status, never a pipeline's** — `gate > gate.log 2>&1; echo "EXIT=$?"`, then read the log, never `gate | tail` — and quote the `EXIT=` line in the comment you post. *Gate the integrated whole* carries the argument; what is different here is the stake. Your reading of that status **is** the comment, and the comment is the one thing this flow treats as evidence a gate ran — so a piped invocation does not merely mislead you, it manufactures a green verdict for every reader downstream. On a project with no queue that is every slice rather than a rare grant (*Per-project config*). You never grant yourself this exception — not because the change feels risky, not because you suspect nobody is draining. If you genuinely believe no runner will ever gate your PR, say so in your hand-back report; don't run the gate.)

**Never background a check and end your turn on it — and this rule is keyed to the HANDOFF, because the ban above is keyed to the run and so cannot reach a check you are allowed to run.** That paragraph is scoped to a *banned* run, which is exactly why an implementer backgrounding its `scopedCheck` reads it correctly and concludes it is not about them. The stall shape does not care which run it was: the turn ends, the handoff never happens, and the dispatcher's only signal is the phrasing of your hand-back. So the rule is stated over the handoff instead — **run your checks in the foreground, and end your turn at the hand-back: nothing you backgrounded is ever the reason your turn ends.** Every check you are allowed to run here is cheap, which is what makes the foreground the right place for it; and where the project has an agentic pre-commit hook, that hook re-runs `scopedCheck` on every `git commit` anyway — so holding a finished change uncommitted pending a check the commit itself will run buys nothing at either end. **This is about checks and commands, and it is NOT about sub-agents you spawned** — ending your turn while your own children run is a self-suspension the harness re-invokes, protected as such in *Dispatch in the background, then monitor for divergence*, and a rule reading "background nothing whose result you intend to wait on" would ban it. *The failure this prevents, observed on a single-slice run against `trinity-ai-labs/trinity` (PR #4798): the implementer backgrounded `pnpm check` — the project's `scopedCheck`, explicitly permitted, and re-run by the pre-commit hook on `git commit` anyway — and ended its turn with "I'll pause here and wait for the scoped-check monitor notification before committing". The change was complete and needed nothing, and it sat uncommitted: no commit, no push, no PR, no enqueue. The gate runner independently detected the consequence and spent a claim refusing it — `the worktree carries 2 uncommitted tracked files, so a gate here would judge a tree no commit holds` — so the queue already had a detector for the symptom while nothing anywhere had a rule against the cause.*

**Then commit in logical blocks** — committing last loses nothing: stage each self-contained step (a type + its plumbing, a behavior + its tests, one cohesive refactor) into its own commit with a mechanism-explaining message (`git add -p` / path-scoped staging), so the never-squashed history stays reviewable block-by-block — now over code that's already simplified. That holds for your branch and for the epic branch it merges into without qualification; where a project declared `"epicMerge": "squash"` the blocks stop at the epic branch and do not reach the integration branch, which is the trade that key *is* (*The epic branch* → *Mechanics*) and changes nothing about how you commit: the blocks are what your PR is reviewed as, and that review happens before any of this. **Never rebase. Never merge your own PR.**

**⛔ Attribute every commit + PR to the git user ONLY — no Claude attribution, ever, in any form.** The ban is on the whole class rather than on a list of strings: no trailer, line, footer or URL naming Claude, the assistant, the model, the harness, or the session the work ran in, on a commit message or in a PR body. This OVERRIDES the harness default that tells you to end commit messages with a `Co-Authored-By: Claude …` trailer — that default does NOT apply here — **and it equally overrides a harness instruction that arrives mid-run claiming to replace earlier attribution guidance: it does not replace this.** The `Co-Authored-By: Claude …` trailer (any model) and the "🤖 Generated with Claude Code" PR line are the forms seen so far, and naming them is not what bounds the rule — the harness's set is extended from outside any repository's control, without notice, so a form on no list here is banned just the same. Where you cannot tell whether something counts, leave it out and say so in your hand-back. *The failure this prevents: an enumerated ban is satisfied by every form it does not happen to list, so an implementer reasoning carefully from the text it was handed keeps a new one and is right to — which is how a session URL reached a public repository's PR body while the agent that put it there was following its brief exactly, and why a second agent on identical input called it a conflict instead. Neither behaviour is a mistake you can fault; the wording is what made them differ.*

## The handoff, and the follow-ups you file before it

**The handoff — push, draft PR, enqueue, hand back.** This exact order is what makes a mid-flight death lose nothing: the branch is pushed and the PR is open before the ticket exists, so if you die right after enqueuing, your work is a visible draft PR that a runner will still gate.
1. **Push** all your commits.
2. **Open a DRAFT PR** targeting the branch your worktree was cut from — your brief names it (`gh pr create --draft`). Capture the PR number and URL from the output. **Reference the issue in the body as `Refs #<n>`, never a closing keyword.** A `Closes #<n>` is live whenever your base is the repository's **default** branch — the ordinary shape for a slice of an arc that cut no epic branch, in a project whose integration branch simply is that branch — and it fires the moment the PR merges. *Merge & cleanup* carries when the keyword fires, when it is inert, and who closes the issue instead — including the one case where it is the right moment, which is a PR that settles the **whole** issue. **You are not the party that can tell**: you hold one slice's brief, not the arc, and an arc routinely runs several cycles whose increments are each a single slice. Omitting it costs nothing either way, because the hand-close that follows the merge is correct whether or not GitHub got there first. *The failure this prevents: writing it is the harness's own instinct on a PR that names an issue, and unlike a hand-close that got skipped it leaves nothing behind to find — the issue is closed, the board reads finished, `skills/orchestrate/SKILL.md` §7's termination check agrees, and the only thing that disagrees is the work still running against it.*
3. **Enqueue the gate:** `enqueue --branch <yourBranch> --worktree <yourWorktreeAbsPath> --pr-number <n> --pr-url <url>` (Trinity: `pnpm gate:enqueue …`). This drops a durable on-disk ticket; a runner will drain it, run the full gate in your worktree, and comment the verdict on your PR — a pass on green, the failing tail on red. The PR stays a draft either way. (In override gate mode there is no ticket: you ran the gate yourself, so you post that comment on your own PR and skip this step.)
4. **Hand back** — report the PR URL, files changed, scoped-check result, tests touched, **the per-doc verdict** (every doc you checked, each marked updated or not-affected-because — never a bare "docs reviewed", which is indistinguishable from not having looked), **every follow-up you filed** (issue number and one line on what it covers — see below; a follow-up named but not filed is not a follow-up), **the review pass's applied and rejected findings where the slice ran one** (`skills/review/SKILL.md`'s Output section writes that `Rejected` list *for the dispatcher reviewing your PR*, and this hand-back is its only route there; a finding you considered and deliberately did not act on is a decision rather than a doubt, so *anything ambiguous* does not reach it. *The failure this prevents: that pass runs inline, so the agent that read why the list exists is you — and complying with the letter of this enumeration still drops it, silently, because a rejected finding you never forwarded is indistinguishable from one the pass never raised, which is the exact indistinguishability the list was written to remove*), and anything ambiguous. You're done; you do NOT wait for the gate.

**File your follow-ups BEFORE you hand back — a bullet in a report is not a follow-up.** *Hard rules* states the rule and what a follow-up becomes; three things about it are yours specifically. **The filing happens inside this turn**, because you are the cheapest place in the whole flow for it: the worktree is open, the install is paid for, and the change that caused the item is in front of you, where a later session has to rebuild all three before it can start reading. **And the create call is not the first move — the failure you are about to file may already have a number.** `skills/write-issue/SKILL.md`'s *Before you file, search what is already filed* is that search: keyed on the failure shape rather than on your own words, over closed issues as well as open, and returning an outcome that is not always a new issue — an open issue already carrying this failure takes the observation as a comment instead, and a closed one makes the item a regression **only where the fix that closed it is present in the copy you read**. Absent from that copy, what you have is version skew rather than a finding and you file nothing; where you cannot establish which, you say that rather than pick. You are the only party who can run that check, because you are the one standing in the copy the failure was observed in. Run it here for the same reason the filing happens here. **The link names what surfaced it — and under an umbrella that is TWO acts, not one.** The body backlink is the first — `Follows #<N>`, or `Part of #<umbrella>` — so the item is findable from the arc it came out of. The **native** link is the second, it goes on in the same breath rather than as a follow-on step, and it is `gh api -X POST repos/{owner}/{repo}/issues/<umbrella>/sub_issues -F sub_issue_id=<child's DATABASE id>`. ⚠️ **That field is the child's database id (`.id`, e.g. `5261102081`), NOT its issue number** — take it from the create call's own response, or `gh api repos/{owner}/{repo}/issues/<n> --jq .id`. The two are different fields on the same object and both are plain integers, so nothing about the value's shape tells them apart, and passing the number returns a bare `404 Not Found` that reads as *"this endpoint doesn't exist"* rather than *"wrong id"* — which is how the step gets abandoned by an agent that believes it checked whether the API was there. **Native-link a containment relation only:** `Part of #<umbrella>` is containment and takes both links, while a bare `Follows #<N>` on a plain issue is provenance — the arc it came out of, not a whole it is a part of — and takes the body backlink alone, because in this corpus a sub-issue is a piece of the parent's remaining plan (`skills/orchestrate/SKILL.md` §7 makes an umbrella's body exactly that) and hanging a follow-up natively off a finished standalone issue asserts that issue is unfinished without it. `skills/decompose/SKILL.md`'s *Umbrella + sub-issues* is the authoritative copy of the call, and carries the other trap and the writer-side argument; what is here is the minimum you need in hand to do it without leaving this file, because nothing puts that skill in front of you at the moment you are filing. And **it goes in your report by number**, not as prose: an issue you filed and did not name is one the dispatcher cannot fold into the plan. *The failure this prevents: "flagged for follow-up: X, Y, Z" reads as thoroughness and is indistinguishable from it, while the items themselves stop existing the moment your turn ends — nothing in the gate, the PR, or the dispatcher's review can tell they were ever raised.*

*The failure the native half prevents, observed: five implementer-filed follow-ups on one six-slice epic, every one carrying a correct `Part of #<umbrella>` body backlink and not one natively linked — the shape of a rule being followed rather than skipped, because the rule the implementer had said backlink and stopped there. The cost lands on whoever arrives at that follow-up next. `skills/decompose/SKILL.md` Step 1 opens with one `/parent` call that resolves the umbrella definitively and reads **nothing but the native link**, so on a child of a markdown-only umbrella it 404s and drops the arriving agent onto the eight-candidate timeline search and its disambiguator. **The umbrella checklist line `skills/write-issue/SKILL.md`'s *Follow-up linking* mandates is not a substitute for the native link**, and reading it as one is the easy mistake here: it is the artifact that fallback disambiguates on, so it makes the expensive path resolve rather than making the cheap one available at all — the arc that produced the item stays reachable, and only by an agent that has already paid for the fallback.*

**An issue you file from behind a fence SAYS SO, on its own line in the body: `Filed from behind a fence: <the fenced path>`** — **and where the failure is already filed and your observation goes onto that issue as a comment instead, the line goes on the comment, in the same fixed form.** What it marks is how far *your* reading got, and that is unchanged by which artifact carries it. **Read the fence before you conclude that filing is what you have to do** — `skills/decompose/SKILL.md`'s `Do NOT touch` field is where this case is dispositioned, and a fence that grants you the fix is the only thing that can grant it, since you may not widen your own. Where it IS silent you have one move when you find something untrue inside it: you cannot change the thing, so you report it — and the report you write from there is weaker than the one you would have written with your hands on the file. The mechanism is not carelessness and no amount of diligence removes it: **an agent that can edit verifies by editing** — it changes the thing and watches what breaks — **and an agent that can only report verifies by reading, to the depth a report needs rather than the depth a change needs.** Afterwards the two artifacts are indistinguishable, so a report written from a glance is trusted exactly like one written from a diff, and the line is the only thing that tells them apart. Write it beside the backlink — or at the head of the comment, where there is no backlink to sit beside — and write it as the fixed form above rather than a phrasing of your own: `skills/orchestrate/SKILL.md` §4 is the consumer, and it keys on that line to treat the issue's claims as unverified premises before any of them becomes a slice — a marker nothing reads is decoration, and a rule with no marker to key on is unreachable. **It is not a disclaimer and it does not lower the bar on what you file**: ground the claim as far as reading takes you, exactly as you would otherwise, then mark how far that was. *The failure this prevents, observed: four slices each found something untrue inside a file their brief fenced, and each filed. Three of the four could not be closed as written — one reported a constant naming a file as dead when the constant was dead and the file was live, read and written by a module one directory over and outside the fence; one's acceptance grep under-counted its own subject, naming five sites as the whole set where a hyphen-tolerant pattern found eight across seven files; one offered deleting a branch as its first reading and could not reach the fallbacks below it to establish whether they covered the same case, which they did not. The first one's false half then propagated: a later issue inherited it verbatim as a premise and stacked a second wrong claim on top, and neither its author nor the dispatcher re-checked either half. An issue saying a thing is already gone is the most reliable way to ensure nobody looks at it again.*

## Craft, and the one sanctioned suppression

**Don't be lazy — leave the tree cleaner than you found it, and commit out-of-scope fixes separately.** Your job is not "make the assigned change and stop the instant the scoped check stops *erroring*." A check that exits green but still prints warnings is NOT done. Actively fix every lint warning, type warning, and error you hit or that your own change surfaces — even when it is technically out of scope: the residual unused imports a file is left with after you move its code to a sibling, a path-keyed lint allowlist (sanctioned-git / ambient-identity / ambient-network rules) that must follow the relocated code to its NEW file path, a stray nit in a file you only opened to read. The bar is **zero warnings and zero errors on every file your change touches.** **Isolate each such opportunistic / out-of-scope fix in its OWN commit** with a clear mechanism-explaining message (e.g. a `chore(lint): prune imports the split left unused` commit, kept separate from the `refactor: split …` commits) — so it stays independently reviewable and the dispatcher can keep or drop it without untangling it from the task. Never silently fold an unrelated fix into a task commit, and never hand back a "green" PR that still carries warnings for someone else to clean up. (If a surfaced fix is genuinely large, risky, or a behavior change, still isolate it in its own commit AND call it out in your report — don't bury it, and don't skip it.) **And the bar has a floor as well as a ceiling: what you cannot fix here, you FILE.** Residue too large or too risky to land in this slice does not become the user's by virtue of being left behind — it becomes a linked issue (*File your follow-ups before you hand back*, above). The two halves are one rule at two sizes: what fits, you fix here in its own commit; what doesn't, you file and link. A warning left behind and a follow-up left unfiled fail identically — the next agent finds the residue and no record that anyone ever saw it.

**And when you improve a bar without reaching it, leave a residual you can COUNT.** A partial fix is often the right call — the honest whole fix is too big for this slice, and landing the improvement beats landing nothing. What makes it a stopping point rather than a fudge is the *shape* of what is left: one blanket escape hatch replaced by three named assertions is finishable, because they can be grepped, counted and filed; the same improvement expressed as a slightly narrower escape hatch is not, because nothing separates what you reasoned about from what merely survived. So the leftover is a named cast, a listed exception carrying its reason, a ledger entry — never a widened type or a general suppression that happens to be smaller than the last one. Then file it, with the count in the issue. *The failure this prevents: a partial fix with an implicit residual is indistinguishable from a complete one, so nobody ever finishes it, and the next reader cannot tell which parts were decided from which were merely tolerated.* `skills/decompose/SKILL.md`'s scaffolding-and-teardown rule is the same instinct at planning scale — a ratchet is a countable residual with a slice already booked to drive it to zero.

**⛔ Never game a guardrail — fix the cause, not the number.** A lint rule, type check, size cap, or complexity threshold that fires is a *signal to fix the underlying code*, never an obstacle to route around. If a file trips a max-lines cap, **split it** — extract a cohesive module and re-export it from the barrel so consumers are untouched; do NOT shave comments, compact readable code, or nudge to one-line-under to sneak past. That ships *worse* code that merely passes — the exact opposite of what the check is for. Never silence a rule to go green: no bare `eslint-disable` / `oxlint-disable`, no `@ts-ignore` / `@ts-expect-error`-to-hush, no widening a type to `any`, no deleting the assertion the check flagged. Never sacrifice clarity — a dropped explanatory comment, a mangled refactor — to hit a metric. **Zero warnings AND zero errors on every file you touch is the bar** — a warning is not a lesser class you may leave behind: where the gate lints at `--max-warnings=0` a warning IS a hard failure, and even where it isn't yet, you still fix it. The only acceptable path to green is fixing what the guardrail pointed at; anything else gets caught and bounced at review. If the honest fix is genuinely too big for this slice, STOP and hand it back (see below) — do not paper over it.

**The one carve-out — a DOCUMENTED suppression, for when the flagged construct IS the intended behavior.** That is rare, and it is never "the check is wrong": it is that the thing the rule points at is the feature, so there is no cause to fix and "fix the cause instead of suppressing" has nothing to point at. (This plugin's own `bin/setup-worktree.ps1` is one — it suppresses `PSAvoidUsingInvokeExpression` on a single function, because a project's `install` config value is a command *line* (`pnpm install --frozen-lockfile`, possibly with a pipe) that must be **interpreted** rather than spawned as an argv, exactly as the bash sibling's `eval "$INSTALL_CMD"` does. Deleting it turns CI red; spawning an argv instead breaks every project whose install command carries a flag.) A suppression you ADD is permitted then, and ONLY when **all four** of these hold — it is gaming the moment any one of them fails:

- **Narrowest scope the tool allows** — one function, or one line. Never file-wide, and never a settings-file or config exclusion that switches the rule off repo-wide: a global exclusion is indistinguishable from deleting the check.
- **A written justification in place, through the tool's own mechanism** where one exists — `SuppressMessageAttribute`'s `Justification=`, a `// eslint-disable-next-line <rule> -- <reason>` — never a bare disable comment. This is the load-bearing condition, and the reason is the diff: a justification-bearing suppression puts a claim in front of a reviewer who can reject it, while a bare `// eslint-disable-next-line` asserts nothing and so cannot be argued with. Invisible to review is exactly what gaming looks like, which is why the mechanism matters and not just your intent.
- **The justification says why the flagged construct is correct HERE** — what the code does and why that is the behavior wanted. "Noisy rule", "false positive", "the check is wrong" are not justifications; they are the claim this carve-out exists to refuse. If you can't write the sentence without arguing with the check, you don't have an exception — you have the fix you were avoiding.
- **You call it out in your hand-back report** — file, rule, and the one-line reason — so it is reviewed at merge rather than discovered later by someone who has to reconstruct why it is there. A suppression nobody flagged is a suppression nobody reviewed, and gets bounced at review even when the other three hold.

**An EXISTING suppression is not yours to re-justify, and not yours to delete for compliance.** These four conditions test a suppression you are introducing; one that was already in the file when you opened it is the previous author's claim, already reviewed on the PR that added it. If you think it fails a condition, say so in your report and leave it — removing it is a behavior change you were not asked for, and load-bearing suppressions are exactly the ones a green-at-any-cost instinct removes first.

Nothing here softens the prohibitions two paragraphs up — a bare disable with no reason, widening to `any`, deleting the assertion the check flagged, shaving comments to duck a max-lines cap, nudging one line under a threshold. None of them can satisfy the four conditions, because for none of them is there a correct-construct claim to write down. **The failure this carve-out prevents:** an implementer who reads the rule as an unqualified absolute and then opens a repo that correctly violates it has two bad options — delete a load-bearing suppression to comply, or conclude the rule is violated in the repo that ships it and stop trusting it at all. A rule with an undocumented exception doesn't get followed carefully; it gets ignored wholesale. Stating the exception precisely is what keeps the default absolute.

## When the BRIEF itself is wrong — report it, never resolve it silently

**This cluster stays here, inline, and is not a candidate for extraction — now or later.** Every rule below fires only once something has already gone wrong, which is the moment its reader is under the most pressure and least able to afford a detour; a safety net reached through a pointer is one that gets read after the fall. The rule this is an instance of lives in the contributor conventions of the repository these skills ship from: a body is safe behind a pointer only if its reader reaches it on the happy path, so an error-path body stays inline however cleanly it separates. *The failure this prevents is the one this corpus has watched happen on a single brief, both ways round: an implementer that silently resolved a contradiction it was supposed to report, and an implementer that caught the same shape only because the rule was in front of it at the time.*

**If you get stuck, hand back a reviewable artifact — never spin or die silently.** A blocker, an ambiguity you can't resolve, a scoped check you can't get green, or running low on room all mean the same thing: STOP and give the dispatcher something it can act on. Commit-push and open a **draft PR** with what you have (and enqueue it if it's far enough along to gate); if you can't even do that, hand back a complete report of your worktree state — what's done, what's broken, the exact error/blocker, and the decision you need. Partial-but-clean beats stuck-and-silent (e.g. land the solid part and flag the rest). **Never leave a dirty worktree with no PR and no report, and never leave a committed-but-unpushed branch — push and open a DRAFT PR so the dispatcher inherits a reviewable, mergeable artifact rather than invisible work trapped in your worktree.**

⚠️ **This sanctions handing back when you are BLOCKED — never handing back work you simply did not do.** It is the narrow rule, and read as the broad one it becomes "list what is left and stop", which is exactly the defect the follow-up-ownership rule names. The test is mechanical and takes a second: **if you can still act on it, it is not a blocker.** You can fix it — do that, in its own commit. You cannot fix it here but you can describe it — file and link it as a follow-up. Only what you can do neither of those to is what this paragraph is for. *The failure this prevents: a hand-back reporting a blocker and a hand-back reporting an unfinished intention look identical on the dispatcher's side — both are prose naming work that did not land — so a paragraph that legitimizes the first, read loosely, launders the second.*

**A missing input is a hand-back, not a value to invent — and this is the one that will NOT feel like being stuck.** The paragraph above covers blockers you can see. This covers the opposite: your brief needs an id, a key, an owner, a path, a version — something that identifies a real thing — and the thing does not exist yet, or you cannot reach it from where you are. Nothing is erroring. You can produce a value of the right *shape*, and everything downstream will accept it: the types are satisfied, the scoped check is green, the tests pass, the PR reads clean. **That is precisely the failure.** A fabricated identifier does not fail loudly at review; it records the wrong fact, permanently and quietly, and every guardrail you have confirms it. So when the input names something real and you cannot obtain the real one, STOP and report exactly that — what you needed, why it was not available where you stand, and what the dispatcher must decide (dispatch it later, hoist a wave-0 slice, or hand you the value). *The failure this prevents: an implementer that could not obtain an owning identifier at the point its slice ran, declined to synthesize one, and reported the gap — where a plausible substitute would have passed every check while silently attributing the work to the wrong thing.* Shape-correct and fact-wrong is the hardest defect class to find later, because nothing about it looks broken.

⚠️ **Narrow in the same way, and for the same reason: this covers an input that names a real thing you cannot obtain — not a decision you would rather not make.** A gap that an existing pattern, `AGENTS.md`, or a plainly obvious default already settles is not a missing input at all: adopt the answer, write the assumption down in your report, and move on. `skills/decompose/SKILL.md`'s *Step 2 — Validate the plan and fill the gaps* is the canonical statement of that split — fill what the grounding already answers, escalate only what it genuinely cannot — and it binds every role here, not just `decompose`. *The failure this prevents: escalating a settled question spends a user turn on something the repo already says, and each one teaches the next reader to route around a rule that fires too often — so the escalation that actually matters, the fabricated-identifier one this paragraph exists for, arrives already discounted.*

**Evidence that contradicts your brief is a finding you report, and producing it IS the job.** A brief is written from the plan, one step further from the code than you are standing: by the time you are in the worktree you can read the thing it describes, and sometimes it is not what the brief says it is. Follow the source and say so — plainly, in your report, naming what the brief asserted and what the code actually does. **Do not make the stated thing compile.** This is the stronger form of `decompose`'s `Assumes X (existing pattern in <file>); flag if wrong`, which only ever covers what a dispatcher *labelled* as an assumption; the damage comes from what a brief states as settled fact, because an implementer does not challenge a coordinate presented as established. *The failure this prevents: the incentive runs the wrong way unless this is said out loud. Contradicting the brief reads as scope creep and costs a paragraph to defend, while implementing the assertion is cheap and comes back green — so the dispatcher's error becomes your output with a gate's endorsement on top, and the brief stays the only record that anyone ever believed it. An implementer that overturns a false assertion with evidence has done more of the job than one that merely satisfied it, not less.* **A correction that arrives from your reviewer is a claim of the same kind.** A dispatcher reading your PR is standing one step further from the code than you are, exactly as the brief's author was — and a correction it reached by calling a module directly is evidence about that module, not about the path production takes. Answer it with the call path; where it is right, say so and fix it. (*The PR review loop* carries the reviewer's half of this, and the run where a reviewer made this exact error while auditing the fix for it.)

**A brief that contradicts ITSELF is the same finding, and the shape to watch for is a boundary that forbids the verify bar the same brief demands.** A `Do NOT touch` is written to fence production code; a verify bar routinely needs the *test* file beside it, in the directory that glob names. A fence over a directory covers behaviour and not the tests under it unless the brief says otherwise, so the ordinary case resolves itself — take the test file, and **say in your hand-back that you did**, since a diff landing inside a fenced directory is exactly what the dispatcher's divergence check is watching for and it cannot read your reasoning off the paths. Where the brief *does* say otherwise, or names the test file outright, and the bar still needs that file, the two halves genuinely contradict and you have three moves of which two are silent. Drop the test and the bar evaporates with nothing to mark it. Breach the fence and you do the thing the fence existed to prevent, which on a security or authorization boundary is the entire hazard your slice was scoped around. The third — parking the assertion somewhere else — is the one that looks most like compliance and can be worth nothing, since an assertion placed outside the module it is about is exactly as green as one placed correctly. **You do not get to widen your own fence and you do not get to quietly narrow your own bar**, so this is a report, not a judgement call: name the file the assertion needs, the instruction that forbids it, and hand the choice back to whoever wrote both. *The failure this prevents: nothing errors on any of the three moves, and a diff read afterwards cannot tell a verify bar that was dropped from one that was never load-bearing — so the resolution that costs you the least is also the one nobody can audit.* `skills/decompose/SKILL.md`'s `Do NOT touch` field is where the contradiction is supposed to be settled before it ever reaches you; this is what to do with the ones that get through.

**A brief that asks you to derive something from a source you cannot reach is the same finding wearing a different shape, and the silent move here is transcription, not one of the three above.** `skills/decompose/SKILL.md` Step 3's closing check now names this as its own pair: a `Brief` that says *derive X from Y* is unsatisfiable when Y does not resolve from where your worktree sits, however real Y is elsewhere in the tree. The compliant-looking move is not to skip, breach, or park — it is to write down, by hand, the values the derivation would have produced. That output can be entirely correct, the slice green, the diff clean, and the brief's false premise never contradicted anywhere, which is exactly what makes it the most dangerous of the four. **A derivation you had to satisfy by transcription is a finding you report, whatever the output looks like** — name the source, where it actually sits, and why it does not resolve from here, rather than silently hand-writing the values and moving on. *The failure this prevents, observed: a slice told to derive its field set from a map on the wrong side of a workspace boundary did exactly that, correctly, and the premise surfaced only because the dispatcher happened to read the diff.*

**An enumeration a brief hands you is a FLOOR on what your change must reach, and one that comes back short is a FINDING — never evidence that you have misread your own scope.** The consumers, the call sites, the declarations of a chain: every such list came out of a command *somebody* ran, and `skills/decompose/SKILL.md` Step 1's *An enumeration is a claim* is why a list cannot vouch for its own length. Read the argument there rather than a copy of it here; what is yours is what to do standing in the tree with a set bigger than the brief's. **The list is the floor on reach and the `Do NOT touch` fence is the ceiling on edit** — two different fields, and the second is the one that governs your hands: **land** the member the list missed where no boundary covers it, **stop and report** where a fence or a sibling's `Owns` does, and **report it either way**, because every other slice in the wave was sized against that list. The Dispatcher section's *Scope + hard do-not-touch boundaries* is the authoring end of the same pair — your brief is supposed to arrive carrying this sentence, and this is what to do when it does not. **This is not the finding *A brief that contradicts ITSELF* names, and that rule structurally cannot reach it**: a short enumeration lists real files, in the right format, reconciling with every other field the brief carries, so the brief is internally perfectly consistent and there is nothing in it to contradict; the claim is false against the **tree**, and nothing you can read off the brief alone will say so. **And your own enumerations are held to the identical bar, whether or not anybody handed you one:** the greps you run to find what your change must touch are the same claim made by you, so take the count from the command that filtered nothing before you treat the set as your scope — **and say what that count counts when you report it**, since `grep -c` and `grep -o | wc -l` are both true about one sweep and only one of them is the size of your scope. A direct implementer — one entered by being told to *build / fix / implement* a specific thing, with no dispatcher and no brief — authors every enumeration in its slice itself, and this half is the only statement of the rule that reaches it. *The failure this prevents runs the same way at both ends and is silent at both. Told nothing, the one party actually standing in the tree reads its own nineteenth hit as evidence it has misread the boundary and discards the answer — and where the brief skipped the sentence, or where there is no brief at all, there is nothing anywhere for it to check that reading against; the short set simply becomes the change.*

**A measured value your brief hands you is a cross-check, never your baseline — re-measure it here, and report your delta against YOUR number.** A test count, a timing, a row count, a file count, a hit count from a sweep: the dispatcher gathered it somewhere, and *somewhere* is routinely a different tree from yours — a slice's own hand-back rather than the tip, one branch's total quoted as a merged one, a figure taken before the last two merges landed. So measure it yourself before you change anything, and where the two differ, **yours wins**, because it is the only one taken in the tree the work is being done in. Say so plainly rather than substituting it silently. **This is not the fork-point rule below**: that one settles what a measurement is taken *against*, and this one settles *whose* measurement wins when there are two. **Where the brief hands down a number and does NOT say which one wins, name that gap in your hand-back rather than adjudicating it on your own** — a rule that settles a disagreement is worth something only while it predates the disagreement, and arriving afterwards it is indistinguishable from either party defending its own figure, with nothing available to separate them. **Two more gaps of the same kind, and both are yours to NAME rather than to resolve quietly.** A brief that hands down a number without saying it was measured in the tree the brief describes, and without marking it inherited and unverified (`Assumes N; flag if wrong`), is the first — the tie-break catching it is exactly what stops it costing anything, and nothing anywhere counts a catch, so the only record it ever gets is the one you write. **And before you report a delta at all, check that the two numbers are in the same UNIT.** A count of the lines a term appears on and a count of its occurrences are both true over one sweep and routinely differ by a factor of two or more, so a difference is not evidence the tree moved until the instruments match: say which one you used, and where the brief did not say, report that as a gap rather than as a discrepancy — a unit difference reported as a delta sends the dispatcher hunting a change that never happened, wearing the one form this flow trusts most. *The failure this prevents: an implementer that takes a handed-down baseline as its own and measures higher afterwards reports a phantom regression, or spends a run hunting a break it never caused — and the dispatcher is the party least able to catch it, because the number looks authoritative precisely because it wrote it down. The Dispatcher section's* A measured value you did not measure in THIS tree *is the authoring end of this pair; this is what to do when a brief reaches you without it.*

**Before you report a NEGATIVE from your verify bar, measure it against the FORK POINT — never your own last commit, and never `HEAD`.** *X is unchanged*, *no new Y*, *that grep comes back empty*: each is a claim about a difference, so it is worth exactly as much as the base it was taken from. `git merge-base HEAD origin/<base>` is that base — the tree as it stood before your slice existed. Your own previous commit is not: it is **inside** the change you are asserting about, so a claim checked against it is a claim about a fragment of your own work and comes back true whatever the work did. `HEAD` is worse than either, because it shows only uncommitted changes and goes clean the moment you commit, at which point the claim holds against nothing at all. **Where the honest answer is narrower than the bar's phrasing — the output is unchanged *for a caller who has not opted in*, rather than unchanged — report the narrow one and say which it is**; *A brief that contradicts ITSELF* above is why the wording is not yours to quietly widen or narrow. **This is not the trap the dispatcher's two fork-point rules guard, and blurring them costs you both**: theirs is a baseline that **moves** — the integration tip advancing under an open worktree, so a sibling's merged work reads as this branch's phantom deletions — while yours is one that is too **close**. `skills/decompose/SKILL.md`'s `Verify` field carries the argument and the observed failure; this is the same rule at the end that runs the check. *The failure this prevents: nothing downstream can separate a negative measured from the fork point from one measured from your previous commit — both arrive as a single confident sentence in a hand-back, and the second is true by construction, so it clears the bar, survives the gate, and reads in review exactly like the check that was actually performed.*

**A verify bar's command is an INSTRUMENT and the sentence beside it is a PROPERTY — a command that could not have fired is a finding, not a pass.** Every rule above is about a bar you cannot satisfy; this one is about the bar you satisfy trivially. An instrument **narrower** than its property fails a correct slice, and you find out, because you are stuck. One that is **wider** — or that has **no instances at all** on the files it names, a grep for a construct the target does not contain — comes back green carrying no information, and green is what this flow reads as a bar met, so nothing after you can tell it from a sweep that ran and found the target clean. So before you report a bar green, ask whether its command could have gone red at all on the tree you are standing in; where it could not, **report that the instrument could not fire, and name the property you read it as standing for**, rather than reporting the bar passed. `skills/decompose/SKILL.md` Step 3's `Verify` field carries the argument and the observed failures; what is yours is that you are the first party to run the thing and the last that can see it did not run. *The failure this prevents: your other two moves are both silent — obey an instrument you can see is wrong and nothing in the diff afterwards says why, or declare the bar met on your own reading of what it obviously meant and nothing records that you substituted your judgement for the bar. Every instance this corpus has recorded was caught here rather than by the seat that wrote the bar, which is the one seat with no say in what the bar said.*
