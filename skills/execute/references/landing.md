# Gate the integrated whole — conditional on what the merge actually produced

Reference for `skills/execute/SKILL.md` → *Dispatcher*. **Read it after any merge that combined work from more than one slice** — each branch was gated against its own fork point, so the whole was never gated by its parts.
Each branch was gated against *its own fork point*, blind to the other slices, so the branch that now carries all of them together **may** be carrying a tree no gate has ever run. May — and the merge itself tells you which. Every merge this check reads makes a real merge commit, so every one of them has a second parent — with the single exception the closing-merge paragraph below takes up, an epic → integration merge in a project that declared `"epicMerge": "squash"` (*The epic branch* → *Mechanics*), where there is no `^2` to read and a different instrument answers instead. After each of the rest:

```
git diff --name-only <merge-commit>^2 <merge-commit>
```

**Non-empty ⇒ the merge produced content no gate has seen**, and the merged result needs ONE `gate` run — **enqueued** in a project whose runner takes the ticket, and run by hand where there is no queue or the runner refuses it (*Enqueue it rather than running it*, below). Exactly two things cause it: a **conflict resolution**, whose resolved tree is new content by definition; and a **sibling branch that merged in between**, where this branch was cut before it and gated without it — the parallel case the reasoning above is really about.

**Empty ⇒ the merge's tree is byte-identical to the branch tip the gate already ran on**, so re-running executes the same tree for the same answer. A run that cuts every worktree from the current tip and merges sequentially without conflicts comes back empty on every merge and needs no dedicated integration gate at all.

**It is a check rather than a rule because it runs both ways.** An unconditional close-out gate re-executes a tree that was already gated — on a monorepo with a ten-minute gate that is real cost for zero information. And "the last slice was green, so the epic is green" costs nothing and is wrong the moment two slices ran in parallel, which is this flow's default dispatch shape.

Two things the empty answer does **not** buy you:

- **It proves the tree was *run*, not that the run was *green*.** In the transient-red window above, slices merge on a green-modulo-baseline judgment rather than a green exit — so an epic tip can be byte-identical to a tree that was never observed fully green. Skipping needs both halves: the merge added nothing **and** the gate it inherits was an actual green. When the last slice merged on judgment, the close-out gate is the first real green signal there has ever been, and it runs.
- **It governs re-running the suite, nothing else.** It says nothing about the merged *code*: a shared hotspot still gets its merged region read by hand (*Merging a shared hotspot* above), because the semantic drift that section describes is invisible to a green gate and equally invisible to an empty diff.

**Re-derive the merged tip's derived artifacts before you gate it — and do that whether the `^2` diff came back empty or not.** An artifact whose correct contents are a function of the whole tree rather than of any one branch — a ratchet ledger, a backlog a checker regenerates, a generated type, an unimported-exports manifest — is the thing per-slice gates structurally could not have covered: each slice was correct about its own files, and the artifact derives from all of them. Run the project's own regenerator against the merged tip and commit what it writes, or send the delta back as a fix. The breakdown names these per slice in its `Derives` field, so the list arrives with it rather than being reconstructed here.

**Install the tree you are about to gate — unconditionally, and the main checkout is a tree like any other.** This gate runs against the merged tip of the integration branch, which is the **main checkout**: the longest-lived tree in the flow, fast-forwarded by `merge-pr.sh` on every close-out without ever installing, while other sessions merge `package.json` and lockfile changes onto that branch continuously. Run the project's `install` (*Per-project config*) there immediately before the gate — the same command `setup-worktree.sh` runs when it cuts a tree, and a no-op in a project that declares none, this repo included. **The conditional version is the trap:** you cannot tell from the merge's own diff whether a dependency arrived, because that fast-forward means every range you might compare against is unreliable in both directions. The diagnostic order is *The epic branch* → *Mechanics*' rule applied to this tree: **on an integration gate a module-resolution failure is a stale install until proven otherwise** — install and re-run before reading a line of the diff.

**Enqueue it rather than running it — the tree has no PR, and the ticket shape admits that.** In a project whose runner takes the ticket this gate goes in as a **PR-less ticket**: `enqueue --branch <branch> --worktree <worktree>`, with no `--pr-number` and no `--pr-url` — those two fields are optional on a ticket precisely so this gate can be recorded like any other. A runner claims it, gates that worktree behind the machine-wide slot, and settles it into `done/` with the verdict written on the ticket; the only step it skips is the comment, because there is no PR to put one on. So **you read the verdict off the ticket**, not off a shell's exit status, and the ledger watch already armed for the wave sees it settle by `branch` (*Wait on your own tickets settling — one Monitor over the queue's ledger*; a PR-less ticket carries no `prNumber`, so print the branch as its handle). Then fire **one** drain and react only if the ticket is still sitting unclaimed in `queue/` a couple of polls later — do not pre-flight whether a runner is already draining, because the two instruments for that question are the ones this file records as unreliable (a process list cannot separate gating from blocked-on-a-slot, and `--status` silently drains on a runner scaffolded before that flag existed), while a second drain is idempotent and safe by construction.

**A runner scaffolded before the PR-less ticket REJECTS it with a usage error, and the hand-run gate is the sanctioned fallback there too — not only where the project declares no queue.** `/pipeline:setup` scaffolds the queue **into** a project and the project owns it from there, so a project scaffolded before `prNumber`/`prUrl` became optional has a runner that still requires them, and the enqueue above exits non-zero on a missing-required-field usage error naming both. **Every fallback clause in this file is keyed on a condition that case does not satisfy** — the project *has* a queue, and that queue works correctly for every ticket a PR is attached to — so a dispatcher reading them is pushed away from the hand-run gate by an instruction that is emphatic about it (*The durable gate queue*: in a project whose runner will take them, no gate is run by hand) and toward an enqueue that cannot accept the ticket. That is why the clauses now name **two** conditions rather than one. Run the gate yourself in that worktree, capture its own exit status (*Where you do run a gate yourself*), and say in the close-out that this verdict has no ticket behind it. **Only the mid-arc gate is reachable this way**: the epic's close-out gate sits behind a draft PR and therefore always has a `--pr-number` to carry, so it enqueues on any runner.

*The two halves of that rollout fail in OPPOSITE directions, and the safe one is the one that strands you.* The sibling half is a `--status` flag an older runner does not recognise, which **silently drains** — dangerous precisely because it looks like it worked; *Draining the gate queue* carries what that costs a dispatcher. A PR-less enqueue on an older runner does the opposite: it exits non-zero and does nothing, so no tree is mis-gated, no gate run is spent and no verdict is invented. What it costs instead is a dispatcher stopped mid-close-out with the sanctioned route refused and — until this paragraph — no other one the file admitted, which is the failure this prevents. **Read a usage error naming `prNumber` and `prUrl` as the runner's age, not as a defect in your invocation**, and do not re-type the command with invented PR fields: a ticket pointed at a PR the tree does not have sends a real verdict to a real PR that no gate on that PR ever produced, which is the one outcome worse than having no route at all.

**Where you do run a gate yourself, capture the gate's OWN exit status, never a pipeline's.** `pnpm gate > gate.log 2>&1; echo "EXIT=$?"`, then read the log — not `pnpm gate | tail`, whose status is `tail`'s, because a shell reports the exit code of a pipeline's **last** command. A gate you run yourself posts no comment, so that status is the whole verdict, and every natural way to shorten a long gate log throws it away while still printing the output that makes you feel you have read it. Report the `EXIT=` line itself rather than a summary of the log: a green you cannot quote is one nobody can check. **This is the reading for a gate nobody drained, and in a project with a queue that is now almost none of them** — both gates this section used to have you run by hand are enqueued above, on a runner that takes their tickets. What is left is two cases. A project that declares no `enqueue` and no `drain` at all (*Per-project config*), where every gate is hand-run: a slice in **override gate mode**, and this section's own two gates where there is no queue to put them in. And, **in a project whose queue works**, the mid-arc integration gate by itself, where the runner refuses the PR-less ticket (*A runner scaffolded before the PR-less ticket REJECTS it*) — the one case in which this reading is needed by a dispatcher who has every reason to believe it does not apply to them. There an implementer's or a dispatcher's own reading of that status *becomes* the comment everything downstream trusts (*Implementer*). **`set -o pipefail` is not the fix to reach for** — it is shell-specific, off by default in every shell these commands are typed into, and a rule that depends on an option being set somewhere else fails silently in exactly the case it was added for; a redirect and `$?` work everywhere and show their own working. **And `| grep`, the one that feels like diligence rather than a shortcut, is worse than the others: it does not discard the verdict, it INVERTS it.** `gate | grep -i failed` exits 0 exactly when it found a failure and non-zero when the gate was clean — so the status now reports red as green and green as red, and the reading that looks most careful is the one that is wrong in both directions.

**On an epic branch, apply the check to the closing merge too — it is the one merge that is usually non-empty.** A gate on the epic tip is not a gate on what lands: the integration branch moved while the epic ran, so `epic → integration` combines two histories nothing has tested together. The fix is ordering, not another gate — before the close-out gate, merge the integration branch INTO the epic one last time (the same merge the tick already runs, *The cost* above; that cadence buys this, not just bounded conflicts). Then the epic already contains everything the integration branch has, the gate covers the exact tree the closing merge will produce, and that merge's `^2` diff comes back empty. Skip the cadence and it won't, and the gate moves to *after* the closing merge, on the shared branch, where a cross-slice break is found only once every slice has already landed on it.

**And when that closing merge is a squash, the same reasoning has a consequence: the cadence stops being advisory.** A squash commit has no second parent, so there is no `^2` to read at all — the tree comparison `merge-pr` runs takes its place (*The epic branch* → *Mechanics*), and it is stronger, comparing the gated epic tip against what landed rather than inferring coverage from parentage. What changes for you is the *enforcement*, not the check. Those two trees are equal **only** if the final `merge origin/<integration>` into the epic actually ran before the gate, so on the squash path a skipped cadence does not surface as a non-empty diff you were free not to look at — it surfaces as a **failed comparison that blocks the branch delete**, and the close-out stops there with both copies of the branch intact.

That ordering is the whole point of which branch the gate runs on. On an epic branch the failure surfaces while the integration branch has seen none of the epic, and the fix is one more slice PR into the epic; without one, it surfaces on the branch every other session cuts worktrees from. A failure that first appears here is a real cross-slice interaction the per-PR gates *structurally could not* catch (none of them saw the others) — fix it forward, don't rationalize it away. Independent-green is necessary; *integrated*-green is what actually ships. **On an epic branch a green gate is the precondition for MERGING the epic → integration PR — not for opening it.** What finally puts the whole change set on the shared branch is the merge, and a **draft** PR puts nothing anywhere: GitHub refuses to merge one, and this flow already spends the draft flag as the interlock against merging an unread diff. So the PR opens first, as a draft, and the gate is enqueued against it (*The epic branch* → *Mechanics*) — read the other way round, as a precondition over the OPEN, it forces the one gate whose tree no per-slice gate has ever seen to run with nothing to attach a ticket to: no log, no ledger entry, no comment, and a verdict surviving only as an exit status in one terminal, on the least-witnessed gate in the flow.

## Merge & cleanup


Reference for `skills/execute/SKILL.md` → *Dispatcher*. **Read it before you merge a slice PR** — the steps have exactly one correct order, and syncing the local integration branch is the one nothing forces.
The steps below have exactly one correct order, and syncing the local integration branch is the one with **no forcing feedback** — every visible signal after the merge (`✓ Merged`, branch deleted, PR closed) says "done", so it's silently skipped, and the miss only surfaces later when the *next* worktree is cut from a stale HEAD. So **default to the helper, which does all of them but the last, atomically: `merge-pr.sh <pr-number>`** — plus the mergeability preflight the list below has you run by hand before its first step. It resolves the main checkout + the PR's base/head branches, confirms GitHub can actually merge the PR before anything irreversible happens, tears down the worktree, marks the PR ready and immediately `gh pr merge --merge --delete-branch`es it, and — anchored to the main checkout regardless of your cwd — brings that local base branch up to the merged tip. (The one PR it merges any other way is an epic → integration close-out in a project that declared `"epicMerge": "squash"`, which it decides from that project's config before anything irreversible happens and finishes with a tree check in place of the delete — *The epic branch* → *Mechanics*. Every other PR, in every project, takes the sentence above unchanged.) It does that **without ever switching the checkout**, via one of **three** sync paths picked by where the base actually is: the main checkout is standing on it → `merge --ff-only` there; a **linked worktree** is standing on it → `merge --ff-only` **inside that worktree**, which is the ordinary path for every slice PR of an epic now that the epic branch lives in one; nothing is standing on it → move the **ref** (`fetch` + `branch -f`), which needs no working tree. All three only ever move the branch forward, so none can discard a commit, and none opens a window for another session to land in or leaves anything to switch back afterwards. It then verifies the checkout is still on the branch, and at the commit, it was on when the run started — the alarm the shared-main-checkout hazard above calls for. When the fast-forward inside a linked worktree cannot proceed, the helper stops and names **which** worktree and **why** — commits the local branch carries that the remote does not, or a working tree not clean enough to fast-forward — rather than forcing the ref or reporting a sync that did not happen. Running it *is* the approval: the ready flip lives one line above the merge precisely so a PR can never sit around wearing a review it has outgrown. **So the satisfied review goes onto the PR BEFORE you invoke it** (*The PR review loop*): the helper flips and merges as one atomic step, so a review posted after it lands on a merged PR with no draft left to review, and the reasoning has to arrive ahead of the signature it explains. It's idempotent (a re-run finishes a half-done close-out) and it's the reason a hand-run sync can't get dropped: don't split these steps back out by hand unless the helper can't handle a case.

**Of the steps below, the one the helper cannot do is closing the issues the work resolved — and it is the one that silently goes missing.** `merge-pr.sh` knows the PR, not which issues it settled — and whether GitHub closes them on its own turns on where that PR was based. Closing keywords in a PR description "are interpreted only when the pull request targets the repository's **default** branch. If the pull request targets **any other branch**, then these keywords are ignored, **no links are created**, and merging the PR has no effect on the issues." **The predicate is the PR's base against the repo's DEFAULT branch — not "integration or epic branch", which stands in for it only where the two are different branches.** A slice PR based on an epic branch is genuinely inert, and so is any PR based on an integration branch that is not the default one. But a project whose integration branch simply **is** `main` — this repo and both sibling skills repos are that shape — has nothing between a PR and the default branch unless an epic branch is standing there, so every PR that is not a slice of an epic bases on the default branch, and there the keyword is **live**. Where the base is not the default branch the keyword **does not fire later either**: it belongs to a PR whose base was never the default branch, and nothing re-evaluates it when the integration branch eventually merges. (The one that *does* fire later is a closing keyword in a **commit message**, when that commit reaches the default branch — a different mechanism, delayed by the whole life of the release branch, and not a plan.) So close them yourself, in the same breath as the merge — **unchanged by any of this, because the hand-close is the one action that is correct under both readings**: a no-op when GitHub has already closed them, and the whole mechanism when it has not. Learning that keywords sometimes fire is not learning that this step is sometimes skippable. **Which issues you close here, and therefore when any given issue closes, turns on a different question from the one above: what did THIS PR settle.** The issues this PR settled close at this merge; an issue no single increment settles — an umbrella, or an arc whose next cycle is still to run — closes when the arc does, at the loop's own termination check, not this step.
```sh
gh api -X PATCH repos/{owner}/{repo}/issues/<n> -f state=closed
gh api repos/{owner}/{repo}/issues/<n>/comments -f body='Fixed in #<pr> (merged into <base>).'
```
REST rather than `gh issue close`: the high-level `gh issue` writes go through GraphQL and hit rate limits exactly when you are closing a batch of them.

**And the inverse is the half no rule here covered — the one that can actually bite: where the base IS the default branch, a closing keyword is LIVE, so do not write one into a slice PR while its arc is still running.** Single-slice work never cuts an epic branch, so in a project whose integration branch is `main` such a PR goes straight to the default branch, and `Closes #<n>` in its body fires the instant it merges. **That is the right moment only if this one PR settles the whole issue** — and an increment is not an arc: `orchestrate` grounds one horizon per cycle, so an arc can run several cycles whose increments are each a single slice, cutting no epic branch and basing every one of those PRs on the default branch. A keyword written into the first of them closes the issue while the cycles after it are still outstanding, and the same shape reaches an umbrella that a sub-issue's PR happens to name. The loop counts the tracker in its termination check, so an issue closed early is a false "done" in exactly the artifact it reads back to decide whether it is finished. Reference the issue without the keyword — `Refs #<n>` — and close it by hand when the ARC closes rather than at this merge, since this PR did not settle it (the question above).

**The teardown comes before the merge, so the helper checks the merge is possible before the teardown.** The branch lives in a linked worktree, and **git refuses to delete a branch that's checked out in a worktree** (`cannot delete branch 'X' used by worktree …`), so `gh pr merge --delete-branch` would error on the local-branch step if the worktree still existed — the order below is load-bearing and stays. What that order costs is that the two irreversible steps run *before* the one that can fail: a PR whose base moved under it fails at the merge with `GraphQL: Pull Request has merge conflicts`, and without a preflight that leaves no worktree to resolve the conflict in and a PR marked ready with no review behind it. So `merge-pr.sh` asks GitHub whether the PR is mergeable **first**, and a `CONFLICTING` answer stops it cleanly — worktree intact, PR still draft — naming the fix. Two consequences for you: a conflict now costs you a resolve rather than a recovery, and if the merge fails anyway (GitHub computes mergeability asynchronously, so a just-pushed PR can answer `UNKNOWN` and the helper falls through rather than blocking) the helper puts the draft flag back on its way out, and its message tells you to re-attach a tree with `setup-worktree.sh --existing <head-branch>`. Resolve a conflict by **merging the base in, in the branch's worktree** (`git fetch origin && git merge origin/<the PR's base>` — the branch the PR actually targets, which for an epic's slice is the epic branch, not the integration branch) — never rebase — then push, re-gate, and re-run `merge-pr.sh`.

If you ever run the close-out by hand (helper unavailable, or an edge it can't cover), do it in this exact sequence, every time — and check `gh pr view <n> --json mergeable` yourself before step 1, since by step 2 the worktree is gone:
1. **Confirm the ticket is done before you tear down.** The runner gates in the ticket's worktree, so don't remove a worktree whose ticket is still `queue`/`processing` — wait until its gate has resolved (its verdict comment is on the PR). Removal is one half of the frozen-worktree rule; **editing** it mid-gate is the other and is just as damaging — see *Draining the gate queue*. Then **remove the worktree — always via the helper:** `remove-worktree.sh <branch-leaf>` (or the absolute path). **Do not use `git worktree remove` directly.** Plain `git worktree remove` evicts the directory but does NOT signal any running processes — so a gate running in it survives as an orphan. The helper kills all processes rooted in the worktree first — via `lsof` + `pgrep`, escalating SIGTERM → SIGKILL — then removes the worktree. On Windows it instead scans `Win32_Process` command lines and kills the matching process trees with `taskkill /T /F`, since neither `lsof` nor `pgrep` exists in Git Bash and there is no SIGTERM to escalate from; it also prints a notice that open-handle enumeration was **skipped** (the `lsof +D` half has no built-in Windows equivalent), so a removal that fails on a locked file has a stated cause rather than looking like a mystery. Nothing is lost — it's all pushed — and this frees the branch so it can be deleted.
2. **Post the satisfied review, then mark the PR ready and merge with branch deletion:** the review goes on first, since it is the reasoning behind the flip and a review posted after the merge explains a decision already taken — then `gh pr ready <n>` immediately followed by `gh pr merge --merge --delete-branch`. The flip is your review approval, so it belongs against the commit you are merging this second, not earlier in the sequence. Real merge commit (never squash), and with the worktree gone `--delete-branch` cleanly removes BOTH the local and remote branch. Skipping `--delete-branch` is what let merged `origin/*` branches pile up indefinitely (they did: dozens accumulated). Verify it's fully merged first; STOP on git's "not yet merged to HEAD" warning. **If the merge fails after you flipped it, flip it back** (`gh pr ready <n> --undo`) — a non-draft PR that isn't being merged right now is a bug, and here it would be one wearing a review the merge never earned.

  **The one PR this step reads differently is an epic → integration close-out in a project that declared `"epicMerge": "squash"`** — the exception in full at *The epic branch* → *Mechanics*, including both conditions it depends on, so check them there before doing this by hand rather than deciding from the branch's name. **The hand-run form is `gh pr merge <n> --squash`, and it is NOT `--squash --delete-branch`:** the branch has to outlive the merge so what landed can be compared against what was gated. Then `git diff --quiet <the epic tip you captured BEFORE the merge> <the squash commit>` — capture that sha first, because after the squash the PR no longer points at a branch anything will hold for you — and delete the branch, local and remote, **only** if that comes back empty. Git's "not yet merged" warning fires here on every squashed close-out and is answered by that comparison rather than overridden by you; if the comparison does not pass, or you could not make it, stop and leave both copies of the branch alone. This is the whole reason to prefer `merge-pr.sh`: it captures the tip, compares, and refuses to delete on a mismatch, in one command with no step you can drop.
3. **Sync the local base branch — anchored to the MAIN checkout, never `&&`-chained, and without switching if you can avoid it.** `gh pr merge` advances the branch only on the *remote*; the local copy in the main checkout does NOT move, and syncing it is what keeps the next worktree from forking off a stale HEAD. When the base is **not** what the main checkout is standing on, move the ref and leave the checkout alone — `git -C <main-checkout> fetch origin` then `git -C <main-checkout> branch -f <base> origin/<base>` — for the reason the shared-main-checkout hazard gives: switching a checkout other sessions share is what corrupted a release branch. When the base **is** the checked-out branch there is nothing to switch, so: `git -C <main-checkout> pull --prune --ff-only`. ⚠️ Do NOT hand-run the old `git checkout <integration> && git pull` form: with no `-C` anchor it assumes your shell is in the main checkout, but the dispatcher's cwd is usually inside a worktree — there `git checkout <integration>` fails with `already used by worktree at …`, and the `&&` swallows the `git pull` so the sync silently never happens (this is exactly the "merged but never synced" bug). Anchoring every call with `-C` is what makes the step survive being run from anywhere, and is why the helper above can't drop it.
4. **Close the issues the work resolved** — the step named above that the helper cannot do, in full: GitHub will not do it for a PR based on anything but the default branch, and no keyword you wrote will do it later.

**When this close-out ends the whole arc rather than one increment, one arc-level question is still owed and it is answered in writing: did the arc surface a defect or gap in the pipeline itself?** Exactly one of three answers — **filed**, naming the issue; **none found**; or **not enabled here**, where `.agents/worktree.json`'s `upstreamFindings` is anything but exactly `true`, in which case the finding goes to the maintainer in the run's report instead. The bar is an **observed failure the finding can name** — a run that broke, a rule read and not followed, a check green over a tree it never saw — never an improvement that would be nice; a finding that clears it is **filed** as an artifact with a number, into the plugin's own repository resolved from `repository` in `.claude-plugin/plugin.json`, genericised of every path, symbol, branch and client name because that tracker is public. It binds a dispatcher invoked directly exactly as it binds the loop, and it is asked **per arc, never per increment** — asked five times in an evening it becomes noise and gets tuned out, which is worse than not asking. "None found" is cheap but still written down, since an arc that surfaced nothing and one where nobody asked look identical afterwards.

**And one arc-level action, on the same cadence and for a different reason: where the project declares `reclaim` (*Per-project config*), run its `report` here.** Every worktree the arc cut has by now been torn down, and each one that ran a check left behind whatever its `sharedResources` mechanism created — named after a path that no longer exists. Per arc, never per increment, and the reason is not noise: an arc's waves overlap, so a mid-arc run reports resources belonging to slices still live and invites exactly the wrong conclusion about them. **Run `report`; never `drop` on your own judgement.** A drop is the maintainer's call on the maintainer's box, for the same reason a merge is not yours to approve — and it is barred outright while any ticket is outstanding — queued as much as claimed — by the frozen-worktree rule (*Draining the gate queue*), because a queued ticket names a worktree whose resources a runner is about to need.
