# Merge & cleanup — one command, because the sync is the step that gets dropped

Reference for `skills/execute/SKILL.md` → *Dispatcher*. **Read it before you merge a slice PR** — the steps have exactly one correct order, and syncing the local integration branch is the one nothing forces.
The steps below have exactly one correct order, and syncing the local integration branch is the one with **no forcing feedback** — every visible signal after the merge (`✓ Merged`, branch deleted, PR closed) says "done", so it's silently skipped, and the miss only surfaces later when the *next* worktree is cut from a stale HEAD. So **default to the helper, which does all of them but the last, atomically: `merge-pr.sh <pr-number>`** — plus the mergeability preflight the list below has you run by hand before its first step. It resolves the main checkout + the PR's base/head branches, confirms GitHub can actually merge the PR before anything irreversible happens, tears down the worktree, marks the PR ready and immediately `gh pr merge --merge --delete-branch`es it, and — anchored to the main checkout regardless of your cwd — brings that local base branch up to the merged tip. (The one PR it merges any other way is an epic → integration close-out in a project that declared `"epicMerge": "squash"`, which it decides from that project's config before anything irreversible happens and finishes with a tree check in place of the delete — *The epic branch* → *Mechanics*. Every other PR, in every project, takes the sentence above unchanged.) It does that **without ever switching the checkout**, via one of **three** sync paths picked by where the base actually is: the main checkout is standing on it → `merge --ff-only` there; a **linked worktree** is standing on it → `merge --ff-only` **inside that worktree**, which is the ordinary path for every slice PR of an epic now that the epic branch lives in one; nothing is standing on it → move the **ref** (`fetch` + `branch -f`), which needs no working tree. All three only ever move the branch forward, so none can discard a commit, and none opens a window for another session to land in or leaves anything to switch back afterwards. It then verifies the checkout is still on the branch, and at the commit, it was on when the run started — the alarm the shared-main-checkout hazard above calls for. When the fast-forward inside a linked worktree cannot proceed, the helper stops and names **which** worktree and **why** — commits the local branch carries that the remote does not, or a working tree not clean enough to fast-forward — rather than forcing the ref or reporting a sync that did not happen. Running it *is* the approval: the ready flip lives one line above the merge precisely so a PR can never sit around wearing a review it has outgrown. It's idempotent (a re-run finishes a half-done close-out) and it's the reason a hand-run sync can't get dropped: don't split these steps back out by hand unless the helper can't handle a case.

**Of the steps below, the one the helper cannot do is closing the issues the work resolved — and it is the one that silently goes missing.** `merge-pr.sh` knows the PR, not which issues it settled — and whether GitHub closes them on its own turns on where that PR was based. Closing keywords in a PR description "are interpreted only when the pull request targets the repository's **default** branch. If the pull request targets **any other branch**, then these keywords are ignored, **no links are created**, and merging the PR has no effect on the issues." **The predicate is the PR's base against the repo's DEFAULT branch — not "integration or epic branch", which stands in for it only where the two are different branches.** A slice PR based on an epic branch is genuinely inert, and so is any PR based on an integration branch that is not the default one. But a project whose integration branch simply **is** `main` — this repo and both sibling skills repos are that shape — has nothing between a PR and the default branch unless an epic branch is standing there, so every PR that is not a slice of an epic bases on the default branch, and there the keyword is **live**. Where the base is not the default branch the keyword **does not fire later either**: it belongs to a PR whose base was never the default branch, and nothing re-evaluates it when the integration branch eventually merges. (The one that *does* fire later is a closing keyword in a **commit message**, when that commit reaches the default branch — a different mechanism, delayed by the whole life of the release branch, and not a plan.) So close them yourself, in the same breath as the merge — **unchanged by any of this, because the hand-close is the one action that is correct under both readings**: a no-op when GitHub has already closed them, and the whole mechanism when it has not. Learning that keywords sometimes fire is not learning that this step is sometimes skippable. **Which issues you close here, and therefore when any given issue closes, turns on a different question from the one above: what did THIS PR settle.** The issues this PR settled close at this merge; an issue no single increment settles — an umbrella, or an arc whose next cycle is still to run — closes when the arc does, which is `skills/orchestrate/SKILL.md` §7's termination check and not this step. *The failure this prevents, observed: a dispatch brief asserted that during an epic no issue closes for the epic's whole life and they all close together at the end, and instructed an implementer to write that into this file. It is false — the hand-close runs at each slice merge inside an epic exactly as it does outside one — and it was caught only because the implementer read this section end to end before writing. A brief is the artifact this corpus is read into most often and the one nothing gates.*
```sh
gh api -X PATCH repos/{owner}/{repo}/issues/<n> -f state=closed
gh api repos/{owner}/{repo}/issues/<n>/comments -f body='Fixed in #<pr> (merged into <base>).'
```
REST rather than `gh issue close`, for the reason `skills/decompose/SKILL.md`'s *GitHub write mechanics* gives: the high-level `gh issue` writes go through GraphQL and hit rate limits exactly when you are closing a batch of them. *The failure this prevents, observed: nine issues, every one genuinely complete, every one named with `Closes #<n>` in a PR that merged clean — all nine still open at close-out, found by accident because somebody happened to list what was outstanding. Nothing errors, the keyword sits in the PR body looking like it worked, and the board diverges from the tree for as long as the release branch lives.*

**And the inverse is the half no rule here covered — the one that can actually bite: where the base IS the default branch, a closing keyword is LIVE, so do not write one into a slice PR while its arc is still running.** Single-slice work never cuts an epic branch, so in a project whose integration branch is `main` such a PR goes straight to the default branch, and `Closes #<n>` in its body fires the instant it merges. **That is the right moment only if this one PR settles the whole issue** — and an increment is not an arc: `orchestrate` grounds one horizon per cycle, so an arc can run several cycles whose increments are each a single slice, cutting no epic branch and basing every one of those PRs on the default branch. A keyword written into the first of them closes the issue while the cycles after it are still outstanding, and the same shape reaches an umbrella that a sub-issue's PR happens to name. `skills/orchestrate/SKILL.md` §7 treats the tracker as part of termination, so an issue closed early is a false "done" in exactly the artifact the loop reads back to decide whether it is finished. Reference the issue without the keyword — `Refs #<n>` — and close it by hand when the ARC closes rather than at this merge, since this PR did not settle it (the question above). What closes it is `skills/orchestrate/SKILL.md` §7's termination check, not the per-merge step above. *The failure this prevents is the mirror of the one above and strictly worse, because the two leave opposite residue. A hand-close that got skipped leaves an open issue, which any later sweep of what is outstanding can still find — that is how the nine were found. A keyword that fired early leaves nothing to find: the issue is closed, the board reads finished, the arc's own termination check agrees, and the only thing that disagrees is work still running against it.*

**The teardown comes before the merge, so the helper checks the merge is possible before the teardown.** The branch lives in a linked worktree, and **git refuses to delete a branch that's checked out in a worktree** (`cannot delete branch 'X' used by worktree …`), so `gh pr merge --delete-branch` would error on the local-branch step if the worktree still existed — the order below is load-bearing and stays. What that order costs is that the two irreversible steps run *before* the one that can fail: a PR whose base moved under it fails at the merge with `GraphQL: Pull Request has merge conflicts`, and without a preflight that leaves no worktree to resolve the conflict in and a PR marked ready with no review behind it. So `merge-pr.sh` asks GitHub whether the PR is mergeable **first**, and a `CONFLICTING` answer stops it cleanly — worktree intact, PR still draft — naming the fix. Two consequences for you: a conflict now costs you a resolve rather than a recovery, and if the merge fails anyway (GitHub computes mergeability asynchronously, so a just-pushed PR can answer `UNKNOWN` and the helper falls through rather than blocking) the helper puts the draft flag back on its way out, and its message tells you to re-attach a tree with `setup-worktree.sh --existing <head-branch>`. Resolve a conflict by **merging the base in, in the branch's worktree** (`git fetch origin && git merge origin/<the PR's base>` — the branch the PR actually targets, which for an epic's slice is the epic branch, not the integration branch) — never rebase — then push, re-gate, and re-run `merge-pr.sh`.

If you ever run the close-out by hand (helper unavailable, or an edge it can't cover), do it in this exact sequence, every time — and check `gh pr view <n> --json mergeable` yourself before step 1, since by step 2 the worktree is gone:
1. **Confirm the ticket is done before you tear down.** The runner gates in the ticket's worktree, so don't remove a worktree whose ticket is still `queue`/`processing` — wait until its gate has resolved (its verdict comment is on the PR). Removal is one half of the frozen-worktree rule; **editing** it mid-gate is the other and is just as damaging — see *Draining the gate queue*. Then **remove the worktree — always via the helper:** `remove-worktree.sh <branch-leaf>` (or the absolute path). **Do not use `git worktree remove` directly.** Plain `git worktree remove` evicts the directory but does NOT signal any running processes — so a gate running in it survives as an orphan. The helper kills all processes rooted in the worktree first — via `lsof` + `pgrep`, escalating SIGTERM → SIGKILL — then removes the worktree. On Windows it instead scans `Win32_Process` command lines and kills the matching process trees with `taskkill /T /F`, since neither `lsof` nor `pgrep` exists in Git Bash and there is no SIGTERM to escalate from; it also prints a notice that open-handle enumeration was **skipped** (the `lsof +D` half has no built-in Windows equivalent), so a removal that fails on a locked file has a stated cause rather than looking like a mystery. Nothing is lost — it's all pushed — and this frees the branch so it can be deleted.
2. **Mark the PR ready, then merge with branch deletion:** `gh pr ready <n>` immediately followed by `gh pr merge --merge --delete-branch` — the flip is your review approval, so it belongs against the commit you are merging this second, not earlier in the sequence. Real merge commit (never squash), and with the worktree gone `--delete-branch` cleanly removes BOTH the local and remote branch. Skipping `--delete-branch` is what let merged `origin/*` branches pile up indefinitely (they did: dozens accumulated). Verify it's fully merged first; STOP on git's "not yet merged to HEAD" warning. **If the merge fails after you flipped it, flip it back** (`gh pr ready <n> --undo`) — a non-draft PR that isn't being merged right now is a bug, and here it would be one wearing a review the merge never earned.

  **The one PR this step reads differently is an epic → integration close-out in a project that declared `"epicMerge": "squash"`** — the exception in full at *The epic branch* → *Mechanics*, including both conditions it depends on, so check them there before doing this by hand rather than deciding from the branch's name. **The hand-run form is `gh pr merge <n> --squash`, and it is NOT `--squash --delete-branch`:** the branch has to outlive the merge so what landed can be compared against what was gated. Then `git diff --quiet <the epic tip you captured BEFORE the merge> <the squash commit>` — capture that sha first, because after the squash the PR no longer points at a branch anything will hold for you — and delete the branch, local and remote, **only** if that comes back empty. Git's "not yet merged" warning fires here on every squashed close-out and is answered by that comparison rather than overridden by you; if the comparison does not pass, or you could not make it, stop and leave both copies of the branch alone. This is the whole reason to prefer `merge-pr.sh`: it captures the tip, compares, and refuses to delete on a mismatch, in one command with no step you can drop.
3. **Sync the local base branch — anchored to the MAIN checkout, never `&&`-chained, and without switching if you can avoid it.** `gh pr merge` advances the branch only on the *remote*; the local copy in the main checkout does NOT move, and syncing it is what keeps the next worktree from forking off a stale HEAD. When the base is **not** what the main checkout is standing on, move the ref and leave the checkout alone — `git -C <main-checkout> fetch origin` then `git -C <main-checkout> branch -f <base> origin/<base>` — for the reason the shared-main-checkout hazard gives: switching a checkout other sessions share is what corrupted a release branch. When the base **is** the checked-out branch there is nothing to switch, so: `git -C <main-checkout> pull --prune --ff-only`. ⚠️ Do NOT hand-run the old `git checkout <integration> && git pull` form: with no `-C` anchor it assumes your shell is in the main checkout, but the dispatcher's cwd is usually inside a worktree — there `git checkout <integration>` fails with `already used by worktree at …`, and the `&&` swallows the `git pull` so the sync silently never happens (this is exactly the "merged but never synced" bug). Anchoring every call with `-C` is what makes the step survive being run from anywhere, and is why the helper above can't drop it.
4. **Close the issues the work resolved** — the step named above that the helper cannot do, in full: GitHub will not do it for a PR based on anything but the default branch, and no keyword you wrote will do it later.

**When this close-out ends the whole arc rather than one increment, one arc-level question is still owed and it is answered in writing — `skills/orchestrate/SKILL.md` §7: did the arc surface a defect or gap in the pipeline itself?** It binds a dispatcher invoked directly exactly as it binds the loop, which is why it is pointed at here rather than left where only the loop would read it, and it is asked **per arc, never per increment** — asked five times in an evening it becomes noise and gets tuned out, which is worse than not asking. Read the bar and the "none found" rule there; this file does not carry a second copy.

**And one arc-level action, on the same cadence and for a different reason: where the project declares `reclaim` (*Per-project config*), run its `report` here.** Every worktree the arc cut has by now been torn down, and each one that ran a check left behind whatever its `sharedResources` mechanism created — named after a path that no longer exists. Per arc, never per increment, and the reason is not noise: an arc's waves overlap, so a mid-arc run reports resources belonging to slices still live and invites exactly the wrong conclusion about them. **Run `report`; never `drop` on your own judgement.** A drop is the maintainer's call on the maintainer's box, for the same reason a merge is not yours to approve — and it is barred outright while any ticket is outstanding — queued as much as claimed — by the frozen-worktree rule (*Draining the gate queue*), because a queued ticket names a worktree whose resources a runner is about to need. *The failure this prevents runs both ways. Skipped, the resources accumulate silently for as long as the machine lives, which is the whole reason the key exists. Run as a drop instead, on a report you did not have to read, it deletes a live worktree's database mid-gate — and a missed reclaim is a disk-space cost, while a wrong one is unrecoverable.*
