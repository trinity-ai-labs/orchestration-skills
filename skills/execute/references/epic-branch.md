# The epic branch

Reference for `skills/execute/SKILL.md`. **Read it when the increment is an epic** — when to cut the branch, the one cost it carries and the mandatory mitigation, where the docs go, and the mechanics. Single-slice work never cuts one, and the rest of the playbook reads the same when there isn't one.

**Skip this section unless you are running a multi-slice epic.** Single-slice work — one fix, one feature, one PR — never cuts an epic branch, and nothing else in this playbook changes when there isn't one.

An **epic branch** is a branch cut from the integration branch that an epic's slices fork from and PR into, gated as a whole once they have all landed, then merged back to the integration branch in one ordinary PR. It is the same shape as the integration branch, one level down: the epic converges there instead of on the shared branch, so the shared branch only ever sees the epic finished.

## Two rules reach for one — and neither of them is a slice count

They answer different questions, and either one fires on its own. When neither does, there is no epic branch: the slices merge into the integration branch as they land, exactly as they do today.

**Unless the user already decided — then there is nothing to ask.** These rules are for when nobody has made the call. When the user names the approach, that is a decision rather than a hypothesis to check: **"do it as an epic" means the branch is decided.** Read the rest of this section for the **mechanics** — how the branch is cut, who owns its lifecycle, what it costs, and the merge-back cadence it requires — then cut it and point the slices at it. Do not re-run either rule to see whether the user was right. **The general form, and it is not specific to this decision: a skill's decision procedure never overrides a stated instruction — once the call is made, the skill is read for how, not for a second opinion.** *The failure this prevents: the user spends turns repeating an instruction they already gave, and the overruling does not stay in the conversation — this question is answered in one line inside a plan that gets handed onward and executed as written, so every slice targets the shared integration branch while the user had asked for exactly the isolation this branch provides. An unwarranted "not needed" produces a perfectly well-formed plan, so nothing downstream can tell it apart from a correct one.*

**Rule 1 — the shippability trigger. It answers: _would a partial state on the shared branch be broken?_**

> **Does any intermediate state leave the integration branch in a condition you would not ship?**

If yes, cut one — at any width from two slices up. A two-slice epic whose foundation lands before its consumer migrates needs the isolation exactly as much as a ten-slice one does.

- **Primary — the epic is only correct as a whole.** A foundational change whose consumers must all follow it: a NOT-NULL schema swap, a required interface field, a renamed module. Every state between the foundation landing and the last consumer migrating is unshippable. This is exactly the shape *Transient-red window* below describes, and the case this branch exists for — the window has to sit somewhere, and an epic branch is what keeps it off the branch everyone else forks from. It is still a recommendation you weigh, not an automatic cut: a small foundational change whose consumers all land in the same afternoon may not be worth the branch.
- **Secondary — a contract seam.** `decompose` emits a producer → consumer map naming the shape one slice emits and another reads. Two halves of one contract landing separately means the branch is wrong in between — the primary condition arriving by a different route.

**Rule 2 below cuts the branch on width alone, so Rule 1 has stopped deciding *whether* and now decides *which kind of branch you are holding* — answer it on every multi-slice arc anyway.** A "yes" says the epic is **knowingly red** until its last consumer migrates, and that is what opens the `transient-red/<epic-slug>` window (*Mechanics* below, and *Transient-red window* for what reads it). A "no" leaves a branch that is isolation and nothing else, strictly gated at every step, with no window and no marker ref. Two things downstream key on exactly that distinction, which is why Rule 1 survives Rule 2 widening past it. *The failure this prevents: once every multi-slice arc cuts a branch, Rule 1 reads as dead weight and the next editor tidies it away as redundant — taking the only thing that says whether the window opens with it. Nothing reports that, because a window that never opened and a project that has none are byte-for-byte indistinguishable: every slice of a knowingly-red epic just pays full strict-path friction for a relaxation the repo believes it has, and the loss surfaces as nothing at all.*

**Rule 2 — the multi-slice default. It answers a different question: _what does landing one change on the shared branch as N separate merges cost, whether or not every intermediate state would ship?_**

**Multi-slice work defaults to an epic branch.** The condition is one change decomposed into slices — not a number you count to, and not how you dispatch them. Five costs land on the shared branch whenever it does. None of them depends on any intermediate state being broken, and the first four are each already documented elsewhere in this playbook as something to work around:

- **Base churn — concurrency only.** N slices merging as they land means every live slice's base moves under every other live slice. The scar is already here: the phantom-deletion false alarm that burned a review cycle, and the standing discipline of anchoring every divergence check and every review diff to a **fork point** rather than the tip — a discipline that exists precisely because the tip moves. An epic branch bounds that churn to the epic's own slices instead of the epic's slices plus every other session's traffic.
- **The integration gate signal — concurrency only.** *Gate the integrated whole* calls the `^2` diff non-empty when a sibling branch merged in between — which under parallel dispatch is the ordinary case, not an edge one. The shared branch then routinely carries a tree no gate has run, covered only by N interleaved partial gates. An epic branch converges once and gates the whole thing once, which is the signal you actually wanted.
- **Revert granularity.** An epic that turns out wrong is N separate merges to unpick from the branch everyone else forks from, against one merge to revert.
- **Cross-slice seam review.** *The PR review loop* requires diffing both halves of a contract seam against each other before merging either. That is materially easier while both halves are still converging on a branch you control than once each has landed on the shared one — and halves that land in slice 1 and slice 4 are a seam however far apart in time those two merges are.
- **One arc, N releases.** In a project where shipped content must move a version, every merge into the integration branch is a release — so N slices merging there is N versions for one coherent change, on top of making the version file and the changelog a hotspot every slice has to touch. *Observed on the arc that shipped 3.15.0 in this repo.* `AGENTS.md` requires any PR touching shipped content to move `.claude-plugin/plugin.json`'s `version` and add a matching `CHANGELOG.md` heading, and `.github/workflows/ci.yml`'s `version-bump` job enforces it — but only on a PR whose base is `main`. That arc's three slices merging into `main` directly would each have needed their own bump, colliding on both files, and would have shipped three versions for one change; converging on an epic branch made it one release, and the epic → `main` PR still faced the bump check in one shot. That `if:` condition was written knowing this — its own comment says the epic → main PR *"is itself a PR into main… so the whole arc's accumulated content is still checked in one shot"* — so the CI already assumed this topology while the rule that produces it was still keyed on fan-out.

**Two of those five are artifacts of concurrency and genuinely do not apply to a sequentially-dispatched arc — conceded here rather than left for a reader to catch.** With one live slice at a time no sibling's base moves under anything, so base churn is zero; and conflict-free sequential merges come back empty on the `^2` check every time, so the shared branch is never left carrying an ungated tree. **The other three hold whatever the dispatch order is.** An arc that turns out wrong is still N merges to unpick, a seam is still a seam, and N merges into the branch a project releases from are still N releases — which is why the rule is stated over multi-slice work rather than over fan-out. *The failure this prevents is a reader's, and it is why the accounting is written down instead of assumed: someone who notices that base churn cannot happen sequentially, and finds the section silent about it, concludes the rule was widened past its own argument — and the next edit narrows it back to the qualifier this one removed.*

None of this makes the branch free. *The cost* below is the bill, and the merge-back cadence that bounds it is mandatory — and load-bearing in proportion, because this default fires on every multi-slice arc.

**Neither rule is a slice count, and what still bounds Rule 2 is its subject rather than its width.** Counting slices measures how long a partial state sits on the branch, never whether that state is broken — a real five-slice run (cache invalidation, a UI gate, a query poll, a SQL predicate, a store guard) was independently shippable at every step, and every merge left the integration branch green and coherent. That is why a count can never answer Rule 1, and it is also why that run is now the clearest case *for* Rule 2 rather than against it: it answered Rule 1 "no" and wanted the branch anyway, because the costs above landed on the shared branch however green each intermediate state was. What bounds Rule 2 instead is what counts as multi-slice at all — **one change decomposed into slices**, which is the thing an epic branch exists to converge. A handful of unrelated one-slice fixes running side by side is not an epic and cuts nothing: that is branch traffic, not an arc, and there is no half-finished arc for a branch to hold.

**And it is still not "the integration branch is busy."** Other sessions' traffic is the opposite concern — isolating you from them rather than them from you — and in a multi-session shop it is near-permanently true, so as a standalone trigger it degenerates into "always". What Rule 2 keys on is *your own* arc, which begins and ends with this epic.

**Single-slice work never cuts an epic branch.** Neither rule can fire on it: one slice has no intermediate state to leave behind, cannot churn its own base, gates the tree it produced, is one merge to revert, and has no sibling to hold a contract seam with.

**`decompose` recommends; you decide and act.** It is the pass that grounds slices in real code and produces the seam map, so it is the one positioned to see whether two halves must land together — it says so in its breakdown. You cut the branch and point the slices at it. Same find/act split already established for contract seams. A decomposition that recommends nothing means no epic branch.

## The cost — conflicts are deferred and concentrated, and the mitigation is mandatory

Conflicts do not disappear. Today a slice author resolves a small collision against the integration branch while the code is still theirs and still fresh in mind. Behind an epic branch that collision instead accumulates until the epic lands, and whoever lands it resolves a bigger one, later, with less context. That is the whole bill, and it is why this is trigger-gated rather than the shape everything uses.

**The mitigation rides the tick you already run.** On the same wakeup tick that drains the gate queue and fast-forwards the local integration branch, merge the integration branch INTO the epic branch — merge, never rebase, same as everywhere else here. *Draining the gate queue* carries the exact commands, because that is where you will be when you run them. That keeps the drift bounded and surfaces each collision while the slice author who caused it is still live to resolve it. Skipping this cadence is precisely how the deferred conflict becomes the concentrated one.

## Docs land at the end — one closing slice, fed by a falsification ledger

**Docs describe an end state, and an epic's intermediate states are by construction never shipped** — that is what this branch is for. So a doc rewritten by slice 1 gets rewritten again by slice 3, and the intermediate version was true of nothing anyone ever saw. Doc files are also hotspots in a way source files usually are not: one chapter describes a mechanism four slices are each changing a quarter of, so four slices patching four sentences is four conflicts whose resolution is **semantic** — reconciling four partial accounts of one mechanism, which is the thing the person holding the merge is least equipped to do.

Deferring docs wholesale is not the answer either, because it breaks the forcing function that makes naming them worth anything: **the implementer is the only party that knows what its change actually falsified**, and deferred docs are docs that do not get written. So the two halves split rather than move together:

- **`decompose` still names the docs each slice falsifies**, slice by slice, at grounding time (`skills/decompose/SKILL.md` Step 1). That discipline does not move, and neither does deriving it from the diff rather than from a grep.
- **The slice's deliverable is an entry in the epic's falsification ledger, not the edit** — *"this change makes paragraph Y of `<doc>` false"* — reported in the same hand-back that already carries a per-doc verdict. **That is the rule for prose describing behaviour**; a **structural coordinate** the slice itself moved is fixed by the slice, under the coordinate carve-out below.
- **Two questions, not one — the second asks what the slice ADDED that no doc describes at all.** *What did this change make false?* is a question about a **difference**, so a slice that gates, guards or exposes a surface **no doc has ever described** answers it with *nothing* — correct, complete, and indistinguishable from the answer a slice gives when it genuinely touched no documented behaviour. So ask the second question of the same diff and put its answer in the same ledger, marked as **needing new prose** rather than a correction: *"this change adds `<surface>`, which no doc describes."* **A slice reporting "nothing falsified" is doing the first rule correctly** — the defect was never implementer diligence and no amount of it closes a gap in what the question can return, which is why this is a second question rather than a warning to look harder. **It bites hardest on the surfaces most worth documenting**, since new behaviour is the likeliest thing to have no prose about it yet. *The failure this prevents, observed: a five-slice epic added seven gates across two workspaces, and the two that produced no ledger entry from anyone were both on undocumented surfaces — one slice checked the chapter covering its area, correctly found that the chapter says only that the thing fires and never what it contains, and reported in as many words that its surface "has nothing to falsify and nothing to document". The closing slice then consumed a ledger that was accurate and short by exactly the entries nobody could write, with no signal that anything was missing, because from there an absent entry and a not-affected verdict look identical.*
- **The ledger is the epic's record, not a file in the tree.** A file every slice appends to is exactly the shared hotspot this whole arrangement exists to avoid. Accumulate the entries where the arc's state already lives: the per-increment comment on the umbrella issue, or the orchestration record when the arc has none (`skills/orchestrate/SKILL.md` §7).
- **One closing docs slice consumes the ledger — and derives its work from what the epic ADDED as well, never from the inherited entries alone.** Last in the wave map, depending on every other slice, writing against the final tree with the whole picture in view. **Both halves are one rule and landing only the producer's is worth nothing**: a second question nobody consumes leaves its entries sitting unanswered, and a consumer reading only what it inherited is blind to exactly the surfaces that question exists to surface — so the closing slice's brief says to derive its rows from the arc's landed diff, the gates and flags and endpoints and surfaces the epic added, and to **reconcile** that list against the ledger rather than substituting either for the other. *The failure this prevents, observed on the arc above: a dispatcher had to write that instruction into the closing slice's brief by hand — derive the rows from the gate list, not from the ledger — and it is the only reason one of the two undocumented surfaces was documented at all.*
- **The epic cannot close with a non-empty ledger.** Every entry is answered by the closing slice's PR, and the epic → integration PR does not open while any remain. **This one really is a precondition over the OPEN, where the green close-out gate below is a precondition over the MERGE** — a draft PR puts nothing on the shared branch, so a gate can be enqueued against one, while an outstanding ledger entry means the epic is not finished and there is nothing to open a close-out for yet. It is the thing that stops this becoming the deferred-docs failure.

**Three carve-outs.** A **docs-only slice** writes inline: it has nothing to defer to, and its diff *is* what the closing slice would otherwise be doing. And **single-slice work has no end of an epic** — its docs ship in the same PR as the behavior, exactly as they do today, which is the same reason this section opens by telling you to skip it unless you are running a multi-slice epic. The third is unlike those two in the case it reaches: neither of them can help a **code slice in the middle of a multi-slice epic**, which is exactly the shape this rule is written for.

**A structural coordinate — a file path, or a route literal sitting in the same clause as one — is fixed by the slice that moves it.** The line is testable rather than a matter of judgement, and this is the operative statement of it: **if a checker can tell the reference is stale without reading the sentence, the slice that broke it fixes it.** A coordinate qualifies because it names something the tree either has or does not — which is *why* a gate can enforce it mechanically, and why repointing one is a **rename, not a rewrite**: no two slices can hold conflicting accounts of which path a file now has, so the semantic conflict this whole arrangement defers against has nothing to attach to. Everything on the other side of that line is untouched — **prose describing behaviour still defers to the closing docs slice, ledger and all.**

**A renamed IDENTIFIER lands on the prose side of that line, and it is the case the nouns above do not settle by looking.** A function, a param, an exported symbol is neither a file path nor a route literal, so the rule already returns an answer — but it returns it by the **test**, not by the nouns, and the test is the part to apply: nothing resolves a bare identifier in running prose against the tree. A path either exists or it does not. A symbol name in a sentence may be the current API, a superseded one a migration note is deliberately quoting, or a hypothetical in an example, and separating those is exactly the reading-the-sentence the test excludes. So an identifier your slice renamed goes to the ledger — **the whole sentence, not the name on its own** — and it usually costs no entry at all, because a sentence that names an accessor is almost always also describing what the accessor does, which was going to the ledger regardless. **Where a repo's docs gate genuinely does resolve identifiers — a code fence it compiles, a docs build that imports the symbol — the same test returns the other answer and the slice fixes it inline**, under the ⛔ below like any other sanctioned edit. Read the test, not the list of nouns; the nouns are what the test has returned so far.

*The failure this prevents: an identifier swap does not read as prose, it reads as exactly the mechanical repoint this carve-out sanctions — so it gets made inline, silently, by an agent that believes it is complying, and lands in the half-corrected state the adjacent-fact test below exists for. And unlike a stale path it costs nothing to defer: no gate reds on it, and an epic's intermediate states are never shipped, so there is no reader to mislead in the meantime.*

⛔ **Repointing a coordinate is NOT licence to fix the paragraph around it.** You change the path and nothing else; the sentence containing it, and the section containing that, stay in the ledger. A slice that "while I'm here" rewrites the surrounding prose reintroduces exactly the semantic conflict the deferral exists to prevent — and does it wearing a sanctioned edit, which is strictly worse than the failure it started from, because a diff that is *supposed* to touch that file no longer looks wrong to anyone reviewing it. This boundary is what keeps the carve-out from swallowing the rule.

⚠️ **"Nothing else" is only half the instruction — before you land an inline fix, read the sentence you just edited for a fact YOUR OWN change moved.** The rule above forbids you from improving the paragraph; it does not licence you to leave a sentence you have half-corrected, and the two are different obligations. This one is narrow by construction: it fires on facts *your diff* falsified — a TTL, a limit, a default, an ordering — and on nothing else that happens to be wrong in that sentence, which stays the closing slice's exactly as before. **Where you find one there is exactly one move: fix both halves. Never land the half.** **Reverting your inline edit is not a second way to satisfy that, and the reason is this carve-out's own test.** Every inline edit this test can fire on is one a checker *compelled* — a coordinate repoint, or an identifier fix in a repo whose docs gate resolves identifiers — and the edit is admitted precisely *because* a checker can tell the reference is stale without reading the sentence. So undoing it hands that checker back exactly what it reds on, which is the red-before-your-own-work-is-evaluated this carve-out exists to escape, and no ordering escapes it because the closing docs slice is last by construction. Putting the sentence in the ledger does not rescue the revert either: the rule above already leaves that sentence there, so the ledger gains nothing it did not already have while the slice loses its own gate. **Nor is there a leftover case where reverting is harmless** — where no checker resolves the reference, the carve-out never sanctioned an inline edit in the first place, so this test has nothing to fire on. And the one move is always available to you: the fact is one your own diff moved, which makes you the only party that already knows its new value. *The failure this narrowing prevents: an implementer that reverts has followed a sanctioned instruction to the letter and hands back a clean slice, so the red arrives afterwards from the gate runner, on a PR whose diff contains nothing wrong — and it reads as a defect in the slice rather than as the rule contradicting itself.* The asymmetry is why this is an obligation rather than advice — an untouched sentence is uniformly stale and a reader discounts all of it, while a fresh coordinate beside a stale number reads as evidence someone checked, so the wrong half inherits the credibility of the right one, and the closing docs slice, arriving at a sentence that was visibly attended to, has the least reason of anyone to look at it again.

*The failure this prevents, observed: one slice renamed a settings-cache accessor and moved that cache's TTL from 15 seconds to 60. The doc sentence naming the accessor was swapped to the new name and left reading "15-second cache" — the identifier right, the number describing a mechanism that no longer existed. Nothing in the slice, the gate or the ledger pointed at it; it was caught in review, and only because the reviewer happened to know the TTL had moved in the same change. The dispatcher's workaround was to tell the closing docs slice by hand to read that paragraph fresh, "do not treat it as done and do not treat it as untouched" — written per-slice, and only because someone remembered.*

*The failure this prevents, observed: a wave-2 slice of a six-slice epic deleted four files, four docs cited those files by path, and the repo's docs gate — which validates that every file path cited in a doc resolves in the tree — went red at **step 1 of 6**. `format`, `check` and `test` never ran, so the slice got no signal at all about its own work; nothing was wrong with it. It could not pass its gate without editing a doc the rule forbade it to edit, and no ordering escapes that, because the closing docs slice is last by construction. Neither of the first two carve-outs reaches it. The cost is a full drained-gate round trip plus a fix-agent dispatch per affected slice, and it arrives looking like a defect in the slice rather than a gap in the convention — and waves 3–4 of that same epic delete more files the docs cite, so it recurs by construction rather than by accident.*

*The failure the deferral itself prevents runs both ways, which is why it is a split and not a deferral. Docs written per slice inside an epic are rewritten by a later slice and collide semantically in between, so the work is done twice and the merge is resolved by whoever has the least context for it. Docs merely postponed are written at the end by an agent that watched none of it happen, from a diff too large to read — which is how an epic ships a chapter describing neither the old mechanism nor the new one, with every gate green.*

## Mechanics

- **It gets its own worktree, like every other branch that is not the integration branch.** One governing rule covers the whole flow: **the main checkout holds the integration branch and nothing else, ever.** The epic branch is not a special case — it is a slice-shaped thing one level up, cut the same way:
  ```
  setup-worktree.sh <epic-branch> <integration-branch>
  git -C <epic-worktree> push -u origin <epic-branch>
  ```
  `setup-worktree.sh` creates the branch **and** its tree in one command and **never touches the main checkout** — which is why this *replaces* the old switch/push/switch-back ceremony rather than relocating it. You cannot forget to step off a branch you never stepped onto, so there is no second half to get wrong. **Push it**, or `origin/<epic-branch>` does not exist: invariant 2 has nothing to compare a slice worktree's `HEAD:` against, and `gh pr create --base <epic-branch>` has no base on GitHub to open against. *The failure this prevents runs on two levels. Structurally, parking the epic branch in the main checkout caps you at exactly **one** epic — one checkout, one HEAD — while Rule 2 above makes an epic branch the **default** for multi-slice work, so the flow reaches for a branch constantly whose mechanics permit one at a time. And it puts the epic on the one piece of shared mutable state this flow has (the ⚠️ in *Worktree creation*, which named the main checkout as exactly that and was then contradicted by this bullet). Observed: another session moved the main checkout off the epic branch while a close-out gate ran. The gate was fine; the verification that followed ran against a different release branch entirely and reported an absurd count of schema blocks and a missing migration. **Nothing errored.** It was caught only because the numbers were absurd — with a subtler change it would have reported a green "verified" against the wrong tree. The safe workaround people actually reached for was `setup-worktree.sh --existing <epic-branch>`, a worktree on the epic branch: the skill's own recovery tool was the right answer to a problem the skill created, which is the tell that the tool was the design all along.*
- **⛔ The epic branch's leaf must be unique across the whole epic — no slice may reuse it, and the helper now refuses rather than letting the reuse through.** The worktree path is `$WORKTREE_HOME/<project>/<branch-leaf>` and the leaf is everything past the last slash, so `epic/checkout-flow` and a slice `feat/checkout-flow` resolve to the **same directory**. That collision is impossible until the epic branch has a worktree; it is live from the moment it does. On the second call `setup-worktree.sh` asks only whether a worktree is already **registered at that path**, finds the epic's, prints `worktree already exists: <path>`, and **skips `git worktree add` entirely** — so the slice branch is never created. It then reads the branch back off the tree, finds the epic's where the slice's was asked for, and **stops**: both branch names and the shared leaf on stderr, a non-zero exit, and no `READY:` line at all. The likeliest slice to reach for the collision is the epic's own **closing docs slice** — its wrap-up has no more natural name than the epic's — so pick a leaf that slice would not want, or name it for what it does rather than for the epic. *The failure this prevents: **invariant 2 is structurally blind to this one**, which is why the refusal has to live in the helper rather than in the check. Invariant 2 has you compare the printed `HEAD:` against `git rev-parse origin/<base>` — and the tree you were handed is standing on `<base>` itself, so the two shas **match**. The one check built to catch a wrong tree cannot see this wrong tree, because it is the base's own; the helper stops first, so there is never a `HEAD:` line for invariant 2 to be fooled by. Which generalizes past this one case: **a `READY:` line is not by itself evidence that the branch was created — the helper's own branch-back check is what makes it so.** Still choose the epic's leaf so that no slice will want it; what changed is that forgetting now costs you one refused command instead of a whole dispatch that looks correct.* **And the branch-back check is not the last thing standing between a skipped `git worktree add` and a `READY:` line — read that sentence as naming what makes the line evidence about the BRANCH, not as an inventory of the refusals.** The ancestry check that follows it asks a different question of the same handed-back tree — whether it contains `<base>` — which is the state a tree on exactly the right branch can still be in, and is why *Worktree creation* says the helper automates part of invariant 2. Neither refusal retires that invariant: its comparison is for equality and against `origin/<base>`, and invariant 2 is where the two gaps that leaves are named.
- **The epic worktree is a merge point and a gate target, not a workspace — nobody codes in it.** It exists so the epic branch has somewhere to be fast-forwarded, merged into, and gated. Every line of the epic is written in a slice worktree and arrives by PR, so this tree should never have uncommitted changes in it. *The failure this prevents: a dirty tree blocks **both** of the jobs this worktree exists for, and neither failure surfaces where it was caused. The every-tick `merge origin/<integration-branch>` refuses to run over uncommitted changes, so the mandatory mitigation for the epic's one real cost silently stops happening and the deferred conflict goes back to being the concentrated one. And `merge-pr.sh` now fast-forwards the base **inside this tree** on every slice close-out, so it fails there too — mid-close-out, after the merge is already irreversible. Both land as a failure in somebody else's slice, naming a tree that slice never touched.*
- **A module-resolution failure in the epic worktree is a stale install until proven otherwise, not a defect in the merged code.** The bullet above keeps this tree fit for two jobs that are both *git* operations; its **dependencies** are a third thing that can fall behind the branch, and no git-shaped rule covers them. They can fall behind in any tree that **outlives the merges landing in it**, which is precisely what this one is for — while every slice worktree is cut once the code it needs already exists and so installs correctly by construction. **This is not the only such tree, and it is not the most exposed one:** the main checkout outlives every merge the arc makes, holds the integration branch for all of it, and is fast-forwarded by `merge-pr.sh` on every close-out without ever installing — so the same question is asked of it, immediately before the integration gate runs there (*Gate the integrated whole*). So ask that question before you read a line of the diff: the tick's install (*Draining the gate queue*) is what keeps this tree current, and what you are checking is whether one has run since the package arrived, not whether a slice broke its imports. *The failure this prevents, observed: a slice added a workspace package and merged into the epic branch; the epic worktree's install predated it, and the integration gate there came back `TS2307: Cannot find module` on five files across two apps. The natural reading of that shape — five files, two apps, one module nobody can find — is a slice that repointed its imports at a path which does not resolve, and it invites dispatching a fix agent against code that is already correct, or hunting a package-name typo that is not there. The install took 1.2 seconds and the gate went green. The cost was never the install; it was arriving at it as a diagnosis.*
- **A conflicted tick is resolved before you walk away from it — never left half-merged for the next tick to find.** The every-tick merge of the integration branch into the epic branch is *where the deferred conflict surfaces*; surfacing it early is the entire reason the cadence exists. So resolve it in the epic worktree, commit the merge, push, and only then carry on. *The failure this prevents, and it is a second reason this merge no longer runs in trunk: the old cadence ran `git -C <main-checkout> merge origin/<integration-branch>` while the main checkout was standing on the epic branch, so a conflict — again, the exact case the tick exists to produce — left the **shared** checkout wedged mid-merge, conflict markers in the tree and `MERGE_HEAD` set. Every other session's `pull --ff-only` against that checkout then failed, in a checkout none of them had touched, for a reason none of them could see from their own worktree. The mitigation for the epic's one cost was itself a shared-state hazard. In a worktree you own the same conflict is yours alone and blocks nobody — but only until you leave it there, because an unfinished merge in the epic worktree is precisely the dirty tree the bullet above is about.*
- **Its *prefix* is free; its leaf is not, and the marker ref beside it is the exact opposite of both.** Nothing anywhere reads an epic branch's **prefix** — no helper in this plugin's `bin/`, no step in this playbook: the branch is identified by what forks from it and PRs into it, never by what it is called, so whatever prefix a team likes is fine. Its **leaf** is a different matter now that it has a worktree, because `setup-worktree.sh` derives the directory name from it — hence the uniqueness rule above. That is a collision constraint, not a naming contract: no leaf carries meaning, one just has to be unlike the others. **`transient-red/<epic-slug>` in the next bullet is not free in the same way — its name IS the contract**, because the detector finds the window by looking for that exact ref; spell it as written. The two are one fact rather than two: the branch's name is free *because* the marker took the job of being found. *The failure this prevents: a reader who carries "the name is free" across to the marker spells that to taste too, and a marker under any other name is a window that never opens — which nothing reports, because a window that failed to open and a project that has none behave identically.*
- **Cut under Rule 1's primary trigger? Open the window in the same breath — the branch alone does not open it.** A Rule 2-only epic branch — one Rule 1 answered "no" — is isolation and nothing else: every intermediate state on it would ship, and it stays strictly gated. A Rule 1 primary epic branch is *knowingly red* until the last consumer migrates (*Transient-red window* below), and a project whose commit-time tooling relaxes for that window has to be able to tell the two apart. It cannot read your decomposition, so declare the window structurally — one marker ref, pushed beside the epic branch and never committed to:
  ```
  git -C <epic-worktree> branch transient-red/<epic-slug> <epic-branch>
  git -C <epic-worktree> push origin transient-red/<epic-slug>
  ```
  Run them from the epic's own worktree, in the same breath as the two commands above. Creating a ref needs no working tree at all — the `-C` here only picks the repo — so this is about not reaching back into a checkout you no longer have any reason to touch, not about where the ref ends up. Nothing forks from it and nothing merges into it; it exists to be **found**, by tooling running inside a slice worktree that has no other way to know. **It answers one question — is the window open — and it is never a fork point.** A detector that needs the branch's own footprint takes its merge-base against the **epic branch**, which is what the slices actually forked from and which moves under them every time the tick merges the integration branch in. *The failure this prevents: the marker is static by design, so anchoring a merge-base on it silently widens every slice's "owned" file set to include everything merged into the epic since it was cut — which fails closed, quietly tightening the relaxation as the epic runs, and looks exactly like slices getting sloppier.* *Transient-red window* below states what reads it and what it must not be keyed on instead.
- **Slices fork from it and PR into it.** `setup-worktree.sh <slice-branch> <epic-branch>`, and invariant 2 then compares the tree's printed `HEAD:` against `git rev-parse origin/<epic-branch>` rather than the integration tip — **fetch first and read the freshness count, exactly as invariant 2 says, because this is the base most likely to have moved since you last looked.** The epic branch advances on every slice close-out, which fast-forwards it inside its own worktree, and again on every tick that merges the integration branch into it and pushes — so a cached `origin/<epic-branch>` goes stale on this flow's own cadence rather than on some other session's, and it does so between waves you are yourself running. Each slice's brief names the epic branch as its PR base. *The failure this prevents: nothing tells you the epic branch moved, because the close-out that advanced it ran in a worktree that is not yours and left no signal in yours — so a slice cut against a cached tip forks from a base the epic has already left, and the first sign is either a conflict at merge on files the slice had no reason to touch, or a sibling's half of a contract seam silently missing from the tree the slice was built and gated against.*
- **A follow-up the epic surfaced is part of the epic, so it lands on the epic branch.** The follow-up-ownership rule (*Hard rules*) turns every leftover into a filed, linked item — a new issue, or a comment on the issue already carrying that failure, which needs no branch at all and so has nothing for this bullet to place; while the epic branch is live, a new issue's slice forks from and PRs into the **epic branch** like any other slice of the arc, and that issue links to the arc's umbrella — or to the originating issue when the arc has none — rather than sitting loose. Only once the epic branch has merged back does a still-open follow-up re-target the integration branch. *The failure this prevents: the epic branch exists so the shared branch only ever sees the epic finished — routing a follow-up straight to the integration branch bypasses precisely the isolation the branch was cut for, and delivers the epic's leftovers to the shared branch piecemeal while the epic itself is still converging.*
- **Per-slice close-out needs no change, and leaves the main checkout where it found it.** `merge-pr.sh <n>` reads the base off the PR itself (`baseRefName`) and drives every later step from it — the mergeability preflight, the merge, and bringing the local base branch up to the merged tip in the main checkout. So a slice PR based on the epic branch closes out identically: worktree torn down, real merge commit into the epic branch, local epic branch advanced to the merged tip. No argument, flag or hand-run step to add, and nothing to switch back afterwards — the helper never switches the main checkout at all. What the epic branch having its own worktree changes is only **which** of the helper's three sync paths runs: the epic branch is now checked out, in that worktree, on every single slice merge, so the helper fast-forwards it **inside that worktree** (`merge --ff-only`, which can only ever move it forward) instead of moving its ref from outside — `git branch -f` refuses to move a branch any worktree is standing on. It then verifies the main checkout is still on the branch, and at the commit, it started on, exactly as before. The headline claim holds and gets **stronger**: this close-out now leaves not just the checkout's HEAD but every local branch in it untouched.
- **The bullet above is scoped to the steps the helper performs; the one it cannot do is the step an epic changes — not when it runs, but what happens when it is skipped.** Closing the issues the work resolved is that step, and *Merge & cleanup* already names it as the one that silently goes missing. An epic branch withdraws its only fallback, for every slice of the arc at once and for the arc's whole life: a slice PR bases on the epic branch rather than on the repository's **default** branch, so its closing keyword is inert — then, and later when the epic merges back (*Merge & cleanup* carries those mechanics and stays the only place they are explained). In a project whose integration branch simply **is** the default branch — this repo, and the shape most work here runs in — that flips at the moment the branch is cut: outside an epic the keyword fires and the hand-close is a harmless no-op, so the board moves whether or not anybody remembers the step; inside one the hand-close is the entire mechanism, on every slice merge. **So while an epic runs the board is not the arc's progress record — the umbrella body is**, rewritten every cycle (`skills/orchestrate/SKILL.md` §7). Read progress there, and where the board has fallen behind, catch it up to what has actually merged into the epic branch, never ahead of it. *The failure this prevents: mid-epic a dispatcher reads a board on which nothing has closed all day and reaches for one of two wrong conclusions. Either the work has not landed — it has, onto a branch no issue tracks — and slices that already merged get re-dispatched. Or hand-closing is overdue and the arc's issues get closed now to catch up, which is the worse branch: §7 counts the tracker in its termination check, so an issue closed ahead of its slice is a false "done" in the exact artifact the loop reads back to decide whether it is finished.*
- **A change to `.agents/worktree.json` is another thing this branch holds open for the arc's whole life: the config-read window ends at THIS branch's close-out, not at the slice merge inside it.** A slice that changes that file merges into the epic branch, which is not the branch the helper's lookup lands on, so that merge exercises nothing — and every worktree the arc cuts afterwards is still provisioned the old way, with the hand-application falling to you. *Worktree creation* is the authoritative copy of all of it: the lookup, the routes that do not get round it, the remedy, and the dispatcher's standing obligation. What is here is only which merge ends the window when there is an epic branch. *The failure this prevents: off an epic branch the window closes at the slice's own merge, so a reader carrying that reading onto one stops hand-applying after a single wave of an arc that has waves left to cut — and nothing reports it, because a worktree provisioned from the old config is not broken, only wrong later.*
- **Close-out is at most one gate plus one ordinary PR — and the ledger has to be empty before either** (*Docs land at the end* above; the closing docs slice is the last slice, so "the last slice merges" below includes it). Once the last slice merges, merge the integration branch into the epic one final time **in the epic's own worktree**, then **open the epic → integration PR as a DRAFT and enqueue the gate against it**, naming the epic worktree as the ticket's worktree so the gate runs there rather than in a checkout something else might move. *The failure that ordering prevents is the observed one that moved the epic branch out of trunk in the first place: a gate and the verification that reads it are two steps, and between them another session moved the shared checkout. The gate itself was fine; the verification ran against a different release branch and reported numbers that happened to be absurd enough to notice. In the epic's own worktree there is no window — nothing else has a reason to touch that tree, so what you gate and what you then verify are the same tree by construction.*

  **The PR opens BEFORE the gate, and the rule that looks like it forbids that does not.** *Gate the integrated whole* states the precondition over the **merge**, not over the open: a draft PR puts nothing on the shared branch, because GitHub refuses to merge one and this flow already spends the draft flag as the interlock against merging an unread diff. Opening it first is what gives the ticket something to attach to, so this becomes the shape every other PR in the flow already has — draft PR, enqueue, runner gates and comments, then merge. *The failure the old order caused: the one gate whose tree no per-slice gate had ever seen was also the only gate in the flow with no ticket, no streamed log, no recorded verdict and no comment, so its result survived only as an exit status in the terminal of whoever ran it — which is the whole reason a hard rule about `EXIT=$?` and piped invocations had to exist for it at all.* Two consequences: **"once the fleet is quiet" stops being something you poll for**, since the queue serializes by construction; and where the project declares **no queue** there is nothing to enqueue to, so you gate the epic branch in its own worktree yourself and read its exit status (*Gate the integrated whole*), with the draft-PR-first ordering unchanged.

  Then merge it with `merge-pr.sh` like any other. That merge is the first thing the integration branch sees of the epic, and it is a complete one. **It is "like any other" in shape now and unlike any other only in authorship** — this is the one PR in the flow with no implementer behind it. It is a draft carrying a gate comment from the moment it opens, exactly as **Hard rules**' reading requires, so there is no exception here to explain any more; what there is no such thing as is a hand-back to promote, because nothing was built on the epic branch directly. You author it and then merge it. What stands in for the missing hand-back has already been spent — every slice was reviewed as its own draft PR, and the epic tip has just been through *Gate the integrated whole*, which when the merges produced a tree no per-slice gate has run is the one signal those gates structurally could not give.
- **This closing merge is the ONE merge in the flow a project may collapse, and it is an option a project declares — never a judgement anyone makes at merge time.** Every other merge here is a real merge commit with no opt-out. This one branch is scaffolding — cut for one arc, deleted at its end — so on a long-lived release branch a project may prefer one commit per arc to N slice merges plus a merge commit, and it says so up front by putting `"epicMerge": "squash"` in `<repo>/.agents/worktree.json` (*Per-project config*). `merge-pr` reads that key itself and picks the mode; there is nothing to pass it, nothing for an implementer or a dispatcher to decide for one PR, and no way to reach the squash from the command line. Read that the way this file's documented-suppression carve-out reads: the exception is real, and stating it precisely is what keeps the default absolute. **The default is `merge`, and it stays `merge` for every project that has never heard of the key.**
  - **Under `"squash"` the squash still requires BOTH conditions, and every unanswerable question falls back to `merge`.** (1) The PR's base is **not** the repository's default branch (`gh repo view --json defaultBranchRef`), and (2) the head branch has merged PRs into it (`gh pr list --base <head> --state merged`) — which *is* the definition of an epic branch rather than a proxy for one, since an epic branch is the branch an epic's slices PR'd into. A slice branch and a single-slice branch both answer zero, which is what keeps `slice → epic` and single-slice → integration real merge commits without needing a rule of their own. gh absent, offline, unauthenticated or rate-limited; a default branch that came back empty or unresolvable; a count of zero; a config that will not parse; a value that is not exactly `squash` — every one of them lands on `merge`. The asymmetry is the whole design: **a missed squash is cosmetic, a wrong squash is unrecoverable history.**
  - **So a project whose integration branch IS the default branch never squashes, even at this boundary — that is deliberate, not a bug.** This repo is such a project: declare `"epicMerge": "squash"` here and it correctly does nothing. Condition (1) is there because condition (2) is true of an integration branch too — it is the branch every slice of every arc PR'd into, so a long-lived one answers in the dozens — and on its own it would take a `release/x.y.z → main`/`dev` close-out and collapse an entire release branch, irreversibly, with the tree check passing and every signal reading like a clean close-out. Nothing distinguishes an integration branch merging into `main` from an epic branch merging into `main` except a branch-name prefix, and no prefix is ever the key for anything in this flow (*Transient-red window*). So the constraint is **enforced rather than advised**, and a project that would have been told to leave the setting alone now has that for free. *The failure this prevents, observed: the first version of this test asked only question (2), and the slice that shipped it found while proving the negative cases that a release branch answers it too (this repo's own #107) — the release-branch squash reproduces on the pre-fix helper, and nothing about it looks wrong until you go looking for the commits.*
  - **Both ports compare the key, the value, and the branch names CASE-SENSITIVELY.** `"epicMerge": "squash"` exactly — `"Squash"`, `"SQUASH"` and `"EpicMerge"` all mean `merge`, identically in bash and in PowerShell. *The failure this prevents, observed on this very pair before it shipped, and in both directions: PowerShell's `-eq` and its property lookup both ignore case by default, so the first `.ps1` draft squashed a config the `.sh` merged — and the same default on the branch comparison, where git refs are case-sensitive, made a base named `Main` in a repo whose default branch is `main` look like the same branch, so the `.ps1` merged where the `.sh` squashed. Two ports disagreeing about the same file on the same input, once in each direction: the exact class the `bin/` parity rule exists for, and the one shape a parity check comparing surface shape cannot see.*
  - **The squash path does not pass `--delete-branch`, and git's "not fully merged" warning is answered by a different instrument rather than waved through.** A squash commit has no second parent, so the epic branch is never an ancestor of the new integration tip and `git branch -d` reports it as not fully merged on **every** squashed close-out — expected, and carrying no information, because squash breaks ancestry by construction. The warning is a claim about ancestry; what actually has to be true is that *what landed is what was gated*, which is a question about **trees**, and a squash preserves the tree exactly. So `merge-pr` captures the epic tip **before** the merge and afterwards runs `git diff --quiet <epic tip> <squash commit>`. Empty ⇒ the integration branch holds, byte for byte, the tree the close-out gate ran on — and only then is the branch deleted, local and remote. Non-empty, or a comparison that could not be made at all, ⇒ the close-out **stops** with both copies of the branch intact and everything else already finished, so re-running resumes from exactly that check. This is **stronger** than the `^2` check it replaces, not a weaker stand-in: it compares the trees directly instead of inferring coverage from parentage.
  - **What the option costs, stated next to the switch: the arc's individual commits stop reaching the integration branch.** They are not destroyed — they live on the epic branch until it is deleted, and on GitHub in each slice's PR and its `refs/pull/*` ref — but after the close-out nothing local holds them, and `git blame` on the integration branch lands on the squash commit for every line the arc touched. That is the trade the key *is*, and it is why `merge` is the default rather than the recommendation.
- **Deleting the epic branch is automatic on the merge path and earned on the squash path — the marker is the one thing left by hand either way.** The epic → integration PR has the **epic branch as its head branch**, so `merge-pr.sh` on it treats the epic largely as it treats a slice: step 2 tears the epic worktree down, and on the merge path `--delete-branch` removes the branch, local and remote, with the never-delete-past-git's-"not merged"-warning guard applying exactly as it does to a slice branch — verify it is fully merged into the integration branch first, and STOP on the warning rather than forcing past it. On the squash path that warning fires unconditionally and says nothing, so the tree comparison in the bullet above is what stands in its place, and the delete happens only once that comparison has passed. Its slice branches are already gone, each deleted by `merge-pr.sh` as it merged, so the only thing the close-out leaves behind is the `transient-red/<epic-slug>` marker, if it has one — delete that yourself, and the window closes with it. *Leaving it behind is the one failure mode this design cannot self-heal: the ref outlives the epic that justified it, and the next unrelated slice to commit gets its compile check quietly relaxed against a window that closed weeks ago.*
