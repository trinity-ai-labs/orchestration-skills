# Decompose — ground the horizon into dispatchable slices

`/pipeline:orchestrate` runs an arc as a just-in-time loop: ground the next dispatchable increment, dispatch it, reconcile everything still outstanding against the tree that increment actually produced, repeat. `/pipeline:execute` ships each increment off an integration branch: one task → one worktree → one PR → merge, and it does its best work when it's handed a **clean, grounded, parallel-aware breakdown** instead of a vague blob it has to slice on the fly.

**Decompose is the grounding step of that loop.** You take the next dispatchable increment — the **horizon** — ground it in the real code, and turn it into independent task slices the dispatcher can dispatch in parallel with minimal collision. Everything past the horizon you carry forward as *shape*: the goal, the area, what it waits on — never coordinates.

You are a **planner, not a builder.** You read, research, and emit a breakdown (in chat, or onto a GitHub issue). You **never** write code, make worktrees, dispatch implementer sub-agents, or merge — that all belongs to `/pipeline:execute` — and you never run the loop around yourself, which is `/pipeline:orchestrate`'s. Your deliverable is the *increment they execute*.

**The whole point is to maximize safe parallelism — but parallelism has a price, so the real goal is the *balance*.** A good decomposition is one where the dispatcher can cut N worktrees and run N implementers at once across the increment you grounded, because you've already worked out which of its slices are independent, which must land first, and where two of them would fight over the same file. What it is **not** is "as many slices as possible." Every slice pays a fixed overhead — a worktree, an install, a review, and **a full gate run**. Implementers don't run that gate themselves (they enqueue it; `/pipeline:execute` drains the queue and runs the gate one PR at a time behind a slim slot), so a wide fan-out doesn't strand agents waiting on a lock — but the gate is still **serialized on the drain side**: N slices means N sequential gate runs to drain. Each run is cheaper than it looks — a **shared build cache** (turbo, for Trinity) lets a gate *replay* the packages a slice didn't touch near-instantly and only rebuild+retest the ones it did — but the runs still queue behind one slot, so past a point more slices means more total gate + review time, not a faster finish. So aim for the *fewest* slices that still expose the real independence — meaty, cohesive slices over a cloud of fragments. See **Sizing** (Step 3) for the economics, including how the cache rewards **package-disjoint** slicing.

## Three input paths

Decide which one you're in from how you were invoked:

- **Invoked by `/pipeline:orchestrate` for one increment** — the loop hands you an arc and tells you which part of it is the horizon. Ground and slice **that increment only**, emit the remainder at shape depth, and hand the whole thing back to the loop; it dispatches, reconciles, and invokes you again for the next horizon. This is the ordinary path in a multi-increment arc.
- **In-chat plan** — the user has a plan in the conversation (they wrote one, you produced one in plan mode, or they just described the work). Decompose it and emit the breakdown **in chat**, ending with the handoff line (below).
- **GitHub issue** — you were given an issue (`decompose #1042`, `decompose issue 1042`, "slice issue 1042"). Read it with `gh issue view <N>`, ground it, then **write the breakdown back to GitHub** — as a comment, or as an umbrella + sub-issues (see *Writing it back to GitHub*).

If it's ambiguous between the last two, ask once; don't guess and post to GitHub when the user only wanted it in chat.

**All three paths ground the horizon and nothing else — only *who names it* changes.** The loop hands you one; on the other two you work it out yourself from the plan's dependency order, exactly as the loop's first cycle does. *The failure this prevents: reading the horizon as a property of being called by `/pipeline:orchestrate` makes a directly-invoked decomposition the one that grounds the whole arc — the same stale coordinates, reached by deciding the discipline did not apply here.*

**`skills/orchestrate/SKILL.md` section 1 is the authority on the horizon and on the two depths** — what each contains, what promotes an item from one to the other, and the failure that sits under each. Read it there; this skill does not carry a second copy. *The failure this prevents: two statements of one definition drift, and once they disagree nothing marks which is stale, so the copy a reader happens to open wins by accident.*

## Step 1 — Read the plan and ground the horizon in the codebase

A breakdown built from the plan text alone is guesswork — it names files that don't exist and misses the real coupling. **Ground every horizon slice in the actual code first.** This grounding is the single biggest lever on how well the dispatcher does: real paths, real boundaries, real dependencies.

**And the grounding stops at the horizon — that boundary is the point of the pass, not a budget saving.** *The failure this prevents: a coordinate grounded now and executed three waves later names a path an earlier wave already moved, and* ***nothing errors*** *— the brief still reads well, the implementer opens a tree where the target is not there, finds the nearest plausible thing, and builds against that. Grounding the whole arc is the version of this pass that looks most thorough at the moment you do it, which is exactly why it is a rule here and not a judgement call.*

- **Read the source plan fully — the whole arc, then ground only its front.** For a GH issue: `gh issue view <N> --comments` (read the body AND the discussion — constraints often live in comments). For an in-chat plan, or an arc handed to you by `/pipeline:orchestrate`: re-read what was laid out. You need all of it to see where the horizon falls and what each remaining item waits on; you *ground* what is inside it. **And the citations the plan itself carries are among the coordinates you re-derive — a SECTION citation most of all, because nothing further down the flow will.** This pass already re-checks the paths a body names, on the reasoning that a plan written weeks ago names files that have since moved. A `§N`, or a named section of a doc or a skill, is a claim of that same kind and decays the same way, with one difference that decides how you check it: a stale path fails to resolve, while a stale section citation **resolves perfectly** — to a real section that simply does not carry the argument attributed to it. So resolve it by **opening the section and reading what it argues**, never by searching for the word the claim turns on; that word is usually there in an unrelated sense, so the search lands in the right section and reads as confirmation. Resolve the ones the horizon rests on, on the same boundary as every other coordinate here, and send one that does not hold to Step 2 as the defect in the plan that it is. *The failure this prevents, observed: an issue body asserted as settled fact that `skills/orchestrate/SKILL.md` §6 argues how a fork gets resolved. §6 is* The decide-don't-ask bar *and argues nothing of the kind, though it does carry the word "fork" as the one class of thing to escalate. This pass grounded that issue's paths, commands and manifest fields and never resolved the section, so the claim went into a slice brief as settled fact and out the far end into shipped prose, past a gate whose citation check validates file paths and cannot see a section number at all. It was caught by a reviewer who happened to resolve it.*
- **Read UP before you read DEEP — on the GitHub path, establish whether the issue is a sub-issue of an umbrella, and read the parent FIRST.** The bullet above sends you deep into one issue; this one asks whether that issue is the whole frame. Two steps, in this order, because the cheap one is not always available:
  1. **`gh api repos/{owner}/{repo}/issues/<N>/parent --jq .number`** — definitive and free when the umbrella used native sub-issue links. With no native parent the API returns **HTTP 404 `No parent issue found`** and `gh` **exits non-zero**: that is the endpoint answering, not failing, so branch on the exit status rather than chaining this call with `&&`.
  2. **When it 404s, fall back to the timeline**, which finds a markdown-only umbrella that step 1 structurally cannot see:
     ```
     gh api repos/{owner}/{repo}/issues/<N>/timeline --paginate \
       --jq '.[]|select(.event=="cross-referenced")|.source.issue.number' | sort -un
     ```
     **This returns a CANDIDATE SET, not the parent** — every issue and PR that ever cross-referenced this one, with the umbrella among them and in no way distinguished. Against this repo's own #41 it yields `37 42 43 45 46 48 49 50`: eight numbers, of which #37 is the umbrella and the rest are the PRs and sibling slices of the same arc. So disambiguate rather than take the lowest or the first — **the umbrella is the candidate whose own body carries this issue in its tracked checklist**:
     ```
     gh issue view <candidate> --json body -q .body \
       | grep -qE "^[[:space:]]*-[[:space:]]*\[[ xX]\][[:space:]]*#<N>([^0-9]|$)"
     ```
     Run against those eight candidates this isolates exactly #37. Use the `([^0-9]|$)` class rather than `\b` — portability across BSD and GNU grep. That checklist line is `- [ ] #<sub>`, **the very artifact step 1 of *Umbrella + sub-issues* below already mandates writing**, so the reader-side check consumes the writer-side artifact; the two halves are one mechanism and neither is worth much alone.

  Then read the parent with `gh issue view <umbrella> --comments` **before** you ground the child. It carries the wave map, the epic-branch answer, the seam list and the constraints the child was written inside, and none of that is restated in the child — a sub-issue holds its own brief, not the frame around it.

  *The failure this prevents, observed: an agent hunting a classification question found a child issue through a keyword search, read it as a standalone issue, and concluded the decision it contained was unowned — while the umbrella that framed it held the wave structure that answered the question, and had come back in that same agent's own earlier search, seen as a title in a result list and never opened. It spent an hour re-deriving decisions that were already filed. The mechanism worth naming is that* ***a child issue reads as complete***: *nothing about it is missing, nothing errors, and its own body gives no sign it was written inside a frame — so the entire cost is paid in re-derivation that is indistinguishable from original work, both to the agent doing it and to anyone reading the result. And the asymmetry that makes this a rule rather than a habit: the frame is something these skills already mandate* ***writing*** *— the checklist, the `Part of #<umbrella>` backlink — and nowhere mandated* ***looking for***.
- **Research the codebase to anchor each horizon slice.** Spawn `Explore` agents (in parallel — one per subsystem the **horizon** touches) to find the real files, modules, existing patterns to copy, and the consumers a change would ripple into — **invoking this skill is the request that authorizes them**; `skills/execute/SKILL.md` → *First: which role are you?* is the authority on why, and this skill does not carry a second copy. You need actual paths before you can assign scope and boundaries. Don't skip this to save time — it's the work. **Don't extend it to subsystems only a later wave touches**: that research costs exactly as much as the research that pays off, and it is the half that goes stale before anyone spends it. **And this establishes only that a coordinate EXISTS somewhere in the tree, never that it is REACHABLE from where the slice that needs it will actually live** — a package the slice does not depend on, the far side of a workspace boundary. Existence and reachability are different facts; Step 3's closing check tests the second as its own pair rather than folding it into this one.
- **Find what each horizon slice will falsify — the docs first, then every other artifact that asserts something about the code — and put it in that slice's scope.** Every slice that changes user-visible behavior has docs describing that behavior, and they belong in its `Owns` list — named here, where you are looking at the code, not left to the implementer to notice. **Derive them from the behavior, never from a keyword grep.** This is the trap and it is a decomposer's trap specifically: you search the docs for the identifiers your change introduces, get no hits, and conclude nothing is affected — but user-facing prose describes features in plain language and contains none of your new terms by construction, so the grep was always going to come back empty. Ask instead what a reader of each doc currently believes, and which of those beliefs this slice makes false. Then read the candidate docs rather than grepping them; a README paragraph that enumerates something your slice adds a member to is the commonest miss, and no search finds it. **Then ask a second, cheaper question, which earns its place precisely by being GREPPABLE where the one above is not: does this slice delete or move a file the docs cite by path?** The warning above is that a keyword grep cannot find the prose case, and it stands — but a path citation is not prose. It names something the tree either has or does not, so `grep -rF '<path>' <doc-set>` answers it exactly and exhaustively, which is why a docs gate can enforce path citations mechanically while a prose claim has to be read. The two are complements rather than one restated: derive the prose case by reading what each doc's reader currently believes, and settle the coordinate case by grepping the paths the slice removes. Asking it here is what turns a red gate into a line in the slice's `Owns`. **Then ask the same question of everything else that asserts something about the code** — a guard-proof table row, a `package.json` script entry, a pre-commit chain entry, a test fixture, a CI job, a ledger entry. Docs are the commonest thing a slice falsifies, not the only one, and an enforcement artifact left behind is worse than a stale paragraph: it keeps *asserting* something the tree no longer supports. And for those, **find every declaration, not the first** — an enforcement chain is routinely declared in more than one place, and stopping at the first hit leaves the rest silently pointing at something that is gone. *Observed: deleting one temporary check meant removing its script entry, its pre-commit chain entry, its fixture, its guard-proof table row and a paragraph of testing docs — and that chain was declared in four places, so removing the one the first search found would have left three referencing a deleted file.* **Scoping a doc OUT is a claim you are making from the plan rather than from the diff** — record it as an explicit not-affected-because in the slice, so the implementer can overturn it when the code says otherwise, instead of inheriting it as settled. For an item **beyond** the horizon, record only that it has docs to falsify and in which area — naming the file is grounding, and a doc set is moved and rewritten by an arc exactly as its code is. **In an epic this bullet does not move — only the edit does.** You still name the docs slice by slice, right here, because the forcing function is that the implementer is the only party who knows what its change actually falsified; what changes is that the slice's deliverable becomes an entry in the epic's **falsification ledger** rather than the rewrite, and one closing docs slice consumes the ledger against the final tree — **except the coordinate case above, which ships with the slice that moved the path rather than going to the ledger.** `skills/execute/SKILL.md` → *The epic branch* → *Docs land at the end* owns that mechanism — including the ratchet that keeps it from decaying into deferred docs, and the carve-outs; `Owns` (Step 3) and the wave map (Step 4) are where it shows up in your breakdown.
- **Then ask which existing assertions depend on the value being produced at the site you are changing — and answer it by reading that site's CALLERS, never by grepping.** The falsification bullet above already reaches tests, in its *everything else that asserts something about the code* clause, and **the methods it carries structurally miss this one**. A test has no reader whose beliefs you can interrogate, so the prose half has nothing to ask; and the grep half is not merely empty here but actively misleading, because the assertion that breaks names nothing the slice introduces — it names a shape that **survives on the type and simply stops being populated at that site**, so the search returns every legitimate use of that shape with nothing in the result distinguishing the one assertion that will go undefined. What does answer it is a question you can only ask cheaply while you are already standing in the file: **who consumes what this site produces, and which of them asserts on it?** Read the callers, and put the test files that come back in the slice's `Owns` — with the disposition written down — *the assertion moves here*, not *build here* — rather than left for the implementer to infer from a path in a list. **They belong in `Owns` and not in a field of their own, because `Owns` is the files the slice is allowed to CHANGE and never the files it opens to do the work** — a test whose expectation this change invalidates is a file the slice must change or leave lying, which is the same relation a falsified doc has and is already scoped that way. *The failure this prevents, observed: a slice moved a value from one channel to another, named its six source files and their test siblings correctly, and two hand-written tests in a different tree read the shape it had stopped producing. Every safeguard in front of the gate is blind to that by construction — the divergence tick watches the files a slice edits and these are precisely the ones it does not edit, and the implementer is banned from whole-suite runs, so the widest instrument it holds is one test file at a time. The gate caught it, which is the gate working; what it cost is that the verdict lands after the run is over, and the same slice paid it twice, because the fix could only be dispatched once the first gate had finished.*
- **Then sweep for the artifacts a REGENERATOR owns, so `Derives` (Step 3) is populated from the repo rather than from memory.** That field is consumed downstream — by the slice, by the dispatcher before it gates the merged tip, and by the loop's reconcile — and **this sweep is the only thing that puts anything into it**, so skipping it does not leave the field visibly empty: it leaves it filled from whatever you happened to remember, which reads exactly like an enumerated one. Half of this is mechanical, and it works off what the repo already declares about itself: a `package.json` script that writes a file **into the tree** rather than into a build directory; a checker with a `--write`/`--update` mode; a pre-commit or gate chain entry that regenerates something; and a generated file `.gitignore` does **not** list, which is the tell that it is committed and therefore driftable. **The other half is the falsification bullet's own question pointed at checkers instead of readers — *which artifact currently asserts something about the tree that this slice makes false?*** — and that is what catches the generated file no script names, because its regenerator is a test. *The failure this prevents, observed: a ratchet-style JSON regenerated from the whole tree was fed by a slice whose breakdown never named it, and it surfaced only because the implementer volunteered it in its hand-back — a channel with nothing behind it. An unnamed derived artifact errors nowhere: not at grounding, not in the slice, not in that slice's own gate. What it produces is a committed file that is correct on neither branch, which is the exact state `skills/orchestrate/SKILL.md` §3's derived-state item exists to catch* ***after*** *the fact.*
- **Read `AGENTS.md` and the per-project config** (`<repo>/.agents/worktree.json`, where `<project>` is the repo's directory name — the same config `/pipeline:execute` reads). They tell you the **framework skills** to invoke per area, the **gate**, the **compat policy**, and comment/style conventions. Bake these into each slice so the dispatcher (and its implementers) inherit them. **If there's no config, that is a hard stop rather than a note.** `/pipeline:orchestrate` §2's *Before the loop: the config precondition* owns it and `skills/setup/SKILL.md`'s *Why an unconfigured repo is worse than an obviously-broken one* carries why. Where you are invoked directly rather than from that loop, say so and stop: grounding slices against an unconfigured repo produces briefs whose implementers fail inside a bare worktree for reasons shaped like code defects. *The failure this prevents: this bullet used to say to note it and carry on, which is the opposite instruction to the one `setup` states as a hard stop — two shipped skills disagreeing about the same observable state, with a reader following either one compliant.*
- **Discover the integration branch**, don't assume it. `git branch --list 'release/*'` / the current branch — slices target the active integration branch, never `main`, never a hardcoded version. (If Step 4 concludes the epic warrants an **epic branch**, the slices target that instead — but it is cut from this branch, so you still have to find it.)

**An enumeration is a claim, and its cardinality is part of it — so take the count from the command that filtered nothing.** Every bullet above is answered by running something, and the lists those runs return become a slice's scope: the consumers a change ripples into, the declarations of an enforcement chain, the callers that assert on a site, the files a predicate names. **The defect is that a set has nothing in it to say it is short.** A truncated enumeration is internally consistent — real files, in the right format, reconciling with every other field the slice carries — so Step 3's closing check reads it as sound, because that check compares a brief's fields against **each other** and this one is wrong against the **tree**. **The rules this corpus already states that come nearest do not reach it — and being precise about why is what makes this a distinct rule rather than a third copy of one of them.** `skills/write-issue/SKILL.md` Step 1's *Grep the WHOLE repo and cite the definition line* fixes the **domain** — the grep that ran under `src/` when the thing lives under `server/` — and `grep -rn '<symbol>' . | head -8` obeys it exactly: the domain was the whole tree, and all eight cited lines are real. Its citation half is what makes a **single** claim checkable, and there is no definition line for eighteen consumers, so it has nothing to attach to a set. `skills/execute/SKILL.md` → *Gate the integrated whole*'s *capture the gate's OWN exit status, never a pipeline's* is the same defect class one artifact over, and its remedy is a **status an enumeration does not have** — that pipeline exits 0 on eight hits and on eighteen alike, so there is nothing to redirect and nothing to quote. So: **count first and print untruncated** — `… | wc -l`, then the set itself with nothing between it and you — and **write the number down beside the list in the slice**, because a count is the only thing you can put in a set that makes a short one visible as short. Never `head`/`tail` the set itself. **And an empty result has three readings, not one**: no match; a command that failed with its error suppressed, which is why `2>/dev/null` is *banned* on a search rather than discouraged; and a search that never ran at all — a regex the engine rejected, a glob the shell ate, a printer that truncated each line before the match. Read the exit status and the stderr before you write *no consumers*. **And exclude the query from its own answer** wherever the command can see itself: a process match on a pattern that also matches its own command line reports back exactly the thing it was sent to look for. `scripts/check.sh` already holds its own checks to this half mechanically — every check that scans a set asserts the set is non-empty before it scans, because an empty scan prints the same green as a passing one — so the repo has already paid for the reasoning; what it never did was ask the same question of the party writing the brief. **And this constrains how you read whatever you ran — it is not a licence to reach for a grep where the bullets above send you to read instead.** **`Owns` (Step 3) carries this failure inverted, and the pair is the point**: there, a brief kept a query's cardinality and threw away its members (*40 references, find them, they are yours*); here, it keeps the members and throws away the cardinality. The list and the count ship together, or neither is worth much.

*The failure this prevents, observed five times — four in one arc, and every one of them silent. `head -8` on a consumer grep reported eight consumers of eighteen and hid a second PRODUCTION consumer, so a cache invalidation was one implementer's scepticism away from shipping with a live un-invalidated path. `tail -20` on a twenty-one-line diffstat cut the last file and made a lint-exclusion list read as regressed. `2>/dev/null` on a failing `git show` produced a clean false negative, because a suppressed error is indistinguishable from no match. A process pattern matched its own command line and reported processes in a worktree that had none. And a reviewer searching this very corpus for a rule concluded it did not exist and sent a slice back on that basis — the rule was the closing sentence of a long bullet, past the point where the printer in use truncated each line, and several of that reviewer's regexes had failed outright with complexity errors that read as "no match" rather than as "the search did not run"; the implementer falsified it in one search. Nothing errored in any of the five, and that is the whole mechanism: a truncated list, a suppressed error and a search that never ran are byte-identical to a complete, clean, empty result.*

## Step 2 — Validate the plan and fill the gaps

Grounding (Step 1) almost always surfaces holes: behavior the plan never specifies, a design fork it leaves open, missing acceptance criteria, scope that's ambiguous about what's in vs. out, a constraint that's implied but never stated. **A breakdown is only as good as the plan under it — slicing a plan with holes just buries the holes inside slice briefs where an implementer hits them mid-build.** So before you slice, validate that the plan is complete enough to slice, and close the gaps.

**Fill what you can yourself — that's the job, not a shortcut.** Most gaps are resolvable from the grounding you already did: the codebase already has a pattern to follow, `AGENTS.md`/config already dictates the convention, the pre-launch/forward-only posture already settles a "do we migrate?" question, or there's a plainly obvious default. When a gap has a sensible answer, **adopt it and write the assumption down explicitly** in the affected slice's brief (`Assumes X (existing pattern in <file>); flag if wrong`) rather than interrupting the user. Filling gaps with grounded, stated assumptions is exactly "do its best to fill in gaps."

**Escalate to the user only the gaps you genuinely can't resolve** — the ones where (a) there's no obvious default, (b) guessing wrong would change the slicing or send an implementer down the wrong path, and (c) the codebase/conventions don't settle it. A product decision ("should deleting an org cascade-delete its projects or soft-archive them?"), a real design fork with no house style, an undefined acceptance bar on something that gates other slices — those are worth a question. Don't ask what you could answer by reading one more file or picking the conventional default.

**Hold a question to the same bar as an issue — a question handed up is a deferral wearing different clothes.** The bar above is the one `skills/orchestrate/SKILL.md` §4 applies to a reconcile finding before it is filed, and it is the same act reached from a different direction: both hand a person reasoning the run was standing in the best possible place to do, with the tree open and the grounding already paid for. Read §4 there rather than here — including the rule that gates it, that you establish *why a thing is the way it is* before you disposition it, which is what turns "I can't resolve this" into a claim you have actually tested. *The failure this prevents, observed in one run: two questions went to the user that were each a few greps from an answer, while the same run filed issues under the same misreading — so both of the flow's channels to the user were running below the bar, and neither could see the other doing it. Holding only one of them to the bar just moves the traffic to the other.*

**When you must ask, ask in plain chat — ONE question at a time.** No option-picker dialogs, no batched wall of questions. State the gap, give your recommendation and why, and ask the single most decision-blocking question. Wait for the answer, fold it in, then ask the next one only if it's still open after that answer (answers often resolve several gaps at once). Order questions by blocking impact — the one that most changes the slice shape first. This keeps the prep conversational and lets the user redirect early instead of reacting to a form.

Only once the plan's decision-blocking gaps are closed (filled-with-assumption or answered) do you move on to slicing. If the user is unavailable and a gap is non-blocking, proceed with the stated assumption and mark it; don't stall the whole decomposition on a minor open question.

**Validate the horizon; past it, validate only what changes the shape.** A gap inside the increment you are about to dispatch blocks now. A gap three waves out blocks only if it moves a wave boundary, changes the epic-branch answer, or creates a seam — everything else waits for the cycle that grounds it. *The failure this prevents: this pass runs once per increment, so a bar set slightly too wide multiplies — eight cycles of one avoidable question each is eight user turns spent on forks the intervening increments would have settled or made moot, and every one of them teaches the user that the loop cannot be left to run.*

## Step 3 — Slice the horizon into independent tasks

One slice = one worktree = one PR. **Optimize for independence**: the more slices that can run concurrently without touching each other's files, the more the dispatcher parallelizes. Aim for slices that are *cohesive* (one logical change) and *isolated* (own a disjoint set of files).

**Everything this step produces is *slice depth*, and slice depth is for the horizon only.** Produce the whole field set below for every item inside the horizon. Outside it, an item carries what **shape depth** allows — goal, area, what it depends on, and one line on why it comes after the thing before it — and **none of the grounded fields**: no branch name, no owned files, no do-not-touch boundaries, no derived artifacts, no framework skill, no model tier, no brief, no verify bar. At that depth it is a *finished* item, not a slice you ran out of time to write.

*The failure this prevents runs in both directions, and both directions are silent. A beyond-horizon item written at slice depth carries owned-file lists and boundaries that a later wave invalidates before anyone reads them — the stale-coordinate failure Step 1 names. A horizon item left at shape depth gets dispatched with no owned files and no do-not-touch boundary, so the implementer invents its own scope, and the first anyone hears of it is a PR in a sibling slice's core files, by which point the sibling has already forked.*

For **each horizon** slice, produce:

- **Title** + **branch name** with the right prefix (`feat/…`, `fix/…`, `refactor/…`, `docs/…`). Flag a docs-only slice for `execute`'s ticket-scoped `--mode docs` gate (its *Gate mode*) instead of a branch-prefix fast path — that mode is set on the ticket at enqueue, never inferred from the branch name.
- **Owns (scope)** — the concrete files / globs / directories this slice is allowed to change. Real paths from your grounding, not guesses. **And a predicate is not a scope until it has been evaluated.** This field admits two very different things: a named list (`src/a.ts`, `src/b.ts`), and a predicate — *every caller of `<helper>`*, *every module that re-declares this type*. A predicate's file set does not exist at decomposition time; it is discovered by the implementer, in its worktree, after dispatch. So there is nothing for you to check a sibling's named list against, and `Do NOT touch` cannot close the gap either, because it would have to name an intersection nobody has computed. **Run the query while you are grounding and write down the files it returns**, then check that list against every sibling's `Owns`. Where evaluating it is genuinely impractical, the alternative is to declare the slice **exclusive over that predicate's whole domain** and give no sibling a named file that could fall inside it — never to ship the predicate as the scope and hope. *The failure this prevents, observed: one slice got a named list, a sibling got "every caller of `<helper>` — 40 references, find them, they are yours", and both edited the same file. Neither diverged, both were exactly in-brief, and the decomposition was wrong. The brief even carried the count, so the query had already been run and only its cardinality kept — listing the forty was one command. It is silent in every channel a dispatcher watches: nothing errors, the divergence tick sees two agents each inside its own brief, and the first sign is two diffs landing on one file at merge, where whoever resolves it has to reconstruct two slices' intentions from hunks rather than from the briefs that produced them.* `Derives` below is the same blind spot from the other end — scope that is not the file list in the brief: there because the decomposer never wrote it down, here because it wrote it down as a question instead of an answer. **This includes the docs the slice falsifies**, named individually — plus, for any doc you considered and left out, a one-line not-affected-because. An implementer told a doc is out of scope will not revisit it, so an unexamined omission ships as a decision. **It also includes the tests Step 1's caller sweep came back with**, the ones whose assertions this change invalidates, each carrying its disposition. *The failure this prevents is a misreading of this field's own name: `Owns` sounds like the files the change forces you to open, and under that reading a test the slice never opens and must nonetheless change has no field at all — so it goes unnamed, and every instrument in front of the gate is watching the files the slice does edit.* **On an epic the docs stay named here and MOSTLY leave the slice's edit scope** — the deliverable is the ledger entry and the closing docs slice owns the file — **except a structural coordinate the slice moves, which is back IN edit scope**: a file path, or a route literal in the same clause as one, is repointed by the slice that moved it, because a checker can tell it is stale without reading the sentence (`skills/execute/SKILL.md` → *The epic branch* → *Docs land at the end*, which carries the argument and the carve-outs). So a named doc on an epic carries one of **three** dispositions, not two — ledger entry, coordinate fix, or both against the same file — and you write down which, rather than leaving the implementer to infer it from a path in a list. *The failure this prevents: "in `Owns`" and "out of `Owns`" no longer partition the question, so a doc listed with neither disposition reads as whichever one the implementer already expected — and both wrong readings are silent. Read as ledger-only, the slice cannot pass a gate that validates path citations; read as edit-scope, it rewrites the paragraph the closing slice was going to.*
- **Do NOT touch** — files another slice owns, or that a foundational slice will change. These are the collision guards that let slices run in parallel safely; name them explicitly. **A boundary fences BEHAVIOUR, not coverage** — a fence goes up around production code the slice must not widen, reimplement or land inside, while a verify bar routinely needs the *test* file sitting beside that code, in the same directory the glob names and often the only place the assertion can honestly live. Neither instruction is wrong alone; the contradiction exists only at the one file, and this pair is the worked example of the closing check at the end of this step. Two rules make it mechanical. **A directory or module glob covers production behaviour and does NOT imply the tests under it** — a fence that means to take the module's test file with it has to say so in words, because a glob that silently swallows coverage turns every verify bar reaching into that module into an unresolvable brief. **And whenever a verify bar asserts something about a module the slice does not own, say in the fence which way the tests go**, rather than leaving the default to be relied on. Where the assertion genuinely belongs to the fenced module *and* the slice must not own it, that is not a fence to soften: it is a seam, and the assertion belongs to the slice that owns the module or to a later wave — say which. *The failure this prevents, observed: a slice's brief fenced off a directory, correctly — the slice's whole hazard was that it might widen a security boundary defined in there rather than land inside it — while the same brief's verify bar required a test asserting that boundary still covered what the slice produced, and the natural home for that test was the fenced directory's own test file. An implementer meeting that alone has three moves and two are silent. Skip the test and the verify bar evaporates, with the slice reporting every other part of the bar met and nothing marking the part it dropped. Breach the fence and it does the exact thing the fence existed to prevent. The third — parking the assertion somewhere else — is the one that looks most like compliance and can be worth nothing, because an assertion placed outside the module it is about is exactly as green as one placed correctly. Nothing errors in any of the three, and a diff read afterwards cannot tell a verify bar that was dropped from one that was never load-bearing.*
- **Derives** — the artifacts this slice's change feeds into whose correct contents are a function of the **whole tree** rather than of any one slice's files: a ratchet ledger, a backlog JSON a checker regenerates, a generated type, an unimported-exports manifest. `Owns` and `Do NOT touch` are both file lists, and between them they cover exactly the collisions git can show you. A derived artifact is the case git structurally cannot: two slices edit disjoint sources, each is individually correct, and the shared artifact is right on neither branch — and it merges clean, because there was never a textual conflict to stop on. So name the artifact here — Step 1's regenerator sweep is what finds it, and this field is populated by nothing else — and hold the slice to one rule: **a slice may not treat a derived artifact as final.** It runs the project's own regenerator where there is one, it *reports what its change did to that artifact* either way, and the **dispatcher re-derives it on the merged tip before gating** (`skills/execute/SKILL.md` → *Gate the integrated whole*). *The failure this prevents, observed: a slice converting an exported `interface` into an inferred type removed an anchor a duplicate-detector scans for, while a sibling slice was simultaneously changing that detector's rules and owned its backlog ledger. Both green in isolation, neither merge conflicted, and the ledger was correct on neither branch.* `skills/orchestrate/SKILL.md` §5's shared **runtime string** — where "the bad merge does not fail to compile at all" — is the same family reached from the other end; read it there. Two things make this its own field rather than a case of that one: what is shared is a derived **file** rather than a **value**, and it belongs to a slice's **scope** rather than to where the work is placed in a wave.
- **Depends on** — which other slices must merge first (or "none — independent"). This is what builds the waves below.
- **Skill to invoke first** — the framework skill the implementer must open with (from `AGENTS.md`/config). For Trinity the split is **app = `frameworks:solid`, sidecar = `frameworks:effect-v3`**: a slice with SolidJS UI (`solid-js`, `@solidjs/router`, `@tanstack/solid-query`, Kobalte) opens with the `frameworks:solid` skill; a slice with Effect-TS on the sidecar (services, layers, HTTP routes, typed errors) opens with the `frameworks:effect-v3` skill; a full-stack slice invokes both; a pure-docs/config slice, none.
- **Model** — `sonnet` (default: well-scoped, mechanical, mirrors an existing pattern) or `opus` (reserve for genuinely hard: subtle algorithms, ambiguous/design-heavy, tricky concurrency/lifecycle, security-sensitive, large cross-cutting). One line of *why*. Remember: the easier the model, the more explicit the brief must be — Sonnet slices need near-deterministic steps and exact files. **Then apply the predictor that catches what the list cannot, because that list is a list of things that *look* hard: does the slice touch something declared, or enforced, in more than one place?** If it does, the work is not the edit — it is adjudicating a disagreement between two sources of truth that nobody has yet checked agree, and that wants the stronger model however small the diff looks. *The failure this prevents, observed: the most dangerous slice of a three-day run matched none of the categories above and read as the most mechanical work on the board — point four imports at a shared schema instead of an inline one. The two disagreed, the shared one was the weaker, and the obvious execution of that slice would have silently removed strictness from three live HTTP routes.* Diff size does not predict difficulty; the number of places the truth is stated does.
- **Brief** — 2–5 sentences the dispatcher can hand almost verbatim to an implementer: what to build, the existing pattern/file to copy, and the hard boundaries. Include any research-first step. **Point at the source, never at your conclusion about it.** Write *read the route handler and use the schema it parses the body with*, not *use `FooRequest`*: the second is unfalsifiable from inside the slice, because an implementer cannot tell a name you verified from one you inferred. *The failure this prevents, observed twice in one run and caught both times only because those briefs happened to send the slice to the source: a brief called a hand-written parameter type known-good and out of scope, where the handler actually parsed the whole body with one discriminated union and the type was narrower than what the route accepts; and a brief grouped three fields as "declared `unknown`, so the builder asserts the narrowing" when one of them was already precisely typed and its cast was covering a readonly-to-mutable variance mismatch — following that brief literally would have pushed a cast into two real callers, which is the exact trap the same brief warned about one paragraph earlier. Neither was labelled an assumption; both read as settled fact, which is exactly what made them dangerous.* **And a claim lifted from a dependency's own documentation or generated output is an INPUT to grounding, not a grounded coordinate.** The two above are your own inferences about this repo; this one arrives already written down, by an author describing every repo there is. A vendor doc, a generated header, a caveat block emitted into a package directory — each states the **general** case, hedged across the configurations it has to cover, while your brief states the **local** one. So settle which branch of that hedge this repo is on before the claim goes in: run the path, list the directory, read the config that decides it, and write down what you found rather than what the vendor said. Where you genuinely cannot, it goes in as `Assumes X; flag if wrong` — never as a coordinate. *The failure this prevents, observed: a brief transcribed a monorepo caveat out of a dependency's own generated output — that the package's version-matched docs may not resolve from the repo root — and asserted it as this repo's layout. A hoisted package manager had put that dependency at the root, so the path resolved exactly where the brief said it would not. This is the hardest of the three to catch, because it reads as the best kind of citation: sourced, quotable, and about somebody else's repo. It reached the implementer, which is the last line of defence rather than the first, and only that implementer going to look kept the false claim out of the doc it was writing — the gate would have been green either way, because a premise is not a thing a gate can test.* **And where the prose you are briefing about SHIPS to other repos, cite it by path.** The two above are about whether a claim is true; this is about whether the reader has the referent at all. In a shipped, project-agnostic file a bare `README.md` or `AGENTS.md` names the **reader's** repo, not yours — so such a sentence may **instruct** (*consult your repo's own doc set*) and may never **cite** (*this corpus argues X there*), because the second is true in the repo that wrote it and false everywhere it is read. A repo whose prose does not ship is unaffected and nothing here asks you to change how it writes; where it does ship, that repo's own conventions carry the full rule and this is the trigger that sends you to them. *The failure this prevents, observed: a decomposition comment and the slice brief written from it told an implementer to point a warning at two places a rule is argued — one a `skills/…` path, the other "`README.md`'s worktree-layout paragraph". The implementer wrote both as instructed and caught the second in its own review pass. Nothing else in the flow would have: the citation resolves perfectly from the checkout that wrote it, so it is not a coordinate any later reader can find failing.*
- **Verify** — what "done" looks like: the behavior, the tests to add/touch, the acceptance check. **For any slice that adds a check or fixes a bug, that bar includes proving the new test fails against the PRE-change code** — and name the specific reversal that proves it: restore the old matcher and confirm the new fixture goes red, point the test's mock back at the old symbol and confirm it fails loudly, reverse the rename and confirm the formatter reproduces the original byte for byte. A bare "confirm it fails first" is a step an implementer can report having done with nothing behind it, which is why the reversal is named here rather than left as an instruction. *The failure this prevents: a test that passes both before and after proves nothing, and in a green run it is indistinguishable from one that proves everything — so the slice reports success having verified nothing, and the check it added stands as evidence for the rest of the arc.* **When the bar asserts agreement with a consumer the slice does not own — a library, a compiler, a runtime matcher, a separate process — name the INSTRUMENT as well as the property, and make the instrument the entry point the production caller actually reaches.** A bar that names only the property leaves the instrument to the implementer, and the cheapest instrument that satisfies it is a faithful-looking local reimplementation of the consumer, usually assembled from a general-purpose library — which is indistinguishable from the real thing right up until the day their semantics differ, which is exactly the day the test was supposed to fire. **A stand-in is allowed where the slice names it as one and justifies it; it is never the silent default.** Be precise about *entry point* rather than just *real code*, because it cuts both ways: calling the consumer's own matcher directly, below the preprocessing its callers go through, reports coverage the real pipeline does not provide, so a stand-in can invent a boundary as easily as hide one and only driving input through the production entry point separates the two. **And here the reversal is two-sided, because the producer-side one structurally cannot reach this.** Breaking the producer reds a test whose consumer is a stand-in exactly as it reds a correctly-wired one — it proves the test is attached to the producer and says nothing whatever about the other end. So name the consumer-side reversal too: break, stub or swap the consumer and confirm the test goes red. *The failure this prevents, observed: a slice was told to prove a boundary held, with the property named explicitly — match the way the real consumer matches, not by string equality or prefix — and wrote a faithful local reimplementation of the consumer's matcher. The real one's semantics differed, and it also preprocessed its input in a layer above the matcher, so the test passed on a boundary that was not there. Two later slices extended that same suite, both green, before one replaced the stand-in with the consumer's own exported functions and the hole appeared immediately.* **A whole-package or whole-suite check named here is the RUNNER's to execute, never the implementer's.** When the bar names the gate it is fixing the ticket's **gate mode** — the full gate, or a project's lighter prose one — which `skills/execute/SKILL.md`'s *Gate mode* establishes as a property of the ticket, set at enqueue, rather than a command anyone types in a worktree; write it that way (*gate in the default mode, not `--mode docs`*), not as a command line. **The only check an implementer may be told to run directly is a single targeted test file.** Route anything wider through the project's cached runner (Trinity: `pnpm check`, or `turbo run <task> --filter=<pkg>`) and never a raw `vitest`/`tsc`/`eslint`, since a direct-binary run bypasses the shared cache and goes cold — but that is routing for whoever runs it, which on a default-mode slice is never the implementer. *The failure this prevents, observed twice in one arc: the bar is pasted into the dispatch brief close to verbatim, beside the block banning whole-suite runs by any invocation and the handoff block saying the runner gates after you enqueue, so a bar reading "Run the FULL `pnpm gate`" contradicts two of the three statements around it. One implementer flagged the contradiction and adjudicated it correctly; the other resolved it silently and handed back a clean run, leaving nothing in the record to tell the next decomposer the bar had been ambiguous. The branch neither took is the expensive one — an implementer that simply obeys runs the gate in the foreground, which is the saturation the machine-wide slot exists to prevent and, per `execute`'s own note on backgrounding a banned run, the classic stall shape.* **A bar that asserts a NEGATIVE names what it is measured against.** *X is unchanged*, *no new Y*, *that grep comes back empty* are claims about a **difference**, and a difference has two ends — a bar that states only one is satisfied by whichever other end the implementer picks, and the nearest one to hand is its own previous commit, which sits **inside** the change being asserted about and so returns true whatever the change did. Name the baseline, and make it the **fork point** unless you name a different one. A sweep is the well-formed exception rather than a counter-example, because it names its **domain** instead — `skills/orchestrate/SKILL.md` §8's bare-string rider greps the old literal across the whole tree and proves either zero hits or that every survivor is deliberate, which is checkable with nothing to compare against. A bar that names neither is the defect. **And where the honest claim is narrower than the bar's phrasing, write the narrow one** — *unchanged for a caller who has not opted in*, not *unchanged* — because an implementer that finds the broad claim false has two moves, overturning the bar or quietly narrowing it, and `skills/execute/SKILL.md`'s *A brief that contradicts ITSELF* establishes which of those is silent. *The failure this prevents, observed: a bar required a frozen helper contract untouched, its stdout lines included, and the implementer reported that line set byte-identical to its own previous commit — true, and carrying no information, because the commit it was compared against was itself part of the change under review. Against the fork point the diff added seven such lines. Every one sat inside an opt-in branch, so the contract really was intact for a caller who had not opted in — but that is the precise claim, and it is neither the one the bar asked for nor the one that was made. Nothing in the run could tell the two apart; it was caught a slice later by a changelog author who happened to re-derive it against the base.*

**Sizing.** A slice should be a meaningful but reviewable PR — not so small that the worktree/PR overhead dominates (fold trivial bits into a sibling), not so large that it owns half the repo (split it, and the split usually reveals a foundational sub-slice). When two candidate slices can't avoid heavy file overlap, either merge them into one slice or sequence them across waves — don't pretend they're parallel.

**The gate-cost economics (size against the gate, not against an idealized infinite machine).** Every slice becomes a PR that must be gated. Implementers don't run the gate — they enqueue it, and `/pipeline:execute` drains the queue, running `gate` **one PR at a time** behind a slim machine-wide slot (Trinity: `pnpm gate`). So the gate still **doesn't parallelize**: N slices = N sequential drained gate runs, and a wave of 8 tiny slices can burn far more total drain (plus 8 reviews) than the 4 cohesive slices the same work would have gated in. This cost never *strands* anyone — implementers enqueue and hand back rather than blocking on the gate, so fan-out width is bounded by genuine independence, not by the gate — but total gate + review time still scales with slice count. The lever isn't "minimize slices" or "maximize slices" — it's **make each slice carry enough weight that its share of the gate cost is justified.** Concretely:
- **A gate run's cost is proportional to what the slice CHANGED, not a flat number — because of the shared build cache.** Trinity's gate runs through a task-runner (turbo) backed by a shared cache, so a drained gate *replays* every package the slice didn't touch near-instantly (a cache hit — even in a fresh worktree, even if another checkout built it) and only rebuilds + retests the packages the slice actually changed and their dependents. Two sizing consequences fall out of this:
  - **Prefer package-disjoint slices.** A slice confined to one leaf package gates cheap (only that package and its dependents rebuild; everything else replays). Slicing along package boundaries keeps every gate in the wave cheap *and* keeps the slices genuinely independent — the cache rewards the same disjointness the parallelism does.
  - **A slice that touches a low-level shared package gates expensive** — it invalidates every dependent, so its gate rebuilds a large fan-out no matter how small the diff. That's a reason to keep such foundational edits in a *tight Wave-0 slice* (gate the expensive rebuild once) rather than smeared across several slices that each re-pay the full-fanout rebuild. And many slices all churning the *same* hot package don't share cache with each other (they forked independently), so each re-pays that package's cold rebuild — another pull toward disjoint packages.
- **Fold sub-PR fragments.** If a candidate slice would gate in a couple of edits (rename, a one-liner, a single test), it does not deserve its own worktree+gate — fold it into the cohesive sibling it's closest to.
- **Bound wave width to the gate, not to the file-independence.** Two slices being *independent* doesn't mean they should both run if a third cohesive slice could absorb one of them; with a serialized gate, a narrower wave of heavier slices often finishes the whole wave sooner.
- **When you catch yourself splitting for "cleaner boundaries" alone, stop.** Boundary aesthetics are not worth an extra full gate. Split only when the slice is genuinely too big to review *or* the split removes a real merge collision.
- **File-disjoint is not independent when the slices share a resource that lives outside the worktree — and this is the one entry here that can make the right wave width ONE.** Everything above prices parallelism in gate *time*; this prices it in correctness. A worktree isolates the filesystem and nothing further, so two slices that touch no common file still contend for the same database, Redis instance, cache directory or fixed port the moment their checks run at once. Read `sharedResources` in the project's `.agents/worktree.json` (`skills/execute/SKILL.md` → *Per-project config*): an entry with `"isolatedBy": null` says that resource stays shared, and the key **missing entirely** says nobody has been asked, which is not an answer and is not a no. **And do not assume the drained gate covers it** — the machine-wide slot serializes *gates*, so what it never sees is every implementer's `scopedCheck` and targeted test file, which run concurrently by construction; in a project that declares no queue the slot does not exist at all. So where a resource stays shared, size the wave against the resource rather than against the files: one live slice touching it, and the rest sequenced across waves. *The failure this prevents: the contention is invisible in the plan and misattributed at the gate — it lands as a red in whichever slice lost the race, on a diff that is innocent, which reads as a code defect and gets debugged as one. A decomposition that calls two such slices independent is wrong in the one direction no gate can correct, because every gate involved is telling the truth about the tree it ran.*
- **Gate once on the merged tip and the binding constraint moves — to the dispatcher's own capacity to read N diffs.** Everything above sizes against a gate drained one PR at a time. An epic that converges on an epic branch and gates as a whole (`skills/execute/SKILL.md` → *Gate the integrated whole*) barely pays that per-slice cost at all, so the gate stops being what bounds the wave — and what replaces it is review. The number of slices such a run would tolerate on gate cost alone is well above the number at which careful diff review stops happening, so size that wave against the reading, not against the drain. *The failure this prevents: removing the serialized gate removes the only bound anyone was measuring, and the wave then grows until the reviews are skimmed — in a flow where a green gate cannot tell whether the agent solved the right problem, the diff review is the only thing standing between a green slice and a wrong one.*
- The *scoped* per-commit check implementers run (Trinity: `pnpm check` — fast, unlocked, parallel) is NOT the sizing cost; the **drained full gate** is. If a project's full gate is genuinely cheap, well-cached, or parallelizable, this pressure relaxes and you can fan out wider — so always size against the *actual* `gate`, cache, and drain model you read in config, not a default assumption.

**Before you emit a slice, read its fields against each other — as these four PAIRS, never as a general check of your work.** Every field above is written for its own reason, **nothing downstream reads any two of them against each other**, and you are the only party who ever holds all of them at once. So a slice can be internally unsatisfiable and still look finished from every other seat: the implementer meets one field by breaking another and reports the half it met, no gate can read a brief, and a diff afterwards cannot tell a requirement that was dropped from one that was never load-bearing. The pairs are named because a rule stated over "the field set" is a check-your-work instruction: nothing distinguishes a decomposer who ran it from one who merely felt careful, so it costs nothing to claim and nothing to skip. Naming the pairs is what gives it the same teeth the fence half already has.

- **A fence against the verify bar** — `Do NOT touch` against `Verify`. The worked example, and the one whose failure is sharpest: a glob and an assertion that both land on the same test file. The `Do NOT touch` bullet above carries the two rules that settle it, and this pair is what they are for; read them there rather than here.
- **A content requirement against a style constraint** — two halves of one `Brief`, or a `Brief` against the conventions the slice inherits. Each is satisfiable alone and they sit in different sentences, so the contradiction exists only in the pair, and only for as long as somebody is holding both.
- **Any requirement against the vocabulary the target actually has** — the pair nothing structural catches downstream. A brief can demand a distinction the target has no way to express: a chapter told to say which consumer a rule is for, in a corpus whose pages never name their readers. That is not a style question, it is a **satisfiability** one — no wording satisfies it, so the implementer either invents vocabulary the medium does not have or drops the requirement — and it is invisible unless someone asks whether the thing being demanded exists in the medium at all. You are the party positioned to ask, because grounding is the last point at which the target was actually read.

*The failure this prevents, observed: a brief for one chapter of a shipped prose skill required that, where a rule differs by consumer, the chapter say which consumer it is for — and, in a different section of the same brief, banned the pipeline's own planning vocabulary. No page in that skill names its readers anywhere, so the words for "which consumer" did not exist in the corpus, and satisfying the first requirement meant breaking the second. Both read as reasonable, neither was a fence, and nothing in the flow compares them. It surfaced only because the implementer chose to raise it: it wrote the requirement situation-shaped instead — a form with nothing behind it is still a form, so what is absent is the request rather than the states around it — which reaches the same reader without naming one, and flagged the conflict in its hand-back. Nothing structural produced that. An implementer satisfying the literal instruction would have introduced reader-class vocabulary into shipped prose, and the style violation would have been the only visible symptom, in a repo where no gate can tell whether prose is correct.*

- **A derivation instruction against reachability from where the slice lives** — a `Brief` that says *derive X from Y* against the workspace position the slice's `Owns` actually sits in. This is a different failure from the vocabulary pair above, not a restatement of it: that one asks whether the target can *express* what is demanded, a satisfiability question settled by reading the target; this one asks whether the slice can *reach* what is demanded at all, settled by resolving an import from the slice's own location. The vocabulary exists, the symbol exists, the derivation is expressible — what is missing is a path from the slice to it: the wrong side of a workspace boundary, a package the slice does not depend on, a module that will not resolve from where its worktree sits. Step 1's research already establishes that Y exists somewhere in the tree, and that is exactly what makes this failure read as grounded — *Y exists* and *Y is reachable from this slice* are different facts, and only the first is checked there. **Whenever a brief says *derive X from Y*, resolve Y from where the slice lives before writing the sentence.** An unreachable derivation invites the most compliant-looking failure available: the implementer transcribes the values the derivation would have produced, the output is correct, the slice goes green, and the brief's false premise is never contradicted anywhere — `skills/execute/SKILL.md`'s *A brief that contradicts ITSELF* is where that move is named as reportable, pointed at rather than restated here.

*The failure this prevents, observed: a slice was told to derive its field set from a map on the wrong side of a workspace boundary. It did exactly that, correctly — and the premise surfaced only because the dispatcher happened to read the diff.*

## Step 4 — The parallelization plan (the part the loop steers by)

Slices alone aren't enough; the dispatcher needs the **shape of the parallelism**, and the loop needs a dependency order to move the horizon along.

**The wave map covers the whole arc; the grounding does not.** A dependency ordering names no files, so laying out waves to the end of the arc is *shape*, not grounding — and it is required rather than merely allowed, because the horizon is *defined* as the next set whose dependencies have landed and there is nothing to compute that from without it. *The failure this prevents: "never ground beyond the horizon" read as "never plan beyond the horizon" drops the wave map, and the next cycle then has no dependency order to move the horizon along — so it re-derives the arc from scratch every cycle, or moves the horizon by guess.*

Lay it out explicitly:

- **Waves.** Group slices into waves by dependency. **Wave 0** is the foundational layer that must land first — a schema change, a shared type/interface, a renamed module, a new core service everything imports. Wave 1+ are the consumers that can each run in parallel *once wave 0 merges*. Most epics have a small wave 0 and a wide wave 1. **Say which wave is the horizon** — the earliest one whose dependencies have all landed, and the only one you grounded. It is usually a whole wave and sometimes only the part of one that is genuinely dispatchable; do not promote the rest on the strength of its blocker landing soon.
- **Transient-red window.** If a wave-0 slice is a breaking foundational change (NOT-NULL schema swap, required interface field, renamed export), say so explicitly: the branch's gate won't be fully green again until every consumer migrates, and `/pipeline:execute` runs its transient-red gate semantics for the consumer slices. Flag which slices live in that window so the dispatcher reads the gate correctly instead of chasing a green exit. **Your flag is also what tells it to OPEN the window**, not merely to expect red: `/pipeline:execute` cuts a `transient-red/<epic-slug>` marker ref beside the epic branch so the project's commit-time tooling can see the window your flag describes, and that ref is the only form of the fact anything running inside a slice worktree can read. *The failure this prevents: a flag stated only in prose is read by the dispatcher and by nobody else — the slices then take the strict path for the whole epic while the breakdown, the gate reading and the merge judgments all say the window is open.*
- **Epic branch — answer it explicitly, every time, in one line — when it is yours to answer.** An epic branch is a convergence branch cut from the integration branch that an epic's slices fork from and PR into, so the shared branch never carries the epic half-finished; `/pipeline:execute` owns its lifecycle, and **you are the pass positioned to see whether it is warranted**, because you ground slices in real code and produce the seam map. **Two rules reach for one, and they answer different questions.** *Would a partial state on the shared branch be broken?* — **does any intermediate state leave the integration branch in a condition you would not ship?** If yes, recommend one — at any width from two slices up — and name the unshippable state: the two shapes are a wave-0 foundational change every consumer must follow (the transient-red case above, where the branch is knowingly red for the whole run) and a **contract seam** whose halves must land together (below), which is the same condition arriving by another route. *What does landing one change on the shared branch as N separate merges cost, whether or not each state would ship?* — **multi-slice work defaults to an epic branch**, on costs that land regardless of shippability and, for most of them, regardless of dispatch order (`/pipeline:execute` → *Two rules reach for one* carries the accounting in full, including which of them are artifacts of concurrency alone; this bullet does not keep a second copy of it). The first rule still gets answered on a multi-slice arc even though this one has already decided the branch, because it decides something else — whether the epic is **knowingly red**, which is what opens the transient-red window. Only when neither rule fires do the slices target the integration branch as usual — say "not needed" and why. Answer it either way: an unanswered question reads as "no" without anyone having asked it. **Neither rule is a slice count, and neither is a busy integration branch.** Counting slices measures how long a partial state sits on the branch, never whether it is broken — a five-slice epic that is independently shippable at every step still answers the first question "no", which is why a count can never answer it; what a count also never showed is that such a run is *operationally* free on the shared branch, and that is the second question's whole subject. So the second rule keys on **one change decomposed into slices**, not on a threshold and not on how you dispatch them: unrelated one-slice fixes running side by side are not an epic and cut nothing, and "other sessions are on that branch" stays rejected outright — near-permanently true in a multi-session shop, so as a standalone trigger it degenerates into "always". And **single-slice work never cuts one**: it has no intermediate state to leave behind, cannot churn its own base, gates the tree it produced, is one merge to revert, and has no sibling to hold a seam with. You recommend; `/pipeline:execute` cuts the branch, points the slices at it, and pays its cost (deferred conflicts, mitigated by merging integration → epic on its poll tick — mandatory, and more load-bearing now that the second rule fires on every multi-slice arc) — the same find/act split as the contract seam map.
  - **A stated instruction settles it — the rules above are for when nobody has decided.** When the user names the approach, that is a decision, not a hypothesis to check: **"do it as an epic" means the branch is decided.** Record it, read this skill and `/pipeline:execute`'s *The epic branch* for the **mechanics** — what the branch is, how it is cut, who owns its lifecycle, what it costs, and the merge-back cadence it requires — and slice against it. Do not re-run either rule to see whether the user was right. **The general form, and it is not specific to this decision: a skill's decision procedure never overrides a stated instruction — once the call is made, the skill is read for how, not for a second opinion.** *The failure this prevents, and the second half is the worse one: the user spends turns repeating an instruction they already gave, and — because this question is answered in one line inside a document that is then handed to `/pipeline:execute` and executed as written — the overruling ships. An unwarranted "not needed" points every slice at the shared integration branch when the user asked for exactly the isolation an epic branch provides, and it produces a perfectly well-formed breakdown, so nothing downstream can tell it apart from a correct one.*
  - **Reconcile the answer against the seam map you just produced.** The answer and the evidence live in one document, so they have to agree: if you wrote down a contract seam whose halves land in different waves — or a wave-0 foundational change every consumer must follow — you cannot answer "not needed" without naming that seam and saying why it does not count. *The failure this prevents: the map and the answer come out of different steps and get read as independent, so the trigger fires on evidence the same breakdown already contains and the answer still comes back "no" — a wrong call reached with every fact needed to get it right already written down.*
- **Conflict map.** Call out any pair of slices that, despite your best slicing, will touch the same file (e.g. both add a route to the same registry, both add a case to the same exhaustive switch). The dispatcher resolves these **at merge time** (merge one, then merge the other and fix the conflict) — never by rebasing. Naming them up front turns a surprise into a planned merge.
- **Shared hotspots — hoist the seam in Wave 0, don't just name the conflict.** The conflict map handles *pairs* that brush one file. But when **3+ slices must all extend the same structure** — a control loop's `tick()`, a reducer, an event handler, an exhaustive switch — that isn't a conflict to resolve, it's a **decomposition smell**. Parallel slices fork off *different* bases and each edits that structure against a different version, so the merges drift **semantically**: textually clean (git sees no overlapping lines, reports `MERGEABLE`) but behaviorally wrong — e.g. each slice adds its new case only to the sibling branches that existed *when it forked*, leaving a newer sibling silently missing it. The right move is to make the structure **pluggable as a Wave-0 slice**: land the extensibility seam first — an interface / registry / `Monitor[]` the others *register into* — so each consumer adds a self-contained module instead of editing the shared body. That converts a semantic-merge hazard into genuinely independent slices. When you can't hoist the seam (the abstraction isn't worth it, or it's already shipped inline), do both: (1) emit an explicit **shared invariant** in every touching slice's brief — the rule the structure must keep no matter who edits it (*"every parked-state branch must freeze ALL kill-clocks"*, *"every new event type must be handled in BOTH the reducer and the renderer"*) — and (2) mark the hotspot so `/pipeline:execute` reviews the *merged region semantically*, not just resolves markers. A green integration gate will NOT save you here — it only catches the drift if a test happens to exercise that exact cross-slice interaction.
- **Contract seams — who *defines* a shape someone else *consumes*.** The conflict map and shared hotspots both key on files: two slices brushing one, or several editing one structure. Neither catches the case where slices touch **no file in common at all** and still break each other, because one produces a shape the other consumes — a return type, a schema field, a tool grant, a prompt variable, a config key. The producer changes what it emits, its own gate is green, the consumer's gate is green, and the break appears only when both are on the branch. Emit a second, separate map: **producer → consumer → the shape between them.** Two seams are the ones a file map structurally cannot see: a producer and consumer in **different languages or different trees** (code defining a value that documentation or a prompt describes — nothing mechanical links them), and a seam with **no compiler between the halves** (a config, a prompt template, a generated brief). Cross-tree seams are the ones to write down most carefully, precisely because nothing else will catch them. Every seam whose halves land in different waves is also evidence for the epic-branch answer above — reconcile the two before you emit either. *The failure this prevents: a run whose slices were perfectly file-disjoint — zero merge conflicts across every worktree — and which still produced several genuine cross-slice breaks, every one of them a contract, none of them visible in a conflict map.*
- **Scaffolding is planned with its teardown, in one plan.** A temporary enforcer — a ratchet file plus the check that reads it — gets built, drained to zero across several slices, and then removed: the check, its fixture, its ledger and its documentation, all in one slice rather than a trail of partial removals. Plan both ends in the same breakdown, and **write the teardown's precondition down when you plan the build, not when you reach it**: the teardown depends on every draining slice, and its verify bar names the state that makes it legal (the ledger at zero, the last consumer migrated). *The failure this prevents runs both ways, and the first way is the one that actually happens. A teardown whose precondition lives only in the dispatcher's head lands early — an empty ledger reads as an invitation, and an implementer that finds one deletes the machinery around it while the thing it enforced is still incomplete, so the enforcement disappears exactly when the stragglers still need it. A teardown never planned at all leaves dead scaffolding behind for good, where it reads as live machinery to everyone who arrives later and gets maintained as though it were.* Observed: the pattern ran twice in three days and worked both times — and both times the precondition had to be fenced off by hand, in four separate briefs, because nothing in the plan said the teardown was a slice with a gate in front of it.
- **Don't schedule documentation of a model another slice is changing.** A slice that documents a subsystem must land *after* every slice that changes it, or it documents a shape that no longer exists by the time it merges — and unlike stale code, nothing fails. Documentation of a part of the system this epic does NOT touch is exempt and should say so explicitly in the wave note, otherwise "docs last" strands a correction that is already misleading readers. *The failure this prevents: two agents dispatched in parallel because their files were disjoint — one documenting a model, the other rewriting it.* **In an epic this stops being a scheduling caution and becomes a slice**: a closing docs slice, last in the map, depending on every other slice, consuming the falsification ledger they wrote and writing against the final tree (`skills/execute/SKILL.md` → *The epic branch*). Put it in the wave map by name — an epic whose docs are "at the end" with no slice owning them is the deferred-docs failure wearing a plan.
- **Critical path.** One line: the longest dependency chain (wave 0 → its slowest/most-coupled consumer), so the dispatcher knows where to start and what gates the finish.

Be honest about what is genuinely sequential. Inventing parallelism that isn't there (two slices that both need the same not-yet-built foundation) just makes the dispatcher stop-and-replace agents later. **Real independence > optimistic independence.**

## Step 5 — Emit the breakdown

### In-chat path — output format

Emit a structured breakdown. Lead with the parallelization plan (waves + critical path), then the horizon's slices at slice depth, then the remainder at shape depth.

**Label every item's depth, and keep the two in separate sections — never interleaved.** A reader, human or loop, must never have to infer which one they are looking at. *The failure this prevents: an unlabeled shape item reads as a slice somebody left half-finished, and both repairs are wrong. Dispatch it and the implementer gets no owned files and no boundaries. "Finish" it by grounding it and you have written exactly the stale coordinates the horizon exists to prevent. One missing label, two failures, and neither of them errors.*

Use this shape (here the arc is mid-flight, with Wave 0 already merged; on a first cycle the horizon is usually Wave 0 alone and every later wave is shape):

```
## Decomposition: <plan title>
Integration branch: release/x.x.x   ·   Epic branch: <epic-branch> (or: not needed — <why>)
Horizon: Wave 1 — Slices 2, 3, 4

### Parallelization plan (whole arc — dependency shape, not grounding)
- Wave 0 (landed): Slice 1
- Wave 1 — THE HORIZON, grounded below, dispatch now: Slices 2, 3, 4
- Wave 2 (after W1 — shape depth, grounded next cycle): Slice 5
- Wave 3 (last — the closing docs slice; consumes the falsification ledger every slice above wrote): Slice 6
- Transient-red: Slices 2–4 run against the W0 schema change (gate read per execute's transient-red rules)
- Epic branch: yes — the W0 schema change leaves the branch half-migrated until Slices 2-4 land, and a six-slice arc reaches for one on width alone regardless; slices fork from and PR into it
- Conflicts to merge-resolve: Slice 3 & 4 both edit src/routes/registry.ts
- Critical path: Slice 1 → Slice 4 → Slice 5 → Slice 6

### Horizon — SLICE DEPTH (grounded against the tree as it stands right now)

#### Slice 2 — <title>
- Branch: `feat/<leaf>`   ·   Wave: 1   ·   Depends on: Slice 1 (merged)   ·   Model: opus (subtle migration)
- Skill to invoke first: effect
- Owns: sidecar/services/foo.ts   ·   docs/foo.md: repoint the moved path (coordinate fix, ships here); §"Retention" prose → ledger entry, Slice 6 writes it
- Do NOT touch: any UI under app/ (Wave 2 owns those)
- Derives: reports/unimported.json — regenerated from the whole tree; report the delta, don't hand-edit
- Brief: <2–5 sentences>
- Verify: <acceptance + tests, incl. the reversal that proves the new test fails pre-change>

#### Slice 3 — <title>
...

### Beyond the horizon — SHAPE DEPTH (deliberately not grounded: no file:line, no owned files, no boundaries, no model tier)

#### Slice 5 — <title>
- Wave: 2   ·   Depends on: Slices 2–4
- Goal: let a user pick the retention window the W0 schema change made storable
- Area: the settings UI
- Why it comes after: it renders the field Slice 2 adds, so its shape is not decided until Slice 2 merges

#### Slice 6 — the epic's closing docs slice
- Wave: 3   ·   Depends on: Slices 2–5
- Goal: answer every falsification-ledger entry the slices above wrote, against the final tree
- Area: the user-facing doc set
- Why it comes after: each entry describes a state that is not final until the last slice merges, and the epic cannot close while one is outstanding
```

**The epic branch's name carries no mechanical meaning** (`/pipeline:execute` → *The epic branch* → *Mechanics*), so that slot takes the real branch name rather than a convention — and the one thing worth choosing for is that it does not read like a slice branch. *The failure this prevents: an epic branch named `feat/…` is indistinguishable in a PR list from the `feat/<leaf>` slices merging into it, and this header is where a reader goes to tell them apart.*

End with the handoff line, verbatim intent:

> **Horizon ready to dispatch.** `/pipeline:orchestrate` takes it from here: it dispatches this increment through `/pipeline:execute` — a worktree per slice, implementers, gate, PR review, merge — then reconciles the remainder against the tree the increment actually produced and moves the horizon. Say that whether the loop invoked you or a user did; the next step is the same either way.

Then **stop.** Do not start making worktrees or writing code — that's `/pipeline:execute`'s turn — and do not ground the next wave while you are here: moving the horizon is a step of the loop, and the tree that wave will run against does not exist yet.

## Writing it back to GitHub

For the issue path, decide **comment** vs **umbrella + sub-issues**. Read the issue, ground it (Step 1), validate and fill gaps (Step 2), slice it (Steps 3–4), then choose:

### Comment (the default)
When the work is small-to-medium — a handful of slices that are clearly one release effort and don't each need independent tracking/assignment — **post the whole breakdown as a single comment** on the issue, carrying both depths and their labels exactly as the in-chat format does. The loop reads the comment and dispatches the horizon from it. Keep the issue itself as the unit of work.

### Umbrella + sub-issues (when warranted)
When the work is **large and multi-area** — many slices, several waves, slices that deserve independent assignment, review, and closure — **convert the issue into an umbrella**:

1. **Rewrite the issue body** into an umbrella overview: the goal, the parallelization plan (waves, conflict map, critical path), and a **tracked checklist** linking each sub-issue (`- [ ] #<sub>`), which GitHub renders as progress.
2. **Create one sub-issue per horizon slice** (or per tightly-coupled slice cluster) containing that slice's full brief — scope, do-not-touch, depends-on, skill-to-invoke, model hint, verify. Beyond the horizon, a slice gets a checklist line or a placeholder sub-issue and no brief (below). Title each with its wave (e.g. `[W1] <title>`) so the dispatch order is visible at a glance.
3. **Link them as native sub-issues — always, never treated as an optional extra.** The relationship is a plain REST endpoint that is simply there, and *GitHub write mechanics* below carries the exact call, so there is no availability to condition on — and conditioning on one is what actually happens when the step reads as optional: observed `sub_issues` length **0** on two separate umbrellas in the wild, and **0** on this repo's own #37. **The native link is also what makes the reader-side check in Step 1 cheap** — its first step is one `/parent` call, and that call 404s on every child of a markdown-only umbrella (verified against #37's four), forcing an arriving agent onto the eight-candidate timeline fallback and its disambiguator. The two rules are one mechanism seen from each end. And *always* keep the umbrella's `- [ ] #N` checklist as well: it is the human-readable index reviewers scan, and it is the artifact that fallback matches on when the native link is missing anyway.
4. Label the umbrella (`epic`/`umbrella` if such a label exists; create nothing exotic).

Warrant the umbrella; don't reflexively shard a 3-slice issue into 3 issues — that's tracking overhead with no payoff. Rule of thumb: **umbrella when slices span multiple waves AND multiple areas AND each is a PR someone would want to track on its own.**

**A sub-issue may exist ahead of the horizon; a grounded brief may not.** File a beyond-horizon slice as a placeholder when you want it tracked and assignable — title, wave, goal, area, depends-on — and mark it on its face as *shape depth, not yet grounded*. It gets its owned files, do-not-touch boundaries, model tier and verify bar when the horizon reaches it and this pass runs again, against the tree as it will be then. *The failure this prevents: a sub-issue reads as a brief at whatever depth it was written, so an ungrounded one gets dispatched from as though it were finished, and a prematurely grounded one hands an implementer coordinates an intervening wave has already moved — inside a document that reads as settled precisely because it was filed before any of the arc ran.* The umbrella **body** is the live remaining plan and is rewritten every cycle rather than appended to; `/pipeline:orchestrate` section 7 owns that state model.

### GitHub write mechanics (important)
- **Use `gh api` (REST), not `gh issue create`/`gh issue edit` for the writes** — the high-level `gh issue` write commands go through GraphQL and hit rate limits in batches; the REST endpoints don't. Read with `gh issue view` is fine.
- **Write the body to a file and reference it with `-F` (not `-f`).** `-f` is `--raw-field`, which sends its value verbatim: `-f body=@file` stores the literal string `@file` as the comment. Only `-F` expands a leading `@` into the file's contents. This fails in the worst direction — the command exits 0 and prints a comment URL, so the run reports success and the damage is visible only to a human opening the issue. **Verify after** — refetch the body and confirm it's the markdown, not `@path`. For writes:
  - Comment: `gh api repos/{owner}/{repo}/issues/<N>/comments -F "body=@<file>"` (a temp file also spares you quoting hell with long markdown).
  - New sub-issue: `gh api repos/{owner}/{repo}/issues -f "title=…" -F "body=@<file>"` then capture the returned number. The title stays `-f` — it's a genuine literal, and only the `@file` value needs `-F`.
  - Edit umbrella body: `gh api -X PATCH repos/{owner}/{repo}/issues/<N> -F "body=@<file>"`.
- **Native sub-issue link:** `gh api -X POST repos/{owner}/{repo}/issues/<umbrella>/sub_issues -F sub_issue_id=<child's DATABASE id>`. Two traps, and both fail in a direction that reads as "this endpoint is unavailable":
  - **`sub_issue_id` is the child's database id (`.id`, e.g. `5261102081`), NOT its issue number (`38`)** — different fields on the same object, both plain integers, so nothing about the value's shape distinguishes them. Passing the number returns a bare `404 Not Found`, which reads as *"this endpoint doesn't exist"* rather than *"wrong id"*, so the natural conclusion is that the API is unavailable and the whole step gets quietly skipped — which is exactly how an umbrella ends up markdown-only. Take the id from the create call's own response, or `gh api repos/{owner}/{repo}/issues/<n> --jq .id`.
  - **`-F` here is doing TYPE work, not `@file` expansion — the rule above does not carry over.** That rule pairs `-F` with `@file` and keeps genuine literals on `-f`, and an id is a literal, so `-f` is the natural reach; but `-f` is `--raw-field` and sends `"38"` as a **string**, which the endpoint rejects with `422 Invalid property /sub_issue_id: "38" is not of type integer`. Only `-F` types a bare number as a JSON integer. Both flags therefore fail on a wrong id, with two different errors and neither one saying *use the other flag*.
- **Cross-reference, don't auto-close.** Each sub carries `Part of #<umbrella>` in its body and the umbrella carries that sub in its `- [ ] #<sub>` checklist — both directions, every time. `skills/write-issue/SKILL.md` Step 4's *Umbrella linking* is the authority on why the backlink is a rule rather than a formatting nicety; read it there, and this skill does not carry a second copy. The dispatcher then closes each sub by hand as its PR merges, never a `Closes #<n>` keyword — `/pipeline:execute`'s *Merge & cleanup* carries when one fires and why the hand-close is right either way.
- End your turn by telling the user what you wrote (umbrella # + sub-issue #s, or the comment link) and the same **Horizon ready to dispatch** handoff.

## What decompose does NOT do (hard boundaries)

- **Never ground beyond the horizon.** No `file:line`, no owned-file list, no do-not-touch boundaries, no framework skill, no model tier, no verify bar on any item outside the next dispatchable set — however well you happen to understand it, however small it is, and however directly a user asked about it. Reaching the horizon is the only thing that promotes an item to slice depth. *The failure this prevents: this is the exact defect `/pipeline:orchestrate` exists to fix, rebuilt one item at a time from inside the pass that is supposed to prevent it — and it arrives looking like diligence, because grounding more of the arc is indistinguishable from grounding it better right up until a wave lands and moves the paths.*
- **No code.** You never edit source files. If you catch yourself opening a file to change it, stop — that's an implementer's job.
- **No worktrees.** You never run `setup-worktree.sh`, never use the Agent tool's `isolation: "worktree"` param, never provision anything. Decompose is read-only against the working tree (plus GitHub writes on the issue path).
- **No dispatch, no merge.** You don't spawn implementer sub-agents to build, and you don't merge PRs. (You *do* spawn read-only `Explore`/research agents in Step 1 — that's grounding, not building, and invoking this skill is what authorizes them.)
- **Don't over-decompose.** Granularity that creates more coordination cost than it saves is a regression. When unsure, fewer, well-bounded slices beat many fragile ones. **And remember the gate is a real, serialized cost** (see Sizing): the dispatcher drains gates one PR at a time, so a wider fan-out of thin slices costs more total drain + review time than a narrower set of cohesive ones. Size against the actual `gate`, and never split for boundary-aesthetics alone.
- **No loop.** Reconciling a landed increment against the remaining plan, deciding what folds in and what gets filed, and rewriting the plan are steps 3 and 4 of `/pipeline:orchestrate`'s loop (its section 2), not a sixth step of yours. *The failure this prevents: a pass that reconciles as well as grounds does it against the tree it read at the top of its own turn — which is the tree* ***before*** *the increment merged, and therefore the one tree that cannot falsify anything.*
- **Hand off, then stop.** Your turn ends at the breakdown + the handoff line. `/pipeline:orchestrate` takes it from there — it dispatches this increment, reconciles the rest against the merged tree, and invokes you again for the next horizon.

**Why this shape:** the dispatcher *can* slice work on the fly, but it does so mid-flight, without deep grounding, while also juggling worktrees and merges. A dedicated grounding pass buys that thinking properly — real file scopes, the dependency waves, the conflict map — so the dispatcher spends its budget executing a good plan instead of discovering the plan while executing. Scoping it to the horizon is what keeps the thinking *accurate* as well as deep: grounding is only ever true about the tree it ran against, so it is bought one increment before it is spent rather than once for the whole arc. Better grounding in → more safe parallelism and fewer wrong-approach restarts out; grounding it just in time → briefs that describe the tree the implementer will actually open.
